## 1. 문제와 시스템 경계

### 1.1 구현 목적

장량동 생활쓰레기 수거 시뮬레이터 소스에서 **근거가 추적되는 SES 초안**을 안정적으로 뽑는다.
"안정적"의 조작적 정의를 이 문서에서 다음 세 가지로 고정한다.

1. **수율(yield)** — 같은 스냅샷·같은 방식을 반복했을 때 확정 항목 수가 0 근처로 붕괴하지 않는다.
2. **보존율(retention)** — 모델이 낸 원시 후보 중 조립에서 `unresolved` 로 떨어지는 비율이 낮다.
3. **재현성(reproducibility)** — 입력·프롬프트·응답·설정·검증 결과가 보존되어 재실행과 대조가 가능하다.

현재 3번은 이미 만족한다. **1·2번이 문제다**(§1.5 참조).

### 1.2 입력과 출력

| | 내용 |
|---|---|
| 입력 | 입력 정책 규칙(`sesx/rules/*.json`) → 승인된 파일 목록 → 불변 스냅샷(바이트 사본 + 파일별 sha256) |
| 중간 | 단계별 요청/응답 원문(`exp/<run-id>/stages/<stage>/attempt-N/`), 원시 후보 식별자, 판정 이력 |
| 출력 | 계약 v1 아티팩트(`urn:sesx:artifact:evidence-v1`) · 검증 결과 · 보고서(md) · 검토 후 승인 리비전 |

### 1.3 포함 범위

- 입력 경계 결정과 스냅샷 동결
- 단계별(T2 계열) · 단일(S2) 추출 경로
- 코드 근거 검증(파일 존재 · 행 범위 · 인용 대조 · 기호 확인)
- 구조 검증(참조 무결성 · 순환 · 단일 부모 · 루트 · 도달 가능성)
- 의미 신호 검사(개체 동일성 모양 · 소비 근거 · 속성 이름 중복 · 배열 차원 형제)
- 보류(`unresolved`)와 판정 이력(`provenance`) 보존
- 전문가 검토 → 새 리비전 → 재검증 → 승인 범위
- **전체(whole) 개체 후보 제안** — 추출기는 제안만 한다
- **PES 요청과 그 결정적 검증** — 요청한 시뮬레이터가 루트를 정한다(§4.13)

### 1.4 제외 범위

- 실행 매개변수 자동 연결(§11 에서 후보 생성 지점만 정한다). **PES 는 구조 선택까지이고 매개변수 결합은 그 다음이다**
- PES 로부터의 시뮬레이터 코드 생성
- 시뮬레이터 자동 생성, 운영 반영
- 범용 온톨로지 · 그래프 DB
- 자동 수리(auto-repair) 루프 — 별도 조건으로 재야 한다
- 정답지(`reference-ses.json`) 자체의 확장

### 1.5 확인된 사실

저장소를 직접 읽고 실행해서 확인한 것만 적는다.

## 2. 후보 구현 방식

세 후보 모두 **기존 `sesx/` 계약·보존·검증 층을 유지**한다. 다른 것은 "단계 간 동일성을 무엇으로 잡는가"이다.

### 후보 A — 프롬프트·재시도 강화 (최소 변경)

**핵심 아이디어.** 이름 목록 지시를 더 강하게 주고, 목록 위반 응답을 같은 단계에서 재요청한다. 구조는 그대로 둔다.

**처리 과정.** 단계 응답 수신 → 코드가 목록 밖 이름을 세어 위반율 계산 → 임계 초과 시 위반 항목만 지목해 같은 단계 재요청(최대 N회) → 마지막 시도를 채택, 모든 시도는 `attempt-N/` 에 보존.

**역할 분담.** LLM: 이름 사용 교정. 코드: 위반 탐지 · 재시도 상한 · 보존.

**변경.** `sesx/stages.py` 에 위반 검사와 재시도 루프, `run_store` 에 시도 사유 기록. 새 모듈 없음.

**장점.** 가장 작다. 계약·검증을 전혀 건드리지 않아 과거 실행과의 비교가 깨지지 않는다.

**구체적 실패 지점.** §1.5-D 가 이미 반증에 가깝다 — 목록 지시가 **있는 상태에서** c 단계가 `"전체 시뮬레이션"` 을 냈다. 재시도는 같은 분포에서 다시 뽑는 것이라 개선 폭이 확률적이고, 토큰 비용은 시도 수에 비례해 늘며, 재시도가 조건을 바꾸므로 S2 와의 공정 비교가 오염된다.

**무효를 보이는 시험.** 같은 스냅샷에서 재시도 상한 N=1 과 N=3 을 각 5회 돌려 `unknown_reference` 건수를 비교한다. **중앙값 감소가 30% 미만이면 A 는 기각**한다.

---

### 후보 B — 코드 앵커 기반 동일성 (권고)

**핵심 아이디어.** 항목의 동일성을 **표시 이름이 아니라 코드 앵커**(파일 경로 + 기호 + 선언 행)로 잡는다. 이름은 사람이 읽는 표지로 강등하고, 단계 간 참조는 코드가 부여한 **앵커 ID** 로 한다.

**처리 과정.**
1. 스냅샷 확정 직후 `sesx/index.py` 로 **앵커 사전**을 만든다: `{anchor_id: {file, symbol, decl_lines, kind_hint}}`. 결정적이고 모델이 개입하지 않는다.
2. 개체·속성 후보를 내는 단계(a · b2 · g)는 각 항목에 `anchor`(파일 + 기호)를 **필수**로 요구한다. 앵커가 없는 후보는 만들지 못한다.
3. 코드가 앵커를 사전과 대조해 `anchor_id` 를 확정하고, 그것으로 개체 ID 를 부여한다. 같은 앵커 = 같은 개체다(이름이 달라도 병합, 판정 이력에 기록).
4. 뒤 단계(c · d · e · e2 · f)에는 **`ID | 이름 | 파일:기호`** 3단 목록을 준다. 참조 필드는 **ID 를 적게** 한다.
5. 조립 시 참조 해결 순서: **① `anchor_id` 일치 → ② 항목 ID 일치 → ③ 정규화 이름 일치 → ④ `alternate_names` 일치 → 모두 실패하면 `unresolved`**. 각 단계가 어느 경로로 풀렸는지 `provenance` 에 남는다.
6. `unknown_reference` 보류 항목에는 근접 후보(앵커 거리 · 이름 거리)를 `resolution_needed` 에 붙여 검토를 돕는다. **코드가 자동 채택하지 않는다.**

**역할 분담.**
- LLM: 무엇이 개체/속성/구성/결합인가의 **의미 판단**, 그 판단의 근거 인용, 앵커로 쓸 코드 기호 지목.
- 코드: 앵커 사전 생성, 앵커 존재·선언 확인, ID 부여, 병합, 참조 해결, 인용 대조, 구조 검사. **의미를 만들지 않는다.**

**변경.**
- 신규: `sesx/anchor.py`(앵커 사전 · 해결기 · 근접 후보).
- 수정: `sesx/index.py`(파일별 → 스냅샷 전체 사전, 캐시), `sesx/artifact.schema.json`(entities/attributes 에 `anchor` 추가, 필수는 아님 — 과거 아티팩트 호환), `sesx/assemble.py`(`_entity_id` 를 4단 해결기로 교체), `sesx/stages.py`(ID 3단 목록 주입), `sesx/prompts/T2/*.md`(앵커 필드 요구), `sesx/validate.py`(`ANCHOR_RESOLVED` 검사 추가).
- 새 프롬프트 계열을 `T2-anchor` 로 만들고 **기존 T2 계열은 그대로 둔다**(대조군 보존).

**장점.** 측정된 최대 손실 원인(§1.5-C·D)을 직접 친다. 동일성이 코드에 고정되므로 반복 안정성이 구조적으로 올라간다. `IDENTITY_EVIDENCE_SHAPE`(§1.5-F)도 앵커가 선언 행을 요구하므로 함께 개선된다. 결정적 검사가 늘고 LLM 재량은 줄어 제약조건에 부합한다. S2 에도 같은 앵커 요구를 넣을 수 있어 **비교가 공정하게 유지된다**.

**구체적 실패 지점.**
- 정규식 색인이 기호를 놓치면(제네릭·중첩 클래스·람다) 정상 후보가 앵커 해결 실패로 보류된다 — **손실 원인이 바뀔 뿐 총량이 안 줄 수 있다**.
- 코드 기호와 1:1 대응이 없는 개체(여러 클래스에 걸친 개념, 배열 차원이 암시하는 개체)는 앵커를 못 붙인다. `anchor` 를 필수로 만들면 이런 개체를 구조적으로 못 뽑는다 → **선택 필드로 두고, 앵커 없는 후보는 `anchor_absent` 사유로 보류**해야 한다.
- 모델이 앵커를 지어낼 수 있다. 사전 대조로 잡히지만 그만큼 보류가 는다.

**무효를 보이는 시험.** 같은 스냅샷·같은 모델로 `T2-evidence`(현행) 대 `T2-anchor` 를 각 5회. **`unknown_reference` + `anchor_absent` 합계의 중앙값이 현행 `unknown_reference` 중앙값보다 줄지 않으면 B 는 기각**한다. 추가로 앵커 사전 자체를 정답 없이 검사한다 — 스냅샷의 모든 `class`/`enum`/`record` 선언을 정규식 두 벌(현행 `TYPE_DECL` + 독립 구현)로 뽑아 불일치가 5% 넘으면 색인이 부족한 것이다.

### 후보 C — 코드 우선 후보 격자 (LLM 은 분류만)

**핵심 아이디어.** 결정적 분석기가 **후보 격자**를 먼저 만든다(클래스 · 필드 · 배열 차원 · 열거 상수 · 쓰기 자리 · 읽기 자리 · 분기). LLM 은 격자의 각 항목을 Entity / Attribute / ASPECT / SPEC / MULTI / Coupling / 비대상 으로 **분류**만 하고 새 항목을 만들지 못한다.

**처리 과정.** 스냅샷 → 격자 생성(코드) → 격자를 묶음으로 나눠 분류 요청(LLM, 각 항목에 판단 이유 + 근거 인용) → 분류 결과를 격자에 되붙임(코드) → 구조 조립(코드) → 검증.

**역할 분담.** 코드가 존재론을 정하고 LLM 은 의미 표지만 붙인다. 가장 결정적이다.

**변경.** 신규 `sesx/lattice.py` + 분류 프롬프트 계열 + 조립기 대폭 수정. 사실상 세 번째 추출 방식(`C2`)의 신설이다.

**장점.** `unknown_reference` 가 원리적으로 0 이 된다(참조 대상이 전부 코드가 만든 ID). 재현 안정성이 가장 높다. 근거가 항상 존재한다.

**구체적 실패 지점.**
- 격자 생성기가 못 본 것은 **영원히 못 뽑는다**. 정규식 수준으로는 배열 차원이 뜻하는 MULTI, 여러 클래스에 걸친 ASPECT 를 못 만든다 → 재현율 상한이 코드로 고정된다.
- 격자가 커지면(필드·호출 자리 수백 개) 분류 호출 비용이 커지고 묶음 경계가 결과를 좌우한다.
- **비교 실험이 망가진다.** C 는 S2(단일 추출)와 비교할 공통 기반이 없다 — 단일 추출은 격자를 쓰지 않는다. 사용자의 §7 요구(단일 대 단계별 비교)를 직접 위협한다.

**무효를 보이는 시험.** 격자 생성기를 스냅샷에 돌려 ref-v8 개체 62개(추출 가능 상한 확정 후, §1.6) 중 격자 항목으로 **대응되는 비율**을 센다. **70% 미만이면 C 는 주 경로로 기각**한다. 이 시험은 LLM 없이 돌아가므로 **가장 먼저 값싸게 칠 수 있다**.

### 후보 D — 전체 개체 제안 + PES 가 루트를 정한다 (권고에 함께 채택)

**핵심 아이디어.** 추출기는 **전체(whole) 개체 후보를 제안만** 한다. 어느 것이 루트인지는 SES 단계에서 정하지 않는다. **요청한 시뮬레이터가 무엇인가**를 사람이 PES 요청으로 선언하고, 코드는 그 요청이 SES 위에서 성립하는지만 결정적으로 검사한다.

이것은 SES 이론의 원래 모양이기도 하다. SES 는 여러 모델을 담는 족(族)이고, 하나의 시뮬레이터는 **pruning 의 결과(PES)** 다. 정답지도 이미 그 어휘를 쓴다 — 결합의 `active_when` 을 "SES pruning 을 결합에 명시하는 최소 표현"이라 적어 두었고(`reference-ses.json:48`), CP-5 는 두 SPEC 축을 합치면 "축별 독립 선택으로 pruning 할 수 없다"는 이유로 분리를 확정했다.

**처리 과정.**
1. 새 단계 `w` — 전체 개체 후보를 낸다. 조건: **조립 자리 근거**(부품들이 한자리에서 조립·주입·실행되는 코드 인용)가 있어야 하고, 실행 지원 소프트웨어(큐·컨트롤러·전송)는 후보가 될 수 없다. `kind: "whole"`, `status: "proposed"`.
2. 뒤 단계의 이름 목록에 전체 후보가 **포함**된다 → c 단계가 "전체 시뮬레이션"에 매단 속성 24건이 붙을 자리를 얻는다.
3. SES 는 루트 미확정 상태로 검증을 통과할 수 있다. 루트 후보 목록과 각각의 근거를 보고서에 싣는다. **코드는 여전히 고르지 않는다.**
4. 사람이 **PES 요청**을 쓴다(§4.13): 어느 시뮬레이터인가 · 그 전체는 어느 개체인가 · 각 SPEC 축에서 무엇을 고르는가 · 각 MULTI 의 개수는 몇인가.
5. 코드가 요청을 SES 에 대고 결정적으로 검사하고(§6 PES 층), 통과하면 가지친 트리를 PES 산출물로 낸다. 요청이 불완전하면 **PES 를 만들지 않는다** — 채워 넣지 않는다.

**역할 분담.** LLM: 전체 후보 제안과 그 근거. 사람: 어느 시뮬레이터를 원하는가(루트·선택·개수). 코드: 후보 목록 제시, 요청의 성립 여부 검사, 가지치기 실행. **코드도 LLM 도 루트를 고르지 않는다.**

**변경.** 신규 `sesx/pes.py` · `sesx/prompts/anchor/w.md` · PES 요청 스키마. 수정 `sesx/validate.py`(루트 검사 재배치) · `sesx/stages.py` · `sesx/report.py` · `extract.py`(`pes` 하위명령).

**장점.** 측정된 최대 보류 덩어리(24/29)를 직접 친다. "루트를 임의로 고르지 않는다"는 제약을 **더 강하게** 지킨다 — 지금의 `reviewer_root` 자유 서술보다 PES 요청이 검사 가능한 선언이기 때문이다. SES 와 시뮬레이터의 관계가 이론과 맞아떨어진다.

**구체적 실패 지점.**
- `w` 단계가 전체 후보를 남발하면 루트 후보가 6개에서 더 늘어난다. 조립 자리 근거 요구가 약하면 그대로 일어난다.
- SES 승인에서 루트를 요구하지 않게 되므로 **승인 문턱이 낮아진다**(§6 에 명시). 루트 없는 SES 가 "승인"된 것으로 잘못 읽힐 위험이 있다 → `approval.scope` 에 "루트 미확정"을 명시해야 한다.
- 정답지 채점은 루트 `장량동 생활쓰레기 수거 시뮬레이터` 를 전제한다. 채점은 **SES 에 대고** 계속하고 PES 에 대고 하지 않는다. 섞으면 수가 달라진다.
- PES 요청을 사람이 쓰므로, 요청 자체가 근거 없이 구조를 만들어 낼 수 있다. 그래서 요청의 `root` 는 **SES 에 이미 있는 개체만** 지목할 수 있다.

**무효를 보이는 시험.** `w` 단계 도입 전후로 (a) `unknown_reference` 중 "전체"류 대상 건수, (b) 루트 후보 수를 각 5회 비교한다. **(a) 가 절반 이하로 줄지 않거나 (b) 가 늘어나면 D 는 기각**한다. PES 검사기는 LLM 없이 시험할 수 있다 — ref-v8 자체를 SES 로 넣고 루트 `장량동 생활쓰레기 수거 시뮬레이터` 로 PES 요청을 만들어 통과하는지 본다.

## 3. 최종 권고 방식

### 선택

**후보 B(코드 앵커 기반 동일성)와 후보 D(전체 개체 제안 + PES 루트 결정)를 함께 채택한다.** 둘은 서로 다른 결함을 친다 — 섞지 않는다.

| 결함 | 크기(q3-flow-2) | 대응 |
|---|---|---|
| 전체 개체 부재 | 보류 24건 | **D** |
| 단계 간 이름 어휘 불일치 | 보류 5건 | **B** |
| 소유 증명 실패 | 보류 27건 | B(앵커가 소유 범위를 좁힌다) |
| 판정·시스템 개체 부재 | 재현율 9/62 | **별도 단계**(§5 D4) |

후보 C 의 격자 생성기는 **B 의 앵커 사전으로 축소해 채택**한다(존재론을 정하는 데 쓰지 않고 동일성을 고정하는 데만 쓴다). 후보 A 의 재시도는 **채택하지 않는다** — 위반 탐지(재요청 없는 계측)만 진단 지표로 넣는다.

**착수 순서는 D 가 먼저다.** 보류 감소 효과가 크고(24 대 5), 앵커보다 변경 범위가 작으며, LLM 없이 시험할 수 있는 부분(PES 검사기)이 있다.

### 선택 근거

1. **D** 는 측정된 최대 보류 덩어리를 직접 친다(29건 중 24건, §1.5-D).
2. **D** 는 "루트를 임의로 고르지 않는다"를 약화시키지 않고 강화한다. 지금의 `reviewer_root`(자유 서술 + 이유)보다 PES 요청이 **검사 가능한 선언**이다.
3. **B** 는 프롬프트 층이 소진된 뒤 남은 유일한 결정적 지렛대다(§1.5-D).
4. 둘 다 제약조건에 부합한다 — LLM 은 의미 후보를 내고, 파일 존재·행 범위·ID 참조·순환·도달 가능성은 코드가 검사한다.
5. 기존 266건 시험과 계약을 유지한 채 증분으로 들어간다. 대조군(`T2-evidence`)이 남아 §10 이 성립한다.
6. `IDENTITY_EVIDENCE_SHAPE`(§1.5-F) 실패도 B 로 함께 개선된다 — 앵커가 선언 행을 요구한다.

### 다른 방식을 선택하지 않은 이유

- **A**: 증거가 이미 불리하다. 지시가 있는 상태에서 위반이 발생했고, 재시도는 조건을 바꿔 비교를 오염시킨다. 비용만 확실히 는다.
- **C**: 재현율 상한을 코드가 고정해 버린다. 더 심각하게는 S2 와의 공통 기반이 없어 핵심 실험(단일 대 단계별)을 깨뜨린다. 앵커 사전이라는 **부분만** 쓰면 장점의 대부분을 비용 없이 얻는다.
- **"이벤트를 개체로 세우는 단계"**: 정답지에 이벤트 개체가 **하나도 없고**, 모델은 이미 시키지 않아도 `이벤트 우선순위 큐` 같은 실행 지원 소프트웨어를 개체로 내고 있다(§1.5-D-3). 막연한 단계 추가는 과잉생성을 증폭한다. 판정만 기준을 걸어 따로 뽑는다(§5 D4).

### 선택을 뒤집을 수 있는 증거

- §2-B 의 무효 시험에서 앵커 도입 후 보류 총량이 줄지 않는 경우 → A 또는 C 로 이동.
- 앵커 사전 이중 구현 대조에서 불일치가 5% 를 넘는 경우 → 정규식 색인 포기, AST(예: `javalang`) 도입을 먼저 한다.
- §2-C 의 격자 대응률 시험이 90% 를 넘는 경우 → C 가 생각보다 강하다. 단일 추출 비교를 별도 조건으로 분리하고 C 를 주 경로로 재검토.
- 실제 개체의 상당수가 코드 기호와 1:1 대응이 없다고 전문가 검토에서 확인되는 경우 → 앵커는 보조 신호로 강등하고 이름 기반 해결을 유지.
- `w` 단계 도입 후 루트 후보가 **늘어나는** 경우 → 전체 개체를 추출에서 빼고, PES 요청이 SES 에 없는 전체를 **선언**할 수 있게 허용하는 쪽으로 바꾼다(그 경우 전체는 `origin: "human"` 이 된다).
- PES 검사기가 ref-v8 을 SES 로 넣었을 때 통과하지 못하는 경우 → 검사기가 아니라 **PES 요청 스키마**가 틀린 것이다. 정답지 구조에 맞춰 스키마를 고친다.

### 4.1 최상위

```yaml
schema_version: "evidence-v2"        # ＋ 앵커 추가로 판올림. v1 아티팩트는 그대로 읽힌다
artifact_id: "r1-draft-1737100000"
parent_artifact_id: null             # 검토 리비전이면 앞 리비전 id
```

```yaml

      status: "ok | held_same_line"

```

**판단 기준(문제 5)** — 코드가 강제하는 형태로 적는다.

| 관계 | 성립 조건 | 코드가 확인하는 것 |
|---|---|---|
| Attribute | 개체 하나에 속한 값이며 그 개체의 선언 범위 안에 근거가 있다 | 소유 개체 앵커와 값 앵커가 같은 파일/클래스 범위인가 |
| ASPECT | 부모가 존재할 때 멤버가 **동시에 전부** 존재한다 | 멤버들이 같은 생성/등록 자리에서 함께 나타나는가 |
| SPEC | 멤버가 **택일**이며 선택 근거가 있다 | 열거형 · 분기 · 유형 계층 근거가 있는가 |
| MULTI | **동일 유형**이 반복된다 | 배열·컬렉션·반복 생성 근거가 있는가, 멤버 유형이 하나인가 |
| Coupling | 한 개체의 값이 다른 개체에서 읽힌다 | 쓰는 자리와 읽는 자리가 각각 인용되는가, 출발≠도착인가 |

애매하면 확정하지 않고 보류한다. 특히 **같은 선언 행이 두 자식의 역할 근거인 ASPECT·MULTI 는 보류**한다(규칙 10, SPEC 은 예외).

### 4.13 PES 요청과 PES (＋ 신규) — 루트는 여기서 정해진다

```yaml
  - decomposition_id: "D7"
```

## 5. 단계별 구현계획

각 단계는 독립적으로 되돌릴 수 있고, 끝날 때 266건 + 신규 시험이 전부 통과해야 한다.

### S0 — 기준선 동결 (코드 변경 없음)

- **구현**: 미커밋 변경 4건을 커밋 경계로 정리한다. 현행 `T2-evidence` 를 같은 스냅샷에서 5회 실행해 기준선을 만든다.
- **구성요소**: 없음(실행만). 결과는 `exp/base-<날짜>-{1..5}/`.
- **입력**: `P-evidence-v1`, 모델·설정 고정.
- **출력**: 5개 실행의 `ses.json` · `report.md`, 요약표(E/A/D/C/U, 사유별 보류, 인용 실패율).
- **완료조건**: 5회 모두 산출물이 남고, 보류 사유 분포가 기록됐다.
- **자동 테스트**: 기존 266건 통과. 요약표 생성기에 자체 검증 1건.
- **실패 시**: 실행이 깨지면 그 자체가 1순위 결함이다. §5 를 멈추고 원인을 먼저 고친다.

### D1 — 전체 개체 후보 단계 `w`

- **구현**: 전체 후보를 내는 단계 하나. 조건 — 조립 자리 근거(부품이 한자리에서 조립·주입·실행되는 인용) 필수, `scope: simulation_target` 필수, 실행 지원 소프트웨어(큐·컨트롤러·전송·채팅)는 후보 불가. 후보는 `kind: "whole"`, `status: "proposed"`. **루트라고 말하지 않는다.**
- **구성요소**: 신규 `sesx/prompts/anchor/w.md`; 수정 `sesx/stages.py`(`PLANS` 에 `w` 삽입, `NAME_LIST_STAGES` 에 전체 후보 포함), `sesx/composition.py`(전체 후보 형식 계약), `sesx/assemble.py`(`kind: whole` 수용).
- **입력**: 스냅샷 + a·b2 산출물.
- **출력**: 전체 후보를 포함한 개체 목록. 뒤 단계 이름 목록에 포함된다.
- **완료조건**: c 단계가 전체에 매단 속성이 **보류되지 않고 붙는다**(q3-flow-2 의 24건이 표적).
- **자동 테스트**: 조립 자리 근거 없는 후보가 보류되는지, 실행 지원 소프트웨어 후보가 거절되는지, 전체 후보가 이름 목록에 주입되는지.
- **실패 시**: 루트 후보가 오히려 늘면 §3 의 뒤집기 조건에 걸린다 → 전체를 추출에서 빼고 PES 요청이 선언하게 한다.

### D2 — PES 요청 스키마와 검사기 (LLM 없음)

- **구현**: `sesx/pes.py` — 요청 로드·검증·가지치기. §6 의 PES 층 검사 전부. 요청이 불완전하면 **PES 를 만들지 않는다**.
- **구성요소**: 신규 `sesx/pes.py` · `sesx/pes-request.schema.json`; 수정 `extract.py`(`pes` 하위명령), `sesx/report.py`(PES 절).
- **입력**: 검증된 SES 아티팩트 + PES 요청.
- **출력**: `exp/<run-id>/pes/<request-id>/pes-0001.json` + 보고서. 같은 request-id 로 덮어쓰지 않는다.
- **완료조건**: **ref-v8 자체를 SES 로 넣고** 루트 `장량동 생활쓰레기 수거 시뮬레이터` 로 요청했을 때 PES 가 나온다. LLM 없이 시험된다.
- **자동 테스트**: 루트가 SES 에 없으면 거절 · SPEC 미선택이면 거절 · MULTI 개수 없으면 거절 · 선택으로 비활성인 결합이 `dropped` 에 기록 · `unresolved_in_scope` 가 숨겨지지 않음 · 같은 요청 2회 → 같은 PES 해시.
- **실패 시**: ref-v8 이 통과하지 못하면 검사기가 아니라 요청 스키마가 틀린 것이다(§3 뒤집기 조건).

### D3 — 루트 검사 재배치

- **구현**: `ROOT_UNIQUE` 를 SES 층에서 **비차단**으로 내리고 `ROOT_CANDIDATES` 로 바꾼다. 단일 루트·도달 가능성은 **PES 층에서 차단**으로 검사한다. 승인에 `caveats` 를 더해 "루트 미확정"을 명시한다(`approval.scope` 는 승인된 항목 ID 목록이라 문구를 넣을 자리가 아니다).
- **구성요소**: 수정 `sesx/validate.py` · `sesx/strict.py`(`BLOCKING` 목록) · `sesx/review.py`(승인 범위) · `sesx/report.py`.
- **완료조건**: 루트 미확정 SES 가 검증을 통과하되, 보고서와 `approval.scope` 양쪽에 루트 미확정이 **눈에 띄게** 남는다.
- **자동 테스트**: 루트 후보 6개짜리 아티팩트가 SES 검증은 통과하고 PES 요청 없이는 PES 가 안 나오는지. 승인 범위 문구 시험.
- **실패 시**: **이 단계는 승인 문턱을 낮춘다.** 승인 범위에 루트 미확정이 안 실리면 되돌린다.

### D4 — 판정 개체 단계

- **구현**: 판정 후보를 따로 묻는 단계. 식별 기준 3종을 **전부** 요구한다 — ① 분기 조건 인용, ② 그 결과가 쌓이는 별도 집계 인용, ③ 실험 설정이 바꾸는 임계값(속성 ID 참조). 하나라도 없으면 보류.
- **근거**: ref-v8 의 판정 4개(민원·적재초과·임대인 점검·교통혼잡)는 v7 에도 동일하게 있고, CP-1 이 이들을 **ASPECT** 로 못박는다. 추출 29건에서 맞은 건 0건이다(§1.5-D-2).
- **구성요소**: 신규 `sesx/prompts/anchor/j.md`; 수정 `sesx/stages.py` · `sesx/validate.py`(`JUDGMENT_EVIDENCE_SHAPE`, 비차단).
- **완료조건**: 판정 후보가 나오고, 기준 3종을 못 갖춘 후보가 보류된다.
- **자동 테스트**: `민원 수` 같은 **누적 카운터**가 판정으로 승격되지 않는지(이건 판정의 출력이지 판정이 아니다), `이벤트 우선순위 큐` 가 거절되는지.
- **실패 시**: 과잉생성이 늘면 단계를 빼고 판정을 검토에서 사람이 넣는다. **이벤트 개체 단계는 만들지 않는다** — 정답지에 대응이 없다.

## 6. 검증계획

| 층 | 검사 | 차단 | 무엇을 못 하는가 |
|---|---|---|---|
| **JSON 스키마** | `JSON_SCHEMA`(Draft 2020-12) · `SCHEMA_VALID` · `EXTRACTION_NONEMPTY` | 예 | 의미가 맞는지는 모른다 |
| **코드 근거 위치** | `SOURCE_READY`(스냅샷 해시 일치) · `EVIDENCE_LOCATION`(파일 존재 + 행 범위) · `EVIDENCE_QUOTE_MODES`(정확/들여쓰기/줄이음/불일치) · `EVIDENCE_REQUIRED` · `ANCHOR_VERIFIED`＋ | 예(앵커는 아니오) | 인용이 맞아도 그 줄이 그 주장을 받치는지는 모른다 |
| **SES 참조 무결성** | `REF_INTEGRITY`(모든 ID 참조 실재) · `NESTED_REFERENCES` · `PROVENANCE_COMPLETE`(판정 없는 원시 후보 0) · `RAW_MANIFEST_REQUIRED` | 예 | — |
| **루트·순환·고립·도달 (SES)** | `DECOMP_ACYCLIC` · `DECOMP_SINGLE_PARENT` · `ROOT_CANDIDATES`＋(후보와 각 근거를 **보고**한다) · `ROOT_INTRODUCED_BY_EXTRACTOR` · `REACHABILITY`(루트 미확정이면 `not_checked`) · `COUPLING_FEEDBACK`(되먹임은 오류가 아니다) | 순환·단일부모만 예. **루트는 아니오** | 루트를 SES 에서 정하지 않는다 |
| **PES**＋ | `PES_SES_IDENTITY`(요청이 지목한 SES 해시 일치) · `PES_ROOT_EXISTS`(SES 에 있는 개체인가) · `PES_SPEC_RESOLVED`(도달 범위의 모든 SPEC 에 선택 정확히 하나) · `PES_MULTI_RESOLVED`(모든 MULTI 에 개수, `unknown` 금지) · `PES_SINGLE_ROOT` · `PES_ACYCLIC` · `PES_REACHABLE`(전부 도달) · `PES_ACTIVATION_NOT_ASSUMED`(모르는 활성 조건이 `activation_unknown` 에 남는다 — 무조건 활성으로 바뀌지 않았다) · `PES_DROP_RECORDED`(빠진 것마다 사유가 있다) · `PES_UNRESOLVED_IN_SCOPE`(보고, 차단 아님) | 예 | **요청이 불완전하면 PES 를 만들지 않는다.** 코드가 채워 넣지 않는다 |
| **ASPECT·SPEC·MULTI 의미** | `MULTI_SINGLE_MEMBER`(멤버 1개 MULTI 는 의심) · `dimension_guard`(두 자식의 역할 근거가 같은 선언 행이면 보류, SPEC 예외) · `IDENTITY_EVIDENCE_SHAPE`(선언·생성·등록 근거 유무) · `ATTR_NAME_OVERLAP` · `CONSUMPTION_IS_DISTINCT` | 아니오 | **전부 신호일 뿐 판정이 아니다** |
| **Coupling·활성 조건** | 출발≠도착(계약) · 방향은 코드가 생성(`flow.py`) · `ACTIVATION_RESOLVED`(미확정 활성 조건이 있으면 fail) · `unconditional` 은 `coverage: complete` 일 때만 | 예 | 정답지에 활성 조건이 없어 **외부 정답 대비 채점은 불가**(§1.5-G) |

> **주의 — 이 변경은 SES 승인 문턱을 낮춘다.** 지금은 `ROOT_UNIQUE` 가 차단이라 루트 없는 SES 는 승인될 수 없다. D3 이후에는 승인될 수 있다. 그 대가로 두 가지를 강제한다. ① `approval.scope` 에 "루트 미확정"이 명시된다. ② 단일 루트·도달 가능성은 사라지지 않고 **PES 층의 차단 검사로 옮겨간다.** 루트 없는 SES 로는 시뮬레이터를 만들 수 없다는 사실은 그대로다.

### 전문가 검토가 필요한 항목

기계가 판정할 수 없어 반드시 사람에게 넘기는 것:

1. **루트 선택** — 이제 **PES 요청**으로 한다(§4.13). 자유 서술이 아니라 검사 가능한 선언이며, SES 에 이미 있는 개체만 지목할 수 있다. q3-flow-2 는 후보 6개였다.
2. **개체인가 아닌가** — 특히 `scope: support_software` 로 분류된 코드에서 나온 후보, `*Result` 류 출력 값.
3. **ASPECT/SPEC/MULTI 구분이 코드 모양과 어긋나는 경우** — `IDENTITY_EVIDENCE_SHAPE` · `dimension_guard` 가 신호를 올린 항목.
4. **`unresolved` 전량** — `near_candidates` 는 제안이지 결정이 아니다.
5. **단위·기본값·범위의 의미** — `unknown` 을 채우는 것은 사람 또는 코드 근거뿐이다.
6. **활성 조건의 `unknown` → `unconditional` 승격** — 호출자까지 확인했다는 근거가 필요하다.
7. **입력 경계의 의미적 완전성** — `P-evidence-v1` 의 `approved_by` 가 "expert boundary review pending" 이라고 스스로 적고 있다.

`accepted` 는 사람만 붙인다. 검토 판정은 새 리비전을 만들고 **재검증을 다시 통과해야** 승인 범위에 들어간다.

## 7. 실험계획

### 7.1 실험 단위

한 단위 = (스냅샷 고정) × (방식 ∈ {S2-anchor, T2-anchor, T2-evidence(대조)}) × (모델 고정) × (반복 n). 산출물은 `exp/<방식>-<날짜>-<회차>/` 로 분리하고 **기존 디렉터리를 덮어쓰지 않는다**(현행 `_publish` 가 이미 강제).

### 7.2 반복 횟수의 목적

반복은 **우열을 증명하기 위한 것이 아니라 분산을 보기 위한 것이다.** §1.5-B 가 보여주듯 같은 방식 내 편차가 방식 간 차이보다 크다. 최소 n=5, 가능하면 n=10. **n<10 에서 나온 차이를 통계적 우위로 보고하지 않는다.**

### 7.3 평가 지표

| 지표 | 정의 | 왜 |
|---|---|---|
| 확정 항목 수 | E/A/D/C 각각 | 수율 |
| 보류율 | `unresolved` / (확정 + 보류) | 보존율 |
| 보류 사유 분포 | `reason_code` 별 비율 | 어디서 잃는가 |
| 인용 통과율 | `EVIDENCE_LOCATION` pass / 전체 | 근거 품질 |
| 인용 모드 분포 | 정확 / 보정 / 불일치 | 근거 품질(세부) |
| 루트 후보 수 | 1이면 좋다 | 구조 수렴 |
| 차단 실패 목록 | `blocking_failure_ids` | 승인 거리 |
| 활성 `unknown` 비율 | `state == unknown` / 전체 | 과잉 확정 방지 확인 |
| 토큰 · 시간 | 입력/출력 토큰, `elapsed_s` | 비용 |

### 7.4 정확도 평가 방법

- **개체·분해**: ref-v8 대비 `score_ses.py`(별칭 사전 `aliases.json` 은 **채점자에게만** 준다).
- **결합**: `score_couplings()` — 정답지 결합 6건 대비. 표본이 작다는 점을 반드시 함께 보고한다.
- **활성 조건**: 정답지에 없다 → **자기 일관성 지표만**(§5 C1). 정확도라고 부르지 않는다.
- 분모 주의: ref-v8 62개 중 추출 가능 상한을 확정한 뒤 재현율을 계산한다(§1.6 확인 필요).

### 7.5 반복 안정성

방식마다 n회 실행의 **쌍별 Jaccard**(개체 집합 · 분해 간선 집합)를 계산한다. 중앙값과 사분위를 보고한다. 평균만 보고하지 않는다.

### 7.6 전문가 수정 시간

`unresolved` 1건, `ROOT_UNIQUE` 1건, 의미 신호 1건을 처리하는 실측 시간을 기록한다. **확인 필요** — 검토 인력 예산이 정해져야 이 지표가 성립한다. 예산이 없으면 "검토 항목 수"를 대리 지표로 쓰되 시간으로 환산하지 않는다.

### 7.7 비용과 입력량

요청·응답 토큰, 호출 수, 벽시계 시간. 단계별 추출은 호출이 많아 **입력 토큰이 중복 계상**된다 — q3-flow-2 는 9단계 합계 입력 약 78만 토큰이다. 단일 추출과 비교할 때 이것을 숨기지 않는다.

### 7.8 오염 방지

1. `input_policy` 가 `evaluation_asset_globs`(정답지 · 별칭 · `runs/` · `src/main/java/com/wastesim/ses/**`)를 **모델 호출 전에** 차단한다. 차단이 있으면 스냅샷을 만들지 않는다.
2. 별칭 사전은 채점 단계에서만 쓴다.
3. 기존 SES 를 입력으로 쓰는 실험은 `experiment_kind: structure_update` 로 분리하고 같은 표에 놓지 않는다.
4. 프롬프트·설정·스냅샷·상위 산출물 중 하나라도 바뀌면 재개 키가 바뀌어 단계를 다시 부른다.
5. 대조군 `T2-evidence` 프롬프트를 실험 기간 중 수정하지 않는다.

### 7.9 성공 기준

D 트랙과 B 트랙을 마친 뒤 같은 스냅샷·모델에서:

**트랙마다 표적이 다르므로 기준도 따로 잡는다.** 하나로 묶으면 어느 쪽이 들었는지 알 수 없다.

**D 트랙 (전체·PES·판정)**
- "전체"류 대상 `unknown_reference` 가 **절반 이하**. 기준선 q3-flow-2 는 24건이었다.
- 루트 후보 수가 **늘지 않는다**(기준선 6개).
- PES 검사기가 ref-v8 을 SES 로 넣었을 때 PES 를 낸다. **LLM 없이 판정되는 기준이다.**
- 판정 개체가 1건 이상 나오고, 누적 카운터(`민원 수` 류)가 판정으로 승격되지 않는다.

**B 트랙 (앵커)**
- `unknown_reference` 중 **"전체"류를 뺀 나머지** + `anchor_absent` + `anchor_unverified` 합계가 기준선의 절반 이하. 기준선 q3-flow-2 는 5건이므로 **표본이 작다 — 이 한 실행으로 판정하지 않는다.**
- `unproven_ownership` 중앙값이 줄어든다(기준선 27건).
- 인용 통과율 중앙값이 기준선 이상(기준선 83.4%).

**공통**
- 확정 개체 수 중앙값이 기준선 이상이고, **5회 중 0건 붕괴가 없다**.
- 활성 `unknown` 비율은 **올라가도 된다** — 과잉 확정을 막는 것이 목적이므로 실패가 아니다.

### 7.10 재설계 기준

- §2-B 무효 시험에 걸리면 앵커 경로를 접고 A 또는 C 로 간다.
- 앵커 도입 후 보류 사유가 `anchor_*` 로 **이동만 하고 총량이 그대로**면 원인은 색인이다 → AST 도입.
- 5회 중 2회 이상 붕괴(확정 개체 ≤ 2)가 계속되면 방식이 아니라 **모델·문맥 크기**가 원인일 수 있다 → 모델 변경을 통제 변수로 올린다.

## 10. 결정적 실험

### 10.1 경쟁 가설

앞선 초안은 H1 하나에 "개체 부재"와 "이름 어휘 불일치"를 묶고 있었다. §1.5-D 의 24 대 5 분해가 나온 이상 **둘을 갈라야 한다.** 가르지 않으면 어느 쪽이 들었는지 이 실험으로 알 수 없다.

- **H1a(개체 부재 가설)** — 손실의 지배적 원인은 **전체 개체가 SES 에 없어서** 거기 매달 것이 갈 곳을 잃는 것이다. 전체 후보를 제안하게 하면 보류가 크게 준다.
- **H1b(어휘 불일치 가설)** — 원인은 단계 간 이름 어휘 불일치다. 동일성을 코드 앵커에 고정하면 보류가 준다.
- **H2(의미 판단 가설)** — 원인은 모델이 개체·관계를 **의미적으로 못 알아보는 것**이다. 전체를 주고 앵커를 붙여도 보류 사유만 `anchor_absent` 로 옮겨갈 뿐 총량은 그대로다.
- **H3(용량 가설)** — 원인은 문맥 크기·모델 능력이다. 방식과 무관하게 큰 문맥·큰 모델에서 수율이 오른다.

### 10.2 통제 조건

고정: 스냅샷(`P-evidence-v1`, 파일별 해시 동일) · 모델과 설정(`temperature` · `num_ctx` · `max_tokens`) · 조립기와 검증기 개정 · 채점 정답지(ref-v8) · 별칭 사전. 반복 n=5(가능하면 10).

### 10.3 비교할 변경요소

| 팔 | 방식 | 전체 단계 `w` | 앵커 | 목적 |
|---|---|---|---|---|
| 1 | `T2-evidence` | 없음 | 없음 | 기준선 |
| 2 | `T2-whole` | **있음** | 없음 | **H1a 검정** |
| 3 | `T2-anchor` | 있음 | **있음** | H1b 검정 (팔2 대비) |
| 4 | `S2-anchor` | 있음 | 있음 | 단일 대 단계별 |
| 5 | `T2-anchor`, `num_ctx` 2배 | 있음 | 있음 | H3 분리 |

**팔2 와 팔3 의 차이만이 앵커의 효과다.** 팔1 과 팔3 을 직접 비교하면 두 변경이 섞여 어느 쪽이 들었는지 알 수 없다 — 초안의 설계 결함이었다. 팔5 는 팔3 의 **다른 조건**이지 반복이 아니다.

### 10.4 각 가설의 예상 결과

| | H1a 참 | H1b 참 | H2 참 | H3 참 |
|---|---|---|---|---|
| 팔2 의 "전체"류 `unknown_reference` | **급감** | 변화 없음 | 변화 없음 | 변화 적음 |
| 팔2 의 **보류 총량** | **급감** | 변화 없음 | 변화 없음 | 변화 적음 |
| 팔3 − 팔2 의 나머지 `unknown_reference` | — | **급감** | 사유만 이동 | 변화 적음 |
| 팔3 − 팔2 의 보류 총량 | — | **감소** | **변화 없음** | 변화 적음 |
| 확정 개체 수 | 증가 | 증가 | 변화 없음 | 변화 적음 |
| 쌍별 Jaccard | 상승 | 상승 | 변화 없음 | 변화 적음 |
| 팔5 대비 팔3 | 차이 작음 | 차이 작음 | 차이 작음 | **팔5 가 뚜렷이 우세** |

**H1 계열과 H2 를 가르는 것은 사유별 감소가 아니라 보류 총량 감소다.** 사유가 옮겨간 것을 개선으로 읽지 않는다.

### 10.5 현재 권고를 바꾸게 할 결과

1. 팔2 의 보류 총량이 팔1 의 **90% 이상** → H1a 기각. 전체 개체는 원인이 아니었다. `w` 단계를 빼고 PES 요청만 남긴다(전체는 `origin: "human"`).
2. 팔3 의 보류 총량이 팔2 의 **90% 이상** → H1b 기각, H2 지지. 앵커를 주 지렛대에서 내리고 의미 판단(프롬프트 · 모델 · 후보 격자)으로 옮긴다.
3. 팔5 가 팔3 을 **모든 지표에서 뚜렷이 상회** → H3 지지. 방식 개선보다 용량 확보를 먼저 한다.
4. 앵커 사전 이중 구현 대조 불일치 > 5% → 정규식 색인을 버리고 AST 를 B1 로 올린다.
5. PES 검사기가 ref-v8 을 통과시키지 못함 → 요청 스키마를 정답지 구조에 맞춰 고친다. **LLM 실행 전에 드러나는 결과다.**
6. 팔4(S2-anchor)가 팔3 을 상회 → 단계별 추출의 전제를 재검토한다. **이 경우에도 n=5 파일럿을 통계적 우위로 보고하지 않는다.**
7. 전문가 검토에서 "개체의 상당수가 단일 코드 기호에 대응하지 않는다"가 확인되면 → 앵커는 보조 신호로 강등하고 이름 기반 해결을 주 경로로 되돌린다.
8. `w` 단계 도입 후 루트 후보가 **늘어남** → 전체 후보 기준(조립 자리 근거)이 약한 것이다. 기준을 조이거나 D 를 철회한다.
