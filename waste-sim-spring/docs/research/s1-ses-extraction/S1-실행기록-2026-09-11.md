# S1 추출 실행 기록 — C 조건 3회

2026-09-11 · `gpt-4.1-mini` · 참조 `ref-v4` · 입력 `develop @ 8b3d67f`(미커밋 변경 포함)

절차서의 C 조건으로 S1을 **실제로 처음 돌린** 기록이다. 그전까지 `runs/`에는 보고서 모양을
보이려고 만든 합성 파일(`DEMO-*`)만 있었다.

## 입력 — C 조건

규칙은 `runs/manifest-C.json`에 박아 두었다. 도메인을 모르는 사람도 적을 수 있는 것만 썼다.

```
포함:  src/main/java/**/*.java · src/main/**/*.py
제외:  경로에 /config/ 포함 · 파일명이 Application.java로 끝남
```

**112파일 · 14,865행 · 783,839바이트.** 제외된 것은 3개
(`WasteSimApplication`·`WebRoutingConfig`·`WebSocketConfig`)뿐이다.

### 먼저 걸린 문제 — C가 128k 컨텍스트에 안 들어간다

783KB는 약 **19만 토큰**이다. `gpt-4o-mini`(128k)로는 C 조건을 돌릴 수 없다. 주석을 떼면
482KB(약 18.6만)로 줄지만 여전히 안 들어가고, 주석을 떼는 것은 근거(`evidence`)를 요구하는
이 실험의 조건을 바꾸는 일이다.

`gpt-4.1-mini`(1M 컨텍스트)로 돌렸다. 실제 사용 입력 토큰은 **189,494**였다.
**절차서 1절의 C 조건은 모델 선택과 묶여 있다** — 128k급 모델로는 D 조건(2단계 자기 선별)이
선택이 아니라 필수다.

## 0점의 원인은 둘이고, 성격이 다르다

### ① 스키마 위반 — 지배적이고, 별칭으로 못 고친다

세 실행의 최상위 키가 매번 다르다.

| 실행 | 최상위 키 |
|---|---|
| 1 | `root` `entities` **`aspects`** **`specializations`** **`multi-aspects`** `evidence` |
| 2 | `root` `entities` **`couplings`** `evidence` |
| 3 | `root` `entities` **`aspects`** **`specializations`** `evidence` |

프롬프트는 분해를 **엔티티 안의 `decompositions`**로 넣으라고 한다. 실행 1·3은 그것을
최상위 키로 빼냈다. 그래서 채점기가 관계를 하나도 보지 못하고 관계·속성이 0.000이 된다.

**구조가 없는 것이 아니라 있는데 다른 자리에 있다.** 실행 1의 `specializations`에는 이런 것이
들어 있었다 —

```
DischargeTimeMode  : PAPER_BASELINE / POHANG_ACTUAL
TravelTimeMode     : LEGACY_CONSTANT / OSRM_HYBRID / ZONE_PROXY_HYBRID
TruckType          : LARGE_5TON / MEDIUM_2P5T / SMALL_1TON
ScenarioPreset     : UNIVERSITY / INDUSTRIAL / FAMILY / BALANCED
ZoneAssignmentRule : NONE / CONTIGUOUS / ROUND_ROBIN
```

**다섯 축 모두 참조의 spec 축과 실질적으로 같다.** 채점에 한 점도 반영되지 않았다.

실행 2는 `couplings`를 제대로 냈다(15개).

> **정정 (아래 "형식 교정" 절 참조):** 처음에 이것을 "지시 준수의 불안정"이라고 적었다.
> 틀렸다. **3절 프롬프트는 `decompositions`가 엔티티 안에 들어간다는 것을 한 번도 말하지
> 않는다** — 스키마가 `"entities": { ... }` 축약형이고, 전체 스키마는 2절(사람용 문서)에만
> 있다. 모델이 분해를 최상위로 뺀 것은 **합리적인 추측**이었다. 지시 준수 실패가 아니라 지시
> 부재다.

### ② 이름 언어 — 별칭으로 분리된다

추출은 영문 이름을 쓰고 참조는 한국어다. 절차서 5절의 3단계 이름 처리(정규화 → 별칭 → 미매칭
보고)가 바로 이 상황을 위한 것이다. 개념이 분명히 대응하는 7건만 `aliases.json`에 등록했더니
첫 실행의 노드 F1이 **0.000 → 0.255**(P 0.636)로 올랐다. 관계·속성은 **0 그대로**였다.

즉 노드 쪽 0점은 이름 문제이고, 관계·속성 0점은 스키마 문제다. 둘을 갈라 보지 않으면
"아무것도 못 했다"로 읽힌다.

`Subtask`·`SubtaskSet`·`SubtaskGroup`·`SubtaskSession`은 **등록하지 않았다.** 참조에 대응 개념이
없다 — 문항 수집 계층은 시뮬레이터를 구성하는 장치이고 시뮬레이션 대상이 아니다. 별칭으로
넣으면 오답을 정답으로 만든다.

## 가장 중요한 발견 — 클래스로 있는 것만 찾는다

세 실행이 공통으로 **찾은** 것: `WasteType`·`TruckType`/`VehicleType`·`TrafficProfile`·
`CollectionSite`/`Building`·`SimulationConfig`·`SimulationResult`.
전부 **독립 클래스나 enum으로 존재한다.**

세 실행이 공통으로 **못 찾은** 것:

| 참조의 노드 | 코드에서의 존재 형태 |
|---|---|
| 거주민 | `DischargeEvt`(SimulationEngine:227) — 이벤트 |
| 수거지점의 적재량 | `fill[building][type]`(:253) — 메서드 지역 배열 |
| 민원 판정 3종 | `wasteOverflowComplaints++`(:460) 등 — 지역 변수 증가 |
| 적재초과·임대인·교통혼잡 | 723행 `run()` 메서드 안의 분기 |

**이 엔진은 DEVS 원자 모델을 클래스로 두지 않는다.** 거주민도 수거장도 민원 판정도 한 메서드
안의 배열과 이벤트다. 추출기는 그것을 구조로 보지 못했다.

그래서 이 실험의 결론은 "LLM이 구조를 못 만든다"가 아니다. 더 정확히는 —

> **추출기는 코드가 이미 구조로 표현해 둔 것만 구조로 낸다.** 코드가 구현으로만 표현한 것은
> 구조로 올라오지 않는다.

참조 SES를 사람이 만들 때는 `SimulationEngine.run()`을 읽어 이벤트와 배열에서 원자 모델을
복원해야 했다(`참조-검증-기록.md`의 결합 6개가 그 작업이다). 추출기는 그 단계를 하지 않는다.

## 곁들여 나온 것

**실행 3이 클래스 목록으로 흘렀다.** `JangnyangSubtaskDefinition`·`SimulationModelProvider`·
`CoordinateQuality`·`SubtaskError`를 엔티티로 냈다. `SimulationModelProvider`는 인터페이스이고
`SubtaskError`는 오류 타입이다 — 프롬프트 규칙 3("구조를 실행하는 환경은 넣지 마세요")이 막으려
한 것이 다른 형태로 재발했다.

**Java 타입이 새어 나왔다.** 실행 1의 multi-aspect에 `List<String>`과
`RouteDurationEstimator.Hop`이 엔티티로 들어 있다.

## 내가 어긴 것 — 실행 원본 하나를 잃었다

첫 실행을 1회 돌려 보고, 이어서 3회를 돌리면서 **`n`을 1부터 다시 매겨 첫 실행 파일을
덮어썼다.** 절차서 4절("매 실행의 원본 출력을 그대로 남긴다")을 어긴 것이다. 위에서 노드 F1
0.255로 보고한 그 실행의 원본은 남아 있지 않다(측정값만 이 문서에 있다).

`run_s1.py`를 비어 있는 다음 번호를 찾아 쓰도록 고쳤다. 덮어쓰기가 불가능해졌다.

**부수 효과**: `aliases.json`의 7건은 사라진 그 실행의 이름(`Building`·`Truck`·`RoutePlan`·
`WasteSimulation`)에 맞춰 등록한 것이다. 남은 세 실행은 다른 이름
(`CollectionSite`·`TruckType`·`VehicleType`·`Route`·`Simulation`)을 쓰므로 별칭이 절반만 맞는다.
**별칭은 한 실행이 아니라 전체 실행에서 모아야 한다** — 5절이 "미매칭을 목록으로 출력한다"고
한 이유가 이것이다.

# 형식 교정 — Cs · Csr 조건 (같은 날)

C의 관계·속성 0점이 스키마 위반 때문이라고 보고, 교정 둘을 따로 재었다.

| 조건 | 내용 |
|---|---|
| `C` | 3절 프롬프트 원문. 스키마 축약형 |
| `Cs` | 축약 스키마를 **2절의 전체 스키마로 교체**. 새 정보가 아니라 절차서 자신의 스키마다 |
| `Csr` | `Cs` + **코드 뒤에 출력 계약을 다시 적는다**(코드가 19만 토큰이라 앞쪽 지시가 생성 직전 신호에서 멀다) |

`Csr`의 배치 처방은 설계도 경로 벤치마크에서 계약 통과율을 0%→97%로 올린 것과 같다.

## 형식은 고쳐졌다

| | C | Cs | Csr |
|---|---|---|---|
| 계약 밖 최상위 키 | **3회 중 2회** | **0회** | **0회** |
| `decompositions` 산출 | 0 | 5·2·3 | 4·3·6 |
| 관계 산출(예측 수) | 0·0·0 | 9·6·3 | 12·5·6 |
| 속성 산출(예측 수) | 0·0·0 | **166·193·162** | **183·137·272** |
| 반복 간 노드 Jaccard | 0.265 | **0.490** | 0.289 |

**전체 스키마를 보여 준 것만으로 위반이 사라졌다.** 관계와 속성이 비로소 산출되고, 재현성도
두 배 가까이 올랐다(0.265 → 0.490).

**`Csr`는 `Cs`보다 나쁘다.** 재현성이 0.490 → 0.289로 떨어지고 엔티티 수가 22·13·34로 크게
흔들린다. 벤치마크에서 통했던 "계약을 맨 뒤로" 처방이 여기서는 해가 됐다 — **여기서 빠진 것은
계약의 위치가 아니라 스키마의 내용이었다.** 같은 증상에 같은 처방이 듣는다고 가정하면 안 된다.

## 그런데 채점은 여전히 0.000이다

| | C | Cs | Csr |
|---|---|---|---|
| 노드 F1 | 0.138·0.067·0.065 | 0.068·0.066·0.066 | 0.061·0.070·0.051 |
| **관계 F1** | 0.000 | **0.000** | **0.000** |
| **속성 F1** | 0.000 | **0.000** | **0.000** |
| 임계점 | 0/5 | 0/5 | 0/5 |

속성을 166~193개 냈는데 **맞은 것이 하나도 없다.** 원인이 둘 겹쳐 있고, 두 번째가 더 크다.

### ① 언어 — 별칭으로 풀 수 있다

```
추출:  SimulationConfig.wasteMeanKg
참조:  대상 시스템.1인배출량
```

같은 개념, 다른 언어다. `(엔티티, 속성)` 쌍으로 채점하므로 양쪽이 다 영문/한국어면 한 건도
겹치지 않는다. 절차서 5절의 별칭 단계가 이것을 위한 것인데, **엔티티 44개 + 속성 49개의
이중언어 대응표**가 필요하다 — "쓰레기통→수거지점" 같은 몇 건을 예상한 설계였다.

### ② 더 큰 문제 — 대상 시스템이 아니라 코드의 클래스 그래프를 냈다

`Cs-1`의 실제 산출이다.

```
SimulationConfig -[aspect]-> ScenarioScale, ZoneAssignmentRule, TruckType, WasteType, OccupationType
SimulationConfig -[multi]->  WasteType
JangnyangSubtaskDefinition -[multi]-> SubtaskGroup, JangnyangSubtask

couplings:
  JangnyangScenarioSpec.simulationConfig -> SimulationConfig
  JangnyangSubtaskSession.spec           -> JangnyangScenarioSpec
```

- **허브가 `SimulationConfig`다.** 속성 166개가 전부 이 설정 객체에 달려 있다. 참조는 같은
  값들을 *무엇을 서술하는가*에 따라 거주민·수거지점·폐기물 유형·실험에 나눠 붙인다.
  추출은 *어디에 선언됐는가*로 모은다.
- **`aspect`가 "이 설정이 이 enum들을 참조한다"는 뜻으로 쓰였다.** "시스템이 이 구성요소들로
  이루어진다"가 아니다.
- **`couplings`가 객체 참조다.** `spec → simulationConfig`는 필드 참조이고, 시뮬레이션 개체
  사이의 정보 흐름(배출→적재, 수거→비움)이 아니다.
- 거주민·민원 판정은 여기서도 없다.

**별칭으로 고칠 수 없다.** `SimulationConfig`를 참조의 어느 엔티티에 대응시켜도 맞지 않는다 —
그 안의 속성들이 참조에서는 네 엔티티로 흩어져 있기 때문이다. 이름 문제가 아니라 **분류 기준이
다르다.**

## 그래서 지금까지 측정된 것

형식을 고치면 **형식만** 고쳐진다. 9회 실행(C 3 · Cs 3 · Csr 3)에서 일관된 것은 —

> 추출기는 **코드가 선언으로 표현한 구조**를 낸다. 클래스·enum·필드 참조는 찾는다.
> **시뮬레이션 대상의 구조**는 내지 않는다 — 그것은 `SimulationEngine.run()` 723행 안의
> 이벤트와 배열로만 존재하고, 설정 값을 "무엇을 서술하는가"로 재분류하는 일은 하지 않는다.

이것이 베이스라인 분석이 T2·T4(구조 해상도)라고 부른 빈칸이고, 이제 **실제 코드와 사람이
확정한 정답지 위에서 숫자로** 나왔다.
