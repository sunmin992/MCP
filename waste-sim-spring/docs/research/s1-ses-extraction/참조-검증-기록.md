# 참조 SES 검증 기록 — ref-v2 → ref-v4

2026-09-11 · 대조 대상 `develop @ 8b3d67f` · `src/main/java/com/wastesim/**`

`S1-추출절차.md` 7절이 요구하는 선행 작업이다. 참조 SES는 방법론 문서에서 옮긴 초안이었고
코드와 대조된 적이 없었다. **정답지가 틀리면 채점이 전부 무의미하므로** S1을 돌리기 전에
확인했다.

절차서는 이 대조 자체가 S1의 첫 산출물이라고 적는다 — 사람이 코드를 읽어 SES를 확정하는
과정이므로, LLM이 같은 일을 했을 때와 비교할 기준이 된다. 이 문서가 그 기록이다.

## 고친 것 — 여섯 항목

### ① 교통혼잡 판정 — 처음에 잘못 지웠다가 되돌렸다

**ref-v3에서 이 노드를 지웠고, 그것은 내 실수였다.** `Complaints`(복수)로만 검색해
`trafficComplaintAccum`(단수)을 놓쳤다. 코드에 있다:

```java
// SimulationEngine:337-339
if (trafficProfile.isRed(minuteOfDay, zone)) {
    trafficComplaintAccum += cfg.getTrafficComplaintWeight();
}
// :482
double trafficPenalty = Math.round(trafficComplaintAccum * 100.0) / 100.0;
// :483
int total = wasteOverflowComplaints + landlordComplaints;
```

세 판정은 **같은 실행에서 함께 계산된다.** 다만 총 민원 수는 두 항의 합이고, 교통 패널티는
`SimulationResult.trafficPenalty:83`으로 따로 나간다. 코드 주석이 이유를 밝힌다 —

> 교통 패널티는 생활쓰레기 민원과 단위가 다르므로 totalComplaints와 byOccupation에 합산하지
> 않는다.

**결론**: `교통혼잡 판정`은 구조에 남고, CP-1의 `aspect` 판정도 그대로다. 고칠 것은 두 가지였다.

- 속성 `차량정차시간` → **`민원가중치`**. 방아쇠는 정차시간이 아니라 "도착 시각이 그 구역의
  적색 구간인가"이고, 누적되는 값은 `cfg.trafficComplaintWeight:212`다.
- CP-1 근거문 — "총 민원 = 세 판정의 합"이 아니라 **두 항의 합**이고, 교통 판정은 구조에
  있으나 총합의 항이 아니다.
- `교통 구역`에 `적색임계값` 추가(`TrafficProfile.congestionThresholdRed:25`) — 이 판정의 방아쇠다.

**남길 교훈**: 식별자 검색으로 "없다"를 결론하면 안 된다. 단복수·약어 하나로 갈린다.
없다는 판정은 기제를 따라가 확인해야 한다.

### ② 직업은 5종이고 `기타 직업`은 코드에 없다

`OccupationType:8-13`

| enum | 라벨 |
|---|---|
| `BlueCollar` | 생산직(일용직) |
| `Student` | 학생 |
| `Housewife` | 전업주부 |
| `NightShift` | 야간 교대근무자 |
| `OfficeWorker` | 1인 직장인 |

`baseMix()`(`:27`)는 논문 Table 1의 3종만 돌려주지만, 시나리오 유형에 **`new-occupations`가
있으므로** 확장 2종도 구조에 있어야 한다 — CP-3이 "분리배출 실험에서 유형 수가 변해야 한다"고
요구하는 것과 같은 논리다. 실험으로 개수를 바꾸는 축은 구조에 있어야 하고, 속성으로 묻으면
코드를 고쳐야 한다.

- 직업 축 자식: `생산직·학생·전업주부·기타 직업` → `생산직·학생·전업주부·야간 교대근무자·1인 직장인`

### ③ 폐기물 유형에 `부피계수`는 없고, 자기 용량·임계값을 갖는다

`WasteType:18-31` — `key`·`labelKo`·`fraction`·`capacity`·`threshold`·`intervalDays`·
`collectionDaysOfWeek`. 부피 관련 필드는 없다.

- 속성: `종류·배출비율·부피계수` → `종류·배출비율·용량·임계값·수거주기·수거요일`

`threshold`가 여기 있다는 사실이 다음 항목(③-2)으로 이어졌다 — CP-2가 이 값의 소유자를
수거지점으로 잘못 지목하고 있었다.

### ③-2 임계값은 수거지점의 속성이 아니다 — CP-2를 고쳤다

`CollectionSite(49-58)`의 전체 필드다:

```
id · longitude · latitude · name · adminDivision · source · snapMeters
trafficZone · largeTruckAllowed
```

**용량도 임계값도 없다.** 임계값은 폐기물 유형이 갖고(`WasteType.threshold:22`) 기본값은 전역
`cfg.threshold:28`에서 온다. 임대인 임계값은 또 다른 전역값이다(`cfg.landlordThreshold:190`).

CP-2는 "민원임계값은 수거지점의 속성이고 지점마다 달라야 한다"고 했다. 코드에 지점별 임계값은
없다. **이대로 두면 임계값을 폐기물 유형 아래 정확히 배치한 추출기가 CP-2에서 떨어진다.**

- `수거지점.attrs`: `용량·적재량·교통구역·차량진입가능·민원임계값` → `적재량·교통구역·차량진입가능`
- CP-2 `where`: `수거지점.민원임계값` → `폐기물 유형.임계값`, `must_be`: 폐기물 유형의 속성

분리배출을 켜면 유형별로 임계값이 달라지므로 유형 아래 있어야 맞다 — CP-3이 지키려는 것과
같은 이유다.

### ④ `1인배출량`은 거주민의 속성이 아니다

`DischargeTimeMode` javadoc이 명시한다 — "배출량은 전역값(`wasteMeanKg`)". 실제로
`SimulationConfig:26`의 단일 값이고 거주민마다 다르지 않다. 거주민이 지니는 것은 외출·귀가
시각뿐이다(`OccupationType:17-18`).

- `거주민.attrs`: `직업·외출시각·1인배출량·귀가시각` → `직업·외출시각·귀가시각`
- `대상 시스템.attrs`에 `1인배출량` 추가

### ⑤ 두 축은 독립이지만 곱집합은 아니다

CP-5의 근거문이 "두 축은 곱집합이다 ... 4×2=8 조합"이라고 했다. 코드는 다르게 말한다 —
`DischargeTimeMode.POHANG_ACTUAL` javadoc:

> **이 모드에서는 직업이 배출 시각에 영향을 주지 않는다.** ... 시각이 균등분포로 바뀌면 직업
> 구성비가 결과를 바꾸지 못한다. 논문 모델의 "직업 구성이 민원에 영향을 준다"는 기제가 이
> 모드에서는 사라진다.

`POHANG_ACTUAL` 쪽 조합들은 배출 시각 기준으로 서로 구별되지 않는다.

**CP-5의 판정은 유지한다**(spec 축 2개). 두 축을 하나로 합치면 축별 독립 선택으로 pruning할 수
없다는 것은 그대로 맞다. 근거문만 코드가 말하는 것으로 바꿨다. 직업 축은
`SimulationResult.byOccupation`에서 여전히 쓰인다.

## 결합 6개 확정 (절차서 7절 첫 항목)

엔진은 원자 모델을 별도 클래스로 두지 않고 **이벤트**로 표현한다 — `CollectEvt(213)`·
`DischargeEvt(227)`·`InspectEvt(236)`. 그래서 포트를 이벤트와 상태 접근에 대응시켰다.
여섯 결합 전부 `verified: true`이고 `mechanism`에 근거를 적었다.

| from | to | 기제 |
|---|---|---|
| 거주민.배출 | 수거지점.적재 | `DischargeEvt` → `fill[b][t] += amount × fraction` (`:457`). 외출·귀가로 분할 배출(`:363`) |
| 수거지점.적재량 | 적재초과 판정.판정 | **별도 메시지가 아니다** — `DischargeEvt` 처리 안에서 즉시 `fill/capacity ≥ threshold` 판정(`:459-462`) |
| 수거지점.적재량 | 임대인 점검 판정.판정 | `InspectEvt`가 별도 시각에 `max(fill/capacity)`를 전역 임계값과 비교(`:466-475`) |
| 수거차량.수거 | 수거지점.비움 | `CollectEvt` → due 종류만 `fill[b][t] *= keepFraction` (`:420`). 잔여용량 부족 시 비례 부분수거(`:416-425`) |
| 교통 구역.혼잡계수 | 수거 경로.이동시간 | `weightAt` → `congestionWeight` → `hopMinutes`로 도착 지연(`:336,:343`) |
| 교통 구역.혼잡계수 | 교통혼잡 판정.판정 | `isRed`이면 가중치 누적(`:337-339`) |

**초안 4개에서 두 가지가 바뀌었다.**

1. `수거지점.적재량 → 민원 판정.in` 하나를 **둘로 나눴다.** 두 판정은 판정 시점이 다르고
   (배출 즉시 vs 별도 점검 이벤트) 임계값 소유자도 다르다(폐기물 유형 vs 전역 설정).
   하나로 묶으면 그 차이가 사라진다.
2. `교통 구역 → 교통혼잡 판정`을 **추가했다.** 교통 구역은 이동시간과 혼잡 판정 두 곳으로
   간다 — 초안에는 이동시간 쪽만 있었다.

포트 이름은 초안의 `.지체`를 `.혼잡계수`로 바꿨다. 코드가 넘기는 값이 `weightAt`의 가중치이고,
지체(분)는 그 가중치를 `hopMinutes`가 시간으로 바꾼 결과다.

### 결합은 채점되지 않는다

`score_ses.py`에 `coupling`이라는 문자열이 없다. 프롬프트는 `couplings`를 요구하고 스키마에도
있는데, 절차서 5절의 지표 표에는 결합 항목이 없다. **추출기가 결합을 틀리게 내도 점수에
반영되지 않는다.** 지표를 추가할지는 절차 설계의 결정이라 손대지 않았다.

## 맞은 것

- **CP-1의 kind와 자식 수** — 세 판정이 같은 실행에서 함께 돈다. `aspect`도 자식 3개도 맞다.
  틀린 것은 교통혼잡 판정의 속성 이름과 근거문뿐이었다(①).
- **CP-3의 독립성** — `WasteType`은 독립 클래스이고 `SimulationConfig:180`이 `List<WasteType>`로
  여럿을 갖는다. multi 개체가 맞다.

## 아직 대조하지 않은 것

`_meta.status`에도 적어 두었다.

- **CP-4의 소속** — `TravelTimeMode`는 코드상 `SimulationConfig`의 전역 필드이고
  `TravelTimeCalculator`가 소비한다. 차량의 성질이 아닌 것은 확실하지만(차량은 `TruckType`의
  용량·기동성을 갖는다), "수거 경로 아래 spec"은 코드에 명시된 소속이 아니라 해석이다.
  CP-4는 그대로 두었다.
- **수거차량·교통구역·관측 8종의 속성 전수**

## 자체 검증 수정

`score_ses.py`의 자체 검증 [2]가 `assert len(kind_errors) == 3`으로 자식 수를 상수로 박고
있었다. ①로 자식이 3→2가 되면서 **스크립트가 죽었다.** 참조에서 자식 수를 파생시키도록
고쳤다 — 정답지를 고칠 때마다 검증이 깨지면 정답지를 고치기 어려워진다.

자체 검증 6/6 통과.

## DEMO 실행 파일은 이제 낡았다

`runs/DEMO-*.json`은 ref-v2를 기준으로 합성한 파일이다. ref-v4로 채점하면 `기타직업`이
과잉으로, `야간교대근무자`·`1인직장인`이 누락으로 잡히고 **두 파일 모두 CP-2에서 떨어진다**
(임계값을 수거지점 아래 두었기 때문이다). `DEMO-modelA-2`는 ref-v2에서 노드 F1 1.0·임계점
5/5였으나 이제 0.966·3/5다.

**이것은 오류가 아니라 의도한 동작이다** — 교정된 정답지가 낡은 구조를 잡아내고 있다.
합성 파일이므로 다시 만들지 않았다(없는 데이터를 지어내는 일이 된다).
