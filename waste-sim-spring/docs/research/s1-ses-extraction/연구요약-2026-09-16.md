# 소스 코드 → SES 추출: 검증 우선 파이프라인

2026-09-16 · 대상 `waste-sim-spring`(장량동 생활쓰레기 수거 시뮬레이터) · HEAD `12937be`

---

## 한 줄

**SES를 뽑는 데 성공한 것이 아니라, 뽑히지 않는다는 사실을 항목별로 확인할 수 있게 만들었다.**
모든 추출 항목이 코드의 어느 줄에서 왔는지 기계가 다시 대조하고, 통과하지 못한 것은
사유와 원문을 남긴 채 보류된다. 지금까지 13개 조건 모두 **승인 불가**이며, 그 이유가 남는다.

---

## 1. 무엇을 만들었나

```
입력 승인 정책 → 불변 스냅샷 → 8단계 추출(LLM) → 결정적 조립(코드)
                                    ↓
                    층별 검증 → 보고서 → 전문가 검토 → 승인 리비전
```

| 구성 | 내용 |
|---|---|
| 입력 경계 | 평가 자료(참조 SES·별칭)와 SES 선언 패키지를 **모델 호출 전에 차단** |
| 스냅샷 | 원본 바이트 사본. 이후 모든 단계는 작업트리가 아니라 사본만 읽는다 |
| 추출 8단계 | 관찰 → 개체·상태 → 속성 → 구성 관계 → 루트 → 결합 → 활성 조건 → 2차 확인 |
| 근거 요구 | 개체는 **네 근거**(갱신·식별·소유 대응·소비)가 모두 있을 때만 성립 |
| 조립 | 결정적. 버리지 않고 보류한다. 원시 후보마다 판정 기록 1건 |
| 검증 | 차단 13종 + 경고 5종. 경고는 기록만 하고 막지 않는다 |
| 검토 | `accepted` 는 사람만 부여. 기준을 실행 전에 고정 |

규모: 모듈 14개 · CLI · 자동 시험 **112건** · 실행 26회 · 단계 호출 131건

## 2. 무엇을 알아냈나

### ① 검증이 없으면 틀린 것이 통과한다

첫 조건에서 근거 실패 44건 중 **31건이 "원문은 실재하는데 행 번호만 틀린" 인용**이었다.
검사가 없었다면 "근거가 달린 항목"으로 통과했을 것들이다.

인용 대조는 글자 단위로 하되 **옮겨적기 방식을 갈라 센다** — 정확 일치 / 들여쓰기 보정 /
줄이음 보정 / 불일치. 한 칸에 뭉치면 "글자 그대로 옮긴 근거가 얼마나 되는가"가 사라진다.

### ② 한 지표로 방식을 고르면 틀린 답을 고른다

단일 추출(S2)이 근거 정확도 **92%로 가장 높았는데**, 그 산출물은 자바 클래스 목록 7개와
호출 그래프였다. 속성 42개가 전부 `SimulationConfig` 아래 달렸다. 단계별 추출은 근거가
낮고 구조가 나았다. **근거 통과율은 "무엇을 골랐는가"를 재지 않는다.**

### ③ 개입은 자주 실패했고, 실패도 기록했다

| 개입 | 결과 |
|---|---|
| 인용 지시 강화 | **역효과** (90% → 70%, 근거 수 60 → 37) |
| 단계 간 이름 고정 | 유효 (분해 0건 → 복구) |
| 루트 단계 추가(생성 허용) | **검사를 지어내서 통과** — 근거가 순환 논증이었다 |
| 루트 단계(생성 금지) | 모델이 "없다"고 정직하게 답함 (3회 일관) |
| b2 상태/값 규칙 | **무효** — 상류(a)가 집계값만 관찰하고 있었다 |
| a 단계에 색인 요구 | **유효** — 근거 인용이 1개 행 → 30개 행으로 분산 |

### ④ 지금 막힌 곳은 형식이 아니라 의미다

최근 실행(`q3-obs1`)의 근거는 116건 중 100건 통과·전부 정확 일치인데, 구조에는
의미 오류가 남는다.

| 분해 | 판정 |
|---|---|
| `SPEC 직업군 → 생산직·학생·전업주부·야간교대·1인직장인` | **적합** (자식마다 `OccupationType` 열거 상수 인용) |
| `SPEC 요일 → 월~일` | 적합하나 근거가 약함(7개가 같은 한 줄) |
| `MULTI 운행 → 트럭` | **부적합** (방향 반대) |
| `ASPECT 건물과 쓰레기 종류 → 건물·쓰레기 종류` | **부적합** (부모 이름이 둘을 묶은 것) |

결합 23건은 **전부 자기 자신으로의 결합**이라 쓸 수 없다.

## 4. 주장하지 않는 것

- **조건당 1회다.** 조건 간 차이가 반복 흔들림보다 큰지 모른다. 로컬 모델로 4회 반복해 보니
  개체는 완전히 일치(Jaccard 1.00)했으나 상태 소유관계는 0.19로 흔들렸다.
- **참조 대비 F1을 아직 내지 않았다.** 승인 가능한 초안이 없어 F1 을 해석할 수 없다.
- **프롬프트 수정을 참조 SES 를 읽은 상태에서 했다.** 형식·절차 수정만 했고 전부 기록했으나,
  의미 판정은 참조를 보지 않은 사람이 해야 한다.
- 7B 로컬 모델은 재현성이 없어(Jaccard 0.08) 품질 비교 자료로 쓰지 않는다.

## 5. 기여로 주장할 것

1. **근거 추적 가능한 SES 추출의 데이터 계약** — 모든 항목이 파일·행·인용을 갖고,
   기계가 재대조하며, 못 맞추면 보류된다.
2. **형식 검증과 의미 검증의 분리** — 차단 13종(기계) / 경고 5종(기록) / 승인(사람).
   "근거가 실재한다"와 "그 근거가 의미를 보인다"를 같은 칸에 적지 않는다.
3. **실패가 보존되는 실험 기록** — 요청은 보내기 전에 저장하고, 실패한 시도의 원문이 남으며,
   재개 키로 모델을 다시 부르지 않고 조립·검증만 다시 돌릴 수 있다.

추출 성능이 아니라 **추출을 평가할 수 있게 만든 것**이 기여다.

# 부록 B — 파이프라인을 어떻게 설계했나

## 설계 원칙 하나

> **LLM 은 의미 후보를 내고, 코드는 그 후보가 코드에 실재하는지와 구조가 성립하는지만
> 확인하며, 둘 다 의미의 정당성은 판정하지 않는다.**

이 한 줄에서 나머지가 따라 나온다.

### 무엇을 코드가 하는가 (결정적·재현 가능)

| 일 | 구현 |
|---|---|
| 파일 선별·차단·해시·사본 | `input_policy` · `snapshot` |
| 근거 대조(파일·행 범위·인용·기호) | `evidence` · `index` |
| 루트 후보 세기(진입 차수 0) | `stages.root_candidates` |
| 2차 질문 대상 고르기(미확정 끝점) | `stages.pending_endpoints` |
| 조립·병합·보류 이관·판정 기록 | `assemble` |
| 참조 무결성·순환·다부모·도달 가능성 | `structure` · `contract` |

### 무엇을 LLM 이 하는가

무엇이 개체인가, 무엇이 값인가, 어떤 구성 관계인가, 무엇이 오가는가, 언제 활성인가.
**전부 의미 판단이고, 전부 근거를 함께 내야 한다.**

### 무엇을 누구도 하지 않는가

`accepted` 판정. 사람만 한다.

## 설계 결정 일곱

**① 왜 단계로 나눴나**
한 번에 전체 SES 를 받으면 어디서 틀렸는지 알 수 없다. 단계마다 산출물을 저장하면 실패가
격리되고 단계별 통과율이 측정 단위가 된다. 다만 **단일 추출(S2)도 같은 계약으로 돌린다** —
분해가 이득인지가 검증 대상이기 때문이다. 실제로 S2 가 근거는 더 좋고 구조는 나빴다.

**② 왜 단계마다 코드 전문을 다시 주나**
사람이 "이게 도메인 모델이야" 하고 파일을 골라 주면, 추출이 하는 일은 이미 정리된 것을
트리로 옮기는 것으로 줄어든다. 선별은 **규칙 파일로만** 하고 그 규칙은 커밋으로 남는다.

**③ 왜 근거를 네 종으로 나눴나**
한 인용이 통과했다고 그 항목의 이름·소유·단위가 모두 정당해지지 않는다. 그래서 근거마다
**어떤 항목의 어떤 주장을 지지하는지**(`supports.field`)를 적는다 — 갱신·식별·소유 대응·소비.
그러면 "상태 갱신 주장은 3/3 지지되는데 식별 주장은 1/3"처럼 **주장 단위로** 볼 수 있다.

**④ 왜 버리지 않고 보류하나**
조용히 버리면 무엇을 못 봤는지 알 수 없다. 자기 참조·미해결 참조·파싱 실패는 원문과 함께
`unresolved`(17종 사유)로 간다. 불변식은 **개수 등식이 아니라 역추적 가능성**이다 —
병합·분할이 있으면 개수는 맞지 않지만 원시 후보에서 최종 항목으로 가는 길은 늘 있어야 한다.

**⑤ 왜 차단과 경고를 나눴나**
기계가 판정할 수 있는 것(파일에 그 줄이 있는가, 순환이 있는가)과 없는 것(이 인용이 식별을
보이는가)이 다르다. 후자를 차단으로 만들면 **모양만 맞춘 근거가 통과**한다. 그래서 경고는
세기만 하고 막지 않는다. 실제로 "식별 근거가 선언·생성·등록 모양인가"를 차단으로 만들 뻔했다가
기각했다 — 클래스 선언이 실행 지원 클래스일 수 있고, 인덱스 대응은 그 모양에 안 맞는다.

**⑥ 왜 재개 키에 프롬프트·설정·상위 산출물을 넣었나**
조건이 하나라도 바뀌면 캐시가 무효여야 비교가 성립한다. 반대로 **바뀌지 않았으면 다시 부르지
않는다** — 그래서 모델을 한 번도 다시 부르지 않고 검증기를 다섯 번 바꿔 기존 20여 개 실행에
소급 적용할 수 있었다. 응답 원문이 전부 남아 있기 때문이다.

**⑦ 왜 요청을 보내기 전에 저장하나**
시간 초과처럼 응답을 못 받은 경우에도 무엇을 보냈는지 남아야 한다. 그런 시도는 `unknown`
이며 **실패로 단정하지 않는다** — 요청이 닿았는지 모르기 때문이다.

## 기각한 대안

| 대안 | 왜 쓰지 않았나 |
|---|---|
| AST 색인을 주 추출 경로로 | 참조의 판정 계열 개체가 클래스가 아니다. 리콜 상한을 먼저 재야 한다 |
| 자동 수리 루프 | 첫 비교에서 제외. 수리 효과와 방식 효과가 섞인다 |
| 이름 정규화로 자동 병합 | 괄호로만 다른 둘을 같다고 볼 위험. **힌트로만** 적는다 |
| 관측 그릇 자동 생성 | 결과 저장 구조라는 이유로 개체를 만들지 않는다 |
| 모르는 활성 조건을 "항상 활성" | 그런 경로가 코드에 **없다** |
