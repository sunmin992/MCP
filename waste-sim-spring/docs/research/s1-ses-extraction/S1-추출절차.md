# S1 추출 절차 v1 — 시뮬레이터 소스 코드 → SES

목적: **같은 코드에서 같은 구조가 나오는지**를 잴 수 있는 형태로 S1을 고정한다.
한 번 잘 뽑는 것이 아니라, 반복해서 뽑아 흔들림을 재는 것이 이 절차의 목적이다.

---

## 1. 입력을 무엇으로 줄 것인가 — 가장 중요한 설계 결정

장량동 저장소는 101파일 13,682행(테스트 67파일 10,703행 별도)이다. 전부 줄 수 없다.
무엇을 주느냐가 S1의 난이도와 정직성을 동시에 정한다.

| 방식 | 내용 | 문제 |
|---|---|---|
| A. 전체 덤프 | 모든 파일 | 컨텍스트 초과. 테스트가 노이즈 |
| B. 사람이 고른 핵심 클래스 | "이게 도메인 모델이야" | **순환** — 고르는 순간 구조의 절반을 알려준 것 |
| **C. 기계적 규칙으로 선별** | 사전에 고정한 규칙으로 자동 선별 | 규칙이 도메인에 묶일 수 있음 |
| **D. 2단계 자기 선별** | 파일 트리+시그니처 → LLM이 읽을 파일을 고름 → 본문 제공 | 절차가 길다 |

**B를 쓰면 안 된다.** 사람이 도메인 모델 클래스를 골라 주면, S1이 하는 일은 "이미 정리된 것을
트리로 옮기기"로 줄어든다. 발표에서 가장 먼저 찔릴 자리다.

**C로 시작해 D로 올린다.**

- **C (기준선)** — 선별 규칙을 사전에 고정한다:
  `src/main/**` 만, `src/test/**` 제외, 확장자 `.java`/`.py`,
  설정·빌드·마이그레이션·DTO 직렬화 전용 파일 제외.
  이 규칙은 도메인을 모르는 사람도 적을 수 있어야 한다 — 그것이 순환을 피하는 기준이다.
- **D (확장)** — 1단계로 파일 경로 + 클래스/함수 시그니처만 준다. LLM이 "구조를 알려면 이 파일들을
  봐야 한다"고 고르게 한다. 2단계로 그 파일들의 본문을 준다.
  D가 C의 결과를 재현하면, **큰 코드베이스로 확장 가능함**이 증명된다. 두 번째 코드베이스
  (SimPy 예제)에서도 같은 절차가 그대로 돈다.

기록할 것: 선별 규칙, 실제로 포함된 파일 목록과 총 행 수, (D의 경우) LLM이 고른 파일 목록.

## 2. 출력 형식

자유 텍스트는 채점할 수 없다. **JSON 트리를 정본**으로 하고, 여섯 편집 연산은 그 트리를 만드는
편집 이력으로 파생시킨다(채점에는 트리가, 시스템 적용에는 연산이 편하다).

```json
{
  "root": "<루트 엔티티 이름>",
  "entities": {
    "<엔티티 이름>": {
      "attrs": ["<속성 변수 이름>", "..."],
      "decompositions": [
        { "kind": "aspect|spec|multi", "name": "<분해 축 이름>", "children": ["<자식 엔티티>", "..."] }
      ]
    }
  },
  "couplings": [
    { "from": "<엔티티>.<포트>", "to": "<엔티티>.<포트>" }
  ],
  "evidence": {
    "<엔티티 또는 엔티티.속성>": "<파일 경로:행번호 또는 클래스·필드명>"
  }
}
```

### 선택적 확장 (ref-v7, 2026-09-11)

정답지는 아래 둘을 더 쓴다. **3절 프롬프트에는 넣지 않았다** — 넣으면 기존 실행
12건(C·Cs·Csr·Cd)과 조건이 달라져 비교가 끊긴다. 그래서 추출기는 이 구성물을 낼 수 없고,
그만큼은 처음부터 재현 불가로 남는다. 추출 비교로 갈 때 새 조건으로 추가하면 된다.

```json
"couplings": [
  { "from": "...", "to": "...",
    "active_when": "trafficMode=APPLY — NONE이면 이 결합이 통째로 죽는다" }
],
"entities": {
  "<엔티티>": {
    "attrs": ["수거시각"],
    "attr_spec": {
      "수거시각": { "kind": "TIME", "arity": "1..6", "evidence": "..." },
      "직업구성": { "kind": "composition", "over": "거주민.직업 축", "evidence": "..." }
    }
  }
}
```

- **`active_when`** — 결합이 어떤 선택에서만 활성인가. SES pruning(어떤 선택이 어떤 결합을
  포함·배제하는가)을 결합에 명시하는 최소 표현이다. 없으면 항상 활성이다.
  `trafficMode`처럼 **결합을 켜고 끄는 결정**이 이 필드로 자리를 얻는다 — 억지로 어딘가의
  속성으로 넣으면 그것이 구조를 바꾼다는 사실이 사라진다.
- **`attr_spec`** — 속성의 성질. 이름만으로 모호한 자리에만 적는다. `arity`는 값이 하나인지
  목록인지를, `over`는 그 값이 **어느 축에 대한 분포**인지를 말한다(축에서 하나를 고르는
  spec 선택과 구별된다).

`score_ses.py`는 이 둘을 **채점하지 않는다.** 결합이 채점되지 않는 것과 같은 상태이므로,
지표를 넣을지는 따로 판단할 일이다.

`evidence`가 핵심이다. **각 노드가 코드의 어디에서 왔는지 적게 한다.** 이유 셋:

1. 지어낸 노드를 걸러낸다 — 근거를 못 대면 코드에 없는 것이다.
2. Phase 2의 `ConfigArgs` ↔ SES 매핑표가 이 필드에서 바로 나온다.
3. 베이스라인의 "출처 자기 보고"와 같은 장치다. 같은 방법으로 채점된다.

## 3. 프롬프트 (고정. 그대로 쓴다)

> 아래는 한 시뮬레이터의 소스 코드입니다. 이 코드가 무엇을 시뮬레이션하는지 읽고,
> 그 **구조**를 SES(System Entity Structure)로 추출해 주세요.
>
> SES 표기:
> - **Entity** — 시뮬레이션에 등장하는 대상 하나. 이름과 속성 변수를 갖는다.
> - **Aspect** — "…로 구성된다". 자식들이 **함께** 존재하며 동시에 돌아간다.
> - **Specialization** — "… 중 하나다". 자식 중 **하나를 골라** 확정한다.
> - **Multi-aspect** — "동종 개체 여럿". 개수를 정해 같은 유형을 복제한다.
>
> 규칙:
> 1. 코드에 근거가 있는 것만 적으세요. 있을 법한 것을 채우지 마세요.
> 2. 모든 엔티티와 속성에 대해 `evidence`에 근거 위치(파일:행 또는 클래스·필드명)를 적으세요.
>    근거를 댈 수 없으면 그 노드를 빼세요.
> 3. 실행 엔진·프레임워크·로깅·영속화처럼 **구조를 실행하는 환경**은 넣지 마세요.
>    시뮬레이션 대상의 구조만 넣습니다.
> 4. Aspect와 Specialization을 구별하세요. 함께 돌아가면 Aspect, 택일이면 Specialization입니다.
> 5. 출력은 아래 JSON 스키마 하나만. 설명 문장을 붙이지 마세요.
>
> ```json
> { "root": "...", "entities": { ... }, "couplings": [ ... ], "evidence": { ... } }
> ```

**의도적으로 넣지 않은 것** — 참조 SES의 노드 이름, "거주민·수거차량 같은 것을 찾아라" 류의 힌트,
T1~T8 슬롯 목록. 이것들을 넣으면 정답을 알려주는 것이 되어 채점이 무의미해진다.

**규칙 3은 넣는다.** v1 판이 실행 엔진과 이벤트 시스템을 구조 트리의 형제로 둔 오류를 범했기 때문에,
이것은 정답 유출이 아니라 **SES 형식론의 일반 규칙**이다. 다만 이 규칙을 뺀 조건도 한 번 돌려
차이를 보면 좋다(프롬프트 민감도).

## 4. 반복과 기록

- 같은 입력 × **5회** (temperature 기본값 그대로, 시드 기록)
- 모델 **2종 이상**
- 조건: C / D / (규칙3 제외) — 최소 C만 5회부터
- 매 실행의 원본 출력을 `runs/<모델>-<조건>-<n>.json`으로 그대로 남긴다

## 5. 채점 (`score_ses.py`)

**참조 대비** — `reference-ses.json`이 정답지.

| 지표 | 내용 |
|---|---|
| 노드 P/R/F1 | 엔티티 이름 집합 |
| 관계 P/R/F1 | (부모, 종류, 자식) 삼중 집합 |
| 속성 P/R/F1 | (엔티티, 속성) 쌍 집합 |
| **관계 종류 오류** | 부모-자식은 맞는데 kind가 다른 것. 의미를 바꾸므로 **따로 센다** |
| **임계점 CP-1~5** | 틀리면 안 되는 다섯 자리의 통과 여부 |
| 근거 없는 노드 | `evidence`가 빈 노드의 수 |

**반복 간 일치율** — 정답지 없이, 실행 5개를 서로 비교한 쌍별 Jaccard 평균.
재현성은 정확도와 별개로 본다. 정확도가 낮아도 일관되면 프롬프트 문제이고,
정확도가 들쭉날쭉하면 추출 자체가 불안정한 것이다.

### 이름 일치 문제 (먼저 정해야 함)

LLM이 `수거지점 집합`이라 쓰고 참조가 `수거지점`이면 다른 노드로 셀 것인가.
`score_ses.py`는 세 단계로 처리한다:

1. **정규화 매칭** — 공백·가운뎃점·괄호 제거, 소문자화
2. **별칭 사전** — `aliases.json`에 수기로 등록 (`"쓰레기통" -> "수거지점"`)
3. **미매칭 보고** — 남은 것을 목록으로 출력한다. 사람이 보고 별칭에 추가하거나 오답으로 확정한다

별칭 사전은 **채점자가 만드는 것이지 추출기에 주는 것이 아니다.** 이 구분을 지켜야 한다.

## 6. 완료 판정

- C 조건 5회 실행의 원본이 남아 있다
- 참조 대비 노드·관계·속성 P/R/F1과 반복 간 일치율이 숫자로 나온다
- 임계점 CP-1~5의 통과/실패가 실행별로 표시된다
- 미매칭 이름 목록이 정리되어 별칭 사전에 반영되었다

## 7. 선행 작업 — 참조 SES를 코드와 대조해 확정하기

지금 `reference-ses.json`은 **문서에서 옮긴 초안**이고, 코드와 대조하지 않았다.
특히 `couplings` 네 개의 포트 이름은 구조 이름에서 유추한 추정값이다.

정답지가 틀리면 채점이 전부 무의미하므로, **S1을 돌리기 전에** 코드에서 다음을 확인한다:

- 네 결합이 실제로 어느 호출·이벤트에 대응하는가 (포트 이름 확정)
- 민원 판정 세 가지가 정말 함께 도는가 (CP-1의 근거)
- 폐기물 유형이 독립 개체인가, 수거지점의 속성인가 (CP-3)
- 이동시간 방식 3종이 경로 아래 있는가, 차량 아래 있는가 (CP-4)
- 거주민의 두 축이 코드에서 독립인가 (CP-5)

이 대조 자체가 S1의 첫 산출물이기도 하다 — 사람이 코드를 읽어 SES를 확정하는 과정이므로,
LLM이 같은 일을 했을 때와 비교할 기준이 된다.
