# 유도본 v5 ↔ v4 대조 — 측정 1

2026-09-11 · `SesSubtaskDerivation.derive(ProseCatalog.load())`가 만든 `jangnyang-simulator-v5`(34문항)와
사람이 손으로 적은 `jangnyang-simulator-v4`(34문항)를 대조한다 · 코드 `feature/ses-conversion`

이 문서는 Task 7의 산출물이다. **차이가 없을 것으로 보지 않는다** — SES에서 문항을 유도하면
사람이 적은 것과 무엇이 같고 무엇이 다른지가 이 연구의 측정값이다. 아래 세 절은 대조
테스트(`DerivedSetVsV4ReportTest`)의 세 검사에 맞춰 나눴고, 각 검사를 **처음 돌렸을 때** 나온
실패 메시지를 먼저 그대로 옮긴 뒤에 판단을 적었다.

## 검사 1 — 필드 집합이 같은가 (`derivedFieldsMatchV4Fields`)

**처음부터 통과.** 유도본 34개와 v4 34개의 `answerField` 집합이 완전히 일치했다 —
`onlyDerived`도 `onlyV4`도 빈 집합이었다. Task 5·6이 이미 대응표(`구성결정-SES-대응표.md`)로
"29(SES) + 1(SES 밖) + 4(절차 제어) = 34"를 확정해 둔 결과가 유도 코드에도 그대로 반영된
것이다. **이 자체가 측정 결과다** — 34개 중 하나도 어긋나지 않았다.

## 검사 2 — 자료형이 같은가 (`derivedAnswerTypesMatchV4`)

**처음 실행 결과(FAIL) — 실패 메시지 원문:**

```
자료형이 어긋난 문항: [defaultApproval: 유도=BOOLEAN v4=ENUM, executionApproval: 유도=BOOLEAN v4=ENUM,
inputAndScenarioConfirmed: 유도=BOOLEAN v4=ENUM]
```

### defaultApproval / inputAndScenarioConfirmed / executionApproval

- **유도본**: `AnswerType.BOOLEAN` (`SesSubtaskDerivation.nonSesType`의 `default` 분기가
  `engine`·`simulationGoal`을 뺀 나머지 절차 제어 필드를 전부 예/아니오로 취급했다)
- **v4**: `AnswerType.ENUM` — `defaultApproval`은 `ALL`/`NONE`, `inputAndScenarioConfirmed`는
  `CONFIRMED`/`NEEDS_CHANGE`, `executionApproval`은 `RUN`/`REVISE`/`CANCEL` 세 값이다.
- **어느 쪽이 옳은가**: **v4.** `executionApproval`은 애초에 `RUN`/`REVISE`/`CANCEL` 세 값이라
  BOOLEAN(참/거짓 두 값)으로는 표현할 수 없다 — 자료형 자체가 정보를 잃는다. 이 세 필드는
  SES 트리 밖(`NonSesField`)이라 트리에서 유도할 근거가 없고, 애초에 v4가 이미 검증하고 있는
  정확한 정의가 있는데 유도 코드가 그것을 보지 않고 "절차 제어니까 예/아니오겠지"라고
  단순화한 것이 원인이다. 이름 표기 차이가 아니라 **유도 코드의 버그**다.
- **조치**: 대응을 고친다. `SesSubtaskDerivation.nonSesType`/`nonSesRange`에
  `defaultApproval`·`inputAndScenarioConfirmed`·`executionApproval` 세 필드를 v4의
  `answerType`·`allowedRange.values`와 그대로 맞춰 넣었다(트리 유도가 아니라 v4를 그대로
  옮기는 것 — 애초에 이 필드들은 트리 밖에 있어 "트리가 정한다"는 주장과 무관하다).

## 검사 3 — spec 축 허용값이 같은가 (`specChoiceOptionsMatchV4Values`)

**처음 실행 결과(FAIL) — 실패 메시지 원문:**

```
트리의 자식 이름과 v4의 허용값이 다르다 — 가설이 가장 강하게 걸린 자리다:
[dischargeTimeMode: 트리=[직업별 외출시각 기반, 포항시 배출시간대 기반] v4=[PAPER_BASELINE, POHANG_ACTUAL],
scenarioType: 트리=[단일 실행, 직업 구성 실험, 수거시각 실험, 배출행동 실험, 용량·임계값 실험, 밀도 실험,
수거일정 실험, 다중차량 실험, 분리배출 실험, 확장직업 실험, 결합변형 실험, 월별배출 실험, 차종·방문순서 실험]
v4=[single-run, occupation-mix, collection-sweep, behavior-grid, infra-grid, density, collection-schedule,
multi-truck, waste-separation, new-occupations, coupling-variants, monthly-waste, truck-route],
travelTimeMode: 트리=[구간 상수, 교통구역 근사, 실제 도로 기반] v4=[LEGACY_CONSTANT, OSRM_HYBRID, ZONE_PROXY_HYBRID],
truckType: 트리=[5톤 차량, 2.5톤 차량, 1톤 차량] v4=[LARGE_5TON, MEDIUM_2P5T, SMALL_1TON]]
```

spec 축 4개(`scenarioType`·`dischargeTimeMode`·`travelTimeMode`·`truckType`) 전부에서
어긋났다 — spec 축이 4개뿐이니 **전수 불일치**다.

### 공통 원인 — 이름 표기 차이 (구조의 차이가 아니다)

네 자리 모두 **내용은 같다.** 트리는 SES를 만들 때 사람이 읽을 한글 자식 이름을 쓰고, v4는
서버가 실제로 검증·저장하는 영문 코드값을 쓴다. 예를 들어 `truckType`은 트리가
`5톤 차량`·`2.5톤 차량`·`1톤 차량`이라 부르는 것을 v4가 `LARGE_5TON`·`MEDIUM_2P5T`·
`SMALL_1TON`이라 부를 뿐, 가리키는 대상(같은 차종 세 가지)은 정확히 같다. 컨트롤러 판정
(Ruling 3)대로 이것은 **구조의 차이가 아니라 표기의 차이**다.

- **어느 쪽이 옳은가**: 둘 다 "옳다" — 트리는 사람이 읽을 이름, v4는 기계가 검증할 코드이고
  둘 다 필요하다. 다만 **문항이 실제로 내보내는 값**은 v4를 따라야 한다 —
  `JangnyangSubtaskValidator`가 답을 v4의 코드값으로 검증하므로, 트리의 한글 이름을 그대로
  허용값으로 내보내면 사용자가 고른 값이 검증을 통과하지 못한다.
- **조치**: 대응을 고친다. `SesFieldMapping.FieldBinding`에 `Map<String,String> optionCodes`
  (트리의 자식 이름 → v4 코드값)를 추가하고, `scenarioType`·`dischargeTimeMode`·`truckType`·
  `travelTimeMode` 네 바인딩에 채웠다.

**여기서 정확히 나눠 적어야 할 두 가지가 있다(초판에서는 이 둘을 섞어 "순서까지 optionCodes가
옮긴다"고 잘못 적었다가, 코드 리뷰로 바로잡았다 — 아래 "정정" 참고):**

1. **표기(이름 문자열)는 `optionCodes`, 즉 사람이 쓴 선언이 정한다.** 트리도 v4도 표기
   자체를 알려주지 않는다 — "한글 이름 X가 코드 Y를 가리킨다"는 것은 어느 구조에서도
   유도할 수 없는 지식이고, `optionCodes`가 그 지식을 코드로 옮긴 것이다.
2. **구성원(어떤 값이 존재하는가)과 순서(그 값을 나열하는 차례)는 여전히 트리가 정한다.**
   `SesSubtaskDerivation.optionValues`는 `optionCodes.values()`(선언 순서)를 내지 않고
   `spec.options()`(트리의 자식 순회 순서)를 하나씩 돌면서 `optionCodes`로 이름만 코드로
   바꾼다. 트리의 자식이 `optionCodes`에 없으면(대응이 낡았다는 뜻) 예외를 던지고, 반대로
   `optionCodes`에 트리에 없는 이름이 남아 있어도 예외를 던진다 — 양쪽 다 트리와의
   불일치이기 때문이다.

`scenarioType`(13개)·`dischargeTimeMode`(2개)·`truckType`(3개)는 트리의 자식 순서와
v4의 값 순서가 우연히 같아서, 이름만 옮기면 v4와 순서까지 일치했다.

### travelTimeMode — 트리와 v4가 순서에 대해 실제로 불일치하는 자리

이 자리는 다른 세 자리와 달리 **이름만의 문제가 아니다**. 트리의 자식 순서와 v4의 값
순서를 하나씩 맞춰 보면 뒤 두 개가 서로 바뀌어 있다.

| 위치 | 트리(자식 순서) | v4(값 순서) |
|---|---|---|
| 1 | 구간 상수 | `LEGACY_CONSTANT` |
| 2 | 교통구역 근사 | `OSRM_HYBRID` |
| 3 | 실제 도로 기반 | `ZONE_PROXY_HYBRID` |

내용으로 이름을 짝지으면(v4의 질문 문구 "OSRM_HYBRID는 수거 지점 좌표 실측 행렬" =
"실제 도로 기반", "ZONE_PROXY_HYBRID는 교통 구역으로 근사" = "교통구역 근사") 실제 대응은
`구간 상수`→`LEGACY_CONSTANT`, `교통구역 근사`→`ZONE_PROXY_HYBRID`, `실제 도로 기반`→
`OSRM_HYBRID`다 — 즉 **트리의 2·3번째 자식과 v4의 2·3번째 값이 순서가 뒤바뀐 채 대응한다.**
트리의 자식 순서를 그대로 따라 이름만 코드로 옮기면 `[LEGACY_CONSTANT, ZONE_PROXY_HYBRID,
OSRM_HYBRID]`가 나오는데, 이는 v4의 `[LEGACY_CONSTANT, OSRM_HYBRID, ZONE_PROXY_HYBRID]`와
**순서가 다르다.**

- **어느 쪽이 옳은가**: **트리가 옳다고 판단한다.** 이 연구가 재려는 것은 "SES 구조가
  허용값의 구성원과 순서까지 정하는가"이고, 그 주장을 지키려면 순서의 출처는 예외 없이
  트리여야 한다 — 특정 필드 하나(v4)를 보고 트리 쪽을 조용히 바로잡으면, 트리가 순서를
  정한다는 규칙에 "다만 v4와 다르면 v4를 따른다"는 예외가 생기고, 그 예외가 있는 채로는
  "트리가 정한다"는 것을 더는 일반적으로 주장할 수 없다. v4의 순서가 왜 이렇게 됐는지는
  코드에서 확인할 수 없다 — 사람이 나열할 때 우연히 바뀌었을 수도 있고 의도가 있었을 수도
  있지만, 그 의도가 SES 어디에도 근거를 두지 않는다는 사실 자체가 "트리 밖의 판단"이라는
  뜻이다.
- **조치**: **유도본과 v4가 이 필드에서 실제로 다른 순서를 낸다는 사실을 그대로 둔다.**
  트리를 고치거나(전역 제약이 금지) v4를 고치거나(기준선, 절대 금지) `optionCodes`로
  순서를 조용히 바로잡거나(Ruling 7이 금지) 하지 않는다. 대신:
  - `DerivedSetVsV4ReportTest.specChoiceOptionsMatchV4Values`는 **구성원만**(집합) 비교하도록
    바꿨다 — 순서 차이 때문에 "값 자체가 다른 문제"까지 덮어 버리면 안 된다.
  - 순서 차이는 별도 테스트
    `specChoiceOptionOrderMismatchesAgainstV4AreOnlyTheKnownOnes`가 드러낸다 — "지금 순서가
    다른 spec 필드는 정확히 `travelTimeMode` 하나뿐이다"를 고정해서, 이 목록이 조용히
    늘거나 줄면(트리 순서가 바뀌었거나, v4가 갱신됐거나, 대응이 잘못 고쳐졌거나) 실패로
    드러나게 했다. 순서 차이 자체로 빌드를 막지는 않는다 — 트리도 v4도 여기서 고칠 수
    없는 값이기 때문이다.
  - `SesSubtaskDerivationTest.specChoiceOptionOrderFollowsTreeNotV4`가 travelTimeMode의
    유도값이 v4 순서(`[LEGACY_CONSTANT, OSRM_HYBRID, ZONE_PROXY_HYBRID]`)가 아니라 트리
    순서를 그대로 코드로 옮긴 `[LEGACY_CONSTANT, ZONE_PROXY_HYBRID, OSRM_HYBRID]`임을
    단언한다 — "순서는 트리가 정한다"는 규칙이 이 필드에서도 실제로 지켜지는지 회귀로 지킨다.

### 정정 — 초판 서술의 오류

이 문서의 초판은 "트리의 자식 순서가 v4의 값 순서와 그대로 대응했다"(scenarioType·
dischargeTimeMode·truckType)와 "travelTimeMode만 순서 차이가 겹쳤다"고 적으면서, 그 근거로
든 구현이 실제로는 **네 필드 전부에서 `optionCodes`의 선언 순서를 그대로 출력하고 있었다**
(`optionValues`가 `spec.options()`를 버리고 `optionCodes.values()`를 반환했다). 세 필드는
선언 순서를 트리 순서와 같게 손으로 맞춰 적어서 결과가 우연히 같았을 뿐이고, travelTimeMode는
선언 순서를 v4에 맞춰 적어서 순서 차이가 코드 밖으로 드러나지 않고 있었다 — 즉 "트리가 순서를
정한다"는 주장의 범위가 실제로는 이미 줄어 있었는데, 초판은 그것을 "1건만 순서가 다르다"는
좁은 서술로 가렸다. 코드 리뷰(컨트롤러 Ruling 7)로 드러나 `optionValues`가 `spec.options()`를
순회하도록 고쳤고, 이 문서도 그 사실대로 다시 썼다.

해소).** 이 넷 중 **구성원**은 넷 다 트리와 v4가 같지만, **순서**는 `travelTimeMode` 하나가
실제로 다르다 — 이것은 표기 문제로 흡수해서 조용히 맞출 수 있는 차이가 아니라, "SES 구조가
허용값의 순서까지 정한다"는 주장이 이 한 자리에서는 v4와 맞지 않는다는 **측정 결과**다.

"SES로 변환하면 물어야 할 매개변수의 정체(필드 34개, 어떤 자료형인지)와 spec 축 허용값의
구성원이 정해진다"는 주장은 대조에서 깨지지 않았다. 다만 "허용값의 **순서**까지 SES가 정하고
그것이 항상 v4와 일치한다"는 더 강한 주장은 `travelTimeMode` 한 곳에서 깨진다 — 이 구분이
왜 중요한가 하면, 이 연구가 재는 것이 정확히 **"SES가 무엇을 얼마나 정해 주는가"**이기
때문이다. "필드가 있다"(측정 1의 1차 결과)와 "그 필드의 허용값 구성원이 있다"(2차 결과)와
"그 구성원의 순서까지 있다"(3차 결과)는 서로 다른 크기의 주장이고, 이 문서는 그 셋을
뭉뚱그리지 않고 각각 어디까지 참인지를 적어야 한다. 이름 표기(어떤 문자열로 부르는가)는
어느 구조에서도 유도되지 않아 여전히 사람의 지식으로 남는다는 점은 초판의 결론과 같다.

## 정정 — SES가 정해 주는 것과 사람이 정하는 것 (I3, 코드 리뷰로 드러남)

위 요약의 마지막 문단이 "SES로 변환하면 물어야 할 매개변수의 정체(필드 34개, **어떤
자료형인지**)와 spec 축 허용값의 구성원이 정해진다"고 적었는데, **코드는 그렇게까지
주장하지 않는다.** 실제로 SES가 정해 주는 것과 사람이 여전히 정하는 것을 나누면 이렇다.

**SES가 정해 주는 것:**
- spec 축 허용값의 **구성원과 순서**(`spec.options()`가 그대로 최종 목록이 된다,
  `travelTimeMode`는 v4와 순서가 실제로 갈리는 예외로 남는다)
- "이 자리를 물어야 한다"는 사실 자체 — 어떤 지점이 결정 지점인지(`DecisionPointExtractor`)

**사람이 정하는 것(트리가 알려 주지 않는다):**
- 필드 이름(`answerField`) — 트리의 지점 id와 필드 이름을 잇는 다리가 없다
  (`SesFieldMapping`의 존재 이유가 이것이다)
- 자료형(`answerType`) — `SubtaskSkeleton.answerType`은 **예외 없이**
  `SesFieldMapping.FieldBinding`이 손으로 선언한 값이다. spec 지점조차 트리는
  "…중 하나를 고른다"만 알려줄 뿐 그것이 `ENUM`이라는 것도, 정수·소수·문자열 같은
  attr 지점의 자료형도 알려주지 않는다
- 수치 범위(`min`/`max`), 비-spec `ENUM`/`ENUM_LIST`의 허용값, 표기 코드(`optionCodes`)

이 구분이 왜 중요한가: `SesFieldMapping`의 `answerType`·`range`는 전부
**`jangnyang-simulator-v4.json`에서 그대로 옮겨 적은 값**이다(클래스 상단 주석이 이미
그렇게 밝히고 있다). 그래서
- `DerivedSetVsV4ReportTest.derivedAnswerTypesMatchV4`는 **v4에서 베낀 자료형을 다시
  v4와 비교**하고 있다 — 이 검사가 통과하는 것은 "SES가 자료형을 정해 준다"는 증거가
  아니라 "옮겨 적은 값을 옮겨 적힌 대로 잘 옮겼다"는 확인이다.
- `derivedFieldsMatchV4Fields`도 마찬가지다 — 필드 집합 자체가 `구성결정-SES-대응표.md`
  (v4를 코드와 대조해 사람이 확정한 문서)에서 왔으니, v4와 비교해 같게 나오는 것은
  **유도의 측정이 아니라 그 대응표(즉 v4의 전사)가 맞게 옮겨졌는가의 확인**이다.

반대로 **`specChoiceOptionsMatchV4Values`(spec 허용값의 구성원)만이 실제로 유도를
측정한다** — 그 값은 v4에서 베끼지 않고 트리의 `spec.options()`에서 나오기 때문이다.
이 검사가 통과했다는 것(표기 차이를 `optionCodes`로 걷어낸 뒤)이 이 문서가 실제로
확인한 유일한 "SES가 정해 준다"는 증거이고, `travelTimeMode`의 순서 불일치가 실제로
드러난 유일한 반례다.

## SES에 자리가 있는데 묻지 않는 27곳 (I4, Ruling 5)

Ruling 5는 "SES에 자리가 있는데 v4가 묻지 않던 것"을 보고하기로 했다. 그런데
`derivedFieldsMatchV4Fields`는 이 격차를 **볼 수 없다** — `SesFieldMapping.bindings()`가
가리키는 지점 집합 자체가 `구성결정-SES-대응표.md`(v4를 코드와 대조해 사람이 고른 29곳)에서
나오므로, "유도본의 필드 집합"과 "v4의 필드 집합"을 비교하면 항상 일치한다(둘 다 같은
대응표 하나에서 나온 것이기 때문이다). **묻지 않은 지점을 보려면 대응표가 아니라 트리
자체(`DecisionPointExtractor.extract`)가 뽑는 전체 결정 지점과 대조해야 한다.**

`DecisionPointExtractorTest.totalDecisionPointCountsArePinned`로 고정한 실측값:

```
총 결정 지점 55 = AttributeValue 43 + MultiCount 5 + SpecChoice 5 + CouplingActivation 2
묶인 지점 28 (SesFieldMapping.bindings()가 가리키는 서로 다른 pointId 수 — 필드는 29개다,
             attr:수거차량:수거시각 하나가 collectionTime·collectionTimes 두 필드를 낸다)
묻지 않는 지점 27개 = 55 - 28
```

**spec 1개 — 통째로 안 묻힌다:**

| 지점 | 왜 안 묻는가 |
|---|---|
| `spec:거주민:직업 축`(생산직·학생·전업주부·야간 교대근무자·1인 직장인) | 다른 문항이 대신 겸한다 — `occupationPreset`(직업 구성 프리셋: BALANCED·UNIVERSITY·INDUSTRIAL·FAMILY)이 이 다섯 직업의 **혼합 비율**을 미리 정해 둔 프리셋 중 하나를 고르게 한다. 직업 축 자체(어떤 직업이 존재하는가)를 직접 묻지는 않는다 — 다섯 직업이 존재한다는 사실은 `ScenarioPreset`에 모델이 고정해 두었다. |

**multi 2개 — 모델(데이터)이 고정한다:**

| 지점 | 왜 안 묻는가 |
|---|---|
| `multi:폐기물 유형 집합` | 폐기물 종류 개수는 `WasteType` 정의가 고정한다 — 사용자가 몇 종류를 둘지 고르지 않는다. |
| `multi:교통구역 집합` | 교통 구역 개수는 `TrafficZoneRegistry`의 실측 데이터가 고정한다 — 사용자가 구역 수를 정하지 않는다. |

**coupling 1개 — 다른 문항이 대신 겸한다:**

| 지점 | 왜 안 묻는가 |
|---|---|
| `coupling:교통 구역.혼잡계수->교통혼잡 판정.판정` | `trafficMode` 하나가 두 결합(이동시간 쪽·혼잡 판정 쪽)을 동시에 켜고 끈다 — `SesPruner.killAllCouplingPoints`가 `trafficMode≠APPLY`일 때 `coupling:`으로 시작하는 지점을 **전부** 죽인다. 이 결합만 따로 묻는 문항이 없는 이유는 이미 다른 결합(이동시간 쪽)에 묶인 같은 답이 겸하기 때문이다. |

**attr 23개:**

| 지점 | 분류 | 왜 안 묻는가 |
|---|---|---|
| `attr:장량동 생활쓰레기 수거 시뮬레이터:대상지역` | 모델이 고정 | 이 시뮬레이터 자체가 "장량동" 하나를 대상으로 만들어졌다 — 지역을 고를 이유가 없다. |
| `attr:장량동 생활쓰레기 수거 시뮬레이터:기준연도` | 모델이 고정 | 기준연도(포항시 실측 데이터의 연도)는 데이터셋에 고정돼 있다. |
| `attr:대상 시스템:대상지역` | 모델이 고정 | 위와 같은 지역 값의 중복 선언 — 실험마다 바뀌지 않는다. |
| `attr:대상 시스템:시간범위` | 다른 문항이 겸한다 | 시뮬레이션 기간은 `실험:기간`(`days`)이 정한다 — 별도로 "시간범위"를 또 묻지 않는다. |
| `attr:거주민:직업` | 다른 문항이 겸한다 | 개별 거주민의 직업은 사용자가 한 명씩 고르지 않는다 — `occupationPreset`의 혼합 비율대로 시뮬레이션이 표본을 뽑는다(계산). |
| `attr:거주민:외출시각` | 계산 결과 | 개인별 외출 시각은 직업별 분포(`외출시각분포`)에서 시뮬레이션이 표본추출한 값이다 — 사용자가 개인별로 답하지 않는다. |
| `attr:거주민:귀가시각` | 계산 결과 | 위와 같다. |
| `attr:직업별 외출시각 기반:외출시각분포` | 모델이 고정 | 직업별 외출 시각 분포(평균·표준편차 등)는 논문 기준 데이터로 코드에 고정돼 있다 — `leaveSigma`(외출시각변동)만 사용자가 답한다. |
| `attr:수거지점:적재량` | 계산 결과 | 특정 순간의 적재량은 시뮬레이션이 진행되며 채워지는 상태값이다. |
| `attr:수거지점:교통구역` | 다른 문항이 겸한다 | 건물을 교통 구역에 배정하는 규칙은 `zoneAssignmentRule`이 정한다 — 건물 하나하나의 소속 구역을 직접 묻지 않는다. |
| `attr:수거지점:차량진입가능` | 모델이 고정 | 자동 생성되는 수거 지점(Node_A~Node_Z)은 전부 차량 진입 가능으로 고정돼 있다 — 물어볼 이유가 없다. |
| `attr:폐기물 유형:종류` | 모델이 고정 | 폐기물 종류 이름·구성은 `WasteType`에 고정돼 있다 — `multi:폐기물 유형 집합`과 같은 이유. |
| `attr:폐기물 유형:배출비율` | 모델이 고정 | 종류별 배출 비율은 `WasteType`의 고정 데이터다. |
| `attr:폐기물 유형:수거주기` | 다른 문항이 겸한다 | 실제 수거 주기는 `수거차량:수거요일`(`collectionSchedule`)이 정한다 — 폐기물 종류별로 별도 주기를 다시 묻지 않는다. |
| `attr:폐기물 유형:수거요일` | 다른 문항이 겸한다 | 위와 같다. |
| `attr:교통 구역:혼잡계수` | 다른 문항이 겸한다 | 구역별 혼잡계수는 `trafficProfileId`가 가리키는 실측 프로파일 데이터에 들어 있다 — 구역마다 계수를 따로 묻지 않는다. |
| `attr:교통 구역:적색임계값` | 다른 문항이 겸한다 | 위와 같다 — `trafficProfileId`의 프로파일 데이터에 포함된다. |
| `attr:수거 경로:총이동거리` | 계산 결과 | 실행 결과로 나오는 값이다 — 사용자가 미리 답할 수 없다. |
| `attr:적재초과 판정:임계값초과판정` | 계산 결과 | 판정 자체가 시뮬레이션의 산출물이다. |
| `attr:임대인 점검 판정:점검시각` | 모델이 고정 | 점검 이벤트가 도는 시각은 `SimulationEngine`이 고정한 스케줄이다 — 사용자가 답하는 값이 아니다. |
| `attr:임대인 점검 판정:잔류량` | 계산 결과 | 점검 시점의 잔류량은 시뮬레이션이 계산해 내는 값이다. |
| `attr:실험:난수시드` | 모델이 고정 | 사용자가 답하는 것은 시드의 **개수**(`반복횟수`→`seeds`)뿐이고, 그 개수만큼 실제로 쓸 시드 값 자체는 엔진이 만든다 — 특정 시드값을 사용자가 지정하지 않는다. |
| `attr:교통혼잡 판정:민원가중치` | 모델이 고정 | `trafficComplaintWeight`는 `SimulationConfig`에 기본값(1.0)으로 고정돼 있고 v4도 v5도 이 값을 묻지 않는다. |

세 분류(모델이 고정 / 계산 결과 / 다른 문항이 대신 겸한다)는 전부 "왜 안 물어도 실험이
망가지지 않는가"에 대한 답이지, "SES가 이 자리를 몰라서"가 아니다 — `DecisionPointExtractor`는
이 27곳 전부를 실제로 결정 지점으로 뽑아낸다. 즉 **SES는 "여기서 결정해야 한다"는 사실은
정확히 알려 주지만, "이미 다른 결정이 겸하고 있어서 또 물을 필요는 없다"는 판단은 알려주지
않는다** — 그 판단은 지금 사람(v4/v5를 적은 사람)이 하고 있고, 이 27곳의 목록이 바로 그
판단이 실제로 일어난 자리들이다.
