# 시스템 구현 보완 계획

작성일: 2026-11-03. 기준 커밋: 0ddc071.
이 문서는 코드와 기존 명세를 읽고 작성한 개발 계획이다. 새 테스트 실행 결과나 구현 완료 보고서는 아니다.

후속 구현: [구현 결과와 검증 기록](reports/implementation-2026-11-03/REPORT.md).
P1~P4의 지원 모델 범위와 P5 회귀·통합 검증을 반영했다.
두 번째 실지역 데이터 확보와 실제 LLM 추출 성능 측정은 해당 보고서에 미완료 실증 과제로 구분했다.

## 1. 목표와 현재 상태

사용자가 시뮬레이터 내부 구조를 몰라도 요청 조건에 맞는 후보를 찾고, 검증 가능한 데이터로 시나리오를 구성해 실행하도록 한다.
제공자는 능력 카드, SES, 템플릿, Task 명세, 데이터 어댑터와 검증 함수를 사전에 정의한다.
시스템이 임의의 새 도메인 모델이나 확보되지 않은 지역 데이터를 자동으로 만들어 내는 것은 이번 범위에 포함하지 않는다.

| 영역 | 확인한 기존 기반 | 이번 보완 방향 |
|---|---|---|
| 요구 구조화 | broker의 RequestProfile, 미제시 null 구분 | 지역·시간·필수/선호 조건·원문 근거 추가 |
| 능력 비교 | CandidateMatcher, 불일치/모호함, 요청 조정, 복수 일치 시 사용자 선택 | 형식화된 시간·범위·지역 조건 비교 및 항목별 결과 |
| 능력 명세 | 능력 카드 JSON과 등록 API | 비교에 필요한 필드의 계약·버전·기동/등록 검증 |
| 지역 데이터 | CollectionSiteRegistry의 장량동 리소스 고정 | 지역 데이터 묶음의 선택·검증·실행 연결 |
| SES/PES | SesTree, SesDerivation, 템플릿 파생, ScenarioBuilder | 실제 구조 선택과 실행 설정의 일치 증명 |
| Task 처리 | TaskManifest, TaskCompletion과 준비 상태 검사 | 지역 산출물 검증 및 기존 완료 규칙 확장 |
| 실행 검증 | 검증 기록, 출처/근거 검사, 승인 토큰, 변경 시 무효화 | 브로커 결정과 실행 기록의 연결 |
| 복수 후보 | 별도 주차·민원창구·구 단위 폐기물 프로젝트, 가상 카드 구분 | 실제 실행 가능한 후보를 이용한 통합 검증 |

## 2. 설계 원칙

- LLM은 자연어 해석과 질문 표현을 담당한다. 서버는 형식·단위·필수 조건·산출물·실행 허용을 판정한다.
- 기존 점수 없는 비교와 복수 일치 시 사용자 선택 정책을 유지한다. 선호 조건은 차이 설명에 사용하며 필수 조건 실패를 상쇄하지 않는다.
- 조건별 결과는 충족, 조건부 충족, 불충족, 정보 부족으로 구분한다. 조건부 충족은 변환이나 데이터 확보가 검증돼야 실행 가능하다.
- 미지원은 불충족, 명세 누락은 정보 부족으로 구분한다. 시간 단위 환산과 시간 해상도 지원은 별도로 판정한다.
- 기본값·사용자값·지역 데이터·계산값의 출처를 기록한다. 사용자 승인은 데이터나 모델의 타당성 검증을 대신하지 않는다.
- 브로커는 탐색·비교·연결 정보를 담당하고, 시뮬레이터는 상세 입력·데이터 검증·구성·실행을 담당한다.

## 3. 단계별 구현

### P0. 기준선과 계약 확정

상태: 완료. [테스트 기준선과 기존 실패](reports/p0-baseline-2026-11-03/REPORT.md),
[계약 비교와 호환 정책](specifications/request-capability-contract.md) 참조.
총 1040건 중 1036건 통과, 3건 스킵, 기존 실패 1건을 재현했다. 실패 수정은 P0-001로 별도 추적한다.

작업:
1. 루트 및 독립 시뮬레이터의 테스트를 실행해 현재 성공/실패/스킵을 기록한다.
2. scenario-readiness.md에 기록된 template-generator 기존 실패의 현재 재현 여부를 확인한다. 기존 실패를 새 변경의 성공으로 집계하지 않는다.
3. 브로커 도구와 네 제공자의 능력 카드·템플릿·Task 명세·오류 응답을 표로 대조한다.
4. 요청/카드/판정의 버전과 호환 정책을 문서화한다. 기존 호출은 보존하되 새 필드가 없으면 검증되지 않았음을 표시한다.

완료 기준: 재현 가능한 기준선, 필드 계약, 변경 대상 목록이 있다. 기존 실패가 후속 작업을 막으면 원인 수정 작업을 별도 등록한다.

### P1. 공통 요구·능력 계약과 규칙 비교

대상: mcp-common, broker/RequestProfile, CandidateMatcher, FindSimulatorsTool, 제공자 능력 카드 로더와 등록 경로.

작업:
1. 공통 계약에 regionId, simulationDuration, timeResolution, requiredOutputs, constraints, preferences를 정의한다. 수치에는 값·단위·범위를 둔다.
2. 원문과 조건의 연결을 기록하고 미제시/명시적 없음/확정값을 구분한다. 거주민 등 기존 필드는 유지한다.
3. 카드에 지원 지역 또는 데이터 요구 조건, 엔진 시간 간격, 출력 집계 간격, 실행 기간 범위, 입력 제약, 출력 지표를 명세한다.
4. 비교 결과에 조건 경로, 요청값, 카드값, 판정, 사유 코드, 필요한 조치를 담는다. 기존 reasons/mismatches 응답과 호환한다.
5. 필수 조건 실패 후보는 제외하고, 정보 부족이면 확인 항목을 반환한다. 요청 완화는 원래 요구를 덮어쓰지 않는다.
6. 입력 스키마·안내·고정 발화 평가 세트를 마련한다. 서버 안에 새로운 LLM 호출을 추가하지 않고 실제 클라이언트 해석을 평가한다.

완료 기준: 시간 단위 요청/주 단위 전용 후보는 거절되고, 같은 시간의 단위 표현 차이는 환산된다. 해상도 미기재 후보는 적합으로 확정되지 않는다. 선호 조건이 좋아도 필수 조건 실패 후보는 선택되지 않는다.

### P2. 지역 데이터와 실행 모델 분리

대상: simulator/site/CollectionSiteRegistry, 지역 데이터 로더, SimulationConfig 연결부, 제공자 리소스 검증 기록.

작업:
1. 지역 데이터 묶음 계약을 정의한다: 지역 ID, 버전, 출처, 좌표계, 지원 모델 모드, 건물/수거 지점, 필요한 이동 데이터, 식별 해시.
2. 장량동 기존 리소스를 같은 계약으로 감싸 기본 동작을 보존한다.
3. 지역 ID로 데이터 묶음을 선택하는 공급자 인터페이스를 만들고 고정 리소스 참조를 단계적으로 제거한다.
4. ID 중복·좌표·참조 무결성·필수 데이터 유무를 검사한다. 도로망 연결성 검사는 실제 도로망 모드를 지원할 때 추가한다.
5. 두 번째 지역 데이터 묶음을 추가한다. 검증된 실데이터가 없으면 합성 데이터임을 명시하고 일반화 시험용으로만 사용한다.
6. 지역 미등록·데이터 누락 시 부족한 항목과 확보 방법을 반환한다. 임의 지리 데이터나 검증되지 않은 기본값으로 채우지 않는다.

완료 기준: Java 실행 코드 수정 없이 두 지역의 시나리오를 구성한다. 잘못된 지역 데이터는 차단되며, 데이터 변경 시 기존 승인과 검증 기록이 무효화된다.

### P3. SES 선택과 Task 산출물의 실행 연결

대상: SesTree/SesDerivation, SubtaskPlanner, PES 생성부, ScenarioBuilder, task-manifest.json, TaskCompletion 검증 함수.

작업:
1. 현재 엔진이 실제 지원하는 선택 구조를 확인하고 SES 결정과 설정 필드의 대응표를 만든다. 지원하지 않는 대안은 명세에서 제외한다.
2. PES에 채택/제외한 구조, 결정값, 출처, 적용한 SES 버전을 추적 가능하게 남긴다.
3. 선택된 가지의 필수 입력과 제약을 검증하고 제외된 가지의 입력이 실행에 섞이지 않도록 기존 검사를 확장한다.
4. 지역 데이터 검증 Task를 추가하고 설정 생성 Task가 그 산출물에 의존하도록 연결한다.
5. 원래 목적, 비교 변수, 관측 지표, 실제 설정 간 기존 PurposeCheck와 역검증을 유지한다. 목적 명세 누락은 검증 완료로 표시하지 않는다.
6. 기존 Task 상태와 입력 변경 시 무효화 규칙을 사용한다. 별도 중복 상태 머신을 만들지 않는다.

완료 기준: 구조 선택을 바꿨을 때 PES와 설정이 함께 바뀌고, 동일 seed에서 해당 모델 경로가 실행됐음을 확인한다. 선행 데이터 검사 실패 시 설정 생성·승인·실행이 차단된다.

### P4. 브로커부터 실행 결과까지 연결

대상: broker 매칭 기록, 제공자 plan/build/status/run 도구, ValidationReceipt, 결과 응답.

작업:
1. matchId와 제공자 requestId/scenarioId를 연결하고 요청 개정 번호, 카드·명세·데이터 버전, 설정 해시를 기록한다.
2. 선택 당시 요청과 목적을 제공자에게 전달하고 상세 입력과 충돌하면 수정 또는 재매칭을 요구한다.
3. 실제 후보의 등록·접속·연결·실행 흐름을 검증한다. 같은 도메인 안에서 다른 능력의 후보를 비교하는 사례를 포함한다.
4. 가상 카드는 비교 시험에만 사용하고 실제 실행 성공 사례에서 제외한다.
5. 후보 없음·복수 일치·서버 중단·낡은 카드·실행 중 입력 변경을 검증한다. 상세 도메인 검증을 브로커에 중복 구현하지 않는다.

완료 기준: 요청 → 후보별 판정 → 선택 → 지역 데이터 → SES/PES → Task 검증 → 승인 → 실행 → 지표를 하나의 기록으로 추적할 수 있다.

### P5. 통합 평가와 미팅 데모

필수 사례:
1. 같은 요청에 능력이 다른 실제 후보의 선택/제외 사유 제공.
2. 시간 해상도 불일치 후보 거절 및 명세 누락 후보 확인 요구.
3. 두 지역의 데이터로 각각 시나리오 구성.
4. 필수 입력 누락 시 추가 질문, 데이터 오류 시 실행 차단.
5. SES 선택 변경이 PES와 실행 경로에 반영.
6. 입력/데이터 변경 후 이전 승인 토큰 사용 차단.
7. 적합 후보 없음, 복수 후보 사용자 선택, 실제 결과 지표 누락 처리.

평가:
- 요구 추출: 사람이 라벨링한 고정 발화에서 필드별 정확 일치와 미제시값 임의 보완율을 측정한다. 모델·프롬프트·버전을 고정하고 반복 실행 변동도 기록한다.
- 후보 판정: 조건별 정답 대비 정확도와 부적합 후보 허용률을 측정한다. 매칭 성공과 실제 접속 성공은 구분한다.
- 구성 검증: 정상 입력 통과율, 잘못된 입력 차단율, 유효 설정 생성률을 함께 측정한다.
- 실행: 유효·승인된 시나리오의 실행 성공률과 목적 지표 반환율을 측정한다. 후보가 없어서 거절된 요청은 실행 실패로 섞지 않는다.
- 구현 회귀용 필수 사례에서는 부적합 허용 0건을 요구한다. 자연어 평가 성능 목표는 별도 평가 세트와 기준선 측정 후 확정한다.
- 기존 방식과 비교할 때 같은 발화·후보·데이터·seed를 사용하고 규칙 비교, 지역 구성, 구조 검증의 효과를 분리한다.

## 4. 순서와 작업 단위

P0 → P1 → P2 → P3 → P4 → P5 순서로 진행한다.
각 단계는 계약/호환성 변경과 구현·검증을 포함한 독립 검토 단위로 나눈다.
첫 구현 범위는 P0와 P1이다. 새 지역 데이터 수집과 새 도메인 엔진 개발은 별도 작업량으로 산정한다.
기간은 기준선 결과와 두 번째 지역 데이터 확보 상태를 확인한 뒤 산정한다.

검증 명령은 루트의 .\mvnw.cmd -B clean test를 기준으로 한다.
독립 시뮬레이터는 mcp-common을 먼저 설치한 뒤 각 프로젝트 래퍼로 검증한다.
확인 UI 변경 시 화면 검증도 포함한다. 실행 결과 보고에는 실제 수행한 검사와 미수행 검사를 구분한다.
