# 1. 소프트웨어 요구사항 명세서 (SRS)

## 1.1 목적

본 문서는 **MCP(Model Context Protocol) 도구 서버**로서 라즈베리파이 엣지 발열·냉각 모델을 자연어로 구동할 수 있게 하는 시스템의 요구사항을 정의한다.

시스템의 존재 목적은 전신 문서와 같다 — **LLM은 자연어를 구조화 인자(JSON)로 바꾸는 일만 하고, 검증과 계산은 전부 서버가 소유한다.**

라즈베리파이 4B(BCM2711)·5(BCM2712)에서 고부하 AI 추론을 지속할 때의 SoC 온도 상승을 열 RC 모델로 적분하고, 펌웨어 클럭 거버너 상태머신을 함께 돌려 스로틀링 진입·에피소드·회복을 재현한다. 냉각 조건(무냉각/방열판/팬), 운용 모드(목표 FPS/최대 처리량), 회복 정책(R1~R3/무조치)을 요인으로 바꿔가며 TTT·TED·TRT를 비교한다.

시뮬레이터의 목적은 **실측 없이 답을 내는 것이 아니라, 실측 몇 점으로 나머지 조건을 외삽하는 것**이다. 따라서 문헌 추정치로 시작하되 `calibrate_edge_thermal_model`로 실측 보정하는 흐름을 1급 요구사항으로 둔다.

**연구 질문은 두 단계로 넓어졌다.** 처음에는 “언제 스로틀링이 걸리는가”를 물었고, 지금은 **“지속가능한 냉각의 적정점은 어디인가”** 를 묻는다 — 최고 성능 냉각은 비용이 과다하므로, 성능을 조금 낮추더라도 비용을 크게 줄이는 지점을 찾는 것이 목표다(SDGs 관점).

이 질문에 답하려면 1노드·상수부하 모델로는 부족했고, 세 가지가 필요했다.

| 필요 | 초기 모델의 한계 | 해결 |
|---|---|--- |
| 냉각의 **비용**을 셀 수 있어야 함 | 소비전력이 SoC뿐이라 팬을 켜는 비용이 0 — 최적해가 항상 최대 RPM | FanSpec — 팬 전력을 별도 집계 |
| 방열판 **질량**이 결과에 나타나야 함 | 1노드 모델은 상수 부하에서 열용량이 식에 아예 없음 — 순위가 열저항으로만 결정 | HeatsinkMass — 2노드 분리 |
| 부하가 **출렁여야** 함 | 상수 부하만 표현 가능 — 과도응답이 안 드러남 | AiLoadProfile — 시변 부하 패턴 |

## 1.2 범위

시스템은 다음으로 구성된다.

- 2노드 열 RC 적분 엔진과 펌웨어 클럭 거버너 상태머신
- 방열판 열저항 회로(형상·오프셋·핀 방향·TIM·기류)와 배치 후보 비교
- 실측 시계열에서 열 파라미터를 역추정하는 캘리브레이터와 프로파일 저장소
- 팬 전력 모델, PWM/RPM 스윕, 예측 냉각(PTM) 제어기, 듀얼 팬 배치 60조합 랭킹
- 위를 MCP 도구 6종으로 노출하는 JSON-RPC 2.0 서버
- STOMP WebSocket 자연어 채팅과 결정론 게이트 기반 도구 선택·파라미터 가드
- 실측 로거 스크립트(scripts/edge)

**범위 외**: 사용자 인증/권한, 영속 저장소(DB), 다중 채팅방·동시 사용자 격리, 캘리브레이션 프로파일의 영속화(서버 재시작 시 소멸 — 원본 실측은 CSV로 별도 보관), 장량동 생활쓰레기 도메인(별도 문서).

## 1.3 용어 및 약어

| 용어 | 설명 |
|---|--- |
| 결정론 게이트 | LLM을 호출하지 않고 정규식·키워드 조합만으로 제어 흐름을 확정하는 판정기 |
| 파라미터 추출 | 실행이 확정된 뒤 JSON 모드로 실행 파라미터만 뽑는 LLM 호출 |
| JSON 모드 | response_format=json_object. 프리텍스트 없는 순수 JSON 응답 강제(Ollama format:json과 동형) |
| 독립 도구(McpToolProvider) | 자체 스키마를 갖는 MCP 도구 확장점. 원본 JSON을 그대로 받아 구현체가 직접 파싱·검증·실행 |
| **TTT** | Time To Throttling — 부하 시작부터 하드 스로틀링(0x4) 최초 지속 감지까지의 시간(초) |
| **TED** | Throttling Episode Duration — 스로틀링 에피소드 하나의 지속시간(초). 여러 개면 중앙값을 대표값으로 쓴다 |
| **TRT** | Throttling Recovery Time — 회복 시간. TRT_state(비트 해제) / TRT_service(처리능력 복원) / TRT_full(유휴+2℃ 이내) 세 가지를 구분해 측정 |
| **R_ja** | 다이(Junction)→주변 공기(Ambient) 전체 열저항 K/W. 정상상태 온도 = 주변온도 + 소비전력 × R_ja |
| **R_jc** | 다이→패키지 표면 열저항 K/W. 어떤 냉각을 해도 직렬로 남는 하한 |
| **C_th** | 등가 열용량 J/K. 시정수 τ = R_ja × C_th |
| **소프트 제한 / 하드 스로틀링** | 라즈베리파이 펌웨어의 온도 대응 단계. 80℃에서 소프트 제한(get_throttled bit 0x8), 85℃에서 하드 스로틀링(bit 0x4) |
| **캘리브레이션 프로파일** | 실측 시계열에서 역추정한 열 파라미터 한 벌. profileId로 시뮬레이션 도구가 재사용 |
| **2노드 열모델** | SoC와 방열판을 별도의 열 노드로 분리한 모델. R_ja = R_int + R_hs이므로 정상상태는 1노드와 동일하고 과도응답만 달라진다 |
| **R_int** | SoC→방열판 내부 열저항 K/W. R_jc + TIM 층. 전체 R_ja보다 반드시 작아야 한다 |
| **C_hs** | 방열판 열용량 J/K = 질량 × 비열. 알루미늄 900, 구리 385 J/(kg·K) |
| **팬 상사법칙** | 팬 소비전력은 회전수의 3승에 비례한다. 냉각(강제대류)은 풍속의 0.8승에 비례하므로, 이 비대칭이 “적정 RPM에서 멈추는 것이 유리하다”의 근거다 |
| **AI 부하 패턴** | 시각에 따라 달라지는 부하 배율의 구간 나열. steady(대조군)·burst·mixed 3종 |
| **시간 규모 판정(TimescaleFit)** | 부하 구간 길이가 시정수 τ에 비추어 과도응답을 드러내는지에 대한 판정. AVERAGED(구간 < 0.3τ) / SENSITIVE / QUASI_STATIC(구간 > 10τ) |
| **순위 역전** | 열저항이 더 나쁜 방열판이 시변 부하의 피크 온도에서는 더 나은 결과를 내는 현상. 질량이 피크를 흡수하기 때문이며, 가성비 논의의 물리적 근거 |
| **PTM** | Predictive Thermal Management — 다가올 부하를 미리 적분해 목표 온도를 지키는 최소 팬 듀티를 고르는 예측 냉각 제어 |

## 1.4 시스템 개요

사용자 문장은 **도구 선택 게이트 → 파라미터 추출(LLM) → 파라미터 가드 재판정(결정론) → 인자 검증(fail-closed) → 실행 → 결과 문장 조립(코드)** 순으로 처리된다. 제어 흐름을 바꾸는 모든 판정은 LLM 없이 결정론적으로 이뤄지며, LLM은 값 추출과 일반 대화 답변에만 관여한다.

MCP 도구는 6종이다.

| 도구 | 설명 |
|---|--- |
| simulate_edge_throttling | 발열·스로틀링 동역학 → TTT·TED·TRT + 온도/클럭/FPS 시계열 |
| simulate_heatsink_layout | 방열판 배치 후보의 R_ja 계산 → 정상상태 온도·TTT 기준 순위 |
| calibrate_edge_thermal_model | 실측 시계열 → 열 파라미터 역추정 → profileId 저장 |
| sweep_fan_rpm | 팬 PWM/RPM을 바꿔가며 반복 실행 → 제약을 만족하는 최소 에너지 운전점 + 발표용 곡선 |
| simulate_ptm_control | 팬 제어 방식(항상최대·반응형·예측형)을 같은 조건에서 비교 → 스로틀링 없이 총에너지 최소인 방식과 절감률 |
| rank_fan_layouts | 40 mm 팬 2개의 위치쌍(15) × 흡·배기 조합(4) = 60조합을 경험적 냉각점수로 순위화 → 실측 전 후보 선별 |

## 1.5 공통 플랫폼 기능 요구사항 (MCP·검증·오류·관측성)

이 시스템의 존재 목적은 MCP 도구로서 시뮬레이션을 노출해, 어떤 LLM이든 자연어를 구조화 인자로 변환해 복잡한 시뮬레이션을 생성할 수 있음을 실증하는 것이다. **LLM은 도구 인자(JSON)만 채우고, 서버가 검증과 실행을 소유한다.**

| ID | 요구사항 | 우선순위 |
|---|---|--- |
| FR-01 | POST /mcp에서 JSON-RPC 2.0으로 initialize·tools/list·tools/call·ping을 처리한다. | 필수 |

## 1.14 팬 배열 및 RPM 스윕

MCP 도구 sweep_fan_rpm이 답하는 질문은 하나다 — **“요구 FPS와 온도 한계를 지키면서 총에너지가 최소가 되는 팬 속도는 얼마인가?”** 팬 전력은 회전수의 3승, 냉각은 풍속의 0.8승에 비례하므로 최적점은 대개 **정격보다 한참 아래**에 있고, 그 지점을 숫자로 찍어 주는 것이 이 연구의 지속가능성 결론이다.

| ID | 요구사항 | 우선순위 |
|---|---|--- |
| FR-46 | PWM 범위(minPwmPercent~maxPwmPercent, steps) 또는 명시적 rpmPoints로 스윕 지점을 정하고, 모든 지점을 **동일한 열·부하 조건**에서 실행한다. 두 방식은 동시에 쓸 수 없다. | 필수 |
| FR-47 | 적합 판정은 TTT 하나가 아니라 **세 제약을 함께** 본다 — maxPeakTempC(기본 85), maxThroughputLossPercent(기본 1), minTargetFpsRatio(기본 0.99). | 필수 |
| FR-48 | 목적함수는 MIN_TOTAL_ENERGY·MIN_ENERGY_PER_FRAME·MIN_FAN_ENERGY·MIN_PWM 중 선택한다. 전부 “작을수록 좋다”로 통일해 비교 로직을 하나로 유지한다. **지정하지 않으면 운용 모드가 기본값을 정한다** — 목표 FPS 모드는 MIN_TOTAL_ENERGY, 최대 처리량 모드는 MIN_ENERGY_PER_FRAME(총에너지로 고르면 일을 덜 한 저RPM 지점이 이기므로). | 필수 |
| FR-49 | **탈락한 지점도 사유 코드와 함께 전부 반환한다.** 최적점만 돌려주면 사용자가 그 값을 검증할 수 없고(“왜 30%가 아니라 50%인가”는 30% 지점의 탈락 사유를 봐야 답이 된다), 발표용 곡선도 탈락 구간이 있어야 “여기서부터 스로틀링”이 보인다. | 필수 |
| FR-50 | **적합 지점이 하나도 없으면 최적점을 만들지 않는다** — 상태를 NO_FEASIBLE_POINT로 반환한다. “그중 제일 나은 것”을 최적점으로 내놓으면 사용자가 스로틀링이 걸리는 운전점을 권장값으로 읽는다. | 필수 |
| FR-51 | 목적함수 동률은 상대 허용 오차(1e-3) 안에서 같은 값으로 보고 **낮은 PWM → 낮은 RPM → 낮은 피크 온도** 순으로 고른다. 허용 오차가 0이면 27000.0J과 27000.1J처럼 물리적으로 구분되지 않는 차이로 부동소수점 끝자리가 운전점을 정하게 된다. | 필수 |
| FR-52 | 선택 근거(optimalReason)를 결과에 남겨 재현 가능하게 한다. | 권장 |

## 1.15 팬 배열 사양

Raspberry Pi 5 전용 4핀 팬 커넥터는 40×40×10 mm 팬 2개를 물릴 수 있고 PWM으로 속도를 제어하며 TACH로 실제 RPM을 읽는다.

| ID | 요구사항 | 우선순위 |
|---|---|--- |
| FR-53 | 팬 배열의 회전수·전력·배치·측정 범위를 **출처와 함께** 보존한다(SourceStatus·verified·RpmSource). 확보한 전력 수치가 검증 전 추정값인지 실측인지, 팬 1개 기준인지 배열 전체 기준인지를 숫자에 섞으면 **나중에 “이 결과가 실측이었나 추정이었나”를 복원할 수 없다.** | 필수 |
| FR-54 | 정격값의 적용 범위(RatedValueScope: PER_FAN·DUAL_FAN_ARRAY_ASSUMED·ARRAY_TOTAL_MEASURED)를 검사해 **이중 계산을 막는다** — 배열 전체 정격을 팬 개수로 다시 곱하면 비용이 2배로 부풀려진다. | 필수 |
| FR-55 | **실측 보정 전에는 팬 위치·송풍 방향으로 냉각계수를 만들어 내지 않는다.** 위치는 실험 조건을 보존하는 메타데이터일 뿐이며, 냉각(열저항)은 배열의 유효 회전수 하나로만 결정된다 — 팬을 2개로 늘렸다고 임의로 더 시원해지지 않는다. **비용(전력)만은 팬 개수에 실제로 좌우된다.** | 필수 |
| FR-56 | 유효 회전수는 TACH 실측이 있으면 그 값을, 없으면 PWM 추정값을 쓰고 어느 쪽인지 rpmSource로 표시한다. 팬 사양 미지정 시 기본 프리셋을 쓰되 **검증 전 임시 사양임을 결과에 명시한다.** | 필수 |

## 1.16 예측 냉각(PTM) 제어기

앞의 스윕이 답하는 것은 **“가장 싼 고정 회전수”**다. 그런데 부하가 시간에 따라 오르내리면 고정 운전은 반드시 손해다 — 한가한 구간에서도 피크에 맞춘 회전수로 계속 돌거나, 피크를 못 버텨 스로틀링을 맞거나 둘 중 하나이기 때문이다. PTM(Predictive Thermal Management)은 **다가올 부하를 미리 보고 회전수를 시간에 따라 바꾼다.**

| ID | 요구사항 | 우선순위 |
|---|---|--- |
| FR-57 | 팬 회전수를 시간에 따라 바꾸는 제어기를 지원한다(PtmController). 제어를 지정하지 않으면 종전대로 고정 회전수로 동작한다 — 기존 실행 결과가 바뀌면 안 된다. | 필수 |
| FR-58 | 제어 방식은 최소 셋을 함께 실행해 비교한다 — ALWAYS_MAX(순진한 기준선)·REACTIVE(라즈베리파이 공식 팬 커브 근사, 현실 기준선)·PREDICTIVE(PTM). **기준선 없는 제어 결과는 해석할 수 없으므로** 단일 실행을 기본으로 두지 않는다. | 필수 |
| FR-59 | 예측형은 지평(기본 60초) 안의 부하를 미리 적분해 **목표 온도를 지키는 최소 듀티**를 제어 주기(기본 5초)마다 고른다. 듀티를 낮출 때만 추가 여유를 요구한다 — 늦게 올리면 스로틀링이지만 늦게 내리면 전기만 조금 더 쓰므로 두 실수의 대가가 다르다. | 필수 |
| FR-60 | 예측은 **1노드 RC·무스로틀 가정**으로 한다. 제어기에 완전한 모델을 주면 “예측이 좋다”는 결론이 모델을 두 번 쓴 결과가 되고, 실제 장치의 제어기도 간이 모델만 들고 있다. 이 가정은 실제보다 뜨겁게 예측하므로 안전한 방향으로 틀린다. | 필수 |
| FR-61 | 승자는 **스로틀링이 없는 방식들 중** 총에너지 최소로 고른다. 전부 스로틀링이면 승자를 만들지 않고 NO_FEASIBLE_MODE로 반환한다(FR-50과 같은 원칙). 결과에는 평균·최대 듀티와 회전수 변경 횟수를 남겨 소음·수명 관점의 부작용도 보이게 한다. | 권장 |

**대가를 함께 보고해야 한다**: PTM은 허용된 온도 여유를 끝까지 쓰기 때문에 반응형보다 **뜨겁게 돈다.** 에너지만 보면 항상 이기므로, 피크 온도와 온도 진폭을 같은 표에 놓지 않으면 부품 수명 쪽 대가가 보이지 않는다(③ 온도 안정성 지표와 연결된다).

## 1.20 제약 및 가정

- 난수를 쓰지 않는 결정론 모델이다 — 같은 입력은 항상 같은 결과를 낸다.
- **열 파라미터 기본값은 문헌·데이터시트 기반 초기 추정치다.** 정답으로 사용해서는 안 되며 실측 캘리브레이션이 전제된다.
- **캘리브레이션 프로파일은 영속화하지 않는다** — 서버 재시작 시 소멸하며 개수 상한을 둔다. 원본 실측은 CSV로 별도 보관.
- **방열판 배치 후보는 최대 12개**까지 비교한다.
- 팬 배치 랭킹의 점수는 CFD도 열 RC 적분도 아닌 **경험적 추정**이며, 실측 보정 전까지 물리 시뮬레이터 결과와 비교할 수 없다.
- 로컬 LLM은 JSON에 주석·후행 콤마·코드펜스를 넣기도 하므로 파서를 관대하게 + 코드펜스 제거로 방어한다.
- 인증·권한 계층이 없다는 것이 배포 전제다 — /mcp·/ws·/actuator는 접근 가능한 누구에게나 열려 있으므로, 노출면을 좁히는 설정 자체가 방어선이다(SDD 2.6).

## 2.2 요청 판별 — 분리 시 재검토 대상

이 서버의 채팅 처리는 **도구 선택 게이트(EdgeToolSelector) → 파라미터 추출(LLM) → 파라미터 가드(EdgeParamGuard) → 인자 검증(EdgeArgs) → 실행 → 결과 문장 조립(EdgeChatFormatter)** 이다. 게이트와 가드의 상세 설계는 2.3.9에 있다.

> **재검토 대상** — 위 도구 선택 순서 앞에는 원래 도메인 게이트(`DomainIntentDetector`)가 있었다. 장량동/엣지 두 벌의 어휘 수를 세어 더 많은 쪽을 고르는 방식이었고, “스윕”·“가성비”처럼 양쪽에 걸치는 단어를 의도적으로 제외하는 규칙(구 D-33)이 여기에 있었다. 단일 도메인 서버에서는 비교 상대가 없으므로 이 게이트는 “엣지 요청인지 아닌지”를 판정하는 형태로 다시 설계해야 한다. 그 전까지는 도구 선택 게이트가 첫 관문이다.

## 2.3 열 모델 설계

### 2.3.1 ThermalSimulator — 열 RC 모델 + 거버너 상태머신

**지배 방정식**

C_th · dT/dt = P(t) − (T − T_ambient) / R_ja
P(t) = P_idle + P_dyn · u(t) · r(t) (u=사용률, r=클럭비 f/f_max)

부하가 일정하고 스로틀링이 없으면 해석해는 T(t) = T_ss − (T_ss − T_0)·e^(−t/τ), τ = R_ja·C_th인 지수 접근 곡선이다. 스로틀링이 걸리면 r이 떨어져 P가 줄고 곡선이 꺾이므로 해석해가 깨진다 — 그래서 dt 간격으로 **수치 적분**한다.

**v1.9 수정 두 건**

- **R2 저부하 정책이 최대 처리량 모드에서 작동하지 않던 문제** — R2는 effTarget만 25%로 줄였는데 그 값은 TARGET_FPS 분기에서만 쓰였다. MAX_THROUGHPUT 분기는 기존 부하를 그대로 써서 **R2가 사실상 무조치처럼 동작**했고, R1/R2/R3 비교 결과 자체가 잘못됐다. 이제 정책 계수(policyFactor)를 부하 수준에 곱해 두 모드 모두에 적용한다.
- **종료 시각 이후 한 스텝을 추가 적분하던 문제** — 루프 조건이 t <= endTime이라 t == endTime인 반복에서도 dt 전체를 적분했다. 실행 시간이 dt만큼 길어지고 SoC·팬 에너지가 과대 계산되며, 마지막 적분에서 오른 온도가 peak에 반영될 수 있었다. 이제 마지막 적분 폭을 min(dt, endTime − t)로 계산하고, 종료 시각에서는 최종 샘플만 기록한다(NFR-12).

**펌웨어 거버너 근사**

| 상태 | 조건 | 동작 |
|---|---|--- |
| 정상 | T < 80℃ | 최대 클럭 |
| 소프트 제한 | T ≥ 80℃ | softFloor 클럭으로 하강(bit 0x8). 실제 펌웨어도 곧바로 최저 클럭까지 떨어뜨리지는 않는다 |
| 하드 스로틀링 | T ≥ 85℃ | minClock까지 하강(bit 0x4) |
| 해제 | T < 85℃ − 히스테리시스 | 비트 해제 |

**보드 프리셋(문헌·데이터시트 기반 초기 추정치)**

| 항목 | Pi4B (BCM2711) | Pi5 (BCM2712) |
|---|---|--- |
| 유휴 소비전력 | 2.7 W | 3.0 W |
| 동적 소비전력 | 3.9 W | **9.0 W** |
| 최대 클럭 / softFloor / 최저 | 1500 / 1200 / 600 MHz | 2400 / 1900 / 1000 MHz |
| 등가 열용량 C_th | 12.0 J/K | 15.0 J/K |
| 최대 FPS(모델 의존) | 12.0 | 28.0 |
| R_jc (하한) | 2.0 K/W | 1.5 K/W |
| R_ja bare / passive / active | 9.5 / 6.0 / 3.2 K/W | 6.5 / 3.9 / 2.6 K/W |
| SoC 패키지 한 변 | 15.0 mm | 16.0 mm |

Pi5는 동적 소비전력이 Pi4의 2배 이상이라 같은 냉각에서도 거동이 완전히 다르다 — 보드가 **결과를 가장 크게 가르는 축**이며, 보드 비교(FR-30)의 축을 보드로 고정한 근거다.

### 2.3.2 2노드 열모델 (신규, v1.9)

#### 왜 1노드로는 부족했나

1노드 모델은 SoC와 방열판을 온도 한 점으로 뭉뚱그린다. **부하가 일정하면 그래도 충분하다** — 정상상태 온도가 T_주변 + P·R_ja로 정해지고 열용량 C_th는 식에 아예 나타나지 않으므로, 방열판 순위가 오직 열저항으로 결정된다. 즉 성능이 제일 좋은 것이 항상 이기는, **결과가 뻔한 실험**이 된다.

그런데 부하가 출렁이면 이야기가 달라진다. 방열판은 실온에서 시작하는 **큰 냉각 덩어리**라 피크를 흡수한다 — 질량이 클수록 온도 진폭이 작아지고, 그래서 **열저항이 더 나쁜 방열판이 피크 온도에서는 이길 수 있다.** 이 역전이 “가성비를 따지면 최고 성능 방열판이 답이 아닐 수 있다”는 연구 질문의 물리적 근거인데, 1노드 모델로는 그 현상 자체를 표현할 수 없었다.

#### 지배 방정식

C_soc · dT_soc/dt = P − (T_soc − T_hs) / R_int
C_hs · dT_hs/dt = (T_soc − T_hs) / R_int − (T_hs − T_주변) / R_hs

정상상태(양변 0)를 풀면 T_soc − T_주변 = P·(R_int + R_hs)가 되어 **R_ja = R_int + R_hs** 다. 즉 **2노드로 바꿔도 정상상태는 1노드와 완전히 같고, 달라지는 것은 과도응답뿐**이다. 이 성질이 하위호환의 근거이자 검산 기준이다(FR-35, NFR-13).

#### 파라미터

| 항목 | 내용 |
|---|--- |
| C_hs | 방열판 열용량 J/K = 질량 × 비열 |
| 비열 | 알루미늄 900 J/(kg·K), 구리 385 J/(kg·K) — **같은 질량이면 구리의 열용량이 오히려 작다** |
| R_int | SoC→방열판 열저항 K/W. R_jc + TIM 층 |
| 불변식 | C_hs > 0, R_int > 0, **R_int < R_ja**(나머지가 방열판→공기 몫). 위반 시 거부 |
| 입력 | heatsinkMassG(0~5000 g) 또는 cThJPerK 직접 지정 |

상수 부하로 2노드를 돌리면 효과가 드러나지 않으므로, 그 경우 **notes로 “부하 패턴을 함께 지정하라”고 안내한다**(조용히 무의미한 결과를 내지 않는다).

### 2.3.3 팬 전력 모델 (신규, v1.9)

#### 왜 전력까지 모델링하는가

팬을 “열저항을 낮춰 주는 장치”로만 다루면 **최적해가 언제나 최대 RPM**이 된다 — 비용이 0이니 안 돌릴 이유가 없기 때문이다. 그러면 이 연구가 도달해야 할 결론(“최고 성능보다 적정 수준이 지속가능하다”)과 모델이 정반대를 가리킨다.

#### 두 법칙이 만드는 비대칭

| 양 | 지수 | 의미 |
|---|---|--- |
| 팬 소비전력 | 회전수의 **3승**(상사법칙) | RPM 2배면 전력 8배 |
| 냉각 이득 | 풍속의 **0.8승**(강제대류 상관식) | 훨씬 완만하다 |

그래서 RPM을 절반만 돌려도 냉각 이득의 대부분을 얻으면서 전력은 1/8만 쓴다. **이 비대칭이 “적정 수준에서 멈추는 것이 낫다”의 물리적 근거**이고, FanSpec이 계산하는 것이 정확히 그 트레이드오프다.

#### 팬 전력은 SoC를 데우지 않는다

팬이 쓰는 전기는 모터에서 소비되고 공기로 흩어진다 — SoC 열 노드에 들어가지 않는다. 그래서 **온도를 적분하는 전력(P_SoC)과 비용을 집계하는 전력(P_SoC + P_fan)을 반드시 구분**해야 한다. 합쳐서 적분하면 팬을 켤수록 온도가 올라가는 거꾸로 된 결과가 나온다(FR-38).

결과는 energyJ / fanEnergyJ / totalEnergyJ로 분해해 반환한다.

| 입력 | 기본값 · 범위 |
|---|--- |
| fanRpm | cooling=active면 정격, 아니면 0. 0~30000 |
| fanRatedRpm | 5000. 100~30000 |
| fanRatedPowerW | 0.5. 0~50 |

cooling=active만 지정해도 정격으로 도는 팬을 만들어 전력을 집계하고, 명시적 fanRpm이 있으면 그 값이 이긴다. passive·bare에 팬 입력이 없으면 팬 객체를 만들지 않는다(기존 동작 보존).

### 2.3.4 AI 시변 부하 패턴 (신규, v1.9)

#### 구간(segment) 방식을 쓴 이유

TrafficProfile처럼 시간대별 배열(길이 24)로 표현할 수도 있었지만, 그러면 **최소 해상도가 1시간**이라 이 실험에 쓸 수 없다. 대신 “얼마 동안 어느 수준”을 그대로 나열해, 시뮬레이터와 측정 스크립트가 **완전히 같은 순서를 재생**할 수 있게 했다.

#### 시간 규모가 이 실험의 성패를 가른다

구간 길이를 시정수 τ와 견주어 정해야 한다.

| 판정 | 조건 | 의미 |
|---|---|--- |
| AVERAGED | 구간 < 0.3 τ | 열용량이 전부 평균해버림 → 방열판 차이가 안 드러남 |
| SENSITIVE | 0.3 τ ~ 10 τ | **과도응답이 그대로 드러남 → 순위가 뒤집힐 수 있음** |
| QUASI_STATIC | 구간 > 10 τ | 매 구간이 준정상상태 → 상수 부하와 같은 결과 |

이 판정을 결과 notes에 실어 보낸다 — **시간 규모를 잘못 잡는 것이 이 실험이 실패하는 대표 경로**이기 때문이다(FR-41).

#### 프로파일 3종

| id | 구조 | 역할 |
|---|---|--- |
| steady | 배율이 항상 1.0 | **대조군.** 학생 팀이 실측하는 조건(계속 최대)과 동일 |
| burst | 2분 몰림 → 3분 한가의 5분 주기 | 구간 길이를 Pi5 방열판 조건의 τ≈58초의 2~3배로 잡은 것이 핵심 |
| mixed | 30분 주기 안에 한가→보통→피크의 느린 흐름, 각 구간 안에서 다시 버스트 | 실제 AI 데이터센터에 가장 가까운 2층 구조 |

등록 순서가 곧 실험 순서다(steady → burst → mixed). **대조군을 반드시 함께 돌려야 “패턴 때문에 순위가 바뀌었다”를 주장할 수 있다.**

패턴을 못 찾으면 null을 돌려주고 상수 부하로 동작한다 — fail-closed가 아니라 “패턴 레이어 비활성” 폴백이다(TrafficDataService의 와 같은 원칙).

### 2.3.5 팬 배열과 RPM 스윕 (신규, v1.9)

#### 왜 단일 실행 도구와 나누는가

simulate_edge_throttling의 결과는 **지표 한 벌**이지만 스윕의 결과는 **곡선·제약 판정·최적점**이다. 한 도구에 섞으면 응답 형식이 호출마다 달라져 채팅 포매터와 UI가 계속 분기해야 한다. 열 계산은 ThermalSimulator를 그대로 재사용하므로 **공식이 두 벌로 갈라지지는 않는다.**

#### 스윕 절차

- PWM 범위(minPwmPercent~maxPwmPercent, steps) 또는 명시 rpmPoints로 지점 생성 — 두 방식 동시 사용 불가
- 각 지점을 **동일한 열·부하 조건**으로 실행(보드·주변온도·부하 패턴·방열판 질량 고정, 팬 속도만 변경)
- 세 제약으로 적합 판정 — 피크 온도 ≤ 85℃, 처리량 손실 ≤ 1%, 목표 FPS 비율 ≥ 0.99
- 목적함수로 최적점 선택 — MIN_TOTAL_ENERGY·MIN_ENERGY_PER_FRAME·MIN_FAN_ENERGY·MIN_PWM. **기본값은 운용 모드가 정한다** — 목표 FPS 모드는 MIN_TOTAL_ENERGY, 최대 처리량 모드는 MIN_ENERGY_PER_FRAME이다. 최대 처리량에서 총에너지를 최소화하면 *일을 덜 한* 저RPM 지점이 이기기 때문이다
- 동률이면 낮은 PWM → 낮은 RPM → 낮은 피크 온도 순

#### 두 가지 “만들어 내지 않기” 원칙

- **탈락 지점을 버리지 않는다.** 최적점만 돌려주면 사용자는 그 값을 검증할 수 없다. 모든 지점이 탈락 사유 코드와 함께 남고, 그 목록이 곧 발표용 곡선의 원본이다.
- **적합 지점이 없으면 최적점을 만들지 않는다.** optimal은 null이 되고 상태는 NO_FEASIBLE_POINT다. “그중 제일 나은 것”을 권장값으로 내놓으면 사용자가 스로틀링이 걸리는 운전점을 최적이라고 읽는다.

#### 동률 허용 오차가 필요한 이유

허용 오차를 0으로 두면 총에너지 27000.0 J과 27000.1 J인 두 지점에서 **부동소수점 끝자리가 운전점을 정한다** — 물리적으로 구분되지 않는 차이로 PWM 100%가 50%를 이길 수 있다. 그래서 상대 오차 1e-3 안에서는 같은 값으로 보고 명시적 우선순위로 고른다.

#### FanArraySpec — 불확실성을 숫자에 섞지 않는다

FanSpec이 팬 1개의 전력·냉각 물리를 담당하고, FanArraySpec은 그것을 **여러 개로 묶고 출처와 불확실성을 보존**한다.

| 축 | 내용 |
|---|--- |
| 회전수 출처(RpmSource) | TACH 실측 / PWM 추정 — 결과 신뢰도를 읽는 근거 |
| 정격 적용 범위(RatedValueScope) | PER_FAN / DUAL_FAN_ARRAY_ASSUMED / ARRAY_TOTAL_MEASURED |
| 검증 상태 | SourceStatus·verified — 검증 전 추정값인지 실측인지 |
| 배치(FanPlacement) | 위치·송풍 방향. **메타데이터 전용** |

세 가지 설계 원칙이 있다.

- **이중 계산 방지** — 배열 전체 정격을 팬 개수로 다시 곱하면 비용이 2배가 된다. RatedValueScope를 반드시 검사한다.
- **냉각은 유효 회전수 하나로만** — 실측 보정 전에 위치·방향으로 냉각계수를 지어내지 않는다. 팬을 2개로 늘렸다고 임의로 더 시원해지지 않는다.
- **비용은 개수에 좌우된다** — 온도와 달리 전력은 팬 개수가 실제로 결정한다. 이 비대칭이 배열 층을 따로 둔 이유다.

### 2.3.6 HeatsinkThermalModel — 방열판 열저항 회로

SoC 다이 ──R_jc── 패키지 표면 ─┬─ R_tim + R_misalign + R_spread + R_base + R_conv ─┬─ 공기
└──────────── R_rest (PCB·패키지 자연대류) ───────────┘

R_ja = R_jc + (R_top ∥ R_rest)

방열판 경로가 아무리 좋아져도 R_jc는 남고, 방열판이 없어도 R_rest 경로는 남는다 — 그래서 **“방열판을 두 배 좋게 해도 온도가 절반이 되지 않는” 수확체감이 모델에서 자연히 나온다.**

입력은 학생이 실제로 손으로 바꿀 수 있는 것만 필드로 뒀다: 방열판 치수·핀 개수/높이/두께·재질, SoC 중심 대비 위치 오프셋(mm), 핀 방향(기류 정렬 여부), TIM 종류·두께, 팬 유무·거리·풍속. 좌표계는 SoC 패키지 중심이 원점(0,0), 단위 mm.

**채팅 경로에서는 서버가 들고 있는 표준 후보 6종(A~F)으로 비교한다.** 후보 치수까지 자연어로 받으면 LLM이 치수를 지어내 실험이 오염되기 때문이다. 후보는 실험 설계서의 가설 H1~H5와 1:1로 대응하도록 **A(기준)에서 한 번에 한 가지 요인만** 바꿔 구성했다 — B(오프셋 15mm), C(핀 방향 가로막음), D(TIM 얇은 그리스), E(기류 팬 8mm), F(크기 20×20). 여기에 무냉각 기준선이 자동으로 추가되어 총 7행이 순위표에 나온다.

응답에는 modelCaveat를 항상 실어, **절대 온도보다 후보 간 상대 비교(Δ℃)를 신뢰하라**고 명시한다(NFR-11).

#### 시간 가중 지표와 결측 3상태 (v1.9)

ThermalRun에 **지속 처리량 손실**(throughputLossPercent)·**처리 프레임 수**(processedFrames = ∫FPS dt)·**온도 진폭**(tempAmplitudeC)·**정착 구간 평균 온도**(loadSettledMeanTempC)를 추가했다. FPS와 처리량 손실은 샘플 개수가 아니라 **시간으로 가중**해 계산한다 — 샘플 간격이 균일하지 않으면 단순 평균이 실제 처리량을 왜곡하기 때문이다.

ThermalCalibrator는 측정된 throttled를 **3상태**로 다룬다(E-04 해소).

| 입력 | 내부 상태 | 지표 계산 의미 |
|---|---|--- |
| true | THROTTLED | 스로틀링이 명시적으로 관측됨 |
| false | CLEAR | 해제가 명시적으로 관측됨 |
| null | UNKNOWN | **상태를 판단할 수 없음** |

이전 상태를 화면 표시용으로 이어 그릴 수는 있지만 **그 보간값을 공식 TTT·TED·TRT 계산에 쓰지 않는다.** TTT는 최초의 명시적 THROTTLED에서 잡되 직전이 결측이면 확정하지 않고, TED는 시작·끝이 모두 명시적이고 중간에 결측이 없는 에피소드만 완결로 본다(나머지는 incomplete로 표시해 중앙값에서 제외). TRT_state는 회복 구간이 명시적 CLEAR로 끝난 경우만 인정한다. 결측 개수와 최장 결측 구간을 결과에 함께 남긴다.

### 2.3.7 ThermalCalibrator — 실측에서 파라미터 역추정

부하 구간에서 온도는 T(t) = T∞ − (T∞ − T0)·e^(−t/τ_h)로 오른다. 양변을 정리하면 ln(T∞ − T) = ln(T∞ − T0) − t/τ_h로 **직선**이 된다. 문제는 T∞를 모른다는 것 — 그래서 T∞를 **0.2℃ 격자로 훑으며 매번 직선회귀를 해보고, 실제 온도 영역에서의 RMSE가 가장 작은 T∞를 고른다**(1차원 그리드 서치 + 선형회귀). 외부 수치 라이브러리 없이 안정적이고 학생이 손으로 검산할 수 있다.

그 다음은 정의식 그대로다.

R_ja = (T∞ − T_ambient) / P_load C_th = τ_h / R_ja

냉각 구간이 있으면 같은 방법으로 τ_c를 따로 구한다 — 가열과 냉각의 시정수가 다르면 그 자체가 결과다(예: 팬이 켜진 채 식으면 τ_c가 작아진다).

**열 파라미터 우선순위(EdgeToolSupport)**: profileId(실측) > thermalOverride(명시) > 보드·냉각 프리셋(문헌 추정치). 존재하지 않는 profileId는 조용히 무시하지 않고 거부한다.

EdgeThermalProfileStore는 결과를 메모리에 보관한다(TrafficDataService와 같은 “서버가 최신 관측을 들고 있는” 패턴). 영속화하지 않는 이유는 원본 실측이 어차피 CSV로 남고 여기 있는 건 다시 만들 수 있는 파생값이기 때문이다. 개수 상한을 둬 무한히 쌓이지 않게 한다.

### 2.3.8 EdgeArgs — 독립 도구의 fail-closed 검증

McpToolProvider는 공용 SimulationConfigValidator를 거치지 않으므로 EdgeArgs가 그 자리를 대신한다. 범위를 벗어난 값은 실행 전에 **전부 모아** 거부한다 — 오류를 만나도 즉시 던지지 않고 계속 모으는 이유는, 인자를 여러 개 잘못 넣었을 때 한 번에 다 알려주는 편이 시행착오가 적기 때문이다.

| 필드 | 허용 범위 |
|---|--- |
| ambientTempC | −20 ~ 60 ℃ |
| loadSeconds | 10 ~ 21600 초 |
| sampleIntervalSeconds | 0.5 ~ 300 초 |
| targetFps / maxFps | 0.1 ~ 1000 |
| rJaKPerW / recoveryRJaKPerW | 0.1 ~ 100 K/W |
| cThJPerK | 0.5 ~ 500 J/K |
| startTempC | −20 ~ 110 ℃ |
| offsetXMm / offsetYMm | −100 ~ 100 mm |
| finCount | 0 ~ 200 |
| layouts 배열 크기 | 1 ~ 12 |
| heatsinkMassG (v1.9) | 0 ~ 5000 g |
| fanRpm (v1.9) | 0 ~ 30000 |
| fanRatedRpm (v1.9) | 100 ~ 30000 |
| fanRatedPowerW (v1.9) | 0 ~ 50 W |
| aiLoadProfileId (v1.9) | steady·burst·mixed 중 하나. 그 외는 INVALID_ENUM |
| socTempC (캘리브레이션 샘플) | −40 ~ 130 ℃ |

오류 코드는 짝 문서(장량동)와 같은 enum 정의를 쓴다: MISSING_FIELD, INVALID_ARGUMENTS, INVALID_ENUM, OUT_OF_RANGE, EXECUTION_ERROR.

**v1.9 검증 강화**: 정수 필드는 isIntegralNumber()로 검사해 finCount=10.9 같은 소수를 조용히 절삭하지 않고 거부한다(공개 스키마의 integer 계약을 서버가 지킨다). 실수 입력은 유한성을 먼저 확인한다 — d < min \|\| d > max 비교는 NaN에 대해 모두 false이므로, 유한성 검사가 없으면 범위 검증을 그대로 우회한다.

### 2.3.9 엣지 채팅 라우팅

DomainIntentDetector가 도메인을, EdgeToolSelector가 도구를 정한다 — 둘 다 LLM 없이.

검사 순서는 **예측 제어(PTM) → RPM 스윕 → 캘리브레이션 → 방열판 배치 → 발열(기본)**(FR-27). PTM이 스윕보다 앞인 이유는 두 도구의 어휘가 거의 겹치는데 답의 형태가 다르기 때문이다 — 스윕은 고정 회전수 하나를 고르고 PTM은 시간에 따라 바꾸는 방식을 비교한다. “팬을 미리 돌리면 이득이야?”가 스윕으로 가면 고정 운전점 곡선이 돌아와 정작 물어본 ’미리’가 답에서 빠진다. 다만 제어를 명시한 어휘(예측·미리·선제·제어·PTM)가 있을 때만 고르고, 스윕과 공유하는 어휘(팬 속도·가성비)만으로는 오지 않는다. 스윕이 캘리브레이션보다 앞인 이유는 “실측 프로파일 기준으로 최적 팬 rpm 찾아줘”처럼 스윕과 캘리브레이션 어휘가 함께 나온 문장 때문이다 — 캘리브레이션으로 가면 채팅에서는 실행 자체를 하지 않으므로(FR-32) 답이 아예 나오지 않는다. “방열판을 어디에 붙여야 스로틀링이 덜 걸릴까”처럼 두 도구의 어휘가 함께 나오는 문장이 흔한데, 이때는 더 구체적인 요청(배치 비교)을 골라야 사용자가 기대한 답이 나온다.

**D-03의 실측 근거**: “라즈베리파이 5를 *방열판만 상태에서* 목표 FPS 고정으로 50분 돌리면 언제 스로틀링이 걸리는지 시뮬레이션해줘”가 배치 비교로 새서, 사용자가 물은 TTT 대신 후보 순위표가 돌아왔다. 같은 문장에서 “방열판만”을 “팬 냉각”으로 바꾸면 정상 동작했으므로 원인이 그 단어임이 확인됐다. 이 오라우팅은 보드 비교까지 망가뜨렸다 — “Pi4와 5를 방열판 상태에서 비교해줘”가 배치 도구로 가면 그쪽은 보드가 하나로 확정돼야 하므로 비교 요청이 “어느 보드인지 알려주세요”라는 되물음으로 바뀐다.

**보드 비교 실행(FR-30)**: 비교가 성립하려면 보드 외의 모든 조건이 완전히 같아야 한다. 같은 ObjectNode를 재사용하면 첫 실행에서 도구가 채운 기본값이 두 번째 실행에 섞여 들어가 “무엇을 통제하고 무엇을 바꿨는지”가 흐려진다 — 실험이 아니라 그냥 두 번 돌린 게 된다. 그래서 매번 deepCopy()로 같은 출발점에서 시작한다. 방열판 도구에는 이 비교를 적용하지 않는다(결과가 순위표라 두 보드를 같은 표에 놓으면 “1위 후보”가 둘인 읽을 수 없는 표가 된다).

**비교 축 확장(v1.9)**: 비교 요청 감지를 보드에서 **재질**(isMaterialComparison)과 **팬 유무**(isFanComparison)까지 넓혔다. 세 감지기는 같은 이유로 존재한다 — 사용자가 두 조건을 나란히 적었는데 서버가 한쪽으로 확정해 버리면, 물어본 것에 대한 답이 아니라 **다른 실험**을 돌린 것이 된다. 반대로 하나만 언급했으면 비교가 아니라 그 조건으로 확정해야 한다(회귀 방지).

**판정 기준 전환(v1.9)**: 비교 결과는 원래 정상상태 온도로 판정했다. 그런데 **재질 비교는 열저항이 같고 열용량만 다르므로 정상상태가 동일**하다 — 그대로 두면 “차이 0℃”라는 무의미한 결론이 나온다(실측 회귀). 그래서 정상상태가 같으면 판정 기준을 **피크 온도**로 옮긴다. 둘 다 스로틀링에 걸리면 TTT로 판정하고, 한쪽만 걸리면 “이 조건이 둘의 경계선”이라고 알린다. 정상상태도 피크도 같으면 조건을 바꾸라고 안내한다.

**한국어 조사 자동 선택(v1.9)**: 결과 문장의 조사를 앞말 받침에 따라 고른다(“팬 없음가” 같은 문장을 막는다). 숫자로 끝나면 **읽는 소리**의 받침을 따른다 — “Pi 5”는 ’오’로 읽으므로 받침이 없다.

**캘리브레이션은 채팅에서 실행하지 않는다(FR-32)** — 측정 시계열을 채팅 메시지로 실어 나를 수 없기 때문이다. 실행하는 척하는 대신 보내는 방법을 안내하고 저장된 프로파일 목록을 보여준다.

### 2.3.10 실측 로거 스크립트

scripts/edge/measure_throttling.py는 한 번 실행하면 BASELINE(유휴, R_ja 계산 기준) → LOAD(고부하 추론) → RECOVERY(회복 정책 적용 후 관찰) 3단계를 자동 진행하며 1초 간격으로 로그를 남긴다. 출력은 두 파일이다.

- <run_id>.csv — 시계열. **calibrate_edge_thermal_model 도구가 그대로 먹는 열 이름**
- <run_id>.json — 실행 메타데이터(보드·냉각조건·모델·실내온도·시작시각)

메타데이터를 반드시 함께 남기는 이유는 실험이 끝난 뒤에는 “이 CSV가 어떤 조건이었지?”를 복원할 방법이 없기 때문이다 — **조건을 잃은 데이터는 그래프를 그릴 수는 있어도 비교를 못 한다.** 라즈베리파이가 없는 환경에서 스크립트 동작만 확인하는 --simulate 모드도 제공한다.

부속 스크립트로 csv_to_mcp_payload.py(CSV → MCP 호출 페이로드 변환), Invoke-Mcp.ps1(PowerShell MCP 호출 헬퍼)이 있다.

### 2.3.11 PtmController — 예측 냉각 제어기 (신규, v1.9)

부록 A.3이 “부하 패턴과 열 모델은 갖춰졌고 제어기만 남았다”고 적어 둔 그 제어기다. 스윕(2.3.5)이 **고정 운전점 하나**를 고르는 데 반해, 이 제어기는 **회전수를 시간에 따라 바꾼다.**

#### 열 지연이 예측의 이득을 만든다

온도는 부하를 시정수 τ만큼 늦게 따라온다. 반응형 제어는 **이미 뜨거워진 뒤에야** 팬을 올리므로 그 지연만큼 온도가 오버슈트하고, 되돌리려면 한동안 정격으로 돌려야 한다. 예측형은 부하가 오기 **전에** 미리 식혀 두므로 같은 피크 온도를 더 낮은 평균 회전수로 지킨다. 전력은 회전수의 3승이라 평균 회전수를 조금만 낮춰도 에너지가 크게 준다 — **PTM의 이득은 이 비대칭에서 나온다.**

#### 세 방식을 항상 함께 돌린다

| 방식 | 무엇을 보고 정하는가 | 역할 |
|---|---|--- |
| ALWAYS_MAX | 아무것도 안 본다(항상 정격) | 순진한 기준선 — 제어를 안 했을 때의 비용 |
| REACTIVE | **현재 온도**(50/60/67.5/75℃ 계단, 라즈베리파이 공식 팬 커브 근사) | 현실 기준선 — 실제 보드가 하는 일 |
| PREDICTIVE | **다가올 부하**(지평 안의 부하를 미리 적분) | PTM |
| FIXED | 사용자가 지정한 고정 듀티 | 스윕이 찾은 운전점과 견줄 때 |

“예측 제어로 돌렸더니 평균 듀티 42%였다”는 문장 하나로는 판단이 불가능하다 — 반응형이 40%였다면 손해다. 그래서 도구가 항상 여러 방식을 함께 돌린다(보드·재질·팬 유무 비교를 두 번 실행으로 처리하는 것과 같은 이유).

#### 예측 알고리즘

- 제어 주기(기본 5초)마다 듀티 격자(0~100%, 10%)를 **낮은 쪽부터** 훑는다
- 각 후보에서 지평(기본 60초) 동안의 부하를 1노드 RC로 미리 적분해 최고 온도를 구한다
- 목표 온도(기본 소프트 제한 −3℃ = 77℃)를 지키는 **첫 후보**에서 멈춘다 → 항상 최소 듀티다
- 듀티를 **낮추는** 방향에만 여유 2℃를 더 요구한다 — 늦게 올리면 스로틀링이고 늦게 내리면 전기만 조금 더 쓰므로, 두 실수의 대가가 다르다

연속 최적화 대신 격자를 쓰는 이유는 재현성이다(NFR-02). 부동소수점 해가 실행마다 미세하게 달라지면 발표용 곡선이 재현되지 않는다.

#### 제어기는 모델을 완벽히 알지 못한다(의도적)

예측은 1노드로 하고 **스로틀링이 없다고 가정**한다. 실제 적분은 2노드일 수 있고 거버너가 클럭을 낮추기도 한다. 제어기에 완전한 모델을 주면 “예측이 좋다”는 결론이 **모델을 두 번 쓴 결과**가 되어 실험이 자기 자신을 증명하게 된다. 무스로틀 가정은 실제보다 뜨겁게 예측하므로 제어기가 조금 이르게·세게 도는 쪽으로 틀린다 — 안전한 방향이다.

#### 대가를 숨기지 않는다

PTM은 허용된 온도 여유를 **끝까지 쓰기 때문에** 반응형보다 뜨겁게 돈다(실측 기준 피크 75.3℃ vs 68.0℃, Pi5·주변 35℃·버스트). 에너지만 보면 언제나 이기므로 결과 표와 채팅 요약 모두 피크 온도를 같은 줄에 놓고, 예측형이 몇 ℃ 더 뜨거운지 한 줄로 덧붙인다. 온도 진폭(③ 지표)과 함께 읽어야 부품 수명 쪽 대가가 보인다.

#### 회복 정책과 함께 쓰지 않는다

회복 정책 R3(능동 냉각)와 제어기는 **같은 액추에이터**를 두고 다툰다. 둘을 동시에 켜면 온도가 내려간 것이 제어기 덕인지 정책 덕인지 분리할 수 없으므로, 비교 도구는 회복 구간 없이(policy=none) 부하 구간만 돌린다.

### 2.3.12 PTM 승자 동률 판정 (신규, v1.12)

`min(총에너지)` 하나로 승자를 고르던 것이 문제였다. 제어 방식은 서너 개뿐이고 부하가 평탄하면 방식 간 에너지가 수 J 안에서 겹치는 일이 흔한데, 그때 **리스트에서 먼저 나온 방식(항상 최대)이 그냥 이겼다** — “왜 이게 이겼는가”에 답할 수 없는 승자다.

팬 스윕이 이미 같은 문제를 풀어 뒀으므로(D-13) 규칙을 재사용한다.

1. 동률 판정은 **상대 오차**(`FanSweepResult.TIE_TOLERANCE`)로 한다 — 총에너지는 수만 J라 절대 오차로는 기준을 잡을 수 없다.
2. 동률 집합 안에서 **최고 온도 → 평균 팬 듀티 → 회전수 변경 횟수** 순으로 고른다. 온도는 수명·안정성 여유이고, 듀티와 변경 횟수는 기계적 마모·소음이다 — 에너지가 같다면 더 시원하고 팬을 덜 돌리고 회전수를 덜 바꾸는 쪽이 낫다.
3. **동률이었다는 사실 자체를 결과에 남긴다** — `energyTiedModes`에 방식 목록을, `tieBreak`에 무엇으로 갈랐는지와 “이 조건에서는 제어 방식 간 에너지 차이가 의미 있는 결론이 되지 못한다”를 적는다.

3번이 핵심이다. “PTM이 이겼다”와 “PTM이 반응형과 사실상 같은데 더 시원해서 이겼다”는 **다른 결론**이고, 후자를 전자로 보고하면 이 연구의 주장(예측 냉각의 이득)이 실제보다 크게 읽힌다. 절감률(`energySavedVsAlwaysMaxPercent`)은 종전대로 “항상 최대” 대비로 적는다 — 그것이 제어를 하지 않았을 때의 비용이기 때문이다.

### 2.3.13 팬 배치 조합 랭킹 (신규, v1.12)

`rank_fan_layouts`는 사진과 유사한 함체에서 40㎜ 팬 2개의 실측 순서를 정하기 위한 **후보 선별기**다. 바닥·상단·좌하·좌상·우하·우상 6곳에서 순서 없는 두 위치를 고르고, 각 팬을 흡기 또는 배기로 둔 15×4=60조합을 P01~P60으로 고정 열거한다.

`candidates`로 배치를 직접 지정하는 모드도 입력 순서로 번호를 새로 매기지 않고, 이 60조합 표를 정규화 키(위치쌍 무순서 + 각 자리의 흡·배기)로 조회해 정식 ID를 그대로 받는다 — 그래야 같은 물리적 배치가 전수 열거 모드와 직접 지정 모드에서 항상 같은 P-ID를 갖는다. 표준 60조합 어디에도 걸리지 않는 배치는 추측하지 않고 거부한다(fail-closed).

점수는 엑셀 `가정` 시트(2026-08-27)의 위치효율 평균에 같은 방향 팬 계수 또는 관통류 계수를 곱하고, 자연대류 방향·역방향·같은 측면 단락 보정을 더해 0.25~1.15로 제한한다. 정렬은 냉각점수 내림차순, 예상 온도 편차 오름차순, ID 오름차순이다. 이 값은 CFD나 열 RC 적분 결과가 아니므로 예상 최고·평균온도와 편차는 `advisory` 아래에만 두고 물리 시뮬레이터와 비교 불가임을 경고한다(FR-62·FR-63·FR-64).

도구 선택기는 팬 어휘(팬·fan·쿨러·흡기·배기·흡배기)와 배치 어휘(배치·조합·“어디에 달/붙/장착/부착”·“어느 위치/자리/쪽”·“어떤 방향/위치/자리”·“위치·방향 + 조합/비교/추천/고르/정하”)가 함께 있을 때만 이 도구를 고른다. 맨 “위치”·“방향”은 배치 어휘에 넣지 않는다 — 캘리브레이션 데이터 설명이나 방열판 조건 설명에서 쓰는 “위치”까지 배치 랭킹으로 새기 때문이다(리뷰 라운드 1). 팬·배치 어휘가 함께 있어도 다른 도구의 주제 어휘(스윕/rpm류, 캘리브레이션류, 방열판 명사 자체)가 문장에 함께 있으면 물러난다 — 맨 “배치”·“조합”에는 부정 가드가 없어 스윕·캘리브레이션·방열판 세 도구의 문장을 흡수하던 결함의 재발 방지책이다(최종 리뷰, FR-65). “최적”은 이 가드에 넣지 않는다 — “최적 팬 배치”가 SWEEP의 “최적...팬”에게 도로 뺏기기 때문이다. PTM 요청이 더 구체적이므로 검사 순서는 PTM → 팬 배치 → RPM 스윕 → 캘리브레이션 → 방열판 → 발열이다(FR-65). 경험적 점수는 기존 열 스택과 컴파일 의존성 수준에서 격리한다(D-18).

채팅 경로는 `EdgeParamGuard`가 합쳐 준 인자를 이 도구에 넘기지 않고 빈 JSON 객체로 호출한다 — `EdgeParamGuard`가 채워 주는 값(보드·냉각조건·부하 등)은 전부 열 시뮬레이션용이라 이 도구의 스키마(배치 후보·topK)와 무관하다.

## 2.5 프론트엔드 구조

`/`가 index.html 하나를 돌려주고, 사이드바·결과 렌더러는 엣지 한 벌이다.

| 파일 | 줄 수(분리 전 기준) | 책임 |
|---|---|--- |
| index.html | 265 | 공통 골격·사이드바 컨테이너 |
| js/chat.js | 181 | STOMP 연결·메시지 송수신·버블 렌더링 |
| js/edge.js | 559 | 엣지 사이드바·구성 단면도 SVG·지표 표·스윕 곡선·팬 배치 랭킹(EDGE_LAYOUT) 렌더 |
| css/app.css | 655 | 다크 테마 공통 스타일 |

줄 수는 분리 직전(2026-08-28) 소스 기준이며, `index.html`·`app.css`에는 아직 장량동 자산이 섞여 있다. 분리와 함께 `js/domain.js`(도메인 전환·시작화면 카드)와 `js/waste.js`, 장량동 사이드바·`RESULT`·`SCENARIO` 렌더러를 걷어내면 실제 줄 수는 더 줄어든다 — 코드 분리를 마친 뒤 실측으로 갱신한다.

결과 메시지 유형은 셋이다 — `EDGE_RESULT`(발열·방열판 실행), `EDGE_SWEEP`(RPM 스윕 곡선), `EDGE_LAYOUT`(팬 배치 랭킹). 세 렌더러 모두 **원본 데이터가 없으면 텍스트로 폴백**하고, `EDGE_LAYOUT`은 실측 전 임시 예측임을 배너로 항상 표시한다(FR-64).

## 2.6 운영·보안 설정

전제는 하나다 — 이 서버에는 인증 계층이 없다(Spring Security 미사용). `/mcp`·`/ws`·`/actuator`가 전부 무방비이므로, 노출면 자체를 좁히는 것이 유일한 방어선이다.

| 항목 | 설정 | 근거 |
|---|---|--- |
| 바인딩 | `server.address=${SERVER_ADDRESS:127.0.0.1}` | 무인증 `tools/call`이 외부에 열리면 안 된다. 외부 노출은 코드가 아니라 환경변수로만 해제한다 |
| Actuator | health 상세 기본 비공개 | 상세 응답이 내부 구성·경로를 노출한다 |
| 비밀값 | 환경변수 전용(OPENAI_API_KEY) | 소스·설정 파일 하드코딩 금지 |
| LLM 백엔드 | Spring 프로파일(openai/ollama) | 코드 변경 없이 로컬/클라우드 교체 |
| 정적 리소스 캐시 | 비활성 | 브라우저 휴리스틱 캐시로 프론트엔드 수정이 반영되지 않는 문제를 겪었다 |
| 추적성 | 요청마다 requestId를 MDC에 주입 | 로그에서 한 요청을 끝까지 따라갈 수 있어야 한다 |

이 절의 결정은 장량동 문서(SDD 2.16)와 동일한 판단을 공유한다 — 두 서버가 같은 배포 전제(로컬 연구용·무인증) 위에 있기 때문이다. 배포 환경이 로컬을 벗어나면 두 문서를 함께 재검토한다.

설계 결정 D-19(회복 지표 의미 분리)·D-20(접촉률 coverage 분리)·D-21(냉각 부정 어휘)의 상세 근거는 2.4 표에 있다.

## 3.8 합격 기준

- 모든 필수(FR) 요구사항에 대응하는 테스트가 통과한다.
- **도구 선택 오탐 0건**(UT-144~156) — 특히 냉각 조건 표현이 배치 비교로 새지 않는다(D-03).
- **물리 모델은 해석해 대비 오차 허용 범위 이내**(UT-01), 캘리브레이션은 무잡음 1%·실잡음 5% 이내(UT-18·19).
- **2노드의 정상상태가 1노드와 일치**(UT-20·21) — 이것이 2노드 확장의 하위호환 합격선이다.
- **에너지 집계가 dt에 의존하지 않음**(UT-48~50) — 상수 전력 조건에서 오차 0.
- **순위 역전이 조건부로만 발생**(UT-24·25) — 무조건 무거운 쪽이 이기면 모델이 틀린 것이다.
- **확장 기능이 미지정 시 종전과 동일한 결과**(UT-22·33·38·39, UT-91).
- **없는 값을 만들지 않는다** — 스로틀링 미발생 시 TTT/TED/TRT는 null(UT-08), 적합 지점 없는 스윕은 NO_FEASIBLE_POINT(UT-71), 동률인 PTM 승자는 동률 사실을 남긴다(UT-99~101).
- **경험적 점수가 물리 결과와 섞이지 않는다**(UT-133·134) — 예상 온도는 `advisory`에만 있고 경고 3종이 항상 붙는다.
- 엔진 커버리지 ≥85%, 전체 ≥70%.

> **분리 시점의 회귀 기준선** — 분리 직전(2026-08-27) 전체 회귀는 Surefire 503건이 통과한 상태였고, 이 값은 장량동 테스트를 포함한다. 코드 분리 후 엣지만의 회귀를 다시 돌려 이 자리에 기록한다.

## B.2 미해결 — 다음 개정 대상

**엣지 항목 중 미해결은 없다.** E-06(회복 지표 의미)·E-08(접촉률 극소 구간)은 2026-08-26에 결정(D-19·D-20)과 함께 코드·테스트로 해소됐고, E-09(냉각 부정 어휘)는 같은 날 라이브 실행에서 발견해 즉시 수정했다(D-21). E-10(PTM 승자 동률)은 D-17과 함께 반영됐다.

두 건이 오래 남아 있던 이유는 구현 난이도가 아니라 결정이 먼저 필요했기 때문이다 — E-06은 공개된 MCP 응답 계약의 하위호환 문제였고, E-08은 어느 쪽이 물리적으로 옳은지를 정하는 모델링 문제였다.

## B.3 남는 교훈

D-21(E-09)과 구 D-33(도메인 어휘 누락)은 같은 유형이다 — 로직·테스트가 모두 정상인데 **사용자가 실제로 쓰는 단어가 목록에 없어** 오류 없이 다른 실험이 실행된다. 두 건 다 정적 검토가 아니라 라이브 실행에서만 드러났다. 새 어휘를 넣을 때는 그 개념의 동의어까지 함께 넣었는지 확인한다(팬 → 쿨러 → 냉각장치 → 냉각모듈).
