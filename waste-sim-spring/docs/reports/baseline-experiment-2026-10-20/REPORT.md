# 기준선 실험 — 서브태스크 템플릿 흐름 vs 스키마만 보고 바로 설정

2026-10-20 · `fix/scenario-requires-plan` (`fbc0c74` + 커밋 안 된 브로커 생존 확인 변경) · 앞선 실험: [브로커 실험 2026-10-19](../broker-experiment-2026-10-19/REPORT.md)

## 무엇을 쟀나

논문은 서브태스크 템플릿이 LLM 의 해석 오류와 구성요소 누락을 줄인다고 주장한다. 2026-10-19 실험은 제안 방식만 쟀으므로,
같은 요청을 **템플릿 없이** 처리하는 기준선을 세워 나란히 쟀다.

| | 방식 | LLM 이 보는 것 | 끝나는 곳 |
|---|---|---|---|
| **A** 제안 | 브로커 `find_simulators` → 시뮬레이터 `get_templates` · `plan_subtasks` · `build_scenario` | MCP 응답(능력 카드 · 템플릿 · 서버 검증) | `build_scenario` 가 `UNCONFIRMED` |
| **B** 기준선 | 장량동 옛 직접 실행 도구 `run_waste_simulation` 하나 | 그 도구의 이름 · 설명 · 입력 스키마([run_waste_simulation.schema.json](run_waste_simulation.schema.json))뿐 | 부를 호출 인자(`plannedCalls`)를 확정 |

확인 화면 승인은 사람 자리라 두 방식 모두 실행하지 않았다. B 는 서버를 부르지 않고 인자만 적는다 — 옛 흐름에서 그 인자로
바로 실행되었을 지점이다.

## 방법

- **요청 8개 (장량동 쪽):** 2026-10-19 의 R01 · R04 · R10 과 새 요청 N1~N5([requests.json](requests.json)). 새 요청은 템플릿의 조건부 ·
  기본값 없는 결정을 건드리게 골랐다 — N1 건물 10동 + 교통구역 근사(구역 배정 · 구역 안 이동시간 · 배차 간격), N2 차종 비교와
  적재 몫, N3 야간 교대 직업 구성, N4 범위 밖 반복 수(200회 — 템플릿 상한 100, 스키마에는 상한 없음), N5 템플릿에 없는 배출 시간 조건.
- **LLM 역할:** 요청 · 방식마다 새 에이전트(Claude Opus 5.5, 일반 목적) 하나, 16개를 동시에. 지시문은 2026-10-19 틀을 따랐다 —
  [A](agent-prompt-A.md), [B](agent-prompt-B.md), 채운 것은 [prompts/](prompts/). 저장소 파일은 읽지 못하게 했다.
- **사용자 역할:** 같은 답변 대본. 에이전트는 질문을 **먼저 기록한 뒤** 대본에서 답을 찾고, 없으면 "기본값으로 해줘". 질문마다
  어떤 매개변수를 물었는지(`keys`)도 적게 했다.
- **채점 자:** 장량동 서브태스크 템플릿의 결정 키 16개([jangnyang-templates.json](jangnyang-templates.json)). 두 방식의 최종 설정을
  이 키로 옮겨(`collectionTime` "HH:MM" → 분, `trafficEnabled` → APPLY/IGNORE) 적용되는 결정마다 분류했다([score.py](score.py)).
  조건부 결정(배차 간격 · 교통 프로파일 · 구역 배정 · 구역 안 이동시간)은 최종 설정에서 조건이 서면 센다.

  | 분류 | 뜻 |
  |---|---|
  | USER | 요청 문장에 있거나 물어서 받은 값과 같다 |
  | 물은 기본값 | 그 결정을 물었고 사용자가 "기본값으로" 라고 답했다 |
  | **조용한 기본값** | 묻지도 않았고 사용자가 말하지도 않았는데 기본값이 들어갔다 (B 는 인자를 빼서 엔진 기본값이 쓰이는 경우 포함) |
  | **조용한 추측값** | 묻지도 말하지도 않았는데 기본값이 아닌 값을 넣었다 |
  | **해석 오류** | 요청 문장에 있거나 물어서 받은 값과 최종 값이 다르다 |
  | **기본값 없는 결정 건너뜀** | `routeAvailableCapacityKg` · `zoneAssignmentRule` · `intraZoneTravelMinutes` 가운데 적용되는 것을 묻지도 받지도 않았다 |

- **검증:** A 의 최종 설정은 에이전트 보고가 아니라 서버가 보관한 시나리오([scenarios/](scenarios/), `values` · `origins`)에서 읽었다.
  장량동 서버의 UNCONFIRMED 시나리오 7개가 A 보고 7개와 정확히 맞았다. B 는 보고의 `plannedCalls` 를 그대로 채점했다.

### 재실행 — A 3개가 행정동 서버로 갔다

첫 A 실행에서 R10 · N2 · N5 는 브로커가 ADJUST_REQUEST 를 냈고, 대본에 서버 선호가 없어 사용자가 "기본값으로 해줘" 라고 답하자
에이전트가 **행정동 서버**(bukgu-district-waste-sim)를 골랐다. 장량동 스키마와 비교할 수 없으므로 이 셋은 따로 두고
([runs/routed-bukgu/](runs/routed-bukgu/)), 대본에 "원룸촌 한 블록(장량동)으로 볼게" 만 더해(`userScriptA2`) `-A2` 로 다시 돌렸다.
B 는 서버를 고를 일이 없어 다시 돌리지 않았다. 아래 A 행은 R10 · N2 · N5 에서 `-A2` 다.

### 읽는 법

1. **차이는 "묻느냐" 에서 난다.** B 도 대본이 자세한 R01 에서는 A 와 똑같이 6개를 물어 조용한 기본값이 0 이었다. 요청 문장이 짧을수록
   (R04 · R10 · N5) B 는 비교할 값 · 기간만 묻고 나머지를 스키마 기본값으로 채웠다. N5 는 질문 없이 바로 인자를 확정했다.
   A 는 템플릿이 결정 목록을 주므로 요청이 짧아도 같은 목록을 물었다 — 요청 문장 길이와 상관없이 0 이었다.
2. **기본값 없는 결정은 스키마로는 보이지 않는다.** 스키마의 `routeAvailableCapacityKg` 설명은 "미입력 시 차종 정격용량" 이라
   B 에게는 빼도 되는 값으로 읽힌다. 템플릿은 같은 값을 `mustAskNoDefault` 로 표시하고 서버가 빈 채로는 시나리오를 막는다.
   R10-A2 는 사용자가 끝까지 숫자를 주지 않자 INVALID 로 멈췄다 — 정격 용량(5톤)으로 조용히 돌린 B 와 대조된다.
3. **범위는 스키마보다 템플릿이 정확하다.** N4 의 반복 200회는 스키마(상한 없음)로는 맞는 값이라 B 가 그대로 넣었다. A 는
   서버가 OUT_OF_RANGE 로 막고, 에이전트가 사용자에게 알려 100회로 고쳤다.
4. **조건부 결정은 B 도 잘 잡았다.** N1 에서 B 는 스키마 설명("5동 이상을 ZONE_PROXY_HYBRID 로 돌리려면 필요")을 읽고 구역 배정 ·
   구역 안 이동시간 · 배차 간격을 한 묶음에 물었다. A 는 같은 결정이 보류 → 생성되는 순서를 따라 묶음을 4번 나눴다(질문 +3).
   설명이 친절한 매개변수에서는 기준선도 묻는다.
5. **B 의 해석 오류 2건은 모두 "사용자 답 + 자기 판단" 이다.** N1 은 사용자가 "덩어리로" 를 골랐는데 스키마 설명의 권고("CONTIGUOUS 와
   ROUND_ROBIN 을 함께 돌려 범위로")를 따라 ROUND_ROBIN 실행 2개를 더 넣었다. N2 는 적재 몫 120kg 을 1톤 실행에만 넣고 5톤은
   정격 용량으로 두었다(A 는 둘 다 120kg). 둘 다 확인 화면이 없으면 사용자가 알기 어렵다.
6. **대가 — 질문과 호출.** A 는 질문 묶음이 2.4배, MCP 호출이 요청당 9회, 시간이 약 2배다. 늘어난 질문은 서버 선택 · 요청 수정
   (ADJUST_REQUEST, 5건)과 연쇄 조건부 결정(N1)에서 나왔다.

### A 쪽에서 드러난 것

- **브로커 판정이 요청을 바꾼다.** N1 · N2 · N4 · N5 · R10 이 ADJUST_REQUEST 를 거쳤고, 목적이 "감당이 될까" → "최대 적재량",
  "다 안 끝나는 날" → "수거 완료 시각" 처럼 카드의 질문으로 바뀌었다. 판정형 · 예외형 목적을 받는 항목이 카드에 없다.
- **"기본값으로" 답이 서버 선택을 정한다.** 서버 선호가 없는 대본에서 3/8 이 행정동 서버로 갔다(첫 실행). R10 은 2026-10-19 에는
  CHOOSE 를 거쳐 장량동으로 갔지만, 이번에는 고친 요청에서 공간 규모가 빠져 행정동이 바로 MATCH 가 됐다.
- **템플릿이 도구보다 좁다.** N5 의 배출 시간 조건(포항 공식 20:00~06:00)은 `run_waste_simulation` 에는 `dischargeTimeMode` 로 있지만
  템플릿 · 능력 카드에는 없어, A 는 조건을 빼고 진행했다(사용자에게 알림). B 는 사용자 조건을 그대로 넣었다.

## 한계

- **자가 템플릿을 자로 썼다.** 채점 자가 A 가 묻는 목록 그 자체라 A 에게 유리하다. 템플릿 밖의 엔진 값(수거장 용량 30kg · 민원 임계
  0.8 · 배출량 표준편차 등)은 두 방식 모두 묻지도 보여 주지도 않고 같은 값으로 들어가며, 이 몫은 세지 않았다.
- **"물었다" 는 에이전트가 적은 `keys` 로 판정했다.** 질문 문장을 사람이 대조했지만 체계적 검증은 아니다.
- **B 의 실행 검증 없음.** B 의 인자는 실행하지 않았으므로 엔진이 seeds 200 을 받거나 막는지는 확인하지 않았다.
- **B 는 서버 선택을 하지 않는다.** B 는 장량동 도구만 알고 시작하므로 R04 · R10 의 서버 선택 질문이 원천적으로 없다. A 의 질문 수에는
  브로커 단계(서버 선택 · 요청 수정)가 들어 있다.
- **재실행 대본이 다르다.** R10 · N2 · N5 의 A 는 서버 선택 답을 더한 대본(`userScriptA2`)으로 돌렸다. 그 답은 서버 선택 질문에만 쓰여
  B 에 영향이 없지만, 두 방식의 대본이 글자 그대로 같지는 않다.
- **LLM 하나 · 요청당 1회 · 요청 8개.** 같은 요청을 다시 돌리면 B 가 얼마나 물을지는 달라질 수 있다(R01 처럼). 동작 확인이지 통계적 주장이 아니다.
- **서버는 다른 세션이 띄운 것이다.** 이 세션은 이미 떠 있던 네 서버(8089~8092)를 썼다. 작업 트리의 커밋 안 된 브로커 변경
  (`EndpointProbe`)이 그 빌드에 들어갔는지는 확인하지 않았다.

## 재현

```
.claude/launch.json 의 broker · simulator · district-waste-sim · parking-sim 을 띄운다
prompts/BL-<요청>-<A|B>.md 의 {SP} 를 mcp.sh 가 있는 폴더의 부모로 바꿔 요청마다 새 에이전트에 준다 (결과: {SP}/exp/runs/)
결과를 runs/ 에 두고, A 의 scenarioId 를 GET http://127.0.0.1:8090/api/scenarios/<id> 로 받아 scenarios/ 에 둔다
python score.py        # metrics.json 과 표
```

원자료: [runs/](runs/) (A 8 · B 8 — A 의 R10 · N2 · N5 는 재실행 `-A2`), [runs/routed-bukgu/](runs/routed-bukgu/) (행정동으로 간 첫 A 실행 3개),
[scenarios/](scenarios/) (서버 보관 시나리오), [metrics.json](metrics.json) (결정별 분류).
