# 시뮬레이터로 넘겨준 뒤에는 그 대화에서 브로커를 부르지 않게 한 기록

2026-09-29 · 커밋 `925157f` (`feature/simulator-mcp`) · 전체 테스트 597개 중 594개 통과(스킵 3) · 확인은 빈 포트 8189 의 브로커로

같은 날 [`broker-verdict-2026-09-29`](../broker-verdict-2026-09-29/REPORT.md) 에 이어진 작업이다.

## 요청

> 시뮬레이터 MCP 가 연결되고 난 뒤에는 시뮬레이터 MCP 하나만 실행되게 하고 싶어

"하나만 실행" 을 세 가지로 읽을 수 있어 사용자에게 물었다.

| 선택지 | 뜻 | 고른 것 |
|---|---|---|
| 대화에서 브로커 사용 종료 | 두 서버 프로세스는 켜 둔 채, 브로커가 넘겨주면 그 대화에서는 시뮬레이터만 쓴다 | **이것** |
| 브로커 프로세스를 끔 | 매칭 뒤 브로커 서버 자체를 종료한다 — 다음 새 요청 때 다시 띄워야 하고 시뮬레이터의 재등록이 계속 실패한다 | |
| 처음부터 시뮬레이터만 띄움 | 평소에는 시뮬레이터만 띄우고 브로커는 서버 찾기를 시험할 때만 — 그림의 3·4단계를 평소에는 건너뛴다 | |

브로커는 요청마다 "어느 서버가 맞나" 를 찾는 안내소다. 프로세스를 끄면 다음 새 요청 때 찾을 곳이
없어진다. 문제는 프로세스가 아니라 **대화**였다 — 채팅 세션에는 `.mcp.json` 으로 두 서버가 모두 연결돼
있어, 넘어간 뒤에도 브로커 도구가 보이고 LLM 이 단계마다 다시 부를 수 있었다.

## 바꾼 것 → `925157f`

**① 다음에 할 일(`nextStep`)** — `find_simulators` 응답에 싣는다.

| verdict | nextStep |
|---|---|
| `MATCH` | 이 대화에서는 브로커를 다시 부르지 말 것. 이후 단계는 `endpoint` 의 시뮬레이터 도구만 — get_templates → plan_subtasks → validate_answers → build_scenario → get_scenario_status → run_scenario_by_token. 전혀 다른 시뮬레이션을 새로 요청할 때만 다시 조회 |
| `ADJUST_REQUEST` | 사용자에게 `requestAdjustments` 를 전하고 고칠지 물을 것. 고치면 고친 요청으로 다시 조회 |
| `NONE` | 쓸 수 있는 시뮬레이터가 없다고 전할 것 |

도구 설명에도 "MATCH 뒤에는 그 대화에서 브로커를 다시 부르지 않는다" 를 넣었다 — 도구 목록을 읽는
시점에 LLM 이 알 수 있게.

**② "같은 대화" 를 MCP 세션으로 알아본다.** 브로커가 `initialize` 때 `Mcp-Session-Id` 헤더를 준다(표준
MCP HTTP 방식). 클라이언트는 이후 요청마다 이 id 를 붙인다. 채팅 세션 하나가 곧 MCP 세션 하나라,
브로커가 대화를 알아볼 수 있는 단서는 이것뿐이다. 세션은 메모리에 최근 1000개까지 두고, 브로커가 다시
뜨면 잊는다 — 그러면 다음 조회가 처음 조회로 보일 뿐 판정은 같다.

**③ 같은 세션에서 `MATCH` 뒤 다시 조회하면 — 막지 않고 알린다.** 같은 대화에서 전혀 다른 시뮬레이션을
새로 물을 수도 있으므로 막으면 안 된다. 대신 응답에 `previousMatch`(이미 넘어간 서버 · endpoint · "같은
시뮬레이션이면 이 서버를 계속 쓰라") 를 붙이고 브로커 로그에 한 줄 남긴다. LLM 은 되풀이인지 새 요청인지
가를 수 있고, 사람은 로그에서 볼 수 있다.

## 한계

- **안내이지 강제가 아니다.** LLM 이 `nextStep` 을 무시하고 다시 부르면 브로커는 답한다. 그 사실이 응답과
  로그에 드러날 뿐이다. 대화에서 브로커 도구를 아예 없애려면 MCP 클라이언트 쪽 설정이 필요하고, 서버가
  강제할 수 없다.
- **세션 헤더를 붙이지 않는 클라이언트는 알아보지 못한다.** 그때는 `nextStep` 안내만 남는다. 이 기록의
  확인은 표준 방식대로 헤더를 붙인 스크립트로 했다 — 실제 채팅 세션(Claude Code)으로는 아직 보지 않았다.
- `nextStep` 의 endpoint 는 카드의 `localhost:8090` 이다. 채팅 세션은 `.mcp.json` 의 `127.0.0.1:8090` 으로
  이미 연결돼 있으니 LLM 이 그 주소로 새로 연결할 일은 없지만, 두 주소가 다르게 적혀 있다.

## 재현 방법

```bash
./mvnw.cmd -q -pl broker -am spring-boot:run
```

`requests/1-initialize.json` 의 `요청` 을 `POST http://127.0.0.1:8089/mcp` 에 보내고, 응답 헤더의
`Mcp-Session-Id` 를 `2-` · `3-` 요청에 같은 헤더로 붙여 보낸다. 장량동 카드가 브로커에 있어야 `MATCH` 가
나온다 — 시뮬레이터를 띄우면 스스로 등록한다.
