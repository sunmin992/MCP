## 이 기록의 성격

`java -jar` 로 띄운 서버에 **실제 JSON-RPC 요청을 보내고 받은 응답을 그대로** 파일로 남겼다.
각 `*.json` 은 `{요청, 응답}` 한 쌍이며 손대지 않았다. 확인(12단계)은 매번 사람이 브라우저에서
직접 눌렀다. 모델은 `get_scenario_status` 를 1초마다 읽다가 `CONFIRMED` 를 보면 다음으로 넘어갔다.
**값을 서버에 직접 밀어 넣거나 확인을 대신 누른 곳은 없다.**

| 폴더 | 내용 |

## 1. 요청과 구성

> 한 동네 정도 되는 규모에서 평일 교통량을 반영해서 하루 몇 시에 쓰레기를 수거하는 게 민원이
> 가장 적은지 알고 싶어

두 번째 요청에서 사용자가 조건을 줬다: **"25세대 주택 4개를 30일 동안 1톤 차량 3대를 15분
간격으로 내보낼 거야."**

| 단계 | 결과 |
|---|---|
| 3 `find_simulators` | `jangnyang-waste-sim` 4점 1위 — 한 동네 → 원룸촌 블록, 평일 교통량 → traffic-profile |
| 6 `plan_subtasks` | `FILLED 12 · NOT_GENERATED 2 · complete=true`. `LEGACY_CONSTANT` 라 `zoneAssignmentRule` · `intraZoneTravel` 은 생성되지 않는다 — 처음엔 `zoneAssignmentRule` 을 넣었다가 뺐다 |
| 8 `validate_answers` | 거절 없음 |
| 9 `build_scenario` | `scn-557d3c7` · 수거 시각 00:00~23:00 1시간 간격 **24벌** · 역검증 통과 |

**출처를 정직하게 붙였다.** 첫 실행에서 사용자가 말한 것은 교통량뿐이라 `trafficMode` ·
`trafficProfileId` 만 `USER` 였고, 나머지 9개는 `MODEL_DEFAULT` 로 보내 확인 화면 맨 위에
"승인하지 않은 기본값 9개" 로 떴다. 두 번째 실행은 사용자가 준 6개를 `USER` 로 바꿔 미승인이
**3개**(`seeds` 30 · `routeAvailableCapacityKg` 150 · `travelTimeMode` `LEGACY_CONSTANT`)로 줄었다.

`travelTimeMode` 는 고를 수 없었다 — 수거 지점 좌표가 0곳이라 `OSRM_HYBRID` 를 쓸 수 없다.

## 2. 결과 — 가장 좋은 시각은 없고, 피해야 할 시각은 뚜렷하다

[`2-sweep-user-values/13-run-by-token.json`](2-sweep-user-values/13-run-by-token.json) · 조건마다 30회

| 수거 시각 | 평균 민원 (표준편차) | |
|---|---|---|
| 00~05시, 16~23시 | 27.2 (6.2) — 13개 구간 전부 같음 | 바닥 |
| 10시 / **11시** / 12시 | 28.4 / **26.9** / 27.1 | 바닥 |
| 06시, 15시 | 29.2, 28.9 | 약간 높음 |
| 13시 | 36.7 | 높음 |
| 07시 / 08시 / 09시 | 59.5 / 47.5 / 58.1 | **피할 것** |
| 14시 | **60.1** | **피할 것 (최고)** |

**11시가 수치로는 최저지만 이긴 게 아니다.** 시드가 1..30 으로 고정이라 조건끼리 짝지어
비교할 수 있다. 00시와 짝지으면:

| 비교 | 평균차 | 95% 구간 | 더 낮은 시드 |
|---|---|---|---|
| 11시 − 00시 | −0.30 | ±1.77 | 19/30 |
| 12시 − 00시 | −0.13 | ±1.78 | 18/30 |
| 06시 − 00시 | +1.97 | ±0.77 | 4/30 |
| 15시 − 00시 | +1.63 | ±0.85 | 4/30 |

11·12시는 00시와 구별되지 않는다. 06·15시는 확실히 높다.

**봉우리는 배출 시각 바로 뒤에 선다** — 모델의 배출 시각 07:22 / 08:58 / 14:00.

**밤·저녁 13개 구간은 `allTotals` 30개가 한 자리도 다르지 않다.** 이 시간대에는 수거 시각이
민원을 움직이지 못하고, 27건 남짓은 다른 원인에서 오는 바닥이다.

**평일 교통량은 이 규모에서 결론을 바꾸지 못했다.** 드러난 곳은 차량 가동률(19.33 → 19.99%)
뿐이다. 4동에 1톤 3대면 여유가 커서 지체가 결과를 가르지 못하고, 이동시간도 구간 상수다.

모든 조건에서 미수거 0kg · 질량 보존 오차 0.00 · `dataQualityFlags` 없음 ·
`notForOperationalUse=true`.

**두 실행의 결과는 한 자리도 다르지 않다.** 값이 같고 출처만 달랐으니 당연하다 — 출처는 확인
화면이 보여 주는 정보이지 실행 설정이 아니다.

## 3. 확인 토큰의 구멍 둘

두 번째 확인에서 받은 토큰이 첫 번째와 **같았다**(`cft-0c98458488ca4afc`). 토큰은 실행 설정의
해시([`ScenarioBuilder.tokenFor`](../../../src/main/java/com/wastesim/pes/ScenarioBuilder.java))라
출처가 들어가지 않는다. "그럼 재구성으로 `UNCONFIRMED` 가 된 사이에 옛 토큰이 통하나?" 를
의심하고 시험했다 — [`3-token-before-fix/`](3-token-before-fix/)

| 시험 | 결과 | |
|---|---|---|
| T1 기존 도구 `run_waste_simulation` + **확인하지 않은 설정**(2일·1대·08시·교통 끔) + 유효 토큰 | 실행됨, `confirmed: true` · "사용자가 확인한 설정입니다" | **구멍** |
| T2 `EXECUTED` 시나리오를 같은 토큰으로 다시 | 실행됨 | **구멍** |
| T3b 재구성해 `UNCONFIRMED` → 옛 토큰으로 `run_scenario_by_token` | 거절 | 정상 |
| T3c 같은 상태에서 옛 토큰으로 기존 도구 | 거절 | 정상 |

**의심한 것은 문제가 아니었다.** `store.put` 이 토큰을 지우므로 재확인 전엔 옛 토큰이 통하지
않는다. 대신 다른 둘이 나왔다.

### 1번 — 토큰이 설정을 묶지 않았다 → `d3b78cd`

기존 실행 도구는 설정을 인자로 **따로** 들고 온다. [`ExecutionConfirmation`](../../../src/main/java/com/wastesim/mcp/ExecutionConfirmation.java)
은 토큰으로 시나리오를 찾아 그 시나리오의 해시만 대조했고, 넘어온 설정이 그 시나리오의
것인지는 보지 않았다. 유효한 토큰 하나면 아무 설정이나 "확인된 실행" 이 됐다.

**토큰은 시나리오가 확인됐다는 뜻이지 이 설정이 확인됐다는 뜻이 아니다.** 넘어온 설정이
확인받은 설정 중 하나와 해시가 같을 때만 통과시킨다(`ScenarioBuilder.isConfirmedRun`).
토큰이 없으면 지금처럼 막지 않고 `confirmed: false` 로 표시한다.

기존 시험 `맞는_토큰이면_확인됨으로_표시한다` 는 **토큰만 보내고 설정은 보내지 않았다** — 버그
동작을 굳혀 둔 것이었다. 확인한 설정을 함께 보내도록 고쳤고, 이것이 초록이라는 것은 정상
경로가 막히지 않는다는 증명이기도 하다.

실서버 — [`4-fix1-live/`](4-fix1-live/)

| | 결과 |
|---|---|
| A 다른 설정 + 토큰 | **거절** · "이 설정은 확인 토큰의 시나리오(scn-557d3c7)에서 사용자가 확인한 설정이 아닙니다" |
| B 확인한 설정(12시 조건) + 토큰 | 실행 · `confirmed: true` |
| C 토큰 없음 | 실행 · `confirmed: false` |

### 2번 — 토큰이 소모되지 않았다 → `4766947`

`run_scenario_by_token` 은 토큰이 있는지만 봤다. 상태 도구는 `EXECUTED` 에서 이미 "다시 돌리려면
확인 화면에서 다시 확인하십시오" 라고 안내하고 있었는데, 실행 경로가 그 안내를 지키지 않았다.
토큰이 계속 통하면 확인은 한 번의 동의가 아니라 **무기한 허가**다.

두 실행 경로 모두 `EXECUTED` 면 거절한다. 그런데 확인 화면은 `UNCONFIRMED` 에서만 버튼을 켰다 —
막기만 하면 **다시 확인할 길이 없어진다.** `EXECUTED` 에서도 "다시 확인하고 돌린다" 를 켠다.
다시 확인하면 `store.confirm` 이 실행 이력을 지운다.

실서버 — [`5-fix2-live/`](5-fix2-live/)

```
1 첫 실행                 → EXECUTED
2 같은 토큰으로 다시        → 거절 "이미 실행한 시나리오입니다 — 다시 돌리려면 …"
3 기존 도구 + 쓴 토큰       → 거절 "이미 실행한 시나리오의 토큰입니다 — …"
4 확인 화면                → EXECUTED · 버튼 "다시 확인하고 돌린다" · disabled=false
```

**남은 한계.** 기존 도구 실행은 토큰을 소모하지 않는다. 시나리오 한 벌에 설정이 여럿(이번엔 24)
이라 한 번 돌릴 때 소모하면 나머지를 돌릴 수 없다. 그래서 `run_scenario_by_token` 이 돌기
전까지는 확인받은 설정을 기존 도구로 반복해 돌릴 수 있다. 설정 자체는 확인받은 것이라 결과가
틀리지는 않는다. 막으려면 설정별 실행 기록이 필요하다.

## 4. 겪은 것

- **서버가 한 번 로그 없이 죽었다.** 마지막 줄이 정상 요청 처리이고 예외가 없다. 원인은 모른다.
  보관소가 메모리뿐이라 시나리오도 함께 사라져 다시 만들었다.
- **시나리오 id 가 출처를 담지 않는다.** `scenarioId` 는 `Objects.hash(pes.values(), …)` 라
  출처만 바뀐 재구성도 같은 `scn-557d3c7` 이 나온다. 재구성은 보관소의 항목을 덮고 토큰을
  지우므로 해는 없지만, 목록에서 "다른 확인" 을 id 로 구별할 수는 없다.
- **확인을 네 번 받았다** — 서버 사망, 출처 변경, 1번 실서버 확인, 2번 실서버 확인. 두 수정을
  한 번에 빌드했으면 실서버 확인은 한 번으로 끝났다.
- **스킵이 3건이다.** README 는 2건(Python 참조 엔진 부재)이라고 적는다. 셋째가 무엇인지는
  보지 않았다.

## 재현 방법

```bash
./mvnw.cmd -B -DskipTests package
java -jar target/waste-sim-spring-1.1.1.jar
```

각 `*.json` 의 `요청` 을 그대로 `POST /mcp` 에 UTF-8 로 보낸다. 확인은 `http://localhost:8090/`
에서 사람이 누른다. 토큰은 설정의 해시라 같은 설정이면 같은 값이 나오지만, 서버가 다시 뜨면
보관소가 비므로 확인을 다시 받아야 통한다.
