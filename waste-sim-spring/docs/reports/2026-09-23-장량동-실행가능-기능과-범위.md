# 장량동 시뮬레이터로 실행 가능한 기능과 범위

조사일 2026-09-23. 대상 `waste-sim-spring`, `develop`, HEAD `2892933`.
근거는 전부 코드와 리소스 파일이다. 범위의 정본은 `SimulationConfigValidator`다.

---

## 0. 분석 단위 — 이 시뮬레이터가 무엇을 모델링하는가

**장량동 전체가 아니라 장량동의 원룸촌 한 블록이다.** 이것을 먼저 고정해야 아래 범위가 읽힌다.

기본 설정이 그 단위와 물리적으로 맞는다.

```
4동 × 25명 × 0.9kg = 90kg/일
지점 4개            → 지점당 22.5kg/일
용량 30kg × 임계 0.8 = 24kg 에서 민원

22.5 대 24 — 매일 수거하면 간신히 안 넘고, 하루만 걸러도 45kg 으로 용량을 넘는다.
```

원룸 건물 4동에 각각 쓰레기장 하나씩 있는 블록이다. **30kg은 원룸촌 쓰레기장 용량으로
현실적인 값이며, 임계 직전 구간이라 수거 시각·주기에 민감하다** — 민원 실험이 작동하는 자리다.

### 장량동 전체는 이 단위가 아니다

지점 하나가 24kg, 즉 약 26명분을 감당한다.

| | 값 |
|---|---|
| 장량동 인구 | 70,576명 (행정안전부 주민등록 인구통계, 2026년 8월 말) |
| 세대 | 31,009세대 (세대당 2.28명) |
| 면적 | 11.25㎢ (포항시 북구청, 법정동 장성동·양덕동) |
| 필요한 수거 지점 | **약 2,700개** |
| 모델 상한 | **26개** (건물마다 1개, `Node_A~Z`) |

약 100배 부족하다. **근본 한계는 건물 수가 아니라 수거 지점 수다.** 인구를 실측으로 넣는
순간 지점당 2,443kg이 쌓여 첫날부터 전 지점이 민원이 되고, 수거 시각을 어떻게 바꿔도 결과가
같아진다 — 민원 실험 자체가 성립하지 않는다.

참고로 2019년 2월 구청 자료는 71,802명 · 26,744세대였다. 인구는 줄고 세대는 늘어
세대당 2.68명 → 2.28명이 되었다. 1·2인 가구 비중이 커졌다는 뜻이며, 원룸촌을 단위로 잡는
근거와 어긋나지 않는다.

### 그래서 필요한 실측이 달라진다

| 자료 | 필요 여부 |
|---|---|
| 장량동 전체 인구·세대 | **불필요** — 블록의 위치와 비중을 말할 때만 |
| 원룸촌 블록의 건물 수·건물당 호수 | **필요** — 현장 조사, 소규모라 가능 |
| 쓰레기장 용량 | **필요** — 30kg이 맞는지 확인 |
| 1인 배출량 | **필요** — 현재 0.9kg은 논문값 |
| 수거 지점 위치 | 필요 (`sites` 비어 있음) |

행정동 전체 통계보다 **블록 하나 실사가 더 현실적이고 더 정확하다.**

### 26동 40명 규모는 원룸촌이 아니다

```
26 × 40 × 0.9 = 936kg/일 ÷ 26지점 = 36kg/지점/일  →  30kg 용량 초과
```

그래서 용량을 60kg으로 올렸다. 60kg은 원룸 쓰레기장이 아니라 더 큰 집합 수거함이다.
**규모를 키우려고 단위를 바꾼 것이므로, 두 규모의 결과를 같은 축에서 비교하면 안 된다.**

## 1. 입력 범위 — 검증기가 강제하는 값

### 규모

| 항목 | 필드 | 범위 | 기본값 | 근거 |
|---|---|---|---|---|
| 건물 수 | `numBuildings` | **1 ~ 26** | 4 | 노드 id가 `Node_A`~`Node_Z` 한 글자 체계다. 27번째부터 `Node_[` 같은 값이 나와 역변환이 깨진다 |
| 동당 세대 | `residentsPerBuilding` | 1 이상, **상한 없음** | 25 | 검증기에 상한 검사가 없다 |
| 1인 배출량 | `wasteMeanKg` | 0 초과 | 0.9 kg/일 | |
| 배출량 변동 | `wasteSigma` | 0 이상 | 0.3 | |

### 시간·일정

| 항목 | 필드 | 범위 | 기본값 |
|---|---|---|---|
| 수거 시각 | `collectionTimeMinutes` | 0 ~ 1439분 | 720 (12:00) |
| 다회 수거 시각 | `collectionTimesMinutes` | 각 0~1439, **중복 불가** | 없음 |
| 주말 수거 시각 | `weekendCollectionTimeMinutes` | 0 ~ 1439분 | 없음 |
| 수거 주기 | `collectionIntervalDays` | 1 ~ 365일 | 1 |
| 수거 요일 | `collectionDaysOfWeek` | 0(월) ~ 6(일) | 없음 |
| 기간 | `days` | **1 ~ 365일** | 30 |
| 반복 | `seeds` | **1 ~ 100회** | 30 |
| 공휴일 | `holidays` | 0 ~ (days−1), 중복 불가 | 없음 |
| 주말 제외 | `skipWeekends` | true/false | false |
| 월별 배출 가중치 | `monthlyWasteFactor` | **정확히 12개**, 각 0 초과 | 없음 |

**함께 쓸 수 없는 조합** — 요일 집합과 `collectionIntervalDays ≠ 1`을 같이 지정하면 거부된다.
서로 다른 스케줄 방식이고 함께 적용하면 교집합이 비어 수거가 한 번도 일어나지 않을 수 있다.
`skipWeekends = true`인데 요일 집합에 주말(5·6)이 있어도 거부된다.

### 차량·경로

| 항목 | 필드 | 범위 | 기본값 |
|---|---|---|---|
| 차종 | `truckType` | 5톤 / 2.5톤 / 1톤 | LARGE_5TON |
| 차량 수 | `numTrucks` | 1 이상 | 1 |
| 배차 간격 | `dispatchIntervalMinutes` | 0 ~ 1439분 | 0 |
| 구간 이동시간 | `routeTravelMinutes` | **0 ~ 600분** | 0 |
| 지점 정차시간 | `serviceMinutesPerSite` | 0 이상 | 0 |
| 구역 내 이동시간 | `intraZoneTravelMinutes` | 0 이상 | 미지정 |
| 경로 배정용량 | `routeAvailableCapacityKg` | 0 초과 ~ **차종 정격용량 이하** | 차종 용량 |
| 초기 적재량 | `initialTruckLoadKg` | 0 ~ 경로 배정용량 | 0 |
| 방문 순서 | `routeSequence` | 0..(건물수−1)의 **정확한 순열** | 없음 |

차종 제원은 고정이다.

| 차종 | 용량 | 기동성 배수 | 골목 진입 |
|---|---|---|---|
| 5톤 `LARGE_5TON` | 5000 kg | 1.0 | **불가** |
| 2.5톤 `MEDIUM_2P5T` | 2500 kg | 1.2 | 가능 |
| 1톤 `SMALL_1TON` | 1000 kg | 1.6 | 가능 |

### 수거장·민원

| 항목 | 필드 | 범위 | 기본값 |
|---|---|---|---|
| 수거장 용량 | `capacity` | 0 초과 | 30.0 kg |
| 민원 임계 | `threshold` | 0 ~ 1 | 0.8 |
| 임대인 점검 | `landlordEnabled` | true/false | false |
| 점검 시각 | `landlordInspectMinutes` | 0 ~ 1439분 | 1200 (20:00) |
| 점검 임계 | `landlordThreshold` | 0 ~ 1 | 0.6 |
| 교통 민원 가중치 | `trafficComplaintWeight` | 0 이상 유한 | 1.0 |

### 거주민·배출

| 항목 | 필드 | 범위 | 기본값 |
|---|---|---|---|
| 직업 구성 | `occupationMix` | 아래 5종 중 선택 | 생산직·학생·전업주부 3종 |
| 배출 시각 모델 | `dischargeTimeMode` | PAPER_BASELINE / POHANG_ACTUAL | PAPER_BASELINE |
| 외출 시각 편차 | `leaveSigma` | 0 이상 | 30.0분 |
| 배출 허용 창 | `dischargeWindow…Minutes` | 각 0~1439, **시작 ≠ 종료** | 20:00 ~ 06:00 |
| 귀가 2차 배출 | `returnDischarge` | true/false | false |
| 귀가 배출 비율 | `returnFraction` | 0 ~ 1 | 0.4 |

직업 5종의 외출·귀가 시각은 고정이다.

| 직업 | 외출(배출) | 귀가 | 기본 구성 포함 |
|---|---|---|---|
| 생산직(일용직) | 07:22 | 18:00 | ○ |
| 학생 | 08:58 | 17:00 | ○ |
| 전업주부 | 14:00 | 16:00 | ○ |
| 야간 교대근무자 | 21:00 | 07:00 | × |
| 1인 직장인 | 07:50 | 19:00 | × |

`POHANG_ACTUAL`을 고르면 **직업이 배출 시각에 영향을 주지 않는다.** 허용 창 안 균등분포이며,
직업 구성이 결과를 바꾸는 기제가 사라진다.

### 분리배출

`wasteTypes`를 지정하지 않으면 전역 용량·임계·주기를 물려받은 **단일 유형**이 된다.
지정하면 유형마다 다음을 만족해야 한다.

- `key` 필수, 중복 불가
- `fraction` 0~1이고 **전체 합이 1.0 ± 0.001**
- `capacity` 0 초과, `threshold` 0~1, `intervalDays` 1 이상
- 유형별 수거 요일을 따로 줄 수 있다 (포항 북구 실제: 생활 월·화·목·금 / 음식물 화·목·토 / 재활용 수·토)

## 2. 선택지 — 열거형으로 고정된 것

| 축 | 선택지 | 현재 사용 가능 여부 |
|---|---|---|
| 차종 | 5톤 / 2.5톤 / 1톤 | 셋 다 가능. **단 전 차량 공통값 — 차량별 선택 불가** |
| 이동시간 방식 | `LEGACY_CONSTANT` / `ZONE_PROXY_HYBRID` / `OSRM_HYBRID` | 앞의 둘만 가능. 세 번째는 데이터 없어 차단 |
| 배출 시각 모델 | `PAPER_BASELINE` / `POHANG_ACTUAL` | 둘 다 가능 |
| 구역 배정 규칙 | `NONE` / `CONTIGUOUS` / `ROUND_ROBIN` | 셋 다 가능 |
| 시나리오 규모 | `PAPER_BASELINE` / `JANGRYANG_CAPACITY` | 둘 다 가능 |
| 거주민 프리셋 | 대학가형 / 공단인근형 / 가족주거형 / 균형형 | 넷 다 가능 |

**시나리오 규모 두 가지의 성격이 크게 다르다.**

| | 논문 기준선 | 장량동 용량 규모 |
|---|---|---|
| 구성 | 4동 × 25명, 지점 30kg, 5톤 1대 | 26동 × 40명, 지점 60kg, 1톤 1대 |
| 하루 생성량 | 90 kg | 936 kg |
| 트럭 가동률 | **1.8% 고정** | **92.5%** |
| 쓸 수 있는 실험 | 민원·수거 시각 | 용량·가동률·미수거·트럭 대수 |

두 규모는 **단위가 다르다.** 논문 기준선은 원룸 4동 블록이고(지점 30kg), 26동 규모는
지점 용량을 60kg으로 올린 더 큰 집합 수거함이다(0절). 같은 축에서 비교하면 안 된다.

논문 기준선에서 트럭 가동률이 1.8%로 고정되는 것은 규모가 작아서가 아니라 **5톤 차 한 대를
통째로 블록 하나에 배정했기 때문**이다. `routeAvailableCapacityKg`로 그 블록에 배정된 몫만
지정하면 용량 축이 원룸촌 단위에서 그대로 살아난다(9절).

26동 규모에서 미수거는 동당 42명(97.1%)에서 처음 나타나 43명에서 2,930kg, 50명에서
64,406kg으로 뛴다 — 기울기가 아니라 절벽이라 민감도를 볼 구간은 가동률 97~99% 사이다.

```
waste-separation      분리배출

```

## 6. 실행할 수 없는 것

| 못 하는 것 | 이유 |
|---|---|
| **실제 도로 기반 이동시간** (`OSRM_HYBRID`) | 지점 간 행렬이 비어 있다. 조용히 상수 모드로 떨어뜨리지 않고 **실행을 막는다** |
| **차량마다 다른 차종** | `truckType`이 전역 단일값이다 |
| **비용 산출** | 연료·인건비·운영비 항이 모델에 없다. 저장소 전체에 비용 심볼이 없다 |
| **27동 이상** | 노드 id 한 글자 체계의 상한 |
| **101회 이상 반복** | 검증기 상한 |
| **366일 이상** | 검증기 상한 |
| **새 모델 코드 생성** | 이 연구의 범위 밖 |
| **골목 접근 판정** | 코드는 있으나 수거 지점이 0곳이라 판정할 대상이 없다 — 5톤으로 돌려도 막히지 않는다 |

### 조건부로만 되는 것

**구역 근사(`ZONE_PROXY_HYBRID`)와 건물 수의 관계**가 특히 걸린다.

| 건물 수 | 구역 배정 규칙 | 결과 |
|---|---|---|
| 1 ~ 4동 | `NONE` (기본) | **동작** — 지점 id를 구역 id로 보는 폴백이 이름이 겹쳐 우연히 통과 |
| 5동 이상 | `NONE` | **차단** — `Node_E`라는 구역이 없다 |
| 5동 이상 | `CONTIGUOUS` | 구역 내 이동이 생기므로 `intraZoneTravelMinutes`를 **반드시 명시**해야 한다 |
| 5동 이상 | `ROUND_ROBIN` | 모든 구간이 구역을 넘으므로 구역 내 이동시간이 필요 없다 |

구역 배정은 **조사한 사실이 아니라 가정**이다. 결과에 `ZONE_ASSIGNMENT_ASSUMED`로 표시되며,
`CONTIGUOUS`와 `ROUND_ROBIN`을 함께 돌려 **범위로 보고**하는 것이 원래 용도다.
한쪽 값을 답으로 인용하면 안 된다.

### 실행이 막히는 다른 조건

- 차량 수 0대 이하
- 예측 적재율 120% 초과 — 배출량이 수거 능력을 지속적으로 넘어선다
- 초기 적재량이 경로 배정용량을 넘음
- 교통 반영을 켰는데 프로파일 id가 없거나 등록되지 않은 id
- 배출 창의 시작과 종료가 같음
- 분리배출 비율 합이 1.0이 아님

### 경고만 하고 실행하는 것

- 수거 시각이 교통 RED 구간(지체 배수 1.45 이상) — 가장 가까운 비-RED 시간대를 대안으로 제시한다

## 9. 연구에 쓸 수 있는 조합

분석 단위는 **원룸촌 한 블록**이다(0절). 그 안에서 실제로 답이 갈리는 조합이다.

| 물을 수 있는 것 | 필요한 설정 | 주의 |
|---|---|---|
| 민원이 가장 적은 수거 시각 | 기본 4동 25명으로 충분 | 지점당 22.5kg 대 임계 24kg이라 민감 구간이다. 배출 시각(07:22/08:58/14:00)과의 관계에서 내부 최적이 생긴다 |
| 수거 주기의 효과 | 기본 4동 25명 | 하루 거르면 45kg으로 30kg 용량을 넘는다 — 격일 수거가 성립하지 않는 것이 결과다 |
| 차량 가동률·용량 | **경로 배정용량을 지정** (아래) | 규모를 26동으로 키우지 않아도 된다 |
| 직업 구성의 효과 | `PAPER_BASELINE` 배출 모델 필수 | `POHANG_ACTUAL`에서는 직업이 배출 시각에 영향을 주지 않아 효과가 사라진다 |
| 교통 반영 여부의 효과 | 교통 프로파일 지정 | 두 프로파일의 피크가 13시와 18시로 달라 결론이 뒤집힌다 |
| 분리배출의 효과 | `wasteTypes` 지정, 비율 합 1.0 | 유형별 수거 요일을 다르게 줄 수 있다 |
| 배차 간격의 효과 | 차량 2대 이상 | **수거를 늦추기만 한다.** 민원 기준이면 0분이 단조 최적이라 비교할 것이 없다 |
| 블록 규모의 효과 | 4 ~ 26동 | 26동을 넘을 수 없다. 5동 이상이면 구역 배정 규칙이 필요하다(6절) |

### 용량 축을 블록 단위에서 살리는 법

기본 설정에서 트럭 가동률이 1.8%로 죽어 있는 것은 **5톤 차 한 대 전체를 블록 하나에
배정했기 때문**이다. 실제로는 청소차 한 대가 여러 블록을 돈다.

`routeAvailableCapacityKg`(경로 배정용량)가 그 몫을 지정하는 필드다. 검증기는 이 값을
`0 < x ≤ 차종 정격용량`으로 받고, 엔진은 이것을 가동률의 분모로 쓴다.

```
가동률 = (초기 적재량 + 수거량) ÷ 배정용량 합계 × 100
배정용량 = min(차종 정격용량, routeAvailableCapacityKg)
```

| `routeAvailableCapacityKg` | 90kg/일 블록의 가동률 |
|---|---|
| 지정 안 함 (5톤 = 5000kg) | 1.8% — 죽어 있다 |
| 150kg | 60% |
| 100kg | 90% |
| 90kg | 100% — 여유 없음 |

**규모를 26동으로 키우지 않고도 용량·가동률·미수거 실험이 성립한다.** `ScenarioScale`은
차를 5톤에서 1톤으로 줄이는 방식으로 이 문제를 풀었지만, 배정용량 쪽이 더 직접적이고
원룸촌 단위를 유지한다.

### 전체 규모로는 답할 수 없는 것

| 질문 | 왜 안 되나 |
|---|---|
| 장량동 전체에 수거차가 몇 대 필요한가 | 지점 26개 상한. 전체를 표현할 수 없다 |
| 장량동 전체 민원 건수 | 같은 이유 |
| 수거 비용 | 모델에 비용 항이 없다 |

전체 규모 질문에 답하려면 **블록 단위 결과를 블록 수로 환산**하는 별도 절차가 필요하고,
그 환산의 타당성은 이 시뮬레이터가 보장하지 않는다.
