# E2 확장 실험 — 제안 방식(A) vs 직접 설정 기준선(B)

2026-10-21 ~ 22. 세 서버(장량동 8090 · 행정동 8091 · 주차 8092) × 요청 6개 × 방식 2개 × 3회 = **108 실행**.
채점 규칙은 2026-10-20 기준선 실험과 같다(`score.py` 머리말). 표의 원본은 `summary.md`, 실행별 값은 `metrics.json` · `e3.json`.

- **A (제안):** 브로커 `find_simulators` → 시뮬레이터 `get_templates → plan_subtasks → validate_answers → build_scenario → get_scenario_status` 에서 멈춘다(확인 · 실행은 사람 몫).
- **B (기준선):** 같은 모델이 실행 도구의 입력 스키마만 보고 호출 인자(`plannedCalls`)를 직접 정한다.
- 사용자 답은 요청마다 정해 둔 대본(`requests.json`)에서 꺼낸다. 대본에 없으면 "기본값으로 해줘".

## 2. 읽는 법

1. **조용한 기본값은 A 가 B 의 약 1/24 이다.** B 는 세 회차 모두 110개 넘게, 사용자가 모르는 값으로 시뮬레이션을 정했다. A 의 14건(세 회차 합)은 모두 사용자에게 "기본값으로 넣었다" 고 알렸고, 확인 화면에도 승인 안 된 기본값(MODEL_DEFAULT)으로 따로 나온다.
   - D6-A-r2 (12건): 브로커 조정 뒤 두 번째 질문 묶음을 건너뛰고 모든 값을 기본값으로 넣었다. 진짜 누락이다.
   - D4-A-r3 (1건): 질문 뒤에 생긴 결정(구역 배정)을 "그 밖 기본값" 답으로 덮었다.
   - P1-A-r2 (1건): 사용자가 "균일 500원" 이라고 답했는데 에이전트가 질문 keys 에 baseFeePer30Min 을 적지 않아 조용한 기본값으로 잡혔다. 채점상의 문제다.
2. **B 의 질적 오류는 A 에 없다.** B 에서는 다음이 나왔다.
   - 범위 밖 값이 그대로 남았다: J5 seeds 200, D5 구역 50, P4 주차장 15곳 · 하루 3만 대.
   - 기본값 없는 결정을 건너뛰었다: J6 적재 몫 3회 모두, J2 1회.
   - 해석 오류가 있었다(J3 · J4 · P4).
   - A 는 같은 요청에서 범위를 알리고 고쳤다(USER_CAPPED). 고칠 수 없는 경우에는 막혔다: D5-A 세 회차 모두 서버가 "3대로 용량 246%" 로 시나리오를 INVALID 로 막았다. 이것이 사용자 질문("3대로 감당되나")의 답이기도 하다.
3. **대가는 질문과 비용이다.**
   - 질문 묶음은 A 가 2.25배다(요청당 2.0 vs 0.9).
   - 모델 호출은 약 4배, 새 입력 토큰은 약 2배, 걸린 시간은 약 2.8배다.
   - 캐시 읽기는 5.5배인데, 대부분 대화가 길어지며 같은 앞부분을 되읽은 것이다.

## 3. A 가 B 보다 못한 곳 — 템플릿이 실행 도구보다 좁다

다음 요청은 B 가 스키마로 바로 표현했고, A 는 브로커 조정이나 템플릿에 막혀 요청을 줄였다.

| 요청 | 사용자 조건 | B | A |
|---|---|---|---|
| D6 | 근무 6시간 | `shiftMinutes=360` 으로 표현 | 템플릿에 결정이 없어 기본 실행으로 대체 |
| J6 | 공식 배출 시간 20~06시 | `dischargeTimeMode=POHANG_ACTUAL` 로 표현 | 브로커가 조건을 빼라고 했고, 템플릿에도 결정이 없다 |
| P6 | 주차장 사이 10분 | `lotSpacingMinutes=10` 으로 표현 | 조건을 뺐다. 브로커는 `changesPurpose=false` 로 표시했지만 실제로는 질문 취지가 사라졌다 |

그 밖에 목적 문장이 카드의 "답할 수 있는 질문" 과 닿지 않아 ADJUST_REQUEST 가 난 요청: D3 · J4 · J5 · J3 · P3("밤").
요청은 그대로인데 브로커 질문이 한 번 늘어난다.

## 4. 주의할 점

- **A 재실행:** 2026-10-22 13:27 에 서버를 다시 띄우면서 메모리에만 있던 시나리오를 잃었다. 그 A 28개를 같은 id 로 다시 돌렸다. 옛 보고 19개는 `runs-superseded/` 에 있다. 시나리오 id 는 설정의 해시라, 같은 설정이면 회차가 달라도 사본 하나를 같이 쓴다(A 51 실행 → 사본 20개).
- **D5-A 3회:** INVALID 라 서버에 시나리오가 남지 않아 품질 지표 채점에서 빠졌다. 질문 · 비용은 포함했다.
- **실행 환경:** 실행은 서브에이전트가 과제 파일을 Read 로 읽고 결과를 Write 로 쓰는 방식이었다. 그래서 B 의 모델 호출 3 가운데 2는 실험 틀의 몫이고, A 에도 같은 2가 들어 있다.
- **3회차 일부:** 3회차는 두 세션에서 나눠 돌렸고, 그 사이 사용량 한도에 한 번 걸렸다. e3 은 두 세션의 기록을 합쳤고, 같은 id 가 둘이면 나중 기록을 쓴다.
- **에이전트가 고른 실험 변수:** 비교 요청이 없는 실행에서도 `build_scenario` 가 실험 변수를 요구해, 에이전트가 한 값짜리 변수를 골랐다(D5 · D6 truckCount, J5 수거 시각, P4 혼잡 프로파일). P4-A-r2 는 "되는 만큼 최대로" 를 주차면 300 으로 해석했고, 이 가정은 사용자에게 알렸다.
- **출력 토큰:** 출력 토큰은 기록이 스트리밍 중간 값을 남겨 보조로만 쓴다.
