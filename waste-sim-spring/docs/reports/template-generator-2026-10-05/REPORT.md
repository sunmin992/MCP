# 서브태스크 템플릿을 시뮬레이터 코드에서 뽑아 손으로 쓴 것과 대조한 기록

2026-10-05 · `feature/simulator-mcp` · 새 모듈 `template-generator` · 전체 테스트 640개 중 637개 통과(스킵 3)

## 왜 만들었나

연구 질문 둘 중 **RQ1 — 시뮬레이션 서비스 제공자가 최소의 노력으로 LLM 기반 시뮬레이션 서비스를
제공한다** 를 재기 위해서다.

이 시스템에서 시뮬레이터마다 새로 써야 하는 것은 서브태스크 템플릿
([`jangnyang-templates.json`](../../../simulator/src/main/resources/ses/jangnyang-templates.json))이다.
서버는 그 파일을 읽어 요청마다 서브태스크를 만들 뿐(5·6단계), 템플릿 자체는 제공자가 시뮬레이터 코드를
읽고 손으로 썼다. 이 손일을 코드에서 얼마나 대신할 수 있는지가 RQ1 의 첫 숫자다.

```
[지금: 제공자가 손으로]         [서버가 요청마다]
 시뮬레이터 코드 ──읽고 씀──▶ 템플릿 JSON ──▶ 서브태스크 생성 ──▶ 질문
        └──── template-generator 가 초안을 쓴다
```

## 무엇을 읽고 무엇을 쓰나

시뮬레이터 클래스를 컴파일 의존성으로 두지 않고 **소스만** 읽는다(JavaParser). 다른 시뮬레이터에도
같은 방식으로 붙이기 위해서다.

| 템플릿 칸 | 읽는 곳 | 규칙 |
|---|---|---|
| 후보 | 설정 클래스 | 세터가 있는 인스턴스 필드 |
| `valueType` | 필드 타입 | `int`→INTEGER · `double`→NUMBER · `List<Integer>`→INTEGER_LIST · enum 으로 해석되는 `String`→ENUM 등 |
| `allowed` | enum 선언 | 필드가 `X.fromName(..)`/`X.valueOf(..)`로 해석되면 X 의 상수 |
| `defaultValue` | 필드 초기값 | 리터럴 · 사칙연산(`20 * 60`) · `Enum.X.name()` |
| `min`/`max` | 검증기 | **오류를 만드는 `if`** 의 "필드 비교 상수". `x < 1`→하한 1, `x <= 0`→0 초과 |
| `unit` | 필드 이름 | `…Minutes`→minute · `…Kg`→kg |
| `question` | Javadoc | 첫 문장(초안) |

모든 값에 뽑아 온 자리(`파일:줄 식`)를 `_extraction.evidence` 로 남기고, 코드만으로 정하지 못한 칸은
`_extraction.needsReview` 에 이유를 적는다. **추측으로 채우지 않는다** — 상수로 풀리지 않는 경계
(`allocated > truckType.capacityKg`)는 비워 두고 식을 넘긴다.

오탐을 막으려고 둔 규칙 셋:

- 게터는 **설정 타입 변수**에서 부를 때만 필드로 본다. 처음엔 분리배출 유형의 `w.getThreshold()` 가
  `threshold` 의 근거로 섞였다.
- 게터는 이름이 아니라 **본문**을 따른다. 검증기가 별칭 `getTruckCount() { return numTrucks; }` 로
  하한을 검사해, 이름 규칙으로는 `numTrucks` 의 하한을 놓쳤다.
- then 쪽이 **바로** 오류를 만드는 `if` 만 센다. 바깥 조건은 범위가 아니라 "이 검사를 할지" 인 경우가 많다.

## 생성 조건 추출 — 엔진이 그 필드를 언제 읽는가

같은 날 이어서 만들었다. 서브태스크의 생성 조건("이 질문을 언제 하는가")을 엔진 코드에서 뽑는다.

### 방법

생성 조건을 **"이 필드는 어떤 설정일 때 결과에 쓰일 수 있는가"** 로 놓았다. 진입점(`SimulationService` 의
public 메서드)에서 닿는 메서드만 훑고, 필드를 읽는 자리마다 감싸는 조건을 모은다.

| 잡는 것 | 예 (장량동) |
|---|---|
| 감싸는 `if`/`else` · 삼항식 · `&&`/`\|\|` 의 앞쪽 | `cfg.isTrafficEnabled() ? trafficData.find(cfg.getTrafficProfileId()) : null` → `trafficEnabled == true` |
| 앞선 조기 탈출 `if (c) return/throw/continue` | `resolveCollectionSlots()` 의 `if (목록이 있으면) return 목록;` 뒤에서만 단일 시각을 읽음 |
| 메서드 사이 — 부르는 자리의 조건을 잇는다 | `zoneProxyHopMinutes()` 는 `mode == ZONE_PROXY_HYBRID` 일 때만 불림 |
| `x = 조건 ? 값 : null` 뒤의 `x != null` | 교통 프로파일 지역 변수 → `trafficEnabled == true` |
| 0 부터 도는 반복 변수에 곱해진 값 | `slot + k * dispatchInterval` → "반복이 두 번 이상 돌아야 함" (실행 조건으로 알림) |

설정 필드로 옮길 수 없는 조건(`route.isEmpty()`, `fromZone.equals(toZone)` …)은 **실행 조건** `?{…}` 로
남기고 "참일 수 있다" 로 읽는다. 그래서 뽑은 조건은 **필요조건**이다 — 안 물어도 될 때 물을 수는 있어도,
물어야 할 때 빠뜨리지 않는 쪽으로 기운다.

만들며 고친 오판 둘:

- **검증기가 막는 설정에서 갈리는 조건.** `RoutePlanner` 는 건물 수가 1~26 을 벗어나면 예외를 던지는데,
  이것 때문에 차량 대수가 "건물 1~26 일 때만" 이라는 조건으로 나왔다(진리표가 건물 0동까지 넣었다).
  진리표를 **검증기에서 뽑은 범위 안**으로 제한해 고쳤다 — 앞 절의 범위 추출이 여기서 쓰인다.
- **결과에 기록만 하는 읽기.** `new SimulationResult(cfg.getCollectionTimeLabel(), …)` 처럼 설정값을 결과에
  그대로 싣는 자리 때문에 단일 수거 시각이 `ALWAYS` 로 나왔다. 진입점이 돌려주는 타입에 값을 **그대로**
  (또는 `.name()` 만 거쳐) 쓰는 읽기는 조건에서 빼고 "(결과 기록)" 으로 표시한다. 계산값을 넣는
  `result.add(fast(cfg))` 는 기록이 아니다.

### 대조

손으로 쓴 조건은 이름(`TRAFFIC_APPLIED`)이라, `GenerateCondition.evaluate` 를 식으로 옮긴
[조건 사전](../../../template-generator/conditions/jangnyang-generate-conditions.json)을 정답지로 두고 진리표로
맞댔다(답변키가 아니라 설정 필드 이름, APPLY → `trafficEnabled == true`).

| 관계 | 16개 중 | 조건부 6개 중 | 뜻 |
|---|---|---|---|
| **같음** | **12** | 2 | 손으로 쓴 조건과 같다 |
| 더 넓음 | 4 | 4 | 필요할 때는 묻지만, 필요 없을 때도 묻는다 |
| **더 좁음** | **0** | 0 | 필요한 질문을 빠뜨린다 |
| 다름 | 0 | 0 | |

`ALWAYS` 10개는 모두 `ALWAYS` 로 나왔다. 조건부 6개를 하나씩 보면:

| 템플릿 | 손으로 쓴 조건 | 뽑은 것 | 왜 |
|---|---|---|---|
| 교통 프로파일 | 교통 반영일 때 | **같음** | 삼항식 |
| 단일 수거 시각 | 시각 목록이 없을 때 | **같음** | 설정 클래스의 조기 반환 |
| 배차 간격 | 실제 운행 2대 이상 | 더 넓음 (ALWAYS) | `k * 간격` — 설정 대신 반복 횟수(`routes.size()`)에 달렸다. 실행 조건으로 정확히 짚었지만, `routes.size()` 가 `min(건물, 차량)` 이라는 것은 `RoutePlanner` 의 계산을 풀어야 안다 |
| 하루 수거 시각 목록 | 사용자가 말했을 때 | 더 넓음 (ALWAYS) | **대화 규칙**이라 코드에 없다. 엔진은 언제나 목록을 먼저 본다 |
| 구역 배정 규칙 | 구역 근사 · 5동 이상 | 더 넓음 | 엔진은 **교통 반영이면 상수 모드에서도** 구역별 혼잡도를 찾는다(`SimulationEngine.java:334`). 아래 참고 |
| 구역 내 이동시간 | 구역 근사 · 5동 이상 · 덩어리 | 더 넓음 (구역 근사일 때) | 나머지 조건은 실행 조건 `fromZone.equals(toZone)` — "같은 구역 안 이동이 생기는가" — 에 숨어 있다 |

**구역 배정 규칙은 손으로 쓴 조건 쪽을 다시 볼 만하다.** 반례는 `구간 상수 · 교통 반영` 이다. 손으로 쓴
조건은 이때 묻지 않지만, 엔진은 혼잡 가중치를 구역별로 찾으므로 배정이 결과에 들어간다 — 엔진 주석도
"상수 모드에서도 혼잡 가중치를 구역별로 찾으므로 배정이 결과에 관여한다"(`SimulationEngine.java:558`) 고
적는다. 손으로 쓴 조건은 "안 정하면 막히는가"(5동부터 이름 폴백이 깨짐)를 기준으로 했고, 뽑은 조건은
"결과에 들어가는가" 를 기준으로 했다. 어느 쪽이 맞는지는 제공자가 정할 일이라 고치지 않았다.

### RQ2 와의 관계

더 넓은 조건은 사용자에게 **질문을 더 하게** 만든다(RQ2 비용). 더 좁은 조건은 필요한 값을 빼먹어
**잘못된 실험**을 돌린다. 이 추출이 더 좁은 쪽으로 틀린 적이 없다는 것은, 제공자가 초안을 그대로 써도
실험이 틀리지는 않고 질문만 몇 개 늘어난다는 뜻이다 — 장량동에서는 최대 4개.

## RQ1 에 대해 이 판이 말하는 것

- 제공자가 템플릿 6칸을 손으로 쓰던 일 중 **값이 있는 칸의 85% 는 코드에서 근거와 함께 나온다.**
  남는 15%는 대부분 선택지를 좁히거나 표현을 바꾸는 **판단**이다.
- **생성 조건 16개 중 12개가 손으로 쓴 것과 같고, 나머지 4개도 필요조건으로 맞다**(빠뜨리는 쪽 0).
  조건부 6개만 보면 2개가 같고, 4개는 제공자가 좁혀야 한다.
- 제공자에게 남는 일은 셋으로 요약된다: ① 40개 후보 중 무엇을 물을지 고르기, ② 더 넓게 나온 생성 조건을
  좁히고 이름 붙이기(대화 규칙 포함), ③ 선택지를 좁히고 질문 문장 다듬기.
- 다음에 숫자를 키울 곳은 **필드 밖 기본값**(2칸)과 **계산을 거친 실행 조건**(배차 간격의 `routes.size()`)이다.

## 한계

- **시뮬레이터 하나**로만 쟀다. 정답지(손으로 쓴 템플릿)를 만든 사람이 같은 코드베이스를 다듬어 온
  사람이라 코드와 템플릿이 잘 맞물려 있다 — 다른 시뮬레이터에서는 일치율이 낮을 수 있다.
- 규칙이 이 코드의 관례(세터 · `fromName` · 오류 객체를 만드는 `if`)에 기대고 있다. 예외를 던지지 않고
  값을 조용히 보정하는 시뮬레이터에서는 범위가 나오지 않는다.
- 일치는 값이 같은지만 본다. 하한이 "이상" 인지 "초과" 인지는 템플릿 형식에 칸이 없어 채점하지 않는다
  (생성기는 `minExclusive` 로 남긴다).
- 생성 조건의 정답지(조건 사전)는 `GenerateCondition` 을 사람이 식으로 옮긴 것이다. 옮기며 틀릴 수 있고,
  보류(UNKNOWN) 상태는 진리표에 없다.
- 생성 조건 추출은 `switch`, 반복문 조건, 예외 흐름, 리플렉션을 따라가지 않는다. 진입점과 엔진 클래스 목록은
  제공자가 준다(`--engine`).

## 재현 방법

```powershell
.\mvnw.cmd -q -pl template-generator -am install -DskipTests
.\mvnw.cmd -q -pl template-generator exec:java
```

결과는 `template-generator/target/` 의 `generated-templates.json` 과 `comparison.md` 다. 이 폴더의 두 파일은
그 실행 결과를 옮긴 것이다. 다른 시뮬레이터에는
`-Dexec.args="--source … --config … --validator … --engine … --out …"` 로 돌린다(`Main` 의 사용법).
`--engine` 을 빼면 생성 조건을 뽑지 않고 모두 `ALWAYS` 로 둔다.
