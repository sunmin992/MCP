# R3. SES와 Java 수기 구성의 변경 비용·일관성 비교

2026-11-03. [해결 설계](../../resolution-design-2026-11-03.md)의 R3 실험이다.
이전 실험([모델 평가](../model-evaluation-2026-11-03/REPORT.md))에서 SES와 같은 규칙을 Java로 짠 대조군은 판정 정확도가 같았다(17/17).
그래서 이번에는 정확도가 아니라 **규칙을 바꿀 때 무엇을 몇 군데 고쳐야 하고, 덜 고치면 무엇이 어긋나는가**를 쟀다.
첫 측정에서 드러난 SES 약점 두 가지를 고친 뒤 같은 실험을 다시 돌려, 개선 전후를 함께 싣는다.

원자료: 개선 전 [results-before.json](results-before.json)·[cases-before.json](../../../simulator/src/test/resources/evaluation/ses-change/cases-before.json),
개선 후 [results.json](results.json)·[cases.json](../../../simulator/src/test/resources/evaluation/ses-change/cases.json). 실행:

```powershell
.\mvnw.cmd -B -pl simulator -am test '-Dtest=SesChangeCostExperiment' '-Dsurefire.failIfNoSpecifiedTests=false'
```

## 설계

**비교 대상**

| 방식 | 규칙이 있는 곳 | 소스 |
|---|---|---|
| SES | `jangnyang-ses.json`의 결정 정의(조건식·범위·질문·설정 필드·카드 칸)와 `task-manifest.json`. 템플릿·카드 요약은 SES에서 파생 | 실제 운영 파일 |
| 수기 구성 | Java 클래스. 결정마다 판정 함수 하나를 두고, 준비 판정·질문·거절·구조 표시·카드·설정 반영·Task 묶음이 같은 함수와 표를 공유 | `ManualConfigurator.java` |

수기 구성은 일부러 엉성하게 짜지 않았다. 규칙을 소비자마다 복사하는 코드가 아니라, 공용 함수를 쓰는 정상적인 설계다.
다룬 범위는 조건부 결정 4개(배차 간격, 교통 프로파일, 구역 배정, 구역 내 이동)다. 항상 생성되는 결정은 두 방식에서 차이가 없어 뺐다.

**변경 사례**

| 사례 | 내용 |
|---|---|
| C1 조건 변경 | 배차 간격이 필요한 실제 운행 차량 수 2대 → 3대 |
| C2 가지 추가 | 구역 근사 이동일 때만 묻는 지점별 정차 시간(새 결정) |
| C3 조건 완화 | 구역 배정을 건물 수와 관계없이 구역 근사 이동이면 묻기 |
| C4 범위 변경 | 배차 간격 최대 1439분 → 120분 |

각 사례를 두 단계로 적용했다.
- **primary:** 규칙 자체만 고침(가장 먼저 떠올리는 한 곳)
- **complete:** 일관성을 위해 함께 고쳐야 하는 곳까지 고침

**측정**
- 비용: 고친 위치 수(SES는 JSON 편집 연산, 수기는 코드 구간), 바뀐 줄 수(추가+삭제), Java 재컴파일 필요 여부
- 일관성: 변경 의도를 Java로 적은 오라클과, 일곱 소비자가 내는 답을 비교해 어긋난 수를 셈. 탐침 입력은 사례당 648개다(건물 수·차량 수·교통·이동 방식·구역 배정·입력 유무 조합).
  소비자: 구조 표시, 준비 판정+질문, 잘못 남은 입력 거절, 범위 거절, 능력 카드 선언, Task 묶음, 설정 반영
- 기준선: 바꾸지 않은 두 방식은 개선 전후 모두 오라클과의 불일치가 0이었다.

드러난 SES 약점:
1. **조건이 서로 이어지지 않았다(C3).** "구역 내 이동" 조건이 "구역 배정" 조건을 참조하지 않고 같은 식을 다시 적어 두었다. 그래서 구역 배정만 고치면 144건이 어긋났다.
2. **카드의 조건 설명·범위·기본값을 손으로 따로 적었다(C1, C4).** 그래서 규칙만 고치면 카드가 예전 내용으로 남았다. 구역 배정·구역 내 이동은 카드에 조건 설명이 아예 없었다.

## 개선

1. **결정 간 조건 참조 `{"active": 답변키}`**: 다른 결정의 활성 여부를 조건에 그대로 쓸 수 있다. 파생 단계(`SesDerivation`)에서 참조한 결정의 조건식으로 펼친다.
   참조하는 결정이 없거나, 항상 생성되는 결정이거나, 서로 순환하면 거절한다. 구역 내 이동 조건을 `{"all": [{"active": "zoneAssignmentRule"}, {"eq": ["zoneAssignmentRule", "CONTIGUOUS"]}]}`로 바꿨다.
   펼친 결과가 손으로 적던 식과 완전히 같아 **파생 템플릿은 한 글자도 바뀌지 않았다**. 실행 시 평가기도 그대로다.
2. **카드 조건 설명·범위·기본값을 결정 정의에서 생성**: 카드의 `generateWhen`은 조건식을 렌더링해 만든다(예: `numBuildings >= 2 && truckCount >= 2`). `range`의 min/max/unit은 결정의 min/max/unit에서, `default`는 `defaultValue`에서 가져온다.
   SES 원본의 카드 칸에 이 값들을 다시 적으면 불러올 때 거절한다. 카드의 사람용 설명(조건 이유, 선택지 설명, 근거)은 그대로 손으로 적는다.

이 개선으로 바뀐 운영 결과는 능력 카드 sesDigest의 표현뿐이다. 조건 설명이 답변키 기준으로 바뀌었다(`min(numBuildings, numTrucks) >= 2` → `numBuildings >= 2 && truckCount >= 2`, `trafficEnabled == true` → `trafficMode == APPLY`).
여기에 수거 시각 조건이 새로 실리고, 교통 프로파일 기본값이 추가됐다. 전체 테스트 918건 중 실패 0건, 스킵 3건이다.

## 해석

- **개선 후 SES는 규칙 한 곳만 고쳐도 모든 소비자가 맞았다(C1, C3, C4).** primary와 complete가 같아졌다. 즉 "함께 고쳐야 할 다른 곳"이 없어졌다.
  수기 구성은 C1·C4에서 여전히 카드를 따로 고쳐야 했다(C1 1곳, C4 2곳 — 디지스트와 브로커 조건 범위).
- **새 결정 추가(C2)는 처음부터 SES가 유리했다.** 결정 정의 하나에 조건·범위·질문·설정 필드가 모여 있어, 그것만 넣어도 준비 판정·질문·범위 거절·설정 반영이 맞았다.
  수기 구성은 판정 함수만 넣으면 324건이 어긋났고, 다 맞추려면 7곳을 고쳐야 했다.
- **결정 간 의존(C3)은 개선 전에는 수기 구성이 나았다.** 함수가 함수를 부르는 구조라 자동으로 맞았기 때문이다. `active` 참조를 넣은 뒤로는 SES도 같아졌다.
- **줄 수는 여전히 SES가 같거나 많다.** JSON이 장황하기 때문이다(C2 complete: SES 23줄, 수기 15줄). JSON 줄과 Java 줄은 단위가 달라 비용 근거로는 약하다.

**결론:** SES의 이점은 정확도가 아니라 **변경 하나가 한 곳에서 끝나고, 그 변경이 코드 수정 없이 질문·검증·카드·설정까지 전파된다**는 데 있다.
첫 측정에서는 SES 안에 중복(카드 칸, 결정 간 조건 복사)이 남아 그 이점이 일부 사례에서만 나타났다. 중복을 없앤 뒤에는 네 사례 모두 한 곳 수정으로 일관성이 유지됐다.

## 남은 중복

- **Task 묶음(`task-manifest.json`):** 새 결정을 어느 Task에 넣을지는 여전히 별도 파일에 적는다(C2 complete의 manifest 편집 1건). 결정 정의에 Task를 적고 manifest를 파생하면 없앨 수 있다.
- **카드 공개 여부:** 결정을 능력 카드에 실으려면 `card` 칸이 있어야 한다(C2 complete의 `card: {}` 1건). 의도적인 선택(무엇을 공개할지)이라 남겼다.
- **카드의 `conditional` 절:** 카드 본문에 사람이 쓴 조건 설명(`"requires": "min(numBuildings, numTrucks) >= 2"`)이 따로 있다. SES 파생 범위 밖이라 이번에 손대지 않았다.

## 한계

- 두 방식, 변경 사례, 정답 규칙을 모두 같은 작성자가 만들었다. 사례는 4개이고 조건부 결정 4개에 한정된다.
- 개선은 1차 측정을 본 뒤 했다. 같은 사례로 다시 쟀으므로, 다른 종류의 변경에서도 같은 효과가 나는지는 별도 사례로 확인해야 한다.
- 수기 구성은 "잘 짠 코드"를 가정했다. 수기 쪽도 카드 설명을 함수에서 생성하도록 고치면 C1·C4의 카드 불일치는 없앨 수 있다. 차이는 그 생성기를 각 시뮬레이터가 따로 짜야 한다는 점이다.
- 개발자가 실제로 얼마나 오래 걸리는지, 실수율이 어떤지 같은 사람 대상 측정은 하지 않았다.
