# R3. SES와 Java 수기 구성의 변경 비용·일관성 비교

2026-11-03. [해결 설계](../../resolution-design-2026-11-03.md)의 R3 실험이다.
이전 실험([모델 평가](../model-evaluation-2026-11-03/REPORT.md))에서 SES와 같은 규칙을 Java로 짠 대조군은 판정 정확도가 같았다(17/17).
그래서 이번에는 정확도가 아니라 **규칙을 바꿀 때 무엇을 몇 군데 고쳐야 하고, 덜 고치면 무엇이 어긋나는가**를 쟀다.

원자료: [results.json](results.json). 실행:

```powershell
.\mvnw.cmd -B -pl simulator -am test '-Dtest=SesChangeCostExperiment' '-Dsurefire.failIfNoSpecifiedTests=false'
```

## 설계

**비교 대상**

| 방식 | 규칙이 있는 곳 | 소스 |
|---|---|---|
| SES | `jangnyang-ses.json`의 결정 정의(조건식·범위·질문·설정 필드·카드 칸)와 `task-manifest.json`. 템플릿·카드 요약은 SES에서 파생 | 실제 운영 파일 |
| 수기 구성 | Java 클래스. 결정마다 판정 함수 하나를 두고, 준비 판정·질문·거절·구조 표시·카드·설정 반영·Task 묶음이 같은 함수와 표를 공유 | `ManualConfigurator.java` |

수기 구성은 일부러 엉성하게 짜지 않았다. 규칙을 소비자마다 복사하는 코드가 아니라, 공용 함수를 쓰는 정상적인 설계다.
다룬 범위는 조건부 결정 4개(배차 간격, 교통 프로파일, 구역 배정, 구역 내 이동)다. 항상 생성되는 결정은 두 방식에서 차이가 없어 뺐다.

**변경 사례** (사례와 적용 방법을 실행 전에 [cases.json](../../../simulator/src/test/resources/evaluation/ses-change/cases.json)·`ManualVariants.java`로 고정)

| 사례 | 내용 |
|---|---|
| C1 조건 변경 | 배차 간격이 필요한 실제 운행 차량 수 2대 → 3대 |
| C2 가지 추가 | 구역 근사 이동일 때만 묻는 지점별 정차 시간(새 결정) |
| C3 조건 완화 | 구역 배정을 건물 수와 관계없이 구역 근사 이동이면 묻기 |
| C4 범위 변경 | 배차 간격 최대 1439분 → 120분 |

각 사례를 두 단계로 적용했다.
- **primary:** 규칙 자체만 고침(가장 먼저 떠올리는 한 곳)
- **complete:** 일관성을 위해 함께 고쳐야 하는 곳까지 고침

**측정**
- 비용: 고친 위치 수(SES는 JSON 편집 연산, 수기는 코드 구간), 바뀐 줄 수(추가+삭제), Java 재컴파일 필요 여부
- 일관성: 변경 의도를 Java로 적은 오라클과, 일곱 소비자가 내는 답을 비교해 어긋난 수를 셈. 탐침 입력은 사례당 648개다(건물 수·차량 수·교통·이동 방식·구역 배정·입력 유무 조합).
  소비자: 구조 표시, 준비 판정+질문, 잘못 남은 입력 거절, 범위 거절, 능력 카드 선언, Task 묶음, 설정 반영
- 기준선: 바꾸지 않은 두 방식은 오라클과의 불일치가 모두 0이었다.

## 해석

**SES가 나은 점**
1. **새 결정 추가(C2):** SES는 결정 정의 하나에 조건·범위·질문·설정 필드가 함께 있다. 그래서 그것만 넣어도(primary) 준비 판정·질문·범위 거절·설정 반영이 바로 맞았다.
   수기 구성은 판정 함수와 등록만 하면 질문 108건, 설정 반영 216건이 어긋났다. 다 맞추려면 7곳을 고쳐야 했다(SES는 2개 파일에서 편집 4번).
2. **코드 변경 없음:** 네 사례 모두 Java 코드를 건드리지 않았다. 평탄화가 `configField`로 설정을 찾아 넣기 때문에, 새 결정도 코드 없이 실행 설정까지 이어진다.

**SES가 못한 점**
1. **조건이 서로 이어지지 않는다(C3):** "구역 내 이동" 조건은 "구역 배정이 활성인가"를 참조하지 않고 같은 조건을 다시 적어 둔다.
   그래서 구역 배정 조건만 고치면 구역 내 이동이 어긋났다(구조 72, 질문 24, 거절 48건). 수기 구성은 `intraActive()`가 `zoneActive()`를 부르므로 한 곳만 고쳐도 맞았다.
2. **카드 조건이 따로 적혀 있다(C1, C4):** 능력 카드의 조건 설명(`"min(numBuildings, numTrucks) >= 2"`)과 범위는 기계용 조건식에서 만들어지지 않고 따로 손으로 적는다.
   그래서 두 방식 모두 규칙만 고치면 카드가 낡은 채로 남았다. 구역 배정·구역 내 이동은 카드에 조건 설명이 아예 없다.
3. **줄 수는 더 많다:** JSON 정의가 장황해서 같은 변경도 바뀐 줄 수는 SES가 같거나 더 많았다(C2 complete 29줄, 수기 15줄). 줄 수는 단위가 다르므로 비용 근거로는 약하다.

**결론:** SES의 이점은 "정확도"가 아니라 **결정 하나에 필요한 정보가 한 곳에 모여 있어, 결정을 추가할 때 코드 수정 없이 모든 소비자에 전파된다**는 데 있다.
반대로 결정 사이의 의존과 카드 설명은 SES 안에서도 중복돼 있어, 지금 구현은 SES가 줄 수 있는 일관성 보장을 다 살리지 못한다.

## 개선하면 SES 주장이 강해지는 두 가지

1. **카드 조건 설명을 조건식에서 생성:** 기계용 조건식을 카드의 설명 문자열로 바꾸면, C1·C4의 카드 불일치가 없어지고 complete에 필요한 편집이 primary 하나로 준다.
2. **조건이 다른 결정의 활성 여부를 참조:** 예를 들어 `{"active": "zoneAssignmentRule"}`를 쓸 수 있게 하면, C3에서 구역 배정 조건만 고쳐도 구역 내 이동이 따라 바뀐다. 수기 구성의 함수 합성과 같은 효과다.

두 가지를 고친 뒤 같은 실험을 다시 돌리면, 개선 전후를 같은 기준으로 비교할 수 있다.

## 한계

- 두 방식과 사례, 오라클을 모두 같은 작성자가 만들었다. 사례는 4개이고 조건부 결정 4개에 한정된다.
- 수기 구성은 "잘 짠 코드"를 가정했다. 규칙을 소비자마다 복사한 코드라면 불일치는 더 커지겠지만 측정하지 않았다.
- SES의 줄 수는 JSON, 수기 구성은 Java 줄이라 직접 비교할 수 없다.
- 개발자가 실제로 얼마나 오래 걸리는지, 실수율이 어떤지 같은 사람 대상 측정은 하지 않았다.
