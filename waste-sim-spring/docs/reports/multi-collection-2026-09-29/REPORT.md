# 하루 수거 횟수 비교 — "지원하지 않는다" 던 질문을 확인 흐름으로 답한 기록

2026-09-29 · 시작 커밋 `1820875` → 끝 커밋 `c01f56a` (`feature/simulator-mcp`) · 전체 테스트 578개 중 575개 통과(스킵 3) · 포트 8089(브로커) · 8090(시뮬레이터)

## 요청

> 한 동네 정도 되는 규모에서 교통량을 반영해서 1대로 하루에 몇 번 수거하는 게 가장 민원이 적은지
> 알고 싶어

채팅 세션의 모델은 **지원하지 않는다**고 답하고, "하루 수거 횟수 템플릿을 추가하고 엔진까지
전달되게 고치자" 고 제안했다.

## 진단 — 엔진은 이미 됐다

모델의 제안은 절반만 맞았다. 엔진 쪽은 전부터 하루 여러 번 수거를 돌렸다.

| 자리 | 상태 |
|---|---|
| `SimulationConfig.collectionTimesMinutes` | 하루 수거 시각 목록. 주석이 `[540,1080]` = 09·18시 |
| `SimulationEngine` → `resolveCollectionSlots()` | 목록이 있으면 그 시각마다 수거한다 |
| `SimulationConfigValidator.validateCollectionTimes` | 각 시각 0~1439, 중복 금지 |
| 능력 카드 | `multiValueField: collectionTimesMinutes` 를 이미 선언 |
| 기존 도구 `run_scenario` · `COLLECTION_SCHEDULE` | "1일 1회 vs 1일 2회(09·18시)" 를 이미 비교한다 — 단 확인 흐름 밖(`confirmed:false`)이고 둘뿐이다 |

막혀 있던 것은 **대화 쪽** 넷이다.

1. 템플릿이 수거 시각 **하나**(`collectionTimeMinutes`)만 받았다. LLM 이 "하루 몇 번" 을 물을 자리가 없었다.
2. `build_scenario` 가 JSON 배열을 `asText()` 로 읽어 **빈 문자열**로 만들었다. 목록이 들어와도 조용히 기본 1회(12시)로 돌았을 것이다. `validate_answers` 도 같은 이유로 "답 없음" 으로 거절했다.
3. 정규화에 정수 목록 타입이 없었다.
4. 평탄화가 `List` 세터를 찾지 못했다.

엔진은 손대지 않았다.

## 고친 것 → `c01f56a`

- **템플릿 `jn.collectionTimes`**(`INTEGER_LIST`, 각 원소 0~1439분). **사용자가 다회 수거를 말했을
  때만** 생성된다(`MULTI_COLLECTION_TIMES_GIVEN`). 목록이 있으면 시각 하나는 묻지 않는다
  (`SINGLE_COLLECTION_TIME`) — 둘 다 받으면 엔진이 목록을 쓰고 시각 하나는 조용히 버려지기
  때문이다. 다회 수거를 말하지 않은 대화는 지금과 똑같이 흐른다.
- **배열을 목록으로** 옮긴다(`JsonValues.plain`, `validate_answers`).
- **정규화**: JSON 배열이나 쉼표 구분을 받는다. 범위·중복을 보고, **순서를 바꾸거나 겹친 값을 지워
  주지 않는다** — 고쳐 주면 사용자가 확인한 것과 다른 목록이 돈다.
- **평탄화**: 목록 세터를 찾고 원소를 정수로 맞춘다. 맞출 수 없으면 거절한다.
- **실행 결과** 행에 `collectionTimesMinutes` 를 싣는다. 빠뜨리면 네 행이 모두
  `collectionTimeMinutes=720` 으로 보여 어느 조건의 결과인지 알 수 없다.

### 횟수마다 몇 시에 — 사람이 확인한다

"하루 몇 번" 을 비교하려면 횟수마다 시각이 정해져야 하고, 그 시각이 결과를 크게 바꾼다(전날 기록:
시각 하나만 바꿔도 27~60건). 세 방식 가운데 **LLM 이 제안하고 사람이 확인 화면에서 승인**하는
쪽을 골랐다. 서버가 하루를 N 등분하면 그 규칙 자체가 숨은 가정이 되고, 조합을 전부 훑으면 2회만
276가지다.

이것이 성립하려면 제안된 시각이 확인 화면에 **"승인하지 않은 기본값"** 으로 떠야 한다. 두 곳을
고쳤다.

- `ScenarioBuilder` 가 실험 변수의 출처를 무조건 `USER` 로 덮었다 → 적혀 온 출처를 지킨다.
- 실험 변수는 값이 여럿이라 기본 PES 에 없고, 그래서 `MODEL_DEFAULT` 로 보내도 경고에 잡히지
  않았다 → 보관 PES 에 비교할 목록을 함께 싣는다. 식별자와 토큰은 builder 가 이미 계산했으므로
  바뀌지 않는다.

확인 화면이 목록의 목록을 `660,660,1380,180,…` 로 뭉개 보였다(`String(array)`). 어디서 한 조건이
끝나는지 읽을 수 없으면 무엇을 승인하는지도 모른다 — 괄호를 살려 `[[660],[660,1380],…]` 로 낸다.
실행 중인 서버에 반영한 뒤 사람이 확인했다.

**조건** — 사용자가 말한 것(`USER`): 차량 1대, 교통량 반영(평일 실측). 모델이 채운 것

**횟수별 시각**. 시각은 전날 민원이 적었던 11시를 공통으로 두고, 배출 직후(07~09 · 13~14시)를 피해
골랐다.

## 결과

| 하루 수거 | 시각 | 평균 민원 (30일 누적) | 차량 가동률 |
|---|---|---|---|
| 1회 | 11 | 26.9 (±4.8) | 59.3% |
| **2회** | 11 · 23 | **0.0** | 30.0% |
| 3회 | 03 · 11 · 19 | 0.0 | 20.0% |
| 4회 | 03 · 11 · 17 · 23 | 0.0 | 15.0% |

- **1회 → 2회는 확실하다.** 시드를 맞춰 짝지으면 −26.9건(95% 구간 ±1.8), 30개 시드 전부에서
  2회가 낮았다.
- **3·4회는 2회와 시드마다 같다.** 2회에서 이미 0 이다.
- **0 이 정확히 나오는 것은 모델 구조상 맞다.** 지점마다 하루 약 22.5kg 이 나오고, 통이 임계
  24kg(용량 30kg × 0.8)을 넘으면 민원이 생긴다. 하루 1회면 가끔 넘고, 2회면 한 번에 쌓이는 양이
  반쯤이라 넘지 않는다.
- **가동률 59% 는 범위 보고서 §9 의 "1대 기준 60%" 와 맞는다.** 9/27 기록이 "3대라 20%" 로
  설명했던 것의 반대편 확인이다.
- **교통량은 이번에도 결론을 가르지 못했다.** 이동시간이 구간 상수다(수거 지점 좌표 0곳).
- 모든 조건에서 미수거 0kg · 질량 보존 오차 0 · 품질 경고 없음 · `notForOperationalUse=true`.

## 한계

- **이 결론은 고른 시각에 달려 있다.** 2회라도 배출 직후(예: 08 · 14시)에 수거하면 달라질 수 있다.
  "나쁜 시각의 2회" 는 돌리지 않았다.
- **운영비가 모델에 없다.** 2회는 운행이 두 배다. 능력 카드도 비용 산출을 미지원으로 적는다 —
  "2회가 최선" 은 민원만 본 결론이다.
- 설정 간 비교이지 운영 예측이 아니다.

## 겪은 것

- **옛 서버가 떠 있었다.** 수정 뒤 띄운 서버가 "포트 사용 중" 으로 못 떴고, 요청은 16:57 에 뜬 옛
  서버(템플릿 14개)가 받아 "템플릿에 없는 답변키" 로 거절했다. 옛 서버와 그 Maven 부모를 끄고 다시
  띄웠다.
- **다시 띄울 때 한 번 오판했다.** 대기 루프가 새 로그가 써지기 전에 전날 실패한 **같은 이름의
  로그 파일**을 읽어 "시뮬레이터가 못 떴다" 고 봤다. 실제로는 정상이었다 — 포트를 가진 프로세스의
  시작 시각과 부모를 대조해 확인했다.
