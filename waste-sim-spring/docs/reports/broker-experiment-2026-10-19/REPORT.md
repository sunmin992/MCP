# 브로커 탐색 · 호출 실험 — 실제 시뮬레이터 서버 3개

2026-10-19 · `feature/simulator-mcp` · 계획: [외부 시뮬레이터 서버 두 개](../../superpowers/plans/2026-10-19-외부-시뮬레이터-서버-두-개.md)

## 무엇을 쟀나

브로커가 **실제로 부를 수 있는 서버 여럿** 가운데서 요청에 맞는 서버를 고르고, LLM 이 그 추천을 따라
그 서버의 서브태스크 흐름을 시나리오 생성(확인 대기)까지 끝까지 가는지.

| 서버 | 프로젝트 | 포트 | 도메인 · 분석 단위 |
|---|---|---|---|
| `jangnyang-waste-sim` | `waste-sim-spring/simulator` | 8090 | 쓰레기 수거 · 원룸촌 한 블록 |
| `bukgu-district-waste-sim` | `district-waste-sim` (별도 프로젝트) | 8091 | 쓰레기 수거 · 행정동 전체(구역 집계) |
| `pohang-parking-sim` | `parking-sim` (별도 프로젝트) | 8092 | 공영주차장 · 도심 한 구역 |
| `district-waste-sim`, `water-leak-sim` | 브로커 후보 파일 | — | 가상(추천되면 안 됨) |

## 방법

- **LLM 역할:** 요청마다 새 에이전트(Claude, 일반 목적) 하나. 아는 것은 브로커 주소와 MCP 호출 스크립트뿐이고,
  저장소 파일 · 코드 · 기대 판정은 주지 않았다([지시문 틀](agent-prompt-template.md)). 12개를 동시에 돌렸다.
- **사용자 역할:** 요청마다 답변 대본([requests.json](requests.json) 의 `userScript`). 에이전트는 질문을 **먼저 기록한 뒤**
  대본에서 답을 찾는다 — 질문 수를 세기 위해서다. 대본에 없으면 "기본값으로 해줘".
- **확인:** 사람만 하므로 에이전트는 `build_scenario` 가 `UNCONFIRMED` 가 되면 멈춘다. 이번 실험은 실행까지 가지 않았다.
- **검증:** 에이전트 보고([runs/](runs/))를 서버 로그와 대조했다 — 브로커 `[4 매칭]` 로그(MCP 세션별)와 각 서버의
  `/api/scenarios` 보관 목록. 세 서버에 남은 시나리오 10개가 보고와 정확히 일치했다(추천받지 않은 서버에 생긴 시나리오 0).

| 추천 준수 — MATCH 뒤 추천 서버를, CHOOSE 뒤 사용자가 고른 서버를 불렀는가 | **10 / 10** |
| 가상 후보를 부른 횟수 | 0 |
| 확인 대기까지 완주 (서버로 간 10개) | **10 / 10**, 값 거절 0 |
| 브로커 재호출 | 2 (R06 · R10 — 둘 다 ADJUST_REQUEST 뒤 고친 요청으로, 안내대로) |
| 사용자에게 물은 질문 묶음 | 평균 1.4 (MATCH 1, CHOOSE 2, ADJUST 뒤 서버로 가면 2~3) |

질문 수는 에이전트가 여러 질문을 한 묶음으로 물은 것을 1회로 센 값이다. 묶음 안의 항목 수는 6~10개였다.

### R10 — 두 도메인이 섞인 요청

"수거차가 공영주차장 주변 골목에 못 들어가 수거가 늦어진다" 는 쓰레기 서버 둘 모두 환경 조건 · 목적이 맞지 않아
ADJUST_REQUEST, 주차 서버는 도메인이 달라 "목적이 바뀜" 으로 나왔다. 사용자가 쓰레기 쪽을 고르자 고친 요청이 CHOOSE 가
됐고, 에이전트는 장량동 카드의 `unsupported`(골목 진입 판정 — 수거 지점 미등록으로 발동 안 함)를 스스로 읽어 차종 비교로
대신하며 그 한계를 사용자에게 알렸다. **브로커는 이 한계를 알려 주지 않았다** — 아래 발견 3.

## 에이전트가 짚은 문제 (보고의 `difficulties`)

같은 지적이 여러 에이전트에서 따로 나온 것을 묶었다. 괄호 안은 지적한 요청.

1. **출처(origin) 규칙이 도구 설명에 없다** (R01 · R02 · R05 · R06 · R07 · R09). 사용자가 "기본값으로 해줘" 라고 답한 값을
   `USER` 로 볼지 `MODEL_DEFAULT` 로 볼지 에이전트마다 달랐다 — R02 는 USER 로 보내 미승인 기본값 0개, 나머지는 MODEL_DEFAULT 로
   보내 5~7개. **확인 화면에 보이는 "미승인 기본값" 수가 LLM 의 해석에 따라 달라진다.**
2. **실험 변수 넣는 법이 설명에 없다** (R01 · R07 · R08 · R09). `values` 에 변수 키를 넣어야 하는지, 어떤 값을 넣는지 모호했다.
   R05 는 변수(차량 1 · 2 · 3대)에 따라 생성 여부가 갈리는 결정(구역 배정)을 한 값으로만 평가할 수 있었다.
3. **환경 조건의 미지원 판정이 부분 문자열에 기댄다** (R10). "골목에 수거차가 못 들어감" 이 장량동 카드의 골목 진입 미지원
   항목에 걸리지 않아 "조건을 빼면 된다" 로만 안내됐다.
4. **장량동은 기본값 없는 값이 빠져도 시나리오가 통과한다** (R10). `routeAvailableCapacityKg` 없이 `build_scenario` 가
   valid 였고 미승인 기본값에도 안 나왔다. 새 두 서버는 같은 경우를 검증기가 막는다(이번 작업에서 넣음).
5. **목록이 둘이라 헷갈린다** (R04 · R05 · R06 · R11 · R12). CHOOSE · ADJUST 응답의 `matches`(가상 후보 포함)와
   `candidates`/`suggestions`(부를 수 있는 서버만)의 관계가 설명에 없다.
6. **대안이 내부 식별자다** (R12). `metric:leftoverKg` 같은 값을 사용자 말로 옮기며 뜻을 추정했다.
7. **장량동 `tools/list` 에 옛 직접 실행 도구가 섞여 있다** (R04). 서브태스크 흐름과 어느 쪽을 먼저 쓸지 안내가 없었다.
8. **규모 경고가 지명과 이어지지 않는다** (R06). "장량동 전체" 를 기본 8구역 × 600세대(4,800세대)로 받아도 경고가 없다.

### 후속 조치 (같은 날)

1번과 4번을 세 서버 모두에서 고쳤다.

- **1번 → 출처 규칙을 도구 설명에 넣었다.** `build_scenario` 설명과 `origins` 스키마에 USER · MODEL_DEFAULT · DERIVED 의
  기준을 적었다("기본값으로" 처럼 값 없이 넘긴 것은 MODEL_DEFAULT). 출처를 적지 않은 값은 USER 가 아니라
  MODEL_DEFAULT 로 보고(확인 화면에 보이는 쪽), 모르는 출처 문자열은 거절한다. `plan_subtasks` 는 출처를 받으면
  싣고, 받지 않으면 비워 둔다(예전에는 항상 USER).
- **4번(과 2번의 일부) → 서브태스크 완결을 서버가 다시 센다.** `ScenarioBuilder` 가 실행 설정마다 실험 변수 값을
  넣은 답변으로 생성 조건을 평가해, 물어야 할 결정이 비었거나 보류된 채면 그 실행을 막는다. 변수에 따라 생기는
  결정(차량 3대일 때의 배차 간격 등)은 그 실행에서만 요구된다.
- 시험: 장량동 559개(새로 8개 — `CompletenessAndOriginTest`), parking-sim 25개, district-waste-sim 22개 통과.
  장량동의 기존 시험 몇 개는 물어야 할 결정이 빠진 PES 로 시나리오를 만들고 있어, 완결된 PES 로 고쳤다.
- 이 실험의 수치(질문 수 · 미승인 기본값 수)는 고치기 **전** 서버에서 잰 것이다.

## 제공자 작업량 (RQ1)

장량동 `simulator` 를 기준으로, 새 프로젝트의 Java 코드(빈 줄 · 주석 · import 제외)를 셌다.

| | parking-sim | district-waste-sim |
|---|---|---|
| 그대로 복사 | 22파일 · 640줄 | 23파일 · 703줄 |
| 복사 후 고침 | 16파일 · 890줄 중 **230줄** 변경 | 16파일 · 849줄 중 **248줄** 변경 |
| 새로 씀 (설정 · 엔진 · 검증기 · 열거형) | 10파일 · **642줄** | 10파일 · **604줄** |
| 템플릿 + 능력 카드 JSON | 237줄 | 244줄 |
| 그 밖 자료 | 혼잡 프로파일 2 (가정값) | 공휴일 달력, 포항 북구 수거 일정 (실자료) |

고친 230~248줄 가운데 큰 몫은 실행 도구(`run_scenario_by_token`, 약 125줄)와 생성 조건(약 25줄)이다 — 결과 필드와 규칙이
도메인마다 다르다. 나머지는 패키지 · 리소스 경로 · 예시 문자열 · 포트다. district-waste-sim 은 parking-sim 을 복사했으며,
결합 조건 변환을 필드 이름 대신 허용값(APPLY/IGNORE)으로 일반화했다(`PesFlattener.isApplyIgnore`).

**정리:** 같은 MCP 흐름을 가진 새 시뮬레이터 서버 하나에 제공자가 새로 쓴 것은 Java 약 600줄 + 흐름 고침 약 240줄 + JSON
약 240줄이다. 공통 흐름 약 1,300줄은 복사로 왔다 — 라이브러리로 묶으면 이 몫은 0 이 된다.

## 한계

- **LLM 하나:** 모든 에이전트가 같은 모델이다. 다른 모델 · 사람 사용자에서의 준수율은 재지 않았다.
- **대본 사용자:** 사용자는 미리 쓴 대본으로 답했다. 실제 사용자는 더 모호하게 답하고 질문이 늘 수 있다.
- **확인 · 실행 안 함:** 10개 시나리오가 확인 대기로 남았다. 실행 결과의 해석 품질은 이번 지표에 없다.
- **요청 12개:** 판정 종류마다 1~6개다. 통계적 주장이 아니라 동작 확인이다.
- **NONE 은 나올 수 없다:** 다른 도메인에 실제 서버가 있으면 도메인 밖 제안이 생겨 ADJUST_REQUEST 가 된다(R11).
- **서버 등록 잔존:** 미리보기에서 서버를 끄면 강제 종료라 등록 해제가 나가지 않는다. 실험은 네 서버를 모두 띄운 상태에서
  브로커 목록을 확인한 뒤 시작했다.
