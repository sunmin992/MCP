# V3 실험 — 다단계 매칭 · SES 원본 · 판정 기록을 넣은 뒤 다시 잰 결과

2026-11-03. V2(2026-10-21) 제안 방식(A)과 같은 요청 18개 × 3회 = 54회를 새 시스템으로 다시 돌리고, 판정별 요청 10개(판정 세트, 1회씩)를 더했다. 모두 64회.

- **같은 것:** 실행 방법(서브에이전트가 LLM 비서 역할로 MCP 를 직접 부름, 모델 claude-opus-5-5), 요청 문장, 사용자 답변 대본, 생성(UNCONFIRMED)에서 멈춤, 채점 규칙(`score.py`).
- **바뀐 것:** 브로커 다단계 매칭(matchId · 고친 조회 · 판정 4종), 생성 조건 식 · 3값 논리, SES 원본과 PES 가지 검사, 서브태스크 판정 기록(planId), 템플릿이 V2 뒤에 늘어난 결정(장량동 `binCapacityKg`·`complaintThreshold`·`dischargeTimeMode`, 북구 `shiftMinutes`, 주차 `lotSpacingMinutes`).
- **결과 지시문에 더한 칸:** brokerCalls 의 `matchId` · `round`, `planIds`. 나머지 지시문은 V2 와 한 글자도 다르지 않다.

파일: `requests.json`(V2 요청 + 판정 세트 S1~S10), `agent-prompt-A.md`, `prompts/`, `runs/`(실행별 결과), `scenarios/`, `schemas/`(실험 시점 템플릿), `plan-history/`(판정 기록 원본 JSONL), `metrics.json` · `metrics-v2keys.json`, `plan-history.json` · `plan-history.md`, `e3.json`.

다시 재기: `python score.py`, `V2KEYS=1 python score.py`(V2 때 있던 결정만 센다), `python plan_history.py plan-history`, `python e3.py <subagents 폴더>`.

## 2. 브로커 다단계 매칭

V2 요청 54회: 첫 조회 판정 MATCH 30 · ADJUST_REQUEST 21 · CHOOSE 3. **54회 모두 기대 서버에 닿았다.** ADJUST_REQUEST 21회는 전부 고친 조회 1번으로 MATCH 가 됐다(`ADJUST_REQUEST→MATCH`).

판정 세트(실제 LLM 대화에서 각 판정이 나오는지와 그 뒤 행동):

| 요청 | 기대 | 실제 | 그 뒤 |
|---|---|---|---|
| S1 창구 수 | MATCH | MATCH(민원 창구) | 대기 한도에 기본값이 없는데 대본이 값을 주지 않아 INVALID — 대본 결함 |
| S2 공휴일 · 차량 수 | CHOOSE | CHOOSE(북구 · 장량동) | differences 를 보여 주고 북구를 고름. 공휴일 처리에 기본값이 없어 멈춤 — 대본 결함 |
| S3 차량 몇 대 | CHOOSE | CHOOSE | 장량동을 고르고 UNCONFIRMED |
| S4 장량동 전체 + 교통 | ADJUST | ADJUST→MATCH | 한 블록으로 줄여 targetServerId 로 재조회, UNCONFIRMED |
| S5 비용 | ADJUST | ADJUST→MATCH | 목적을 완료 시각으로 바꿈, UNCONFIRMED |
| S6 노인 | ADJUST | ADJUST→MATCH | 거주민을 주부로 바꿈, UNCONFIRMED |
| S7 시내버스 | ADJUST | ADJUST(다른 도메인 4곳, 목적 바뀜) | 사용자가 그만둠 |
| S8 음식물 | ADJUST 기대 | **MATCH(장량동)** | 장량동 카드가 음식물을 못 한다고 적지 않았다. 템플릿에 수거 요일 결정도 없어 진행 불가 — 3-3 |
| S9 조건 그대로 반복 | NONE(한도) | ADJUST ×3 | 에이전트가 세 번째에서 "같은 조건으로는 더 찾을 수 없다" 며 스스로 멈춤 — 한도(5)에 닿기 전에 끝남 |
| S10 서버 모두 끔 | NONE | **NONE(NO_CALLABLE_SERVER)** | "모두 응답하지 않는다, 다시 켜지면 같은 요청으로" 를 그대로 전함 |

## 3. 실험에서 드러난 시스템 결함 (중요한 순서)

1. **PES 가지 검사가 비교 실험의 onlyFor 결정을 막는다(장량동, 이번 작업에서 생긴 결함).** J3 은 차량 1대 대 2대 비교에 배차 간격 10분(USER)을 준다. `build_scenario` 의 values 는 모든 실행 설정에 공통이라 넣으면 1대 쪽이 "가지친 쪽의 값"(branchBlocks)으로, 빼면 2대 쪽이 "물어야 할 결정"(blocks)으로 막힌다. 3회 모두 막혔고(r1 은 시나리오를 둘로 쪼개 우회, r2 · r3 은 INVALID). 같은 꼴이라도 값이 MODEL_DEFAULT 면 빠지고 통과한다(S3 · S5). 고칠 곳: USER · DERIVED 값도 가지친 실행 설정에서는 막지 말고 빼야 한다(`plan_subtasks` 의 onlyFor 와 같은 판단).
2. **장량동 시뮬레이터 응답이 JSON 을 두 번 감싼다(원래 있던 결함).** `McpController.toCallResult` 가 이미 문자열인 결과를 다시 직렬화한다. 다른 서버는 그렇지 않다. 에이전트 다수가 "읽기 번거롭다" 고 적었다.
3. **장량동 카드와 템플릿이 어긋난다.** 카드는 음식물을 못 한다고 적지 않고(S8 이 MATCH), 답할 수 있는 질문에 수거 요일(`collection-days`)을 적었지만 시나리오 템플릿에는 요일 결정이 없다. `plan_subtasks` 는 없는 `variableAnswerKey` 를 조용히 받고 `validate_answers` 에서야 UNKNOWN_ANSWER_KEY 로 막았다.
4. **기본값 동의 근거 거절이 잦다.** V2 요청 54회의 거절 60건(V2 는 18건) 가운데 33건이 근거 검사(GUARD) — 조건부 결정에 기본값을 쓸 때 "기본값으로 해줘" 를 evidence 로 넣어야 한다는 것을 에이전트가 첫 생성 거절에서야 알았다(세 서버 공통). 도구 설명이 "조건부 결정에 기본값을 쓸 때" 라고만 하고 어느 키가 조건부인지 `plan_subtasks` 응답이 짚지 않는다. 한글 표현을 enum 으로 옮긴 값이 `guardUnverified` 로 남는 이유도 설명되지 않는다.
5. **브로커 목적 대조가 문구에 민감하다.** ADJUST_REQUEST 21회 가운데 다수가 목적 문구(예: "쓰레기가 얼마나 쌓일지", "6시 대 9시 중 어느 쪽이 나은지")가 카드 질문 표와 글이 달라 생긴 것이다. 고친 조회 1번으로 모두 풀렸지만 질문 한 차례가 늘었다. 또 첫 응답 조정이 `changesPurpose=false` 인데 고친 조회의 `round.purposeChanged=true` 로 나오는 일이 P3 · J5 에서 있었다.

## 4. 판정 기록(plan-history)

planId 를 받는 서버는 장량동뿐이다(북구 · 주차 · 창구는 다른 저장소). 그래서 판정 기록은 장량동으로 간 23회에만 있다.

| 지표 | 값 |
|---|---|
| 완료에 닿은 실행 | 22 / 23 (S8 은 요일 결정이 없어 완료 전에 멈춤) |
| 평균 단계 / 평균 완료 단계 | 2.22 / 2.27 |
| 평균 최소 필요 단계 | 1.55 |
| 최소 단계에 끝난 실행 | 6 / 22 |
| 브로커 matchId 가 이어진 실행 | 23 / 23 |
| 마지막 판정 FILLED 의 근거 표시 | VERIFIED 100 · UNVERIFIED 15 · NOT_CHECKED 211 |
| 단계 중 붙은 UNFILLED 사유 | NO_EVIDENCE 11 · OUT_OF_RANGE 3 |

- **완료 단계가 최소보다 1 많은 실행(16회)** 은 대부분 첫 `plan_subtasks` 를 답 없이 불러 무엇을 물을지 보는 탐색 호출 때문이다(J2 · J4 · J5 · J6 의 최소 1, 완료 2). 질문이 늘어난 것이 아니다. 최소 단계는 "답이 오는 차례" 를 세므로, 평가에서 이 탐색 호출을 따로 볼지 정해야 한다.
- OUT_OF_RANGE 3건은 J5 의 반복 200회다. V2 에서는 생성 단계에서 막혔는데 V3 에서는 `plan_subtasks` 단계에서 사유와 함께 UNFILLED 로 나왔다.
- NO_EVIDENCE 11건은 조건부 결정(교통 프로파일 · 수거 시각 등)에 기본값을 동의 구절 없이 넣은 경우다 — 3-4 와 같은 원인.

## 6. 실험 전제와 한계

- V3 와 V2 는 같은 모델 · 같은 지시문이지만 다른 날 · 다른 세션이다. 회차 3번이라 편차는 범위로만 보인다.
- 반복 시행을 회차 단위로 묶었지만(1회차 → 2회차 → 3회차) 한 회차 안에서는 서로 다른 요청을 동시에 돌렸다. S3 와 S5 는 설정이 같아 같은 시나리오 id(`scn-c44e6212`)를 받았다 — 생성에서 멈추므로 결과에는 영향이 없다.
- J3-r1 은 시나리오 id 를 둘 적었다. 채점은 2대 쪽(`scn-742ca33f`)으로 했고 원문은 `scenarioIdRaw` 에 남겼다.
- 실험 중(11:57~13:36) 다른 세션이 같은 작업 트리의 네 서버 코드(Pes · ScenarioStore · BuildScenarioTool · confirm.html 등)를 고쳤다. 서버는 그 전(11:38~11:39)에 한 번 떠서 다시 시작하지 않았고 devtools 도 없으므로 실험은 시작 시점 코드로 돌았다고 본다. 다만 처음 쓰일 때 읽히는 클래스가 그 사이 다시 컴파일됐을 가능성은 배제하지 못한다.
- 판정 세트 S1 · S2 의 대본이 기본값 없는 결정(대기 한도 · 공휴일 처리)에 값을 주지 않았다. 시스템은 의도대로 대신 채우지 않고 멈췄다.
