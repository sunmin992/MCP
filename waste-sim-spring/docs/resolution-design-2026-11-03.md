## 1. 현재 상태와 남은 질문

교수님이 다음 미팅에서 답을 요구한 질문은 세 개다. 지금 각 질문에 대해 가진 증거와 빠진 증거는 다음과 같다.

| 질문 | 가진 증거 | 빠진 증거 | 해결 단계 |
|---|---|---|---|
| 어떻게 판단하는가 | 규칙 비교 기준, 정답 입력 24/24 후보 일치 | 실제 LLM 추출 정확도, LLM 오류를 서버가 잡는 비율 | R1 |
| 어떻게 자동 구성하는가 | 임의 지역명 → 가상 블록 → 승인 → 실행 | 임의 지역의 실제 데이터를 자동으로 찾아 입력이 달라지는 사례 | R2 |
| 제안 구조가 왜 필요한가 | 고정 프리셋 대비 오판정 5→0건 | 같은 규칙의 수기 구현 대비 SES의 이점 | R3 |
| (항목 7·8) 역할과 서버 분리 | 구현은 분리됨 | 사용자/제공자 사전 정의 범위, 분리 이유의 논리 | R4 |
| (항목 9·10) 선행연구·논문 | 없음 | 관련 연구 비교표, 논문 그림 | R5 |

진행 순서: R2와 R1은 서로 의존하지 않으므로 병행한다. R3은 R2의 지역 데이터 묶음을 변경 사례로 재사용한다.
R4·R5는 R1~R3의 결과 수치를 받아 문서로 정리한다.

## 2. R1. LLM 판단의 신뢰성: "어떤 LLM이어도 서버가 잡는다"

### 주장 재정의

LLM이 항상 옳게 추출한다고 주장하지 않는다. 주장은 두 개로 나눈다.

1. **추출 정확도:** 모델별로 발화에서 조건을 얼마나 정확히 뽑는가. 모델에 따라 다를 수 있다는 것을 숫자로 보인다.
2. **오류 차단율:** LLM이 틀린 조건을 냈을 때, 서버의 규칙 비교·Task 검증·실행 설정 대조가 잘못된 실행을 얼마나 막는가.
   이것이 연구 기여다. 모델 간 정확도 차이가 있어도 잘못된 실행은 일정하게 낮아야 한다.

### 작업

1. 실행기 다중 모델화: `scripts/run_requirement_model_evaluation.py`의 호출부를 제공자 어댑터로 분리한다.
   최소 세 모델: 상용 모델 두 곳(서로 다른 회사) + 로컬 오픈 모델 하나. temperature=0, 3회 반복.
   키는 환경 변수에서만 읽는다. 크레딧 부족이면 기존처럼 첫 호출에서 중단하고 미측정으로 기록한다.
2. 정답 집합 확장: 24개 → 60개 내외. 애매한 발화(지역만 있음, 단위 혼동, 선호/필수 혼동)를 늘린다.
   연구실 동료 한 명이 독립적으로 라벨을 달아 일치도(Cohen's kappa)를 보고한다. 작성자 혼자 만든 정답이라는 약점을 줄인다.
3. 오류 주입 실험: 정답 프로필에 체계적 오류(기간 단위 바꿈, 해상도와 기간 혼동, 필수→선호 강등, 지역 누락, 지표 누락)를
   주입해 브로커→구성→검증 경로를 끝까지 통과시킨다. 실제 LLM 오류와 합쳐 다음을 센다.
   - 잡힘: 불충족/정보 부족/NEEDS_INPUT/설정 불일치로 실행 전 차단 또는 질문
   - 놓침: 요구와 다른 설정이 READY로 통과
   - 무해: 오류가 있지만 실행 설정과 결과에 영향 없음

### 산출물과 완료 기준

- `docs/reports/llm-robustness-<날짜>/`: 모델별 추출 정확도, 반복 변동, 오류 유형별 차단율 표
- 완료 기준: 모델 셋 이상의 실측값, 놓친 오류 사례 전부에 대한 원인 분류. 놓친 사례가 있으면 그대로 보고하고 규칙 보완 후보로 남긴다.

## 3. R2. 임의 지역의 실제 데이터로 시나리오 자동 구성

상태: 구현 완료(2026-11-03). 결과: [지역명 자동 구성 실험](reports/region-resolution-2026-11-03/REPORT.md).

### 목표

"덕명동"은 예시일 뿐이다. 사용자가 **어느 동네 이름을 말해도**, 사람이 그 지역 데이터를 미리 넣어 두지 않은 상태에서
시스템이 공개 지리 데이터를 찾아 그 지역의 블록 시나리오를 만들고 실행해야 한다.
지금의 가상 블록(이름표만 바뀜)은 데이터를 못 구했을 때의 마지막 대안으로 내린다.

### 범위 결정

- 현재 블록 모델은 건물 26개 상한이다. 동 전체가 아니라 **그 동 안의 실제 주거 블록 하나**를 자동으로 골라 구성한다.
  사용자가 위치(예: "한밭대 근처")를 말하면 그 주변, 말하지 않으면 동 안에서 주거 건물이 가장 밀집한 블록을 고른다.
- 자동 수집은 **키 없이 쓸 수 있는 OpenStreetMap 계열**을 기본으로 한다. 공공데이터포털 같은 키가 필요한 출처는
  키가 설정된 경우에만 보강용으로 쓴다. 출처가 없다고 실행이 막히지 않게 단계별 대안을 둔다.
- "동 전체 예측"이나 실측 민원 재현은 주장하지 않는다. "그 지역의 실제 건물 배치와 도로로 입력이 바뀌고, 각 값의 출처가 끝까지 남는다"를 보인다.

### 자동 구성 파이프라인

`create_neighborhood_scenario`가 지역명을 받으면 다음 순서로 진행한다. 각 단계의 결과는 지역 데이터 묶음에 출처와 함께 쌓인다.

| 단계 | 하는 일 | 데이터 출처 | 실패하면 |
|---|---|---|---|
| 1. 지역 확정 | 지역명 → 행정구역 후보 | Nominatim 지오코딩 (OSM 행정 경계) | 후보 0개: 가상 블록으로 내림 |
| 2. 동명이인 처리 | "중앙동"처럼 여러 시·구에 있으면 후보 목록 반환 | 1단계 결과 | NEEDS_INPUT으로 사용자에게 시·구 질문 |
| 3. 블록 선택 | 경계 안 주거 건물을 모아 밀집 구역 하나 선택 (최대 26동) | Overpass API: building=* | 주거 건물 부족: 가상 블록으로 내림 |
| 4. 건물 속성 | 건물별 좌표, 층수, 면적 → 세대수·거주민 추정 | OSM building:levels·면적, 행정동 인구 통계(키 있으면) | 추정값으로 채우고 ESTIMATED 표시 |
| 5. 수거 지점·이동 | 건물 간·차고지 간 도로 이동 시간 | OSM 도로망 + 기존 OsrmRouteService | 직선 거리 × 보정 계수, ESTIMATED 표시 |
| 6. 배출 정책 | 배출 요일·시간대 | 자동 수집 불가 → 공통 기본값 | 항상 ASSUMED로 표시하고 확인 화면에서 수정 가능 |

수집한 묶음은 `data/regions/<지역 ID>/`에 원본 응답, 조회 시각, 라이선스(ODbL), 파일 해시와 함께 캐시한다.
같은 지역을 다시 요청하면 캐시를 쓰고, 묶음 해시가 시나리오에 기록되므로 같은 결과를 재현할 수 있다.

### 출처 등급

모든 입력값에 출처 등급을 붙인다. 확인 화면, 상태 조회, 실행 결과에 그대로 보인다.

| 등급 | 의미 | 예 |
|---|---|---|
| OBSERVED | 공개 데이터에서 직접 가져옴 | 건물 좌표, 도로 이동 시간 |
| ESTIMATED | 공개 데이터에서 규칙으로 계산 | 층수·면적 → 세대수 |
| ASSUMED | 데이터 없음, 공통 기본값 | 배출 시간대 |
| USER | 사용자가 지정 | 차량 수, 기간 |

데이터 확보 정도를 나타내는 등급도 카드와 결과에 남긴다: `REAL_BLOCK`(1~5단계 성공), `PARTIAL_BLOCK`(일부 추정), `ASSUMED_BLOCK`(지금의 가상 블록).

### 작업

1. `RegionDataResolver`(simulator): 위 1~6단계. 외부 호출은 Nominatim 이용 정책(초당 1회, User-Agent 명시)을 지키고, 타임아웃이 나면 다음 대안으로 넘어간다.
2. `RegionCatalog` 확장: 장량동처럼 사람이 등록한 지역 → 캐시된 자동 수집 묶음 → 새로 수집 → 가상 블록 순으로 찾는다.
3. 지역 데이터 검증 Task 확장: 건물 수 상한, 좌표가 경계 안, 이동 행렬 결측·비대칭, 해시 일치, ESTIMATED/ASSUMED 비율.
   비율이 기준을 넘으면 실행은 허용하되 확인 화면에 경고를 띄운다.
4. 브로커 카드: 임의 지역 요청은 CONDITIONAL("공개 데이터로 블록 구성 시도")로 응답하고, 실제 데이터 확보 등급은 구성 후 시뮬레이터가 확정한다.
5. 테스트: 외부 API는 녹화한 응답으로 대체해 결정적으로 돌린다. 실제 네트워크 호출 시연은 별도 스크립트로 한다.

### 실험

1. **일반화:** 사전에 등록하지 않은 지역 10곳 이상(대도시 아파트 단지, 구도심 주택가, 원룸촌, 농촌 읍·면, 동명이인 지역 포함)을
   이름만으로 요청한다. 등급별(REAL/PARTIAL/ASSUMED/질문) 결과 수와 실패 원인을 보고한다.
2. **입력·결과 차이:** 같은 발화 "OO동 이틀 동안 민원 수 비교해줘"를 여러 지역에 실행해, 건물 수·거주민·이동 시간이
   어디서 왔는지와 같은 시드에서 지표가 어떻게 달라지는지 비교한다. 같은 지역의 가상 블록과 실데이터 블록도 비교한다.
3. **차단:** 수집 묶음의 일부를 빼거나 손상시켰을 때 검증 Task가 실행을 막거나 경고하는지 확인한다.

### 완료 기준

- 등록하지 않은 지역 이름만으로 자동 수집 → 구성 → 검증 → 승인 → 실행이 끝까지 되고, 실험 1의 지역 중 다수가 REAL 또는 PARTIAL이다.
- 모든 입력값에 출처 등급이 붙고, 실행 결과에 지역 데이터 묶음 ID·해시·조회 시각이 남는다.
- 동명이인은 추측하지 않고 질문한다.
- 결과는 "그 지역 실제 블록 배치에 기반한 가정적 수거 운영 비교"로만 서술한다. 실측 민원과 비교하는 모델 타당성 검증은 범위 밖이며 그렇게 적는다.

## 4. R3. SES가 필요한 이유: 정확도가 아니라 변경 비용과 일관성

### 주장 재정의

17개 사례에서 수기 규칙과 SES가 같은 정확도를 냈다. 따라서 "SES가 더 정확하다"는 주장은 버린다.
대신 **구성 지식이 한 곳(SES·Task 명세)에 있어서, 변경할 때 코드 수정 없이 검증·질문·카드·확인 화면이 함께 바뀐다**를 주장하고 측정한다.

### 실험 설계

같은 변경 요청을 두 방식(FIXED_WITH_MANUAL_RULES, SES)에 각각 적용하고 비용과 누락을 센다.

| 변경 사례 | 내용 |
|---|---|
| C1 데이터 출처 추가 | R2 파이프라인에 새 출처 하나(예: 건축물대장 세대수)를 추가 |
| C2 가지 추가 | 새 이동 시간 모델 가지 하나와 그 입력 의존성 |
| C3 조건 변경 | 배차 간격이 필요한 차량 수 조건을 2대 → 3대 |
| C4 제약 추가 | 배출 시간대 밖 수거 금지 같은 정책 입력 |
| C5 결정 제거 | 구역 배정 결정을 고정값으로 바꿈 |

측정:
- 수정한 파일 수·줄 수, Java 코드 수정 여부(명세만 바뀌는가)
- 일관성 누락: 변경 후 검증기·질문 생성·능력 카드·확인 화면 중 바뀌지 않은 곳의 수.
  수기 방식에서는 규칙이 여러 곳에 흩어져 있어 누락이 생길 수 있는지, SES 방식에서는 0인지 확인한다.
- 변경 후 R3 기존 17개 사례 + 변경별 신규 사례의 판정 일치

### 공정성

- 수기 방식의 변경은 SES 변경을 보기 전에 먼저 구현한다. 순서를 기록한다.
- SES 쪽에서 엔진 코드를 고쳐야 하는 변경(C2 가능성)이 나오면 그대로 보고한다. SES가 모든 변경을 명세로 흡수한다고 미리 가정하지 않는다.
- 결과가 차이 없음으로 나오면, SES의 근거는 "제공자 간 공통 명세 형식(브로커가 읽을 수 있음)"으로 한정해 서술한다.

### 추가: 요청별로 실제로 선택되는 것

교수님 질문 "모든 구성이 정해져 있으면 SES로 무엇을 선택하나"에 답하는 표를 만든다.
R1·R2의 실행 사례마다 SES의 어떤 결정(이동 모델, 배차 방식, 구역 배정, 차량 구성)이 요청에 따라 어떤 값으로 선택됐는지,
그 선택이 사용자 입력/지역 데이터/기본값 중 어디서 왔는지를 기록한다. 이 표가 없으면 "고정 구성에 매개변수만 바꿨다"는 지적을 다시 받는다.

## 5. R4. 역할 분리와 서버 분리 근거 (항목 7·8)

문서 `docs/specifications/roles-and-boundaries.md`:

1. 역할표: 사용자 / 클라이언트 LLM / 브로커 / 시뮬레이터 제공자 / 시스템 개발자가 각각
   무엇을 알아야 하고, 무엇을 미리 정의하며, 무엇을 판정하는지.
   - 사용자: 목적, 지역, 기간, 보고 싶은 지표만. 구조·입력 의존성은 몰라도 된다.
   - 제공자: 능력 카드, SES, Task 명세, 지역 데이터 어댑터, 검증 함수를 사전 정의한다.
   - "사용자가 몰라도 된다"는 "아무도 정의하지 않아도 된다"가 아님을 명시해 목표와 구현의 모순을 해소한다.
2. 자동 처리 / 질문 / 거절 경계: 어떤 조건에서 기본값으로 채우고, 질문하고, 실행을 막는지 결정 표로 정리한다.
3. 서버 분리 근거를 요구사항에서 도출: 제공자가 여럿이고 독립 배포된다 → 후보 비교는 제공자 밖에 있어야 한다 →
   브로커는 카드만 보고 상세 입력·데이터는 제공자가 가진다. 실제로 네 제공자 사례와 R1의 선택 결과로 뒷받침한다.

## 6. R5. 선행연구와 논문 그림 (항목 9·10)

관련 연구를 네 축으로 조사하고, 축마다 3~4쪽 세미나 자료를 만든다.

| 축 | 볼 내용 | 비교할 점 |
|---|---|---|
| SES/PES·모델 구성 | DEVS 기반 SES 프루닝, 모델 베이스 구성 연구 | 구성 선택을 누가 하는가(전문가 vs 요청 기반) |
| 시뮬레이션 상호운용·서비스화 | HLA, BOM, 시뮬레이션 서비스/카탈로그 | 능력 명세와 탐색 방식 |
| LLM 기반 시뮬레이션 구성 | LLM이 시뮬레이션 설정·코드를 생성하는 연구 | 검증 없이 생성 vs 서버 검증 |
| LLM 도구 선택·MCP | 도구 검색·선택, MCP 서버 구성 | 기능 설명 기반 선택 vs 능력 조건 비교 |

선행연구 목록은 실제로 읽은 문헌만 넣는다. 각 축에서 R1~R3의 실험이 어떤 기존 한계에 대응하는지 한 줄씩 연결한다.

논문 그림 (각각 실제 실행 기록에서 값을 가져와 그린다):
1. 전체 구조도: 사용자–LLM–브로커–제공자 4곳–데이터 묶음
2. 판정 흐름도: 요청 → 구조화 → 조건별 판정 → Task 검증 → 승인 → 실행 → 추적
3. SES → PES 도출 예시: 등록되지 않은 지역 요청에서 선택된 가지와 각 값의 출처 등급 표시
4. 오류 차단 그림: R1의 오류 유형별 차단 위치
