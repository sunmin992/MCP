# 외부 시뮬레이터 서버 두 개 — 브로커 탐색·호출 실험

2026-10-19 · 상태: **계획 (승인 전)**

## 0. 목표

브로커가 **실제로 부를 수 있는 서버 여럿** 가운데서 사용자 요청에 맞는 서버를 고르고, LLM 이 그 서버를
끝까지(템플릿 → 서브태스크 → 시나리오 → 확인 → 실행) 부를 수 있는지를 실험한다.

지금 브로커가 아는 실제 서버는 장량동 하나뿐이고, 나머지 둘(`district-waste-sim`, `water-leak-sim`)은
지어낸 후보라 추천되지 않는다. 그래서 MATCH 는 늘 장량동이고, CHOOSE 는 실제 서버 사이에서 한 번도
나온 적이 없다.

| | 서버 A | 서버 B |
|---|---|---|
| 축 | 같은 도메인 · **다른 규모** | **다른 도메인** |
| 이름 | 포항 북구 행정동 생활폐기물 수거 시뮬레이터 | 포항 공영주차장 탐색·혼잡 시뮬레이터 |
| `serverId` | `bukgu-district-waste-sim` | `pohang-parking-sim` |
| 도메인 | `waste-collection` | `public-parking` |
| 분석 단위 | `district` — 행정동 전체 | `area` — 도심 한 구역의 공영주차장 묶음 |
| 프로젝트 | `C:\Dev\MCP\district-waste-sim` | `C:\Dev\MCP\parking-sim` |
| 포트 | 8091 | 8092 |

### 결정된 것 (2026-10-19 사용자)

- `waste-sim-spring` 의 모듈이 아니라 **별도 스프링 프로젝트**로 만든다. 현재 시스템은 MCP 로만 부른다.
- 두 서버 모두 장량동과 **같은 도구 이름 6개**를 쓴다.
- 두 서버 모두 기동 시 **브로커에 카드를 등록**하고 종료 시 해제한다.
- 서버 B 의 도메인은 **공영주차장 검색과 혼잡도**.

### 하지 않는 것

- 장량동 서버 코드는 건드리지 않는다.
- 브로커 코드는 원칙적으로 건드리지 않는다(§6.3 의 열린 결정 하나만 예외 후보).
- 지어낸 후보 카드 두 장은 지우지 않는다 — `serverId` 를 겹치지 않게 지어 둘 다 남긴다
  (브로커가 후보 파일과 같은 id 의 등록을 거절한다, `CandidateRegistry.java:170`).

## 1. 공통 계약 — 새 서버가 지켜야 하는 것

코드에서 확인한 브로커·클라이언트 쪽 요구다. 이것만 지키면 브로커는 서버가 어떤 프로젝트인지 묻지 않는다.

### 1.1 등록 (`POST /api/simulators`, `DELETE /api/simulators/{serverId}`)

- 카드 원문을 그대로 보낸다. 브로커가 거절하는 경우: `serverId` 없음, `endpoint` 없음, 후보 파일과 id 겹침,
  **한 카드 안에서** `populationTypes[].key` 중복.
- 브로커가 아직 안 떠 있으면 성공할 때까지 주기 재시도, 성공 뒤엔 다시 보내지 않음, 종료 시 해제
  (장량동 `BrokerRegistrar` 와 같은 동작).

### 1.2 카드에서 브로커가 읽는 칸

`serverId` · `name` · `endpoint` · `fictional`(false) · `domain` · `domainAliases` · `region` ·
`analysisUnit{scope,label,matchKeys,rationale}` · `populationTypes[{key,matchKeys,model}]` ·
`applicability{environmentMatchKeys, objectiveMatchKeys, answerableQuestions}` ·
`unsupported[{capability,matchKeys,reason,alternatives,message}]` · `quality.calibration` ·
`resultFields{judgement, explanation, reference, integrity}` · `alwaysAttachToResult` · `sesDigest`.

### 1.3 MCP (`POST /mcp`, JSON-RPC 2.0)

`initialize` · `tools/list` · `tools/call` · `ping`. 도구 6개는 이름 · 입력 스키마 · 응답 모양을 장량동과 같게:

| 도구 | 하는 일 |
|---|---|
| `get_capability` | 카드 원문 |
| `get_templates` | 서브태스크 템플릿 + `sesId`/`sesVersion` |
| `plan_subtasks` | 답변 맵 → 인스턴스 상태 4종 + `complete` |
| `validate_answers` | 원문 답 → 계약 대조(보정 없음) |
| `build_scenario` | PES + 실험 프레임 → 실행 설정 N벌 → 검증 → `UNCONFIRMED` |
| `get_scenario_status` | 상태 · 확인 화면 주소 · (확인 뒤) 토큰 |
| `run_scenario_by_token` | 토큰 재대조 → 반복 실행 → 결과 |

(`get_capability` 까지 7개. 브로커 안내문이 부르는 순서는 `get_templates` 부터 6개다.)

확인 화면 `GET /confirm.html` + `GET/POST /api/scenarios…` 는 **MCP 도구로 내지 않는다** — 장량동과 같다.

### 1.4 클라이언트

`C:\Dev\MCP\.mcp.json` 에 두 서버를 추가한다(Claude Code 는 브로커가 알려 준 주소에 즉석 연결하지 못한다).
그 결과 LLM 은 처음부터 세 시뮬레이터의 도구를 다 보므로, 실험은 **브로커가 고른 서버와 LLM 이 실제로
부른 서버가 같은지**를 로그로 대조한다(§5).

## 2. 서버 A — 포항 북구 행정동 생활폐기물 수거

### 2.1 무엇을 모델링하나

행정동 하나를 **집계 구역** 여러 개로 나누고, 구역마다 주거 유형별 세대가 매일 배출한 양을 거점에 쌓는다.
수거 차량은 수거 요일에 정해진 시각부터 구역을 돌며 싣고, 차가 차면 적환장에 다녀온다. 지점 하나하나가
아니라 **구역 단위 미수거량과 수거 지연**을 본다.

장량동과 일부러 어긋나게 둔 축(브로커 실험용):

| 축 | 장량동 | 서버 A |
|---|---|---|
| 분석 단위 | 원룸촌 한 블록(≤26동, 지점별) | 행정동 전체(구역 집계) |
| 지점별 적재 · 민원 | 지원 | **미지원** (구역 집계라 표현 못 함) |
| 교통 반영 | 지원 | **미지원** — 이동시간은 구역 간 상수 |
| 수거 요일 · 공휴일 | 부분 | **지원** — 포항 북구 수거 일정 실자료 |
| 주민 구분 | 직업 5종 | **주거 유형 4종** (아파트 · 단독 · 원룸 · 상가) |

→ "한 동네 + 평일 교통량" 은 장량동, "장량동 전체 + 수거 요일" 은 서버 A, "한 동네 + 수거 시각" 은 둘 다
그대로 맞아 **CHOOSE** 가 나와야 한다.

### 2.2 SES 와 서브태스크 템플릿 (15개)

```
행정동수거모델 ─Aspect─┬ 구역집합 ─Multi─ 구역 ─Aspect─┬ 주거구성 (Spec)
                       │                              └ 세대수 (Attr)
                       ├ 수거차량집합 ─Multi─ 차량 ─Spec─ 차종
                       ├ 수거일정 ─Spec─ 주기(매일/격일/요일지정) ─ 요일 목록 · 공휴일 처리
                       ├ 적환장결합 (Coupling) ─ 적환장 왕복시간
                       └ 실험프레임 ─ 수거 시작 시각 · 기간 · 반복
```

| answerKey | 노드 | 생성 조건 | 기본값 |
|---|---|---|---|
| zoneCount | MULTI_ASPECT | ALWAYS | 8 (1~40) |
| householdsPerZone | ATTRIBUTE | ALWAYS | 600 |
| housingMix | SPECIALIZATION (ENUM_LIST) | ALWAYS | [Apartment, Detached, Studio] |
| commercialShare | ATTRIBUTE | **상가가 구성에 있을 때** | 0.1 |
| truckType | SPECIALIZATION | ALWAYS | LARGE_5TON |
| truckCount | MULTI_ASPECT | ALWAYS | 2 |
| dispatchIntervalMinutes | ATTRIBUTE | 차량 2대 이상 | 0 |
| scheduleMode | SPECIALIZATION | ALWAYS | DAILY / ALTERNATE / WEEKDAYS |
| collectionDays | ATTRIBUTE (ENUM_LIST) | **WEEKDAYS 일 때** | 없음 — 물음 |
| holidayMode | COUPLING_CONDITION | ALWAYS | IGNORE / APPLY |
| holidayPolicy | SPECIALIZATION | **공휴일 반영 · 매일 수거가 아닐 때** | 없음 — 물음 (SKIP / NEXT_DAY) |
| transferStation | COUPLING_CONDITION | ALWAYS | IGNORE / APPLY |
| transferRoundTripMinutes | ATTRIBUTE | **적환장 반영일 때** | 없음 — 물음 |
| collectionStartMinutes | ATTRIBUTE | ALWAYS | 360 |
| days / seeds | ATTRIBUTE | ALWAYS | 28 / 30 |

연쇄 조건이 장량동처럼 생기도록 했다: `scheduleMode` 를 모르면 `collectionDays` · `holidayPolicy` 가
DEFERRED, `holidayMode` 를 모르면 `holidayPolicy` 가 DEFERRED, 매일 수거면 `holidayPolicy` NOT_GENERATED.
기본값 없는 템플릿 3개(요일 목록 · 공휴일 정책 · 적환장 왕복시간)가 "반드시 묻는" 자리다.

### 2.3 검증기 (조합)

- 일 배출량 > 차량 수 × 차종 용량 × 하루 왕복 가능 횟수 × 1.2 → 막음(장량동 예측 적재율과 같은 성격)
- WEEKDAYS 인데 요일 목록이 비었음 → 막음
- 적환장 반영 · 왕복시간이 근무시간보다 큼 → 막음
- 구역 수 × 세대수가 행정동 실인구 범위를 크게 벗어남 → **경고**(막지 않음)

### 2.4 결과 4분류

| 분류 | 값 |
|---|---|
| judgement | 일평균 미수거량(kg), 수거 지연 구역-일 수 |
| explanation | 구역별 최대 잔여, 요일별 배출 · 수거량 |
| reference | 차량 가동률, 운행 시간, 적환장 왕복 횟수 |
| integrity | 질량 수지 오차, 가정 메모, 데이터 품질 경고, 시드 |

자료: `waste-sim-spring/simulator/src/main/resources/schedule/` 의 포항 북구 수거 일정과 배출정보 CSV 를
복사해 쓴다. 세대당 배출량 · 주거 유형별 배출 시각은 **가정**으로 카드 `quality.calibration` 에 `measured:false` 로 적는다.

## 3. 서버 B — 포항 공영주차장 탐색·혼잡

### 3.1 무엇을 모델링하나

도심 한 구역에 공영주차장 여러 곳이 있고, 차량이 시간대별로 도착해 목적지에서 가까운 주차장부터 찾는다.
만차면 다음 주차장으로 배회(탐색)하고, 정해진 시간 안에 못 찾으면 포기한다. 안내 방식(없음 · 고정 안내판 ·
실시간 앱)에 따라 만차 주차장을 미리 피할 수 있다. 주변 도로 혼잡이 주차장 사이 이동시간을 늘린다.

브로커 실험용 축: 도메인이 다르므로 쓰레기 요청과 섞이면 안 된다. 다만 "혼잡", "교통", "평일" 같은 말은
장량동 카드와 겹치게 둬서, **도메인 판정이 먼저 걸러 주는지**를 본다.

### 3.2 SES 와 서브태스크 템플릿 (15개)

```
주차구역모델 ─Aspect─┬ 주차장집합 ─Multi─ 주차장 ─ 면수 (Attr) · 요금정책 (Spec)
                    ├ 이용자집합 ─ 이용자 구성 (Spec, ENUM_LIST) ─ 일 도착 대수 (Attr)
                    ├ 안내체계 ─Spec─ 없음/고정 안내판/실시간 앱 ─ 갱신 주기
                    ├ 도로혼잡결합 (Coupling) ─ 혼잡 프로파일
                    └ 실험프레임 ─ 탐색 포기 시간 · 기간 · 반복
```

| answerKey | 노드 | 생성 조건 | 기본값 |
|---|---|---|---|
| lotCount | MULTI_ASPECT | ALWAYS | 4 (1~12) |
| spacesPerLot | ATTRIBUTE | ALWAYS | 80 |
| pricingPolicy | SPECIALIZATION | ALWAYS | FLAT / TIME_OF_DAY / FREE |
| baseFeePer30Min | ATTRIBUTE | **무료가 아닐 때** | 500 |
| peakSurchargeRate | ATTRIBUTE | **시간대 차등일 때** | 없음 — 물음 |
| userMix | SPECIALIZATION (ENUM_LIST) | ALWAYS | [Commuter, Shopper, Visitor] |
| residentPriorityShare | ATTRIBUTE | **거주자가 구성에 있을 때** | 없음 — 물음 |
| dailyArrivals | ATTRIBUTE | ALWAYS | 900 |
| guidanceMode | SPECIALIZATION | **주차장 2곳 이상** | NONE |
| guidanceRefreshMinutes | ATTRIBUTE | **2곳 이상 · 실시간 앱일 때** | 5 |
| congestionMode | COUPLING_CONDITION | ALWAYS | IGNORE / APPLY |
| congestionProfileId | ATTRIBUTE | **혼잡 반영일 때** | weekday-downtown |
| maxSearchMinutes | ATTRIBUTE | ALWAYS | 없음 — 물음 |
| days / seeds | ATTRIBUTE | ALWAYS | 14 / 30 |

연쇄: 주차장 1곳이면 안내 방식 NOT_GENERATED → 갱신 주기도 NOT_GENERATED(장량동 구역 배정 → 구역 내
이동시간과 같은 꼴). 주차장 수를 모르면 둘 다 DEFERRED.

`populationTypes`: Commuter(07:30–09:00 도착, 9시간 체류), Shopper(11–19시, 1.5시간), Visitor(10–17시, 2시간),
Resident(18–20시 도착, 다음날 아침까지). 장량동과 key 가 겹치지 않는다.

### 3.3 검증기 (조합)

- 일 도착 대수 > 총 면수 × 하루 회전 가능 횟수 × 3 → 막음(물리적으로 거의 전원 포기)
- 실시간 앱인데 갱신 주기 > 탐색 포기 시간 → 막음(안내가 탐색에 쓰일 수 없음)
- 거주자 우선 비율 > 0 인데 거주자가 구성에 없음 → 막음

### 3.4 결과 4분류

| 분류 | 값 |
|---|---|
| judgement | 평균 탐색 시간, 포기 차량 수(평균 · 표준편차), 이용자 유형별 포기 |
| explanation | 주차장별 · 시간대별 점유율, 최대 점유율, 만차 지속 시간 |
| reference | 요금 수입, 주차장 간 이동 거리 |
| integrity | 차량 수지(도착 = 주차 + 포기 + 기간 말 탐색 중), 가정 메모, 품질 경고, 시드 |

자료: 공영주차장 위치 · 면수는 공공데이터포털 "포항시 공영주차장 정보"를 쓸 수 있으면 쓰고, 못 구하면
**가정값**으로 두고 카드에 `measured:false` 로 적는다. 도착 시간 분포는 가정이다.

## 4. 구현 방식

### 4.1 공통 기반은 복사한다

두 프로젝트가 같은 흐름을 쓰지만 별도 프로젝트이므로 장량동 `simulator` 에서 **도메인과 무관한 클래스만**
복사한다(§ 장량동 의존성 조사, 2026-10-19). 복사 뒤 바꾸는 곳은 넷이다.

| 그대로 복사 | 복사 뒤 고침 |
|---|---|
| `template/` 의 `SubtaskTemplate` · `SubtaskPlanner` · `SubtaskPlan` · `SubtaskInstance` · `SubtaskStatus` · `Activation` · `AnswerNormalizer` · `TemplateCatalog` | `GenerateCondition` — 상수를 각 도메인 규칙으로 새로 씀 |
| `pes/` 의 `Pes` · `ExperimentFrame` | `PesFlattener` · `PesBackVerifier` · `Scenario` · `ScenarioBuilder` — 설정 클래스 · 검증기 이름만 바꿈 |
| `mcp/ses/` 의 도구 6개 · `ScenarioStore` · `ConfirmScenarioTool` · `JsonValues` | `RunScenarioByTokenTool` — 엔진 호출과 결과 필드를 도메인에 맞게 새로 씀 |
| `capability/` 등록기 · 카드 로더, `static/confirm.html`, 확인 컨트롤러 | — |
| `mcp-common` 의 `McpToolProvider` · `ToolResult` · `ToolFailure` · `ErrorCode` · `ValidationError` | — |

**RQ1 기록:** 프로젝트마다 "복사한 파일 / 고친 파일 / 새로 쓴 파일" 의 줄 수를 `PROVIDER_EFFORT.md` 에 남긴다.
새로 쓴 것(엔진 · 설정 · 검증기 · 템플릿 JSON · 카드 · 생성 조건 · 실행 도구)이 "새 제공자가 쓴 양" 이다.
템플릿 JSON 은 먼저 `template-generator` 로 초안을 뽑아 일치율을 같이 적는다.

### 4.2 스택

Spring Boot 3.2.0 · Java 21 · Maven wrapper — 장량동과 같게. 각 프로젝트는 독립 `pom.xml`.

## 5. 실험

### 5.1 요청 세트 (초안 12개)

| # | 요청 | 기대 판정 | 기대 서버 | 무엇을 보나 |
|---|---|---|---|---|
| 1 | 학생 많은 원룸촌 한 블록, 평일 교통 반영해 수거 시각 비교 | MATCH | 장량동 | 교통 · 거주민으로 A 탈락 |
| 2 | 장량동 전체 아파트 단지, 격일 수거와 매일 수거 비교 | MATCH | 서버 A | 규모로 장량동 탈락 |
| 3 | 공휴일 낀 주에 수거 요일을 바꾸면 미수거량이 어떤가 (행정동) | MATCH | 서버 A | 환경 조건 |
| 4 | 한 동네 쓰레기 수거 시각을 바꾸면 어떤가 | **CHOOSE** | 장량동 · A | 실제 서버 간 차이 제시 |
| 5 | 동네에서 수거차 몇 대가 적당한가 | CHOOSE | 장량동 · A | 같음 |
| 6 | 장량동 전체를 평일 교통량 반영해서 | **ADJUST_REQUEST** | (교통 빼면 A / 규모 줄이면 장량동) | 수정 제안 |
| 7 | 도심 공영주차장 4곳, 실시간 안내 앱이 있으면 배회가 줄어드나 | MATCH | 서버 B | 다른 도메인 |
| 8 | 평일 퇴근길 혼잡할 때 주차장 찾는 시간 | MATCH | 서버 B | "혼잡 · 평일" 이 쓰레기로 새지 않나 |
| 9 | 주차 요금을 시간대별로 다르게 하면 만차가 풀리나 | MATCH | 서버 B | 목적 매칭 |
| 10 | 주차장 수거차 진입 문제 (쓰레기차가 주차장 때문에 막힘) | ADJUST 또는 MATCH | 판단 기록 | 두 도메인이 섞인 요청 |
| 11 | 수도관 누수 위치를 찾고 싶다 | ADJUST_REQUEST | (가상 B 제외, 실서버 없음) | 가상 후보는 추천 안 됨 |
| 12 | 쓰레기 수거 비용 최소화 | ADJUST_REQUEST | — | `unsupported` 비용 |

### 5.2 절차

1. 세 서버 + 브로커를 띄우고 `GET /api/simulators` 로 등록 확인(실서버 3 + 가상 2).
2. 요청마다 새 대화에서 LLM 이 `find_simulators` → (MATCH/CHOOSE 면) 해당 서버 도구로 시나리오 생성 →
   사람이 확인 화면 승인 → 실행.
3. 브로커 로그(`[3 조회]`, `[4 매칭]`)와 시뮬레이터 로그(도구 호출)를 요청 번호로 묶어 표로 남긴다.

### 5.3 지표

- **판정 정확도:** 기대 판정 · 기대 서버와 일치한 비율
- **추천 준수:** MATCH 뒤 LLM 이 실제로 부른 서버가 추천 서버와 같은 비율, 브로커 재호출 수
- **완주율:** MATCH/CHOOSE 요청 중 실행까지 간 비율과, 막힌 단계 · 사유
- **질문 수:** 요청마다 사용자에게 물은 횟수(RQ2), 서버별 비교
- **제공자 부담:** §4.1 의 줄 수(RQ1)

## 6. 위험과 열린 결정

1. **NONE 은 나오지 않게 된다.** 실서버가 다른 도메인에 생기면 `outsideDomain` 제안이 생겨 ADJUST_REQUEST
   가 된다(`FindSimulatorsTool.java:129`). 실험표의 NONE 칸은 비워 두고 그 이유를 적는다.
2. **`matchCount` 해석.** 그대로 맞지 않는 같은 도메인 후보도 센다(2026-10-19 관찰). 실험 지표는
   `matchCount` 가 아니라 `verdict` · `recommended` · `candidates` 로 잰다.
3. **(열린 결정)** 브로커 MATCH 안내문의 도구 순서가 고정 문자열이다(`FindSimulatorsTool.java:104`).
   같은 도구 이름을 쓰기로 했으므로 **고치지 않는다**가 기본안. 다만 서버 B 처럼 다른 도메인에서도
   안내문이 맞는지는 실험에서 확인한다.
4. **확인 화면은 사람이 누른다.** 12개 요청 × 실행이면 승인 클릭이 여러 번 필요하다 — 자동화하지 않는다
   (토큰의 의미가 사라진다).
5. **주차장 실자료.** 오프라인에서 못 구하면 전부 가정값. 브로커 실험에는 지장 없지만 결과 해석에는 한계로 적는다.
6. **NOT_GENERATED 후 서버가 완결을 강제하지 않는 문제**(장량동과 같음)는 새 서버에서도 같은 코드라
   같은 성질을 가진다. 이번 범위에서 고치지 않는다.

## 7. 작업 순서

| 단계 | 내용 | 확인 |
|---|---|---|
| 1 | 서버 B 프로젝트 골격 · 공통 기반 복사 · MCP 7도구 응답(엔진은 빈 껍데기) · 브로커 등록 | 브로커 `GET /api/simulators` 에 뜸, `tools/list` 7개 |
| 2 | 서버 B 설정 · 검증기 · 템플릿 15 · 생성 조건 · 카드 | `plan_subtasks` 연쇄 시험, 요청 7~9 가 MATCH |
| 3 | 서버 B 엔진(이산사건) · 결과 4분류 · 실행 도구 | 단위 시험, 차량 수지 0, 확인 → 실행 종단 |
| 4 | 서버 A 같은 순서(1~3) | 요청 2~5 가 기대대로, 질량 수지 0 |
| 5 | `.mcp.json` 갱신, 실험 요청 12개 실행 · 기록 | `docs/reports/broker-experiment-<날짜>/` 에 결과표 |

서버 A 는 장량동과 닮아 그 점이 가려진다.
