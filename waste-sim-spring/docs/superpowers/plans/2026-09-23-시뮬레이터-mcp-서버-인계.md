## 2. 내가 내린 판정 (rulings)

계획이 답하지 않거나 스스로 어긋난 자리에서 컨트롤러가 결정한 것들이다. **각각 틀렸을 때의 대가를 함께 적는다** — 다시 볼 사람이 되돌릴지 판단할 근거다.

### 사전 스캔에서 (실행 시작 전)

**Ruling A — 태스크의 Interfaces 요약과 본문 코드가 어긋나면 본문 코드가 정본이다.**
요약은 색인이고 본문이 계약이다. 실제로 두 곳에서 어긋났다 — Task 6 의 `ScenarioBuilder` 생성자가 요약의 `TemplateCatalog` 를 받지 않고, Task 4 의 `SubtaskPlan` 요약이 `complete()`·`counts()` 를 빠뜨렸다(본문에는 있다).
*틀렸을 때의 대가*: 요약에만 있는 API 를 후속 태스크가 기대하면 그 태스크에서 컴파일 오류로 즉시 드러난다. 조용히 통과하지 않는다.

**Ruling B — Global Constraints 의 `ValueOrigin` 은 실재 타입이 아니다. 새로 만들지 않는다.**
저장소를 뒤졌으나 그런 타입이 없다. 계획 본문이 쓰는 `String origin` / `Map<String,String> origins` 가 "값마다 출처를 구분해 기록하라"는 요구를 이행하는 형태로 본다.
*틀렸을 때의 대가*: 출처 문자열이 타입 검사를 못 받아 오타가 런타임까지 간다. Task 5 의 역검증과 Task 7 의 도구 출력에서 드러난다.

**Ruling C — 확인 토큰을 실행 지점에서 강제하는 코드는 계획 1의 범위 밖이다.**
Task 6 이 검증을 통과한 시나리오에만 토큰을 발급하고 "그 토큰으로만 실행한다"고 적었으나, Task 7 은 도구 5개만 만들고 **실행 도구를 만들지 않으며**, Task 8 은 `SimulationEngine` 을 직접 호출한다. 즉 토큰을 검사하는 지점이 계획 어디에도 없다. 발급·대조(`tokenMatches`)까지만 구현한다.
*틀렸을 때의 대가*: **검증 안 된 설정으로 실행될 수 있는 경로가 남는다.** 계획 2 또는 별도 태스크에서 실행 도구에 토큰 검사를 붙여야 한다. → **§4 미결 사항**으로 올림.

### 실행 중에

**Ruling D (Task 1) — 쓰이지 않는 enum 상수 `AnswerSourceKind.MCP_RESULT` 를 지운다.**
구현자가 컴파일을 살리려 브리프 밖 상수 6개를 더했고 5개는 실사용이 있었으나 이것만 0건이었다. 이 태스크는 빌드 복구이지 미래 확장이 아니다. MCP 결과 경로는 Task 7 에서 실제 사용처와 함께 들어오면 된다.
*틀렸을 때의 대가*: Task 7 에서 상수 하나를 다시 추가하는 일회성 작업. 컴파일 오류로 즉시 드러난다.

**Ruling E (Task 2) — 브리프에 없던 "조용한 폴백 금지" 예외 경로 테스트를 추가한다.**
`CapabilityCardLoader` 에 리소스 누락 시 예외를 던지는 코드가 있었으나 그것을 확인하는 테스트가 없었다. 브리프의 테스트 목록에 없었던 것은 계획의 빈틈이다. Global Constraints 가 브리프의 테스트 목록보다 상위 권위라고 보고 닫았다 — 예외 코드가 있는데 그것이 정말 던지는지 아무도 확인하지 않으면, 나중에 누가 그 자리에 빈 카드 폴백을 끼워 넣어도 테스트가 침묵한다.
*틀렸을 때의 대가*: 테스트 하나와 package-private 생성자 오버로드 하나. 프로덕션 기본 경로는 불변(검토 확인).

**Ruling F (Task 3) — 브리프에 없던 package-private `TemplateCatalog(String resourcePath)` 오버로드를 재가한다.**
Ruling E 에서 내가 직접 지시한 것과 같은 패턴이다. public 무인자 생성자가 `RESOURCE` 상수로 위임하는 프로덕션 경로는 그대로이고(검토 확인), 예외 경로를 시험할 유일한 수단이다.
*틀렸을 때의 대가*: 테스트 전용 진입점이 패키지 내부에 하나 남는다. 프로덕션 호출자는 볼 수 없다.

**Ruling G (Task 4) — `SubtaskPlan.complete()`·`counts()`·`answeredValues()` 에 테스트를 추가한다.**
브리프가 제공한 테스트 파일 자체가 이 셋을 한 번도 부르지 않았다. 그런데 **Task 7 이 `counts()`·`complete()` 를 응답 JSON 에 싣고 Task 8 이 그 둘을 단언한다.** 검증 없이 넘기면 Task 8 이 깨졌을 때 평탄화 결함인지 `complete()` 결함인지 가릴 수 없다.
*틀렸을 때의 대가*: 테스트 다섯 개. 특히 `counts()` 가 네 키를 항상 갖는지 단언하는 테스트가 없으면 Task 8 의 `counts().get(DEFERRED)` 가 NPE 를 낸다.

**Ruling H (Task 4) — 이 저장소의 surefire 는 `-Dtest=A+B` 를 거부한다. `-Dtest=A,B` 를 쓴다.**
계획 본문의 명령 문법이 이 환경에서 안 먹는다(구현자 실측).
*틀렸을 때의 대가*: 없음.

## 3. 이 환경에서 확인된 사실

다음 세션이 다시 조사하지 않아도 되는 것들이다.

**빌드** — Maven wrapper 실패는 **환경마다 다르다**. 2026-09-23 의 다른 PC 에서는 `./mvnw.cmd` 가 정상 동작했다(Maven 3.9.14 / JDK 21.0.10). 실패하는 환경에서는 로컬 Maven 을 쓴다:

```bash
mvn -o -B -Dmaven.repo.local=.m2/repository compile
mvn -o -B -Dmaven.repo.local=.m2/repository test -Dtest=클래스A,클래스B
mvn -o -B -Dmaven.repo.local=.m2/repository test
```

**종단간 실측** — 1톤 3대·4동 25세대·30일·시드 42·배정용량 150kg 에서 수거 시각을 360·540·720·900·1080분으로 훑으면 민원이 `[32, 64, 36, 33, 30]` 로 갈린다. 축이 죽어 있지 않다는 증거이며 `EndToEndSubtaskFlowTest` 가 이를 고정한다.

**전체 테스트 기준선: 681개, 전부 초록**(계획 1 완료 + §4(a) 마감). 회귀 판정의 기준이다.

**계획이 추측했던 기존 API — 전부 실재 확인**:

| 타입 | 확인된 것 |
|---|---|
| `com.wastesim.ledger.Activation` | enum `{ACTIVE, INACTIVE, UNKNOWN}` — 계획의 전제 성립 |
| `com.wastesim.model.SimulationConfig` | 실재 |
| `com.wastesim.tool.SimulationConfigValidator` | 생성자 4개. `(TrafficDataService)`, `(TrafficDataService, CollectionSiteRegistry)` 포함 |
| `com.wastesim.site.CollectionSiteRegistry` | `static empty()` 실재 |
| `com.wastesim.service.TrafficDataService` | 무인자 생성자 실재 |
| `com.wastesim.tool.ValidationResult` · `ToolResult` | 실재. **둘 다 record 다** — 접근자는 `ready()`·`errors()`·`message()` 이고 계획이 쓴 `isValid()`·`getErrors()`·`getMessage()` 는 없다. `ToolResult` 의 생성자는 `ok`·`rejected`·`needsConfirm` 뿐이고 계획이 쓴 `error(String)` 는 없다 |
| `com.wastesim.mcp.McpToolProvider` | 실재 |
| `com.wastesim.simulation.SimulationEngine` | 실재. **무인자 생성자도 `run(cfg)` 도 없다** — `SimulationEngine(TrafficDataService)` 와 `run(SimulationConfig, int seed)` 가 실재하는 것이다 |
| `com.wastesim.ledger.ValueOrigin` | **없음** → Ruling B |

**Task 1~4 가 만든 것 (Task 5 이후가 소비할 계약)**:

- `com.wastesim.capability` — `CapabilityCard`, `UnsupportedItem`, `CapabilityCardLoader`(`card()`, `matchOne(String)`, `matchAll(Collection)`). 능력 카드 JSON 은 `src/main/resources/mcp/` 에 있고 `docs/superpowers/specs/` 의 원본과 바이트 동일(복사이며 이동이 아님, 검토 확인).
- `com.wastesim.template` — `SubtaskTemplate`(record, 14필드), `GenerateCondition`(명명 상수 **정확히 5개**, 식 파서 없음), `TemplateCatalog`(템플릿 **13개**), `SubtaskStatus`, `SubtaskInstance`, `SubtaskPlan`(`toAsk`·`answeredValues`·`complete`·`counts`), `SubtaskPlanner`, `AnswerNormalizer`.
- `com.wastesim.ledger` — `BasisKind`, `AnswerSourceKind` 가 ledger 패키지로 이동(Task 1).

**지켜지고 있는 핵심 불변**(검토가 조건별·갈래별로 대조해 확인):

- 생성 조건 5개 각각이 의존 값 부재 시 `INACTIVE` 가 아니라 **`UNKNOWN`** 을 돌려준다. `SubtaskPlanner` 는 `UNKNOWN` → `DEFERRED`, `INACTIVE` → `NOT_GENERATED` 로 가른다. 보류를 거짓으로 뭉개는 경로가 하나도 없다.
- `complete()` 는 `DEFERRED` 가 남아 있으면 거짓이다.
- `AnswerNormalizer` 는 실패 시 `value=null` 을 돌려준다 — 조용히 기본값으로 바꾸는 경로가 없다.
- 범위 검증을 새로 정의한 곳이 없다. `SimulationConfigValidator` 가 정본으로 남아 있다.

**Ruling I (Task 5) — §4(b) 를 이월하지 않고 Task 5 안에서 닫는다.**
계획은 `Pes` 에 식별자 검증을 요구하지 않았다. 그러나 PES 는 `sesId`/`sesVersion` 이 값으로 실리는 첫 자리이고, 빈 식별자가 여기를 지나면 확인 화면과 실행까지 그대로 간다. 근원(`TemplateCatalog`)과 관문(`Pes`) 양쪽을 막았다. 출처(`origins`)가 없는 값도 함께 거절한다 — `unapprovedDefaults()` 가 그것을 조용히 "승인된 값"으로 세기 때문이다.
*틀렸을 때의 대가*: 템플릿 JSON 이나 PES 생성부가 식별자를 안 채우면 이제 조용히 넘어가지 않고 예외로 멈춘다. Task 6·7 에서 PES 를 만드는 코드가 두 필드를 반드시 채워야 한다.

**Ruling J (Task 6) — 실행 설정별 `origins` 맵을 `HashMap` 대신 `LinkedHashMap` 으로 둔다.**
계획 Step 4 가 `new HashMap<>(pes.origins())` 를 썼다. 이 저장소는 "같은 요청을 두 번 돌리면 같은 결과" 를 반복해서 지키는데, 순서가 흔들리는 맵을 중간에 끼우면 그 주장을 근거 없이 약화시킨다. 현재 토큰 해시는 설정 게터만 훑어 영향이 없지만, 값이 싼 보험이다.
*틀렸을 때의 대가*: 없다. 동작 차이가 없다.

**Ruling K (Task 7) — `BuildScenarioTool` 이 SES 식별자를 도구에 적지 않고 `TemplateCatalog` 에서 가져온다.**
계획 Step 5 가 `new Pes("jangnyang-ses", "1.0.0", ...)` 로 값을 도구에 박았다. 식별자가 저장소에 두 곳 생기면 템플릿 리소스가 바뀌었을 때 도구가 옛 값을 주장한다 — Ruling I 가 막으려던 것과 같은 실패가 다른 문에서 들어온다. 응답에도 `sesId`·`sesVersion` 을 실어 호출자가 대조할 수 있게 했다.
*틀렸을 때의 대가*: 없다. 현재 값이 같아 동작 차이가 없고, 리소스가 바뀌면 도구가 따라간다.

**Ruling L (Task 7) — 실행 가능한 기능만 남기기로 한 결정(`5aa37c0`)으로 범위가 계획과 달라졌다.**
능력 카드에서 `route-sequence`·`truck-route` 를 내리고, `routeAvailableCapacityKg` 템플릿을 14번째로 더했다. 계획에 없던 작업이고 Task 3 산출물(템플릿 카탈로그)과 Task 2 산출물(능력 카드)을 건드렸다. 근거는 `docs/reports/2026-09-23-장량동-실행가능-기능과-범위.md` §6·§9 다.
*틀렸을 때의 대가*: 템플릿이 13→14 가 되어 "모든 결정이 채워진" 픽스처가 하나 늘었다. 새 템플릿은 `ALWAYS`·기본값 없음이라 모든 요청에 질문이 하나 추가된다 — 사용자가 가동률에 관심이 없어도 묻는다. 부담스러우면 생성 조건을 좁히는 쪽으로 되돌릴 수 있다.

**Ruling M (Task 8) — "답변이 다 차면 계획이 완결이다" 를 단언하지 않는다.**
계획의 종단간 시험이 실험 변수를 빼놓은 답변으로 `plan.complete()` 가 참이기를 기대했다. 성립하지 않는다 — 실험 변수는 모델 구조상 열린 채 남고 그 자리를 닫는 것이 `ExperimentFrame` 의 일이다. 남은 것이 **정확히 실험 변수 하나**인지를 단언하는 쪽으로 바꿨다. 완결 판정은 실험 변수까지 채운 별도 시험으로 옮겼다.
*틀렸을 때의 대가*: 없다. 오히려 원안대로 두면 "실험 변수 말고 다른 것이 남아 있어도" 통과할 수 있었다.

**Ruling N — Ruling C 를 뒤집어 확인 토큰 검사를 계획 1 안에서 닫는다.**
Ruling C 는 "토큰을 검사하는 지점이 계획 어디에도 없다" 를 근거로 발급·대조까지만 하기로 했다. 그 판단은 계획 문서만 보고 내린 것이었고, Task 6·7 이 닫히면서 `ScenarioStore` 에 검증된 시나리오가 남고 `tokenMatches` 가 실행 직전 재해싱으로 동작한다는 것이 실물로 확인됐다. 필요한 것은 그 둘을 잇는 도구 하나뿐이었다. 가장 무거운 미결을 계획 경계 때문에 남겨 두는 것이 더 비싸다고 봤다.
*틀렸을 때의 대가*: 계획 2 가 실행 도구 계약을 다르게 정하면 이 도구를 그 계약에 맞춰 고쳐야 한다. 기존 `run_scenario`·`run_waste_simulation` 은 건드리지 않았으므로 그 경로는 여전히 토큰 없이 실행된다 — **토큰 강제는 이 새 도구를 쓸 때만 성립한다.** 계획 2 가 닫을 일로 §4(d) 에 남긴다.

## 4. 미결 사항 — 최종 검토에 반드시 올릴 것

**(a) ~~확인 토큰이 실행 지점에서 강제되지 않는다~~ — `bfa8dfe` 에서 닫았다.** `run_scenario_by_token` 이 보관된 시나리오를 실행 직전에 다시 해싱해 대조한다. 토큰이 없거나 틀리거나 발급 이후 설정이 바뀌었으면 실행하지 않고, 스키마가 `confirmToken` 을 필수로 둔다. Ruling C 가 계획 2 로 미뤘던 것인데, 앞의 일곱 태스크가 닫히며 실행 도구의 계약이 실제로 정해져 여기서 닫았다(Ruling N).

**(b) ~~`TemplateCatalog.sesId()` / `sesVersion()` 의 조용한 빈 문자열 폴백~~ — Task 5(`ac26184`)에서 닫았다.** `TemplateCatalog` 가 두 필드 부재 시 `IllegalStateException` 을 던지고, `Pes` 도 빈 식별자와 출처 없는 값을 거절한다. 테스트 4개가 이를 고정한다.

**(c) ~~스프링 컨텍스트 로드 테스트 부재~~ — Task 7(`c1699f6`)에서 닫았다.** `SesToolsWiringTest` 가 `@SpringBootTest(webEnvironment = NONE)` 로 컨텍스트를 세우고 도구 다섯이 레지스트리에 모이는지, 이름이 겹치지 않는지 확인한다.

**(d) 기존 실행 도구는 여전히 토큰을 요구하지 않는다.** `run_waste_simulation`·`run_scenario`·`update_route_sequence` 는 그대로다. 토큰 강제는 `run_scenario_by_token` 을 쓸 때만 성립한다. 기존 도구에 검사를 붙일지, 아니면 서브태스크 흐름의 실행 입구를 새 도구 하나로 좁힐지는 계획 2 가 도구 계약을 확정하며 정할 일이다.

**(e) 이월된 소소한 것들** — 막지는 않으나 최종 검토가 병합 전 처리 여부를 판단할 것:

## 5. 다른 PC 에서 재개하는 방법

```bash
git fetch origin
git checkout feature/simulator-mcp
```

그다음 `superpowers:subagent-driven-development` 를 계획 파일에 대해 다시 시작한다. 그 스킬은 `.superpowers/sdd/<계획이름>/progress.md` 를 찾는데 **새 PC 에는 없다.** 이 문서의 §1 과 §2 를 그 원장의 첫 내용으로 옮겨 적은 뒤 Task 5 부터 진행한다 — 원장 첫 줄은 계획 파일 경로여야 한다:

```
# SDD ledger — plan: waste-sim-spring/docs/superpowers/plans/2026-09-23-시뮬레이터-mcp-서버.md
```

브리프·보고서·diff 원본은 이송하지 않았다. 브리프는 스킬의 `scripts/task-brief` 로 계획 파일에서 다시 뽑고, diff 는 `scripts/review-package` 로 위 표의 커밋 범위에서 다시 만든다. 둘 다 결정적이라 같은 결과가 나온다.
