## 판정 기준 — 무엇을 "죽었다" 고 보는가

**프로덕션 호출자가 0건**이고 **스프링 빈도 아닌** 클래스다. 테스트만 부르는 것은 죽은
것이다 — 그 테스트는 자기가 지키려는 코드가 아무 데도 쓰이지 않는다는 사실을 모른다.

지우기 전에 **매번 다시 센다.** 아래 숫자는 `ba0fc5c` 기준이고, 하나를 지우면 다른 것의
참조 수가 바뀔 수 있다.

```bash
# 프로덕션 호출자 0건인 비-스프링 클래스
for f in $(find src/main/java -name '*.java'); do
  n=$(basename $f .java)
  c=$(grep -rlw "$n" src/main/java --include=*.java | grep -v "^$f$" | wc -l)
  [ "$c" -eq 0 ] && ! grep -q "@RestController\|@Controller\|@Configuration\|@Component\|@Service\|@SpringBootApplication\|@ControllerAdvice" $f \
    && echo "$(wc -l < $f) $f"
done | sort -rn
```

## B. 결정기록·등록검증 subsystem 통째 — **판단이 필요하다**

넷이 아니다. **두 패키지가 통째로 프로덕션에서 닿지 않는다.**

| | 파일 | main | test | 살아 있는 것 |
|---|---|---|---|---|
| `com.wastesim.ledger` | 20 | 1,194 | 1,208 | `Activation` (20줄) 뿐 |
| `com.wastesim.registry` | 4 | 227 | 113 | 없음 |
| | **24** | **1,421** | **1,321** | 테스트 74개 |

`Activation` 만 `GenerateCondition`·`SubtaskPlanner` 가 쓴다. `RuleRegistry` 는
`RegistrationValidator` 가 쓰는데 그것도 죽었다. 계획 1 Task 1 이 빌드를 살리려
`BasisKind`·`AnswerSourceKind` 를 ledger 로 옮겼는데, 둘 다 지금은 테스트만 부른다.

**왜 죽었나:** 이 subsystem 은 `ChatController` 와 서브태스크 세션 경로에 물려 있었고,
그 둘은 계획 1 Task 1 과 `ba0fc5c` 에서 지워졌다. 서브태스크 흐름은 값의 출처를
`Pes.origins` 로 나르므로 결정기록이 하던 일을 다른 방식으로 한다.

**그래서 이것은 "죽은 코드 청소" 가 아니라 설계 결정이다.** 두 계획
(`2026-09-13-parameter-ledger`, `2026-09-14-ledger-session-integration`)의 산출물
전체다. 능력 카드와 명세에는 결정기록이 나오지 않으므로 **문서와 얽힌 곳은 없다.**

갈래 셋:

| 갈래 | 내용 | 대가 |
|---|---|---|
| (a) 통째로 지운다 | `Activation` 만 `template` 로 옮기고 두 패키지를 지운다. −2,742줄, 테스트 74개 | 결정기록 개념이 저장소에서 사라진다. 되살리려면 git 에서 꺼내야 한다 |
| (b) 남긴다 | 그대로 둔다 | 새로 오는 사람이 "이게 지금 쓰이나" 를 매번 다시 조사한다. 오늘 내가 그랬다 |
| (c) 표시만 한다 | 패키지에 `package-info.java` 로 "프로덕션에서 닿지 않음, 계획 N 에서 되살릴 예정" 을 적는다 | 줄 수는 그대로. 다만 다음 사람이 다시 조사하지 않는다 |

**먼저 답할 것: 결정기록을 계획 3 이상에서 쓸 생각이 있는가?** 있으면 (c), 없으면 (a).
그 답을 모르는 채로는 지우지 말 것.
