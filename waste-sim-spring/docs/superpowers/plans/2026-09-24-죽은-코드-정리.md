## 판정 기준 — 무엇을 "죽었다" 고 보는가

**프로덕션 호출자가 0건**이고 **스프링 빈도 아닌** 클래스다. 테스트만 부르는 것은 죽은
것이다 — 그 테스트는 자기가 지키려는 코드가 아무 데도 쓰이지 않는다는 사실을 모른다.

지우기 전에 **매번 다시 센다.** 아래 숫자는 `ba0fc5c` 기준이고, 하나를 지우면 다른 것의
참조 수가 바뀔 수 있다.

```bash
# 프로덕션 호출자 0건인 비-스프링 클래스
for f in $(find src/main/java -name '*.java'); do
  n=$(basename $f .java)
  c=$(grep -rlw "$n" src/main/java --include=*.java | grep -v "^$f$" | wc -l)
  [ "$c" -eq 0 ] && ! grep -q "@RestController\|@Controller\|@Configuration\|@Component\|@Service\|@SpringBootApplication\|@ControllerAdvice" $f \
    && echo "$(wc -l < $f) $f"
done | sort -rn
```

## B. 결정기록(ledger) 계열 넷 — **위험 중간, 하나는 보류**

`ledger` 패키지는 대부분 살아 있다(`Activation` 은 `GenerateCondition` 이 쓴다). 죽은 것은
넷뿐이다.

| 클래스 | main | test | 주의 |
|---|---|---|---|
| `ledger/LedgerRecalculator` | 242 | 317 | — |
| `ledger/verify/ConfigBackVerifier` | 102 | 147 | 계획 1 이 `PesBackVerifier` 로 같은 일을 다시 만들었다 |
| `registry/RegistrationValidator` | 101 | 113 | — |
| `ledger/AnswerDecisions` | 59 | 74 | **계획 1 본문이 5번 언급한다** |
| `ledger/JangnyangRules` | 35 | 0 | **테스트 4곳이 헬퍼로 쓴다 — 단독 삭제 불가** |

**`AnswerDecisions` 는 보류를 권한다.** 계획 1 문서가 이름을 5번 적었는데 실제로는 쓰이지
않았다. 계획이 쓰려다 만 것인지, 후속 계획이 쓸 자리인지 확인하기 전에는 지우지 말 것.

**`JangnyangRules` 는 프로덕션에서만 죽었다.** 테스트 네 곳이 헬퍼로 쓴다. 지우려면 그
테스트들을 함께 봐야 하고, 그 테스트가 무엇을 지키는지 먼저 읽을 것.

**`ConfigBackVerifier` 에 한 가지 물음이 남는다:** 계획 1 Task 5 가 `PesBackVerifier` 를
새로 만들면서 이것을 쓰지 않았다. 둘이 같은 일(설정을 되읽어 대조)을 하는데 대상이 다르다
— 하나는 결정기록, 하나는 PES. **지우기 전에 "결정기록 역검증이 정말 필요 없는가" 를
판단할 것.** 필요 없다면 지우고, 필요하다면 왜 아무도 안 부르는지가 진짜 문제다.

## 작업 방법

1. 한 덩어리(A, B의 한 줄, C의 한 항목)씩 지운다.
2. `./mvnw.cmd -B clean test` — **738보다 줄어든 만큼이 지운 테스트 수와 맞는지** 본다.
   맞지 않으면 다른 것을 깨뜨린 것이다.
3. 커밋한다. 커밋 메시지에 **지운 줄 수와 "왜 죽었는가"** 를 적는다. 나중에 되살릴 사람이
   판단할 근거다.

기대 규모 — A와 C를 다 하면 약 600줄과 의존성 하나, B까지 하면 약 1,500줄.

```
ponytail: 한 번에 다 지우고 한 번에 커밋하지 말 것. 무언가 깨졌을 때
          어느 덩어리가 원인인지 가릴 수 없다.
```
