# 브로커 다단계 매칭 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 브로커가 애매한 요청을 몇 바퀴 고쳐야 맞는 시뮬레이터에 닿는지 세고(최대 5번 고친 조회, 6번째는 `NONE`), 첫 조회 판정에서 못 하는 서버를 맞다고 하는 오류를 0 으로 만든다.

**Architecture:** `CandidateMatcher` 가 항목을 일치/불일치/애매로 나누고, 새 `MatchRounds` 가 매칭 id 별로 바퀴 · 목표 서버 · 바퀴별 요청을 기억한다. `FindSimulatorsTool` 이 바퀴 규칙으로 판정하고 측정값을 응답에 싣는다. 정답 모음과 정확도 시험은 규칙을 바꾸기 **전에** 만들어 기준선을 남긴다.

**Tech Stack:** Java 21, Spring Boot, Jackson, JUnit 5, Maven(`mvnw.cmd`). Python 3 (정답 모음 추출 스크립트 하나).

**Spec:** `docs/superpowers/specs/2026-11-02-브로커-다단계-매칭-design.md`

## Global Constraints

- 1단계 = 대화 한 바퀴. 첫 조회 r = 1. 고친 바퀴 수 = r − 1, 측정값 0–5. r ≥ 7 이면 대조하지 않고 `NONE`.
- 브로커는 자연어를 해석하지 않는다. 대조는 카드의 `matchKeys` 를 요청 구절 안에서 찾는 지금 방식(`anyKeyMatches`)을 유지한다.
- 브로커는 후보를 고르지 않는다. 정렬은 보기 위한 것이다.
- `unsupported` 를 먼저 본다. `unsupported` 에 걸리면 불일치다.
- 확실하지 않으면 일치로 보지 않는다. 애매는 `MATCH` · `CHOOSE` 를 막는다.
- 카드가 그 칸의 목록을 아예 적지 않았으면 애매다(목적 · 비교 축 · 거주민).
- 코드 주석 · 메시지 · 시험 이름은 지금 브로커 코드처럼 한국어로 쓴다.
- 시뮬레이터 모듈(`simulator`, `district-waste-sim`, `parking-sim`)은 바꾸지 않는다.

## Review Focus

1. **같은 매칭 id 로 r ≥ 7 이후 또 조회** — 계속 `NONE` 이어야 하고 바퀴가 무한히 늘어 응답이 깨지면 안 된다. → Task 4 `일곱번째_이후도_계속_NONE`.
2. **브로커 재시작 뒤 옛 매칭 id** — 조용히 r = 1 로 세면 측정값이 틀린다. "모르는 매칭 id" 거절이어야 한다. → Task 4 `모르는_매칭_id_는_거절`.
3. **목표 서버가 등록 해제됐거나 꺼짐** — 예외가 아니라 `ADJUST_REQUEST` 와 알림, 전체 후보 재대조. → Task 5 `목표_서버가_꺼지면_전체를_다시_보인다`.
4. **같은 칸 구절을 고쳐 쓴 것과 뺀 것** — 고쳐 쓴 것을 제거로 세면 목적 변경이 부풀려진다. → Task 6 `구절을_고쳐_쓰면_제거가_아니다`.
5. **세션 없이 오는 호출(시험 · 직접 호출)** — 세션 `null` 끼리는 같은 세션으로 본다. 다른 세션 id 의 매칭 id 는 거절. → Task 4 `다른_세션의_매칭_id_는_거절`.

  ```java
  public final class MatchThread {          // 같은 파일 안 정적 중첩 클래스
      String session(); int round(); String targetServerId();
      List<RequestProfile> profiles();       // 바퀴 순서

  String open(String session, RequestProfile first);              // 새 id(UUID), round = 1
  Optional<MatchThread> next(String matchId, String session,      // 세션이 다르거나 모르는 id 면 empty
  ```

- Produces (`FindSimulatorsTool`): `ToolResult call(JsonNode args, String session)`. 기존 `call(JsonNode)` 은 `call(args, null)`. 입력 스키마에 `matchId`(string), `targetServerId`(string) 추가. 생성자에 `MatchRounds` 추가 — 3인자 시험용 생성자는 `new MatchRounds()` 를 넣는다.
- Produces (응답): 모든 판정에 `"round": {"matchId", "round", "revisions": round-1, "remainingRevisions": max(0, 6-round)}`.
- Controller: `tool instanceof FindSimulatorsTool f ? f.call(arguments, session) : tool.call(arguments)`.

규칙:
- `matchId` 없음 → `open`. `targetServerId` 가 있는데 `matchId` 가 없으면 `ToolFailure.of("matchId", "targetServerId 는 matchId 와 함께 보내십시오 — 첫 조회에서 받은 matchId 입니다")`, 바퀴로 세지 않음.
- `matchId` 가 모르거나 다른 세션 것 → `ToolFailure.of("matchId", "모르는 매칭 id 입니다 — 브로커가 다시 시작됐을 수 있습니다. matchId 없이 새 요청으로 조회하십시오")`. 세션 비교는 `Objects.equals`(둘 다 `null` 이면 같은 세션).
