# 브로커와 후보 서버 구현 계획 (계획 2)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 명세의 2·3·4단계를 채운다 — LLM이 요청에서 프로필을 뽑고, 브로커가 등록된 능력 카드들 중에서 후보를 **근거와 함께** 고른다. 계획 1이 남긴 미결 둘(기존 실행 도구의 토큰 검사, 확인 화면 접근 제어)도 함께 닫는다.

**왜 필요한가:** 지금 후보가 장량동 하나뿐이라 **4단계 매칭을 평가할 수 없다.** 후보가 하나면 무엇을 고르든 정답이고, "브로커가 능력 카드로 올바른 서버를 찾는다"는 주장에 근거가 생기지 않는다. 구분 가능한 후보가 최소 둘 더 있어야 한다.

**Architecture:** 브로커는 **별도 배포물이 아니라 같은 서버의 다른 패키지**다. 능력 카드 여러 장을 리소스에서 읽어 보관하고, 요청 프로필과 대조해 후보를 순위와 근거로 낸다. 카드가 곧 서버의 자기소개이므로, 후보 서버를 실제로 띄우지 않아도 매칭은 평가할 수 있다.

```
ponytail: 브로커를 같은 프로세스에 둔다. 후보 서버를 따로 띄워야 하는 것은
          "호출까지 되는가" 를 볼 때이고, 이 계획이 답하려는 것은 "고르는가" 다.
          분리 배포가 필요해지면 CandidateRegistry 뒤만 바꾸면 된다.
```

## 계획 1을 실행하며 배운 것 — 이 계획이 다르게 하는 것

계획 1은 태스크마다 전체 소스를 적어 두었다. 그 덕에 실행은 빨랐지만 **적어 둔 코드가 네 군데에서 틀렸다.**

| 계획 1이 적은 것 | 실제 |
|---|---|
| `ValidationResult.isValid()` · `getErrors()` | record 접근자 `ready()` · `errors()` |
| `ToolResult.error(String)` | 없음. `rejected(ValidationError)` 뿐 |
| `new SimulationEngine()` · `run(cfg)` | `SimulationEngine(TrafficDataService)` · `run(cfg, seed)` |
| "답변이 다 차면 계획이 완결이다" | 실험 변수가 열린 채 남으므로 거짓 |

추측한 API를 코드로 적어 두면 **틀렸다는 사실이 구현 단계까지 숨는다.** 그래서 이 계획은 소스를 적지 않는다. 대신 각 태스크에 **계약(무엇을 받아 무엇을 내는가)과 시험 목록**을 적고, 구현자가 먼저 실측하게 한다.

```
ponytail: 계획에 코드를 덜 쓰는 것이 이 계획의 설계 결정이다.
          전체 소스가 필요한 태스크가 나오면 그때 그 태스크에만 적는다.
```

## Task 2: 구분 가능한 후보 카드 두 장

매칭을 평가하려면 후보가 **서로 다른 답을 내야 한다.** 장량동과 한 축씩 어긋나게 만든다.

**Files:**
- Create: `src/main/resources/mcp/candidates/` 아래 카드 2장
- Create: `docs/superpowers/specs/후보-서버-카드-근거.md`

**두 후보의 설계 — 어긋나는 축을 하나씩만 둔다:**

| | 장량동 (기존) | 후보 A | 후보 B |
|---|---|---|---|
| 도메인 | 생활폐기물 수거 | 생활폐기물 수거 | **상수도 누수** |
| 공간 규모 | 원룸촌 한 블록 (1~26동) | **행정동 전체** | 관로망 |
| 교통 반영 | 지원 | **미지원** | 해당 없음 |
| 수거 시각 비교 | 지원 | 지원 | 미지원 |

- **후보 A**는 같은 도메인이되 규모와 교통이 다르다 → "한 동네 규모 + 평일 교통량" 요청에서 **장량동이 이겨야 한다.**
- **후보 B**는 도메인이 다르다 → 도메인만으로 걸러져야 한다. 도메인이 같은 둘 사이에서 고르는 것이 진짜 시험이고, B는 대조군이다.

**주의:** 후보 카드는 **가상의 서버**다. 실재하지 않는 서버를 실재하는 것처럼 적으면 안 된다. 카드에 `"fictional": true`와 그 이유를 적고, 근거 문서에 "매칭 평가용이며 구현된 서버가 아니다"를 명시한다.

**시험:**
- 세 카드가 같은 필수 키를 갖는다(`serverId`·`domain`·`applicability`·`unsupported`)
- 세 `serverId`가 서로 다르다
- 후보 카드에 `fictional` 표시가 있고 장량동 카드에는 없다

LLM이 발화에서 뽑은 조건을 **구조로** 받는다. 서버가 자연어를 해석하지 않는다(계획 1의 규칙과 같다).

- Test: `src/test/java/com/wastesim/broker/RequestProfileTest.java`

- 도메인이 비면 거절한다
- 미제시 항목이 `null`로 남고 빈 문자열로 뭉개지지 않는다

## Task 4: 매칭기 — 근거와 함께 고른다

**Files:**
- Create: `src/main/java/com/wastesim/broker/CandidateMatcher.java`
- Create: `src/main/java/com/wastesim/broker/MatchResult.java`
- Test: `src/test/java/com/wastesim/broker/CandidateMatcherTest.java`

**계약:**
- `MatchResult` — record `(String serverId, int score, List<String> reasons, List<String> mismatches)`
- `CandidateMatcher.match(RequestProfile)` → `List<MatchResult>`, 점수 내림차순

**판정 순서 — 거르고 나서 점수를 센다:**

1. **도메인이 다르면 후보에서 제외한다.** 점수로 깎지 않는다 — 도메인이 다른 서버는 아무리 다른 축이 맞아도 답을 낼 수 없다.
2. 남은 후보마다 축별로 센다: 공간 규모 적합 · 환경 조건 지원 · 비교축 지원.
3. 요청이 명시한 조건이 카드의 `unsupported`에 걸리면 **그 사유를 `mismatches`에 적는다.** 점수만 깎고 넘어가면 사용자가 "왜 저 서버가 아닌가"를 되물을 수 없다.

**`reasons`에 무엇을 적는가:** 카드의 어느 칸이 요청의 어느 항목과 맞았는지. `"공간 규모: 한 동네 ⊂ 원룸촌 한 블록(1~26동)"` 처럼 **양쪽을 다 적는다.** 한쪽만 적으면 근거가 아니라 결론이다.

**시험:**
- 명세 1단계 발화의 프로필로 매칭하면 **장량동이 1등이고 후보 A가 2등**이다
- 후보 B(다른 도메인)는 결과에 아예 없다
- 교통 반영을 요구하면 후보 A의 `mismatches`에 "교통 미지원"이 적힌다
- 장량동이 1등인 `reasons`에 공간 규모와 교통이 **둘 다** 적힌다
- 도메인이 아무 카드와도 안 맞으면 **빈 목록**과 사유를 낸다 — 억지 1등을 만들지 않는다
- 점수가 같으면 순서가 흔들리지 않는다(`serverId` 오름차순으로 고정)

## Task 6: 기존 실행 도구에 토큰 검사를 붙인다 (인계 문서 §4(d))

`run_waste_simulation`·`run_scenario`·`update_route_sequence`가 아직 토큰을 요구하지 않는다. **토큰 강제는 `run_scenario_by_token`을 쓸 때만 성립한다.**

**먼저 정할 것 — 구현자가 판단하지 말고 올릴 것:**

이 셋은 서브태스크 흐름 **밖에서도** 쓰인다(REST 화면, 기존 시나리오 API). 토큰을 무조건 요구하면 그 경로가 전부 막힌다. 두 갈래다.

| 갈래 | 내용 | 대가 |
|---|---|---|
| (a) 입구를 좁힌다 | 서브태스크 흐름은 `run_scenario_by_token`만 쓰고, 기존 셋은 그대로 둔다. 문서에 "토큰 강제는 서브태스크 흐름에만" 이라고 적는다 | 검증 안 된 설정으로 실행되는 경로가 남는다. 다만 그 경로는 서브태스크 흐름이 아니다 |
| (b) 셋 다 토큰을 받는다 | 토큰이 오면 대조하고, 없으면 "서브태스크 흐름 밖" 으로 표시해 결과에 남긴다 | 결과에 표시가 하나 늘고, 기존 호출부가 그대로 돈다 |

**(b)를 권한다** — 막지 않으면서 "이 결과가 확인을 거쳤는가"를 결과만 보고 알 수 있다. 계획 1이 세운 "무엇으로 계산한 값인가를 결과가 말한다"와 같은 방식이다.

**시험:**
- 토큰 없이 부르면 실행되고 결과에 `confirmed: false`가 실린다
- 맞는 토큰과 함께 부르면 `confirmed: true`
- 틀린 토큰과 함께 부르면 **실행하지 않는다** — 토큰을 줬다는 것은 확인을 주장한 것이고, 틀린 주장은 통과시키면 안 된다
