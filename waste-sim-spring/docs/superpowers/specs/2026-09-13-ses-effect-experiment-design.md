# SES의 독립 효과를 가리는 실험 — 설계

2026-09-13 · 코드 `feature/ses-conversion @ 1760509` · 짝 스펙 `2026-09-13-asset-contract-ledger-design.md`

## 무엇을 시험하는가

SES 변환의 가설은 이것이다.

> 시뮬레이션을 체계요소구조로 변환하고 서브태스크 템플릿으로 결정해야 할 매개변수를 명시하면,
> LLM은 사용자의 답변으로 서브태스크를 채워 시나리오를 생성하고 사용자 요청에 맞는 시뮬레이션을
> 구성할 수 있다.

이 문장은 두 가지를 한꺼번에 주장한다 — **SES라는 표현이 기여한다**와 **서브태스크 템플릿이라는
절차가 기여한다**. 둘을 가르지 않으면 어느 쪽이 효과를 냈는지 말할 수 없다.

더 큰 위험은 세 번째다. **SES는 정보를 더 준다.** 더 많은 정보를 받아 더 잘하는 것은 표현의
효과가 아니다. 그래서 이 실험의 중심 비교는 "SES를 줬을 때 vs 안 줬을 때"가 아니라
**"같은 정보를 스키마로 줬을 때 vs SES로 줬을 때"**다.

이것이 SES에 불리한 설계라는 점은 인정하고 시작한다. 유리한 비교로 얻은 결과는 주장할 수 없다.

## 조건

문서 A·B와 혼동되지 않도록 조건명을 따로 쓴다.

| 조건 | 제공 | 무엇을 가리는가 |
|---|---|---|
| N | 자연어 요청만 | 원래 기준선 |
| T | 같은 자산·제약 정보를 평문으로 | 정보 접근 자체의 효과 |
| S | 실행 스키마 + 같은 제약·관계 정보 | 강한 구조화 기준선 |
| S+W | S + 서브태스크 템플릿 | 템플릿 효과 |
| E | S와 **같은 정보**를 SES 표현으로 | **SES 표현의 효과** |
| E+W | E + 같은 템플릿 | 결합 효과 |
| F | E+W + 질의·MCP·검증·실행 경로 | 전체 시스템 효과 |

- **N 대 F는 전체 시스템의 실용적 효과만 보여준다.** 논문에서 SES의 효과로 인용할 수 없다.
- **SES의 원인 효과는 S 대 E, S+W 대 E+W에서만 판단한다.**
- T를 두는 이유는 S 대 E가 유의해도 "구조화 자체"인지 "SES"인지 가르지 못하기 때문이다.
  T→S 간격과 S→E 간격을 함께 봐야 한다.

### 정보 동등성 규칙

S와 E는 다음을 맞춘다.

- 등장하는 자산·필드·단위·허용 범위의 **집합이 같다**
- 조건부 필수 관계가 **양쪽에 모두 표현된다** — JSON Schema도 조건부 검증을 지원하므로,
  조건 표현을 뺀 약한 스키마와 비교하는 것은 유리한 비교다. 비교 대상은 `if`/`then`·
  `dependentRequired`로 같은 조건을 적은 스키마여야 한다
- 출처·근거 정보의 양이 같다
- 외부 도구·질의·검증 피드백을 **양쪽 다 차단한다** (F만 연다)
- 토큰 수를 맞추는 것으로 정보 동등성을 대신하지 않는다. 토큰은 보고하되 동등성의 근거로 쓰지 않는다

동등성 점검은 사람이 한다. S와 E를 나란히 두고 "한쪽에만 있는 사실"을 열거해 0인지 확인하고,
그 목록을 실험 기록에 남긴다.

## 과제와 골드

기존 40개 요청을 **파일럿 규모**로 쓴다. 확증 실험의 표본 수는 파일럿 후 검정력 산정으로 정한다.

포함할 유형:

- 완전 명세
- 필수값 누락
- 구조 선택이 모호한 것
- **조건 변경으로 필수값 집합이 바뀌는 것**
- 외부 데이터·추가 등록 모델이 필요한 것
- 미등록 자산·의존성 누락·단위 범위 오류
- 정상 종료하지만 목적에 맞지 않는 구성
- **지원 자산이 없어 질문 또는 거절이 정답인 것**

마지막 유형이 없으면 "차단을 늘려 성공률을 올리는" 전략이 벌점 없이 통한다.

### 골드 작성 규칙

- 최소 두 명이 독립 작성한다
- 정답을 단일 JSON으로 제한하지 않는다. **허용 자산 집합·값 범위·필수 질문·정당한 차단 사유**를
  함께 적는다
- **골드의 필수값은 등록 계약을 복사해 만들지 않는다.** 실제 실행 인터페이스·코드·기준 실행과
  대조해 만든다. 계약을 복사하면 계약의 누락이 골드의 누락이 되어, 짝 스펙의
  `checkInputBindingCoverage`가 잡으려는 바로 그 결함을 실험이 재생산한다

## 지표

| 지표 | 정의 |
|---|---|
| 과제 해결 정확도 | 올바른 실행 구성, 또는 골드가 요구한 질문·차단을 낸 과제 비율 |
| 무수정 유효 실행률 | 실행 가능한 과제 중 수동 수정 없이 출력 계약·사전 의미 규칙을 통과한 비율 |
| 필수값 누락률 | 골드 활성 필수값 중 값도 질문도 차단도 없는 비율 |
| 비실재 참조율 | 미등록 자산·필드 참조 비율. **생성 단계와 실행 승인 단계를 따로 집계** |
| 근거 없는 값 비율 | 출처가 없거나 출처가 그 값을 지지하지 않는 확정값 비율 |
| 과차단률 | 실행 가능한 정상 과제를 부당하게 차단한 비율 |
| 재사용률 | 골드 기능 요구 중 기존 자산으로 올바르게 충족한 비율 |
| 접근성 | 완료율 · 응답 필드 수 · 질문 턴 · 총시간 · 수정 횟수 · 이탈 |
| 운영 비용 | 토큰 · 도구 · 실행 비용, 자산 등록·수정 시간 |

### 집계 규칙

- **참조 수가 0인 결과를 "환각률 0"으로 처리하지 않는다.** 빈 답변·거절·도구 실패를 따로 센다.
  아무것도 참조하지 않은 답은 틀리지 않았을 뿐 맞지도 않았다
- **폼 한 번을 질문 1개로 세지 않는다.** 질문 턴과 **사용자가 실제로 답해야 하는 필드 수**를
  둘 다 보고한다. 질문을 묶거나 전문용어를 늘려 질문 수만 줄이는 것을 막는다
- 정당한 거절이 정답인 과제는 별도 집계한다. 정확도에 섞으면 차단 전략이 유리해진다
- 접근성은 질문 수 단독으로 설명하지 않는다. 시간·수정 횟수·이탈을 함께 본다

## 절제 실험

우선순위 순이다.

1. **SES 표현 제거** — 같은 정보와 실행 지원을 유지한다 (E → S)
2. **서브태스크 템플릿 제거** — 표현 효과와 절차 효과를 가른다 (E+W → E)
3. **사용자 질의 제거** — 미해결 필수값을 임의로 채우지 않고 차단한다
4. **MCP 제거** — 외부 정보가 필요한 과제에서만 효과를 본다
5. **검증 피드백 제거** — 최종 채점기는 그대로 둔다
6. **그래프 검색 대 명시적 관계 탐색** — 같은 관계 데이터를 쓴다
7. **질문 순위 변경** — 질문 개수뿐 아니라 시간·이탈을 비교한다

3·5처럼 검증을 떼는 실험은 **격리된 시험 환경에서만** 실행한다.

## 성공 기준

### 공학적 인수 기준

짝 스펙의 테스트 표와 같다.

- 알려진 미등록 참조·필수값·단위·교차 제약 오류 시험을 **모두 실행 전에** 차단
- 실행된 모든 입력에 출처와 변환 이력 존재
- 구조 변경 후 새 필수값을 누락하지 않음
- 정상 골드 구성을 잘못 차단하지 않음
- 고정된 원장·스냅샷으로 같은 실행 설정을 생성

### 연구 성능 기준

- **최소 의미 효과량과 사용자 시간 허용 한도를 파일럿 후, 확증 실험 전에 고정한다.**
  결과를 보고 정하면 그 기준은 결론이지 기준이 아니다
- 효과크기와 신뢰구간 중심으로 판단한다. p값 단독으로 결론짓지 않는다
- 과제 내·사용자 내 반복을 독립 표본으로 세지 않는다
- **저장된 동일 응답의 채점 재현과 LLM 재호출 결과 재현을 구분해 보고한다**

## 반증 조건

- 같은 정보에서 S 대 E 차이가 사전에 정한 **동등성 범위 안**이면 SES의 표현 우위 주장을 철회한다
- 신뢰구간이 그 범위보다 넓으면 "판단 근거 부족"이며, 동등성 확인과 다르다.
  **동등성 한계 ±δ를 정했고 신뢰구간 전체가 ±δ 안에 들어오면 그것은 "작은 차이"를 지지하는
  결과이지 판단 불가가 아니다.** 두 경우를 보고서에서 구분해 쓴다
- 실행률이 올라도 의미 오류·과차단·사용자 시간이 나빠지면 전체 성공으로 보지 않는다
- 그래프가 효과 없이 등록·유지 비용만 늘리면 제거한다
- 두 번째 도메인에서 효과가 사라지면 일반화 주장을 그 도메인 범위로 제한한다

## 기존 베이스라인의 위치

`docs/reports/llm-baseline-2026-09-11/REPORT.md`는 임의 수치를 기록한다. 이는 **자산에 접근할
정보 경로가 없는 조건(N)의 결과**로 설명해야 하며, "프롬프트 개선은 효과가 없다"의 근거가 아니다.
한 사례로 그 결론을 내릴 수 없고, 이 실험의 T 조건이 바로 그 구분을 위해 있다.

## 선행 조건

이 실험은 **짝 스펙의 실행 경로와 채점기가 확인된 뒤에** 시작한다.

실행기나 채점기가 틀리면 조건 간 차이를 해석할 수 없다. 순서는 이렇다.

1. 골드 정상·오류 사례로 기존 실행기와 채점기를 확인한다 (채점기 정답/오답 20쌍을 초기 점검 규모로)
2. S와 E의 정보 동등성 점검 목록을 만들고 0을 확인한다
3. 파일럿(40과제)으로 S·E·S+W·E+W를 돌린다
4. 효과량과 검정력을 보고 확증 실험의 표본 수와 최소 의미 효과량을 고정한다
5. 확증 실험
6. 핵심 효과가 확인된 뒤에 두 번째 도메인·그래프 검색·자산 규모 확대를 평가한다
