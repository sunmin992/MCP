# 브로커 — 거주민 조건으로 거르고, 비슷한 후보는 차이를 보여 주고 사용자가 고른다

2026-10-07. 대상: `broker` 모듈(4단계 매칭)과 시뮬레이터 능력 카드.

## 1. 목적

브로커에 시뮬레이터 서버가 여럿 등록되고 서버마다 거주민(직업) 모델이 다를 때,
"학생이 많고 주부가 많은 동네의 쓰레기 수거" 같은 요청이 **거주민 조건을 근거로** 맞는 서버에 닿게 한다.

지금은 요청 프로필에 거주민을 넣을 칸이 없다(`RequestProfile`: 도메인 · 공간 규모 · 환경 조건 · 목적 · 비교 축).
장량동 카드가 `occupation-mix` 를 할 수 있다고 적어 두었지만 매칭 단어가 "직업" · "거주민 구성" 뿐이라
"학생이 많은 동네" 는 근거로 잡히지 않는다. 같은 도메인의 서버가 여럿이면 점수가 같아져 순위가 서버 id 순서로 정해진다.

**성공 기준**

- 요청한 직업을 모델링하지 않는 서버는 후보에서 빠지고, 빠진 이유와 조정 제안이 남는다.
- 조건을 모두 만족하는 서버가 하나면 그 서버로 연결한다(`MATCH`).
- 여럿이면 브로커가 고르지 않는다. 서버끼리 **다른 점**만 모아 내고, 사용자가 고른다(`CHOOSE`).

## 2. 범위

**한다**

- 요청 프로필에 `population` 칸을 더한다.
- 능력 카드에 `populationTypes` 를 더한다. 후보끼리 비교할 항목은 카드에 이미 있는 칸을 쓴다(4.2).
- 점수 계산을 없애고 "모두 만족하면 남긴다" 로 바꾼다.
- 후보가 여럿이면 차이 표와 함께 `verdict: CHOOSE` 를 낸다.

**하지 않는다**

- 브로커가 자연어를 해석하는 일. 해석은 LLM 이 하고, 브로커는 카드가 적은 말과 대조만 한다.
- 브로커 쪽 공통 어휘 사전. 카드의 `matchKeys` 로 충분하다.
- 의미 검색(임베딩), 두 서버 동시 실행 후 비교.
- "학생이 많은" 을 직업 비율로 바꾸는 규칙. 연결 뒤 시뮬레이터 템플릿(`occupationMix`)과 확인 화면이 지금처럼 처리한다.

## 3. 요청 프로필

```
domain:                waste-collection
spatialScale:          "한 동네"
population:            ["학생이 많음", "주부가 많음"]   ← 새 칸
environmentConditions: ["평일 교통량"]
objective:             "민원이 적은 수거 시각"
comparisonAxes:        ["수거 시각"]
```

- `population` 은 LLM 이 사용자 말에서 거주민에 관한 표현을 뽑아 넣는 문자열 목록이다.
- 다른 선택 칸과 같은 규칙을 따른다. 사용자가 말하지 않았으면 `null`(모름), 말했는데 조건이 없으면 빈 목록이다.
  `null` 은 거르는 데 쓰지 않는다.
- `find_simulators` 의 입력 스키마에 `population` 을 더한다. 구절 하나에 거주민 하나로 받는다고 안내한다 —
  브로커는 구절을 해석하지 않으므로 "학생과 노인" 을 한 구절로 받으면 노인을 못 다뤄도 통과한다.

## 4. 능력 카드

### 4.1 `populationTypes`

카드가 모델링하는 거주민 유형을 모두 적는다. `key` 는 시뮬레이터의 값 그대로 쓴다.
장량동 카드는 `occupationMix` 선택지 다섯 개를 모두 적는다.

```json
"populationTypes": [
  { "key": "BlueCollar",   "matchKeys": ["생산직", "공장", "현장직", "노동자"], "model": "07:22 ± 30분에 배출" },
  { "key": "Student",      "matchKeys": ["학생", "대학생"],                    "model": "08:58 ± 30분에 배출" },
  { "key": "Housewife",    "matchKeys": ["주부", "전업주부"],                  "model": "14:00 ± 30분에 배출" },
  { "key": "NightShift",   "matchKeys": ["야간", "교대 근무", "교대근무", "야근"],"model": "21:00 ± 30분에 배출" },
  { "key": "OfficeWorker", "matchKeys": ["직장인", "회사원", "1인 직장인"],    "model": "07:50 ± 30분에 배출" }
]
```

배출 시각은 템플릿 `jn.occupationMix` 의 질문 문구, ± 30분은 `leaveSigma` 기본값이다.

### 4.2 후보끼리 비교할 항목

새 칸을 만들지 않는다. 카드에 이미 있는 칸을 그대로 비교한다.

| 항목 이름 | 카드의 칸 | 예 (장량동) |
|---|---|---|
| `region` | `region` | 대한민국 경상북도 포항시 북구 장량동 |
| `unit` | `analysisUnit.label` | 원룸촌 한 블록 |
| `calibration` | `quality.calibration[]` 중 `measured: true` 의 `what (source)` 를 카드 순서대로 이은 것 | 교통 지체 배수 (SK TMAP 경로예측 API), … |

칸이 없거나 비어 있는 카드는 그 항목을 "적혀 있지 않음" 으로 비교한다.

## 5. 판정

### 5.1 거르기

카드마다 요청 조건을 하나씩 대조한다. 대조 방식은 지금 `CandidateMatcher` 와 같다 —
`unsupported` 를 먼저 보고, 그다음 지원 목록의 `matchKeys` 가 요청 구절 안에 들어 있는지 본다.

| 조건 | 통과 |
|---|---|
| 도메인 | `domain` 또는 `domainAliases` 에 맞는다 |
| 공간 규모 | `analysisUnit.matchKeys` 에 맞고 `unsupported` 에 걸리지 않는다 |
| 거주민 (`population` 의 구절 하나하나) | `populationTypes[].matchKeys` 중 하나에 맞는다 |
| 환경 조건 (하나하나) | `environmentMatchKeys` 에 맞고 `unsupported` 에 걸리지 않는다 |
| 목적 | `objectiveMatchKeys` 에 맞는다. 그 표가 없는 카드는 판단하지 않는다(지금과 같다) |

**`null` 인 조건은 대조하지 않는다.** 하나라도 통과하지 못한 카드는 후보에서 빠진다.
빠진 카드의 `mismatches` 와 `adjustments` 는 지금 형식 그대로 만든다. 거주민이 어긋나면 조정 제안은
"이 서버가 다루는 거주민: 생산직, 학생, …" 처럼 카드의 `populationTypes` 를 보여 준다.

점수(`SCALE_POINT` · `ENV_POINT` · `OBJECTIVE_POINT`)와 `MatchResult.score` 는 없앤다.

### 5.2 남은 후보 수에 따른 결과

| 남은 수 | verdict | 내용 |
|---|---|---|
| 0 · 같은 도메인 카드 있음 | `ADJUST_REQUEST` | 지금과 같다 |
| 0 · 같은 도메인 카드 없음 | `NONE` | 지금과 같다 |
| 1 | `MATCH` | 지금과 같다 |
| 2 이상 | `CHOOSE` | 새 결과. 아래 5.3 |

### 5.3 `CHOOSE` — 차이 찾기

비교하는 항목:

1. 4.2 의 세 항목
2. 요청의 거주민 구절마다 그 구절에 걸린 유형 **전부**의 `model`(여럿이면 key 순으로 "key: 모델" 을 잇는다). 항목 이름은 `population:<구절>` 이다. 예: `population:학생이 많음` 은 각 카드의 학생 배출 모델

후보들 사이에서 **값이 하나라도 다른 항목만** 낸다. 출력:

```json
{
  "verdict": "CHOOSE",
  "candidates": [
    { "serverId": "jangnyang-waste-sim", "name": "...", "endpoint": "http://localhost:8090/mcp", "reasons": ["..."] },
    { "serverId": "x-waste-sim", "name": "...", "endpoint": "...", "reasons": ["..."] }
  ],
  "differences": [
    { "item": "region", "values": { "jangnyang-waste-sim": "포항 장량동 원룸촌", "x-waste-sim": "대전 유성구 대학가" } },
    { "item": "population:학생이 많음", "values": { "jangnyang-waste-sim": "08:58 ± 30분에 배출", "x-waste-sim": "수업 시간표 기반" } }
  ],
  "nextStep": "사용자에게 differences 를 보여 주고 어느 서버를 쓸지 물으십시오. 고른 서버의 endpoint 로 가고, 그 대화에서는 브로커를 다시 부르지 마십시오."
}
```

- `candidates` 는 서버 id 오름차순이다. 순서에 추천의 뜻이 없다.
- **차이가 하나도 없으면** `differences` 는 빈 목록이고, `nextStep` 은 "후보들이 이 요청에 대해 같습니다. 첫 번째 서버로 가십시오" 다.
  로그에 동등한 후보가 있었다고 남긴다.
- 사용자가 고른 뒤의 흐름은 `MATCH` 뒤와 같다. 브로커는 다시 부르지 않는다(`BrokerSessions` 의 재조회 알림 그대로).

## 6. 연결 뒤

바뀌지 않는다. 시뮬레이터에서 `get_templates` → `plan_subtasks` → `build_scenario` → 확인 화면 승인 → `run_scenario_by_token`.
LLM 은 브로커에 넘긴 `population` 표현을 템플릿 `occupationMix` 질문을 채우는 데 쓰고, 그 값은 확인 화면에서 사람이 승인한다.

## 7. 오류 · 경계

- `population` 에 빈 문자열만 있는 구절은 버린다(`RequestProfile` 의 `blankToNull` 과 같은 이유).
- `populationTypes` 가 없는 카드에 `population` 이 있는 요청이 오면, 그 카드는 거주민 조건을 통과하지 못한다.
  사유는 "이 카드는 다루는 거주민을 적지 않았습니다" 다. 적혀 있지 않은 것을 된다고 하지 않는다.
- 카드 등록(`POST /api/simulators`) 때 `populationTypes[].key` 중복은 거절한다.

## 8. 테스트

**브로커** (`CandidateMatcherTest`, `BrokerVerdictTest`, `RequestProfileTest`)

- 학생 · 주부를 요청 → 장량동 통과, `district-waste-sim`(거주민 미선언) 탈락 + 조정 제안
- 장량동에 없는 거주민("노인") 요청 → 장량동 탈락, 조정 제안에 다섯 직업
- 장량동과 비슷한 테스트 카드 하나를 더 등록 → `CHOOSE`, `differences` 에 다른 항목만 있다
- 두 카드의 비교 항목이 모두 같다 → `CHOOSE`, `differences` 빈 목록
- `population` 이 `null` 이면 거주민으로 거르지 않는다
- 점수 관련 단언은 지운다

**시뮬레이터**

- 장량동 카드의 `populationTypes[].key` 집합 = 템플릿 `occupationMix` 의 `allowed` 집합. 직업이 코드에 더해지거나 빠졌는데 카드가 그대로면 실패한다.
