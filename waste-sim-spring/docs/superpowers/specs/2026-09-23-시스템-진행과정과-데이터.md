# 장량동 SES 기반 시뮬레이션 서비스 — 진행 과정과 주고받는 데이터 전체

2026-09-23. 대상 저장소 `waste-sim-spring`, `develop`, HEAD `13530df`.
이 문서가 정본이다. 앞선 [단계별 메시지 명세](2026-09-22-mcp-단계별-메시지-명세.md)와
[요약](2026-09-22-mcp-단계별-메시지-요약.md)은 배차 간격을 실험 변수로 두던 이전 판이다.

---

## 1. 구성요소와 통신 채널

| 구성요소 | 소유한 것 | 하는 일 |
|---|---|---|
| **사용자** | 목적과 조건 | 요청 제시 · 부족분 답변 · 시나리오 확인 · 결과 확인 |
| **LLM** | 없음 | 요청 해석 · 서버 탐색 · **서브태스크 생성** · 값 추출 · 질문 · PES 조립 · 도구 호출 |
| **브로커 MCP 서버** | 등록된 서버들의 능력 카드 | 후보 탐색과 매칭 |
| **시뮬레이터 MCP 서버** (장량동) | SES · 서브태스크 템플릿 · 실행 연결표 · 검증기 · 엔진 | 규칙 제공 · 검증 · 시나리오 생성 · 실행 |

채널은 넷이다.

| 채널 | 방향 | 해당 단계 |
|---|---|---|
| 등록 | 시뮬레이터 → 브로커 | 0 |
| 대화 | 사용자 ↔ LLM | 1 · 7 · 8 · 11 · 15 · 16 |
| 탐색 | LLM ↔ 브로커 | 3 · 4 |
| 작업 | LLM ↔ 시뮬레이터 | 5 · 8(검증) · 9 · 10 · 13 · 14 |
| **확인** | **사용자 ↔ 시뮬레이터 (직통)** | **12** |

**확인만은 LLM을 거치지 않는다.** 나머지 왕래는 전부 LLM을 지난다. 12단계만 사용자가
시뮬레이터의 확인 화면(`/confirm.html`)을 직접 열어 동의하고, 그때에만 확인 토큰이
발급된다. LLM을 거치게 두면 모델이 스스로 동의를 만들어낼 수 있어 토큰이 "사람이 보고
동의했다"를 뜻하지 못한다.

시뮬레이터 서버 안은 네 블록이다 — 시뮬레이션 정보 / 서브태스크 생성 / 시나리오 생성 / 시뮬레이션 실행.

LLM에게 열려 있는 도구는 여섯이다. **확인은 이 목록에 없다.**

| 도구 | 하는 일 | 단계 |
|---|---|---|
| `get_capability` | 능력 카드 원문 | 0 |
| `get_templates` | 서브태스크 템플릿 14개 | 5 |
| `plan_subtasks` | 답변으로 서브태스크 집합 계산 | 6 |
| `validate_answers` | 허용값·범위 대조, 보정 없음 | 8 |
| `build_scenario` | 실행 설정 N벌 생성·검증 (토큰은 주지 않는다) | 9 · 10 |
| `get_scenario_status` | 확인 상태와 발급된 토큰 **읽기** | 12 |
| `run_scenario_by_token` | 토큰이 맞을 때만 실행 | 13 |

## 2. 반복해서 쓰이는 데이터 객체

단계마다 새 데이터를 만드는 것이 아니라, 아래 여덟 객체가 단계를 지나며 채워지고 변환된다.

| 객체 | 만들어지는 곳 | 담는 것 |
|---|---|---|
| **능력 카드** | 0단계 (시뮬레이터) | 신원 · SES 요약 · 적용 범위 · 품질/비용 · **미지원 항목** |
| **요청 프로필** | 2단계 (LLM) | 목적 · 도메인 · 조건(근거 문구) · **미제시 항목** · 가정 목록 |
| **서브태스크 템플릿** | 제공자가 사전 작성, 5단계에 제공 | 결정 대상 · 선택지/범위 · **생성 조건** · 추출 규칙 · 기본값 · 실행 대응 |
| **서브태스크 인스턴스** | 6단계 (LLM) | 어느 템플릿에서 왔는지 · 생성 조건 판정 결과 · 상태 · 값 · 값의 출처 |
| **PES** | 9단계 (LLM 제출 → 서버 확정) | 선택·개수·속성·연결이 닫힌 모델 구조 |
| **실험 프레임** | 9단계 | 실험 변수 · 기간 · 반복 · 관측 지표 |
| **실험 시나리오** | 10단계 (서버) | 검증 통과한 실행 설정 N벌 · 확인 토큰 |
| **실행 결과** | 14단계 (서버) | 조건별 지표 · 품질 표시 · 가정 · 재현 정보 |

여기에 **출처 기록**이 2단계부터 15단계까지 전 구간을 관통한다. 값마다
`사용자 발화 / 사용자 답변 / 승인된 기본값 / 미승인 기본값` 중 무엇인지를 달고 다닌다.

## 3. 단계별 데이터

원본 스윔레인 표: [`docs/architecture/그림2.png`](../../architecture/그림2.png) — 16단계를
사용자 · LLM · 시뮬레이터 · 브로커 레인으로 나눈 그림이며 이 절의 바탕이다.

**그림에서 고쳐야 할 칸이 셋이다.** 확인 흐름이 바뀌었고(§1 채널 표) 그림은 아직 옛 흐름이다.

| 칸 | 그림에 적힌 것 | 지금 |
|---|---|---|
| 10 · 시뮬레이터 | 시나리오 확인 요청과 함께 토큰 발급 | 토큰을 주지 않는다. 상태는 `UNCONFIRMED` |
| 12 · 사용자 | LLM 레인에 대고 "이 시나리오로 시뮬레이션 실행해줘" | 시뮬레이터 레인으로 **직통** — 확인 화면에서 누른다. 그때 토큰이 나온다 |
| 13 · LLM | 시나리오로 실행 요청 | `get_scenario_status` 로 토큰을 **읽어** 실행 요청에 싣는다 |

5단계 템플릿 칸도 10개가 아니라 14개다 — 경로 배정용량이 늘었다(범위 보고서 §9).

이번 사례의 실제 값을 함께 적는다.

### 0 — 시뮬레이터가 브로커에 등록

**시뮬레이터 → 브로커**

```
[신원]        서버 식별자 / 이름 / 도메인 / 연결 정보
[SES 요약]    구성요소와 요소 간 관계
              사용자가 결정 가능한 항목과 그 선택지·범위
[적용 범위]   분석 단위: 원룸촌 한 블록 — 장량동 전체가 아니다
              공간 규모: 건물 1~26동(Node_A~Z 상한), 동당 세대 상한 없음
                        수거 지점은 건물마다 1개이므로 최대 26개
              환경 조건: 교통 프로파일 · 분리배출 · 임대인 점검 · 요일 일정
              답할 수 있는 질문: 수거 시각 · 수거 주기 · 배차 간격 · 차량 수 · 차종
                        민원 수 · 적재율 · 차량 가동률 · 수거 완료 시각
              보정 지역: 경상북도 포항시 북구 장량동
[품질·비용]   정확도 방식: 이벤트 기반 확률 모형
              기간: 1~365일 / 반복: 기본 30회, 최대 100회
              보정 자료: 포항 북구 수거일정 CSV · TMAP 24시간 실측
              실행 시간: 기간 × 반복에 비례, 보통 2초
              비용: 없음 (로컬 실행)
[미지원]      항목마다 사유 코드 · 매칭 키 · 대안을 함께 등록한다.
              브로커가 요청 프로필과 대조하려면 매칭 키가 있어야 한다.

  비용 산출            UNSUPPORTED_METRIC
    매칭 키  metric:cost, 비용, 예산, 저렴, 경제적
    대안    민원 수 · 차량 가동률 · 수거 완료 시각
    근거    모델에 연료·인건비·운영비 항이 없다

  실제 도로 기반 이동시간  DATA_UNAVAILABLE
    매칭 키  feature:realRoadTravel, 실제 도로, 실도로, 실측 이동시간
    대안    교통구역 근사
    근거    수거 지점 좌표 미확보 (구현은 되어 있다)

  차량마다 다른 차종      UNSUPPORTED_STRUCTURE
    매칭 키  feature:perTruckType, 차량별 차종, 차종 섞어
    대안    차종을 바꿔 여러 번 실행해 비교
    근거    truckType이 전역 단일값이다

  행정동 전체 규모       OUT_OF_SCOPE
    매칭 키  scale:district, 동 전체, 장량동 전체, 만 명
    대안    원룸촌 블록 단위 실행
    근거    수거 지점 26개 상한 (전체는 약 2,700개 필요)

  골목 진입 판정        DATA_UNAVAILABLE
    매칭 키  feature:alleyAccess, 골목 진입, 이면도로 접근
    대안    없음
    근거    수거 지점이 등록되어 있지 않다

  운영 기준선 비교       NO_BASELINE
    매칭 키  compare:currentOperation, 현재 운영, 지금보다
    대안    없음
    근거    실제 투입 차량 대수·차종 자료가 없다

  실측 대조 검증        NO_GROUND_TRUTH
    매칭 키  validate:groundTruth, 실제와 맞는지, 정확한지
    대안    설정 간 비교로만 사용
    근거    실제 민원 기록이 없다

  새 모델·엔진 생성      OUT_OF_SCOPE
  다른 지역            OUT_OF_SCOPE
```

**브로커 → 시뮬레이터** — 등록 확인 · 능력 카드 해시 · 등록 시각

> **미지원 항목을 반드시 등록한다.** 이것이 4단계의 제한 표시와 7단계의 사전 고지로 이어진다.
> 이 연결이 끊기면 사용자가 실행을 다 마친 뒤에야 "그건 못 합니다"를 듣게 된다.

### 1 — 사용자가 목적·조건 입력

**사용자 → LLM**

```
"한 동네 정도 되는 주택가에서 평일 교통량을 반영해서,
 하루 몇 시에 쓰레기를 수거하는 게 민원이 가장 적은지 알고 싶어"
```

### 2 — LLM이 목적과 조건 추출

**LLM 내부** — 요청 프로필

```
도메인:        쓰레기수거                    근거 "쓰레기를 수거하는"
공간 규모:      한 동네                      근거 "한 동네 정도" — 모호, 구체값 미제시
환경 조건:      평일 교통량                   근거 "평일 교통량을 반영해서"
시뮬레이션 대상: 쓰레기 수거차량
목적:          민원이 가장 적은 수거 시각      근거 "하루 몇 시에", "민원이 가장 적은지"

요구 지표:      metric:complaints             근거 "민원이 가장 적은지"
              — 무엇을 기준으로 좋다고 볼 것인가. 비용을 요구하면 여기 담긴다
요구 기능:      feature:trafficAware          근거 "평일 교통량을 반영해서"
              — 어떤 계산을 원하는가. 실제 도로를 요구하면 여기 담긴다

미제시:  건물 수·세대 / 차량 크기·수 / 배차 간격 / 기간·반복 / 거주민 구성
        요구 정확도 / 기한 / 비용
가정한 값: 없음
```

> **요구 지표와 요구 기능을 반드시 채운다.** 이 둘이 3단계로 넘어가 브로커의 미지원 판정
> 대상이 된다. 비워 두면 브로커가 대조할 것이 없어, 지원하지 않는 요청이 7단계까지 살아남는다.
>
> **이 단계에서 추정하지 않는다.** "한 동네"를 곧바로 4동으로 바꾸면 그 순간 임의 가정이 된다.
> 추정은 7단계 이후 기본값 **제안**으로만 하고 반드시 출처를 남긴다.
> 목적이 "민원이 가장 적은 수거 시각"으로 확정된 것이 중요하다 —
> "효율적인지"처럼 기준이 없으면 평가 기준을 묻는 작업이 하나 더 생긴다.

### 3 — LLM이 브로커에 서버 조회

**LLM → 브로커**

```
도메인: 쓰레기수거
공간 규모: 한 동네
환경 조건: 평일 교통량
시뮬레이션 대상: 쓰레기 수거차량
목적: 민원이 가장 적은 수거 시각
요구 지표: metric:complaints          ← 미지원 판정 대상
요구 기능: feature:trafficAware       ← 미지원 판정 대상
선호: 정확도·기한·비용 모두 미지정
후보 수: 3
```

### 4 — 브로커가 매칭

**브로커 → LLM**

```
후보: 장량동 시뮬레이터 MCP
매칭 근거: 도메인 일치 / 원룸촌 블록 규모 지원 / 평일 교통 반영 지원 / 수거 시각 비교 가능
비용 0 · 예상 2초 · 정확도 이벤트 기반 확률 모형
연결 정보: (엔드포인트)

요청 중 미지원: 없음
  요구 지표 metric:complaints  → 지원
  요구 기능 feature:trafficAware → 지원
  공간 규모 "한 동네"          → 원룸촌 블록으로 해석 가능, 구체값은 7단계에서 확인

이 서버의 일반 제한 (요청에는 없었으나 결과 해석에 영향)
  골목 진입 판정 불가 — 수거 지점 미등록
  운영 기준선 없음   — 실제 투입 차량 자료 없음
  실측 대조 불가     — 실제 민원 기록 없음
  실제 도로 기반 이동시간 미지원 — 교통구역 근사로 대체

순위 기준: 도메인 0.4 / 공간 규모 0.3 / 능력 0.3
          사용자가 정확도·기한을 제시하지 않아 기본 가중치를 적용했다
추가 확인 권장: 요구 정확도 — 후보 간 차이가 순위를 뒤집을 수 있다
```

> **요청에 담긴 불가능한 처리는 여기서 전부 드러나야 한다.** 7단계까지 미루면 그때는 이미
> 서버가 정해진 뒤라, 다른 후보가 그 기능을 지원하는지 따져 볼 기회가 사라진다.
> 만약 사용자가 "가장 적은 비용으로"라고 했다면 이 자리에서 이렇게 나온다 —
>
> ```
> 요청 중 미지원
>   [1] 비용 최소화 (metric:cost)
>       사유  이 시뮬레이터는 비용을 산출하지 않습니다
>       근거  모델에 연료·인건비·차량 운영비 항이 없습니다
>       대안  민원 수 · 차량 가동률 · 수거 완료 시각
>       다른 후보  없음 — 등록된 서버 중 비용을 산출하는 곳이 없습니다
> ```
>
> `다른 후보` 칸은 브로커만 답할 수 있다. 개별 서버는 자기 것만 안다.
> **목적 자체가 미지원이면 LLM은 5단계로 가지 않고 먼저 사용자에게 확인받는다.**
> 동의 없이 지표를 바꿔 진행하면 결과가 맞아도 요청 충족 실패로 센다.
>
> **확장(3.5)** 목록 검색으로 부족하면 브로커가 후보에게 직접 묻는다 —
> "이 조건으로 수행 가능한가". 응답에 `수행 가능 여부 / 제약 / 필요 입력 / 가정해야 할 항목`이 담긴다.
> **어느 서버가 더 많이 가정해야 하는가**가 후보 비교 기준이 된다.

### 5 — 시뮬레이터가 서브태스크 템플릿 제공

**LLM → 시뮬레이터** — SES 식별자 · 버전 · 목적(수거 시각) · 범위(목적 달성에 필요한 최소)

**시뮬레이터 → LLM** — 템플릿 9개 + 조건부 1개. 항목마다 여섯 칸이 붙는다.

```
수거차량 크기      5톤 / 2.5톤 / 1톤          기본 5톤    전 차량 공통, 차량별 선택 미지원
수거차량 수        1 이상                     기본 1
수거 시각          0~1439분                   기본 720(12:00)
배차 간격          0~1439분                   기본 0      생성 조건: 실제 운행 차량 2대 이상
수거경로 교통량     반영 / 무시                기본 무시    반영이면 교통 프로파일 항목이 추가 생성
  └ 교통 프로파일   등록된 프로파일 id                      생성 조건: 교통량 반영일 때만
이동시간 방식      교통구역 근사                           구역 간 자유주행시간 × 시간대 지체 배수
                                                        실제 도로 기반은 지점 좌표 없어 차단
건물 유형/수       1~26동                     기본 4동
건물당 세대        1 이상 (상한 없음)          기본 25세대
시뮬레이션 기간     일수 + 반복 횟수            기본 30일 × 30회
거주민 직업·배출시간 생산직 / 학생 / 전업주부    기본 3종 순환 배정
                  배출 시각 07:22 / 08:58 / 14:00, 표준편차 30분

[채우지 못한 칸]  교통 프로파일의 자연어 표현 대응 — SES에서 유도할 수 없어 제공자가 적어야 한다
```

각 항목에 붙는 여섯 칸과 그 출처는 이렇다.

| 칸 | 내용 | 출처 |
|---|---|---|
| 결정 대상 | SES의 어느 지점인가 (선택지 / 개수 / 속성 / 연결) | **SES** |
| 생성 조건 | 이 작업을 언제 만드는가 | **SES** (조건부 연결·의존) |
| 선택지·범위 | 허용값의 닫힌 집합 또는 범위 | **SES** + **코드**(검증기) |
| 추출 규칙 | 발화에서 값을 뽑는 표현형·단위·중의성 처리 | **제공자** |
| 기본값·미충족 시 행동 | 질문 / 기본값 제안 / 차단 | **제공자** + **코드** |
| 실행 대응 | 확정값이 실행까지 가는 경로 | **코드** |

> 템플릿은 **질문 목록이 아니라 규칙집이다.** 서버는 규칙을 주고, 인스턴스는 LLM이 만든다.

### 6 — LLM이 서브태스크 구성

**LLM 내부** — 생성 조건을 평가해 인스턴스를 만든다.

```
[발화에서 채움]
수거경로 교통량 = 반영        근거 "평일 교통량을 반영해서"
교통 프로파일 = 평일          생성 조건 "교통량 반영" 충족 → 생성됨

[질문 필요]
수거차량 크기 · 수거차량 수 · 건물 유형/수 · 건물당 세대 · 기간·반복 · 거주민 직업·배출시간

[보류]
배차 간격 — 생성 조건 "실제 운행 차량 2대 이상"을 아직 판정할 수 없다 (차량 수 미정)

[생성하지 않음]
없음
```

> 두 가지가 여기서 관찰된다. 교통 프로파일은 **다른 답변 때문에 생겨났고**,
> 배차 간격은 **다른 답변이 없어서 보류됐다.** 고정 질문지에서는 나올 수 없는 동작이다.

### 7 — LLM이 미완성 항목 재요청

**LLM → 사용자**

```
수거차량 크기를 무엇으로 할까요? (5톤 / 2.5톤 / 1톤)
수거차량은 몇 대인가요? (1 이상)
   └ 2대 이상이면 차량 간 배차 간격도 알려 주세요
건물은 몇 동이고 한 동에 몇 세대인가요?  (기본값 4동 · 25세대)
며칠치를 몇 번 반복할까요?              (기본값 30일 × 30회)
거주민 직업 구성과 배출 시각은?          (기본값 생산직·학생·전업주부, 07:22 / 08:58 / 14:00)

[묻지 않는 것]
수거 시각 — 이번 요청의 목표값이므로 비교 범위로 다룬다
```

> 배차 간격을 **차량 수에 딸린 조건부 질문**으로 낸다. 1대라고 답하면 그 항목은 사라진다.

### 8 — 사용자 답변, 서버가 검증

**사용자 → LLM**

```
"25세대 주택 4동을 30일 동안, 1톤 차량 3대를 15분 간격으로 내보낼 거야"
```

**LLM → 시뮬레이터** — 항목별 원문 답변

**시뮬레이터 → LLM** — 정규화와 검증 결과

```
수거차량 크기   "1톤" → 1톤              허용 선택지 안
수거차량 수     "3대" → 3                1 이상 충족
배차 간격      "15분 간격" → 15          0~1439 범위 안
건물 유형/수    "주택 4동" → 4            1~26 범위 안(Node_A~Z 상한)
건물당 세대     "25세대" → 25             1 이상, 상한 없음
시뮬레이션 기간  "30일 동안" → 30일        반복 횟수는 기본 30회로 제안
거주민 직업·배출시간  미답변 → 기본값 사용, 사용자 승인 대기

[조건 재평가]
배차 간격: 실제 운행 차량 = min(4, 3) = 3 > 1  →  보류 해제, 값 15분으로 확정

[거부 없음]
[재검증 필요 없음]
```

거부가 나는 경우의 형태:

```
"3톤" → 허용 선택지 밖 (5톤/2.5톤/1톤)         재질문, 기본값 대체 불가
"실제 도로로" → 구간 데이터 미확보             재질문 + 대안 제시(교통구역 근사)
"비용도 알려줘" → 모델에 비용 항 없음          미지원 고지 (0단계 등록 항목)
```

> **값이 바뀌면 그 값에 의존하는 검증을 전부 무효화하고 다시 본다.** 이전 결과를 재사용하지 않는다.

### 9 — LLM이 PES 구성 및 시나리오 생성 요청

**LLM → 시뮬레이터** — PES와 실험 프레임

```
[PES — 모델 구조]
건물 유형/수         주택 4동                        ← 사용자
건물당 세대          25세대 (총 100세대)              ← 사용자
거주민 직업          생산직 34 / 학생 33 / 전업주부 33  [기본값, 순환 배정]
배출 시각           07:22 / 08:58 / 14:00, 표준편차 30분  [기본값]
1인 배출량          0.9 kg/일, 변동 0.3kg            [기본값]
수거지점            건물마다 1개 = 4개                [모델 구조상 고정]
수거지점 용량/임계   30kg / 적재율 0.8                [기본값]
폐기물 유형          단일 유형 (분리배출 미지정)        [기본값]
수거차량 크기        1톤 — 용량 1000kg · 기동성 1.6 · 골목 진입 가능   ← 사용자
수거차량 수          3대, 실제 운행 min(4,3) = 3대     ← 사용자
배차 간격           15분                            ← 사용자
수거 시각           ★미확정 — 실험 변수★
수거경로            건물 4개를 3대에 순환 배정
수거경로 교통량      반영, 평일 프로파일               ← 사용자
                   TMAP 실측 지체 배수 24시간 (04시 1.01 ~ 18시 1.73)
이동시간 방식        교통구역 근사
                   구역 간 자유주행시간 10.2~190.8초 × 시간대 지체 배수 ÷ 기동성 1.6
민원 판정           배출 시 적재 초과 (적재율 ≥ 0.8)
                   임대인 점검 비활성 · 교통 혼잡 가중 1.0  [기본값]
이벤트              배출 · 수거

[실험 프레임]
실험 변수    수거 시각 {06:00, 09:00, 12:00, 15:00, 18:00}   ← LLM 제안, 12단계 확인
기간         30일                                           ← 사용자
반복         30회                                           [기본값]
수거 주기     매일                                           [기본값]
관측 지표     판정 — 민원 수
             설명 — 최대 적재량 · 잔여량 · 직업별 민원
             참고 — 차량 가동률 · 수거 완료 시각 (정차시간 0분의 영향을 받음)
```

> **PES에서 닫히지 않은 것은 수거 시각 하나이고, 그것이 실험 변수다.**
> 실험 프레임이 5개 값으로 닫으면 완전히 닫힌 설정이 5벌 나온다.
> 모델 결정과 실험 결정을 나눠 두는 이유가 여기서 드러난다.

### 10 — 시뮬레이터가 검증하고 시나리오 확인 요청

**시뮬레이터 → LLM**

```
[검증]
선택 닫힘      차량 크기 · 이동시간 방식 · 배출 시각 모델이 모두 허용 집합 안 — 통과
개수          건물 4 ≥ 1, 차량 3 ≥ 1 — 통과
범위          수거 시각 360~1080 ⊂ 0~1439, 배차 간격 15 ⊂ 0~1439 — 통과
데이터 가용성   구역 간 자유주행시간 12쌍 존재 · 평일 프로파일 존재 — 통과
구역 배정      건물 4동은 지점 id를 구역 id로 보는 폴백으로 충족 — 통과
              ※ 5동 이상이면 구역 배정 규칙이 별도로 필요하다
구역 내 이동    4동이 서로 다른 구역이라 구역 내 이동 없음 — 통과
차종 동차      집합 전체가 단일 차종 — 통과
효과 유무      실제 운행 3대 > 1 → 배차 간격 15분이 결과에 반영됨 — 통과
역검증        5벌의 실행 설정을 되읽어 PES와 대조 — 차이 없음

[경고 1건]
지점 정차시간이 0분이다. 차량 가동률과 수거 완료 시각이 실제보다 짧게 나온다.
민원 판정에는 간접적으로만 영향을 준다.

[실험 시나리오 — 실행 설정 5벌]
공통:  건물 4동 · 동당 25세대 · 거주민 직업 기본 3종
      배출량 0.9kg · 변동 0.3 · 수거장 용량 30kg · 민원 임계 0.8
      차량 1톤 3대 · 배차 간격 15분 · 수거 주기 매일
      교통 반영 · 평일 프로파일 · 교통구역 근사 · 정차시간 0분
      30일 × 30회
```

| 실행 | 수거 시각 | 1호차 | 2호차 | 3호차 |
|---|---|---|---|---|
| run-0 | 06:00 | 06:00 | 06:15 | 06:30 |
| run-1 | 09:00 | 09:00 | 09:15 | 09:30 |
| run-2 | 12:00 | 12:00 | 12:15 | 12:30 |
| run-3 | 15:00 | 15:00 | 15:15 | 15:30 |
| run-4 | 18:00 | 18:00 | 18:15 | 18:30 |

```
[적용된 기본값과 근거]
반복 30회 · 거주민 직업 3종 · 배출 시각 07:22/08:58/14:00 · 배출량 0.9kg
수거장 용량 30kg · 민원 임계 0.8 · 정차시간 0분   — 모두 모델 기본값, 사용자 확인 대상

[상태]  UNCONFIRMED — 돌릴 수 있으나 사용자가 확인하지 않았다
       확인 토큰은 여기서 나오지 않는다. 검증 통과는 "돌릴 수 있다"이고
       확인은 "돌려도 된다"이다. 둘을 한 단계로 합치면 "확인하지 않은 것"을
       표현할 자리가 없어지고, 그러면 토큰이 확인을 뜻한다고 말할 수 없다.
```

### 11 — LLM이 시나리오를 사용자에게 전달

**LLM → 사용자** — 값마다 출처를 붙인다.

```
대상    주택 4동 · 동당 25세대              ← 요청하신 값
차량    1톤 3대, 15분 간격으로 출발          ← 요청하신 값
교통    반영, 평일 프로파일                 ← "평일 교통량"에서 읽음
이동시간 교통구역 근사                      (실제 도로 기반은 지점 좌표가 없어 사용 불가)
비교    수거 시각 06 / 09 / 12 / 15 / 18시 5개 조건
기간    30일 × 30회                        ← 기본값
거주민   생산직·학생·전업주부, 배출 07:22 / 08:58 / 14:00   ← 기본값(장량동 기준)
정차시간 0분                               ← 기본값, 가동률·완료시각이 짧게 나옵니다

이대로 실행할까요?  확인 화면을 열어 주십시오 → http://localhost:8090/confirm.html
```

LLM은 요약을 보여주고 **확인 화면으로 안내만** 한다. 대신 눌러 줄 수 없다.

### 12 — 사용자 확인 (사용자 ↔ 시뮬레이터 직통)

**사용자 → 시뮬레이터** — 확인 화면에서 직접 동의한다. 이 단계만 LLM을 거치지 않는다.

화면이 보여주는 것:

```
사용자가 승인하지 않은 기본값     맨 위에 경고로 — 못 보여주면 확인이 확인이 아니다
사용자가 정한 값과 그 출처        답변키 · 값 · USER / MODEL_DEFAULT / DERIVED
조건마다 달라지는 것              실행 설정들을 비교해 화면이 스스로 찾는다
막힌 사유                        있으면 확인 버튼이 잠긴다
```

`이 설정으로 돌린다`를 누르면 그때 **확인 토큰이 발급된다** — 이 시나리오의 설정 해시에
고정되며, 값이 하나라도 바뀌면 무효다. 수정이면 8단계로 돌아가고 토큰은 폐기된다.

**LLM은 `get_scenario_status`로 읽기만 한다.** 확인 전에는 토큰 자리가 비어 있고
다음에 할 일(확인 화면 안내)이 대신 온다. 읽는 문만 열려 있으므로 모델이 동의를
만들어낼 수 없고, 사람이 누를 때까지 기다렸다가 토큰을 집어 갈 수는 있다.

```
쓰기:  사람 ─ /confirm.html ──────────> CONFIRMED, 토큰 발급
읽기:  LLM  ─ get_scenario_status ───> state, (확인됐으면) confirmToken
```

### 13 — LLM이 실행 요청

**LLM → 시뮬레이터**

```
시나리오 식별자 · 확인 토큰 · 동기 실행 · 제한 시간 120초
실행 규모: 5개 조건 × 30일 × 30회 = 4,500 시뮬레이션 일
```

서버는 **토큰의 설정 해시와 현재 시나리오 해시를 대조**한다. 다르면 실행하지 않는다.

### 14 — 시뮬레이터가 결과 전달

**시뮬레이터 → LLM** — 조건마다 한 벌씩 5벌.

```
[판정 지표 — 사용자가 기준으로 지목한 것]
민원 평균 · 표준편차 (30회 반복)
적재 초과 민원 / 임대인 점검 민원 (이번엔 0)
직업별 민원 · 일자별 민원

[설명 지표 — 왜 그런 결과가 나왔는지]
최대 적재량 (용량 30kg 대비 적재율)
잔여량 · 미수거 수요 · 가장 많이 남은 건물

[참고 지표 — 정차시간 0분의 영향을 받으므로 판정에 쓰지 않는다]
차량 가동률 · 수거 능력 사용률 · 평균 수거 완료 소요 · 교통 지체
부분 수거 / 미수거 / 용량 소진 운행 횟수 · 운행별 상세

[검사·품질 — 엔진이 이미 결과에 실어 보낸다]
질량 보존 오차 (배출 − 수거 − 잔여, 0이어야 한다)
좌표 품질: 교통구역 대표점
데이터 품질 경고 · 적용된 가정
시드 · 반복별 값 (재현 정보)
```

결과는 2단계의 목적을 축으로 정렬한다. 물은 것이 수거 시각이므로 수거 시각이 행이 된다.

| 수거 시각 | 민원 평균 | 표준편차 | 최대 적재량 | 잔여량 | 직업별 민원 |
|---|---|---|---|---|---|
| 06:00 | | | | | |
| 09:00 | | | | | |
| 12:00 | | | | | |
| 15:00 | | | | | |
| 18:00 | | | | | |

> **표가 비어 있다.** 채우려면 실제 실행이 필요하며, 지어낸 값을 넣지 않는다.
> 현재 저장소는 삭제된 `ses`·`subtask` 패키지를 참조하는 코드 때문에 빌드가 실패한다.

### 15 — LLM이 결과 전달

**LLM → 사용자** — 네 부분

```
[답]
  ○○시에 수거할 때 민원이 가장 적었습니다 — 30일 평균 ○○건 (표준편차 ○○).

[근거]
  이르면 전업주부 몫(평균 14:00 배출)이 다음날까지 남고,
  늦으면 적재율 0.8을 넘긴 상태가 길어집니다.
  ○○시에서 최대 적재량이 ○○kg (용량의 ○○)로 가장 낮았습니다.
  직업별로 보면 06:00에는 전업주부가, 18:00에는 생산직이 많습니다.

[전제]
  30일 × 30회, 배차 간격 15분입니다.
  거주민 구성과 배출 시각은 포항시 북구 장량동 기준값입니다 —
  일반적인 "한 동네"가 아니라 특정 지역으로 보정된 값이라 다른 동네에 그대로 옮기기 어렵습니다.
  지점 정차시간을 0분으로 두어, 차량 가동률과 수거 완료 시각은 참고치입니다.

[한계]
  이동시간은 교통구역 근사라 같은 구역 안의 방문 순서는 결과에 반영되지 않습니다.
  실제 도로 기반 계산은 수거 지점 좌표가 없어 수행하지 못했습니다.
```

> **답의 대상은 2단계의 목적과 같아야 한다.** 물은 것이 수거 시각이므로 답도 수거 시각이다.
> 민원 건수만 나열하고 끝내면 숫자가 맞아도 요청 충족 실패로 센다.

### 16 — 사용자가 결과 확인

**사용자 → LLM** — 반응에 따라 되돌아가는 단계가 다르다.

| 반응 | 되돌아가는 곳 | 이유 |
|---|---|---|
| 수용 | 종료 | |
| 값만 변경 — "차량 5대로" | **8단계** | 값 검증부터 다시. 단 차량 수는 배차 간격의 생성 조건이라 6단계 재평가가 따라온다 |
| 구조 변경 — "교통 빼고" | **6단계** | 교통 프로파일 작업이 사라진다 — 인스턴스 집합 자체가 달라진다 |
| 범위 밖 — "실제 도로로", "비용도" | **7단계** | 미지원 사유와 대안을 제시하고 다시 묻는다 |

어느 경우든 **이전 검증 결과와 확인 토큰을 폐기한다.**

---

## 4. 전 구간을 관통하는 다섯 규칙

1. **2단계에서 추정하지 않는다.** 모호한 표현은 미제시로 남기고, 추정은 7단계 이후 기본값 제안으로만 한다.
2. **생성 조건이 서브태스크의 존재를 정한다.** 거짓이면 만들지 않고, 판정할 수 없으면 보류한다.
3. **값마다 출처를 달고 다닌다.** 사용자 미승인 기본값으로 실행되면 임의 가정으로 집계한다.
4. **확인 토큰이 확인과 실행을 묶는다.** 토큰은 사람이 확인 화면에서 동의할 때만 나오고, LLM은 읽기만 한다. 설정이 바뀌면 무효가 되어 실행되지 않는다.
5. **값이 바뀌면 재검증한다.** 이전 검증 결과를 재사용하지 않는다.

## 5. 이번 사례 한 장 요약

```
요청   "한 동네 정도 되는 주택가에서 평일 교통량을 반영해서,
        하루 몇 시에 쓰레기를 수거하는 게 민원이 가장 적은지 알고 싶어"
  ↓   브로커가 장량동 서버 선택 (도메인 · 규모 · 교통 · 수거 시각 비교 지원)
  ↓   템플릿 9개 + 조건부 1개 수신
  ↓   교통량 반영 · 평일 프로파일 — 발화에서 추출
      차량 크기 · 수 · 건물 · 기간 · 거주민 — 질문 5건
      배차 간격 — 차량 수 확정까지 보류
  ↓   "25세대 주택 4동을 30일 동안, 1톤 차량 3대를 15분 간격으로"
      → 실제 운행 3대 > 1 → 배차 간격 보류 해제
  ↓   PES 확정, 수거 시각만 열림 → 실험 프레임이 5개 값으로 닫음
  ↓   검증 9항목 통과, 경고 1건(정차시간 0분), 역검증 일치
  ↓   사용자가 확인 화면에서 직접 확인 → 토큰 발급 → 실행
  ↓   수거 시각별 민원 비교 — 06시 32 / 09시 64 / 12시 36 / 15시 36 / 18시 30
```
