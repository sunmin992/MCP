# 흐름 기반 SES 추출 설계 — 색인 축 대신 값 흐름을 읽는다

2026-09-16 · 코드 `develop @ 48d5e9b` · 대상 `docs/research/s1-ses-extraction/sesx/`

파이프라인이 코드에서 뽑아낸 것은 SES 계층이 아니라 **배열의 색인 공간**이었다. 이 문서는
질문을 바꾸고, 코드가 할 수 있는 판단을 코드로 되돌리는 설계를 확정한다. 참조 골격은
ref-v8(`reference-ses.json`)이다.

## 1. 무엇이 어긋났는가

`com/wastesim/model` 의 클래스 16개에 `Building`·`Truck`·`Trip` 이 없다. 전부 DTO·enum·
설정·결과다. 대상 세계의 개체는 배열의 정수 첨자로만 존재한다.

```
SimulationEngine:254   double[][] fill = new double[nB][nT];
SimulationEngine:278   Map<Integer, Double> remainingTruckCapacity;
```

담는 것과 담기는 것의 관계가 코드에 문장으로 없다. `A.getB()` 도 `List<B> bs` 도 없다.
그래서 "무엇이 무엇의 부분인가"를 물으면 모델이 근거로 댈 것이 없고, 손에 잡히는 유일한
구조인 **선언의 차원**을 부모-자식으로 읽는다.

관측된 결과:

| 증상 | 사실 |
|---|---|
| 분해 4건 중 3건이 배열 축에서 나왔다 | `new double[nB][nT]` 를 부모-자식으로, 맵 값의 `truckId` 를 MULTI 로 읽었다 |
| 루트 후보 4개가 정확히 색인 축 4개다 | `fill[건물][종류]`·`tripAccs[운행]`·`byDay[요일]`·`byOcc[직업]` |
| 자식 7개의 역할 근거가 0건이다 | 자식이 기존 개체면 조립기가 근거를 요구하지 않는다 |
| 결합 23건이 전부 `source == target` 이다 | 값이 바뀌는 자리를 전부 결합으로 냈다 |

뒤의 둘은 프롬프트가 아니라 **코드의 구멍**이다.

- `assemble.py:431` — `member_evidence` 를 **자식이 새 개체일 때만** 요구한다.
  `prompts/T2/tree_rules.md` 는 "이미 존재하는 자식에도 필요하다"고 적어 두었으나 집행되지 않는다.
- `contract.py:199` — 분해에는 `SELF_REFERENCE` 검사가 있으나 **결합에는 없다.**
  자기결합 23건이 구조 검사를 그대로 통과했다.

축들은 서로 형제다. 형제만 나오면 트리가 서지 않는다. `r2` 가 3회 일관되게 "루트가 없다"고
답한 것은 정직한 답이었다 — 코드에 "장량동 시뮬레이터"라는 구문이 없기 때문이다.

## 2. 무엇을 바꾸는가 — 네 가지

1. **결합 질문을 쪼갠다.** "무엇이 무엇에게 보내는가" 대신 "이 값을 **쓰는 자리와 읽는 자리**가
   어디인가"(e1 — b2 가 이미 낸 씨앗을 완성한다)와 "그 자리의 **주체는 누구인가**"(e2)로 나눈다.
   짝짓기와 방향은 코드가 만든다.
2. **트리 모양을 계약으로 못 박는다.** ref-v8 이 쓰는 세 층(`boundary` → `set` → `stateful` →
   `type`)만 합법으로 두고, 배열 차원을 부모-자식으로 접은 분해를 기계적으로 보류한다.
3. **루트를 검토 리비전으로 옮긴다.** 추출은 숲으로 끝난다. 사람이 근거와 함께 루트를 넣고,
   그것은 `origin: "human"` 으로 표시된다.
4. **계약의 구멍 둘을 막는다.** 결합 `SELF_COUPLING`, 기존 자식에도 `member_evidence`.

바꾸지 않는 것: 기존 계획 `T2`·`T2b`·`T2c`·`T2d`·`T2-tree`, `runs/`, `run_s1.py`, `run_t.py`.
과거 실행 조건을 그대로 둔다. 새 계획 이름은 `T2-flow` 다.

## 3. e1 — 자리

b2 는 이미 상태 값마다 `state_evidence`(값이 **바뀌는** 자리)와 `consumption_evidence`(값이
**다시 읽혀** 다음 계산·분기를 바꾸는 자리)를 따로 묻고 있다. 쓰는 자리와 읽는 자리의 구분은
이미 있다. 없는 것은 **그 목록이 빠짐없다는 보장**이다 — b2 는 분류를 정당화할 만큼만 인용하면
되고, 실제로 `fill` 의 네 자리를 다 적을 이유가 없다.

그러므로 e1 은 새 질문이 아니라 **완성 단계**다. 같은 질문을 두 번 하지 않는다.

**입력:** `classification == "entity_state"` 인 b2 항목마다, 값 표현식과 b2 가 이미 적은
`state_evidence`·`consumption_evidence` 를 각각 쓰기·읽기 씨앗으로 넣어 준다.

**질문:** 이 값을 쓰는 행과 읽는 행 중 **아래 목록에 빠진 것**을 인용하라. 씨앗을 다시 적지
말고, 씨앗 중 틀린 것이 있으면 `corrections` 에 적어라. **개체 이름을 적지 않는다.**

씨앗과 새로 낸 자리는 합쳐져 하나의 자리 목록이 되며, 각 자리에 `from: "b2" | "e1"` 이 붙는다.
이 단계의 답은 전부 색인으로 대조 가능한 것뿐이다.

```json
{"value_sites": [{
  "value": {"code_expression": "fill[b][t]",
            "declaration": {"file_path": "...", "start_line": 254, "end_line": 254, "quote": "..."}},
  "writes": [{"file_path": "...", "start_line": 424, "end_line": 424,
              "quote": "fill[ce.building][t] *= keepFraction", "effect": "decrease"}],
  "reads":  [{"file_path": "...", "start_line": 414, "end_line": 414,
              "quote": "dueTotal += fill[ce.building][t]"}],
  "corrections": []}]}
```

위 `writes`·`reads` 에는 **씨앗에 없던 자리만** 적는다. `corrections` 에는 씨앗 중 그 값의
쓰기·읽기가 아닌 것을 `{"site_id": "...", "why": "..."}` 로 적는다.

`effect` 는 `increase`·`decrease`·`assign`·`unknown` 중 하나이고, **연산자에서 읽히는 것만**
적는다. 모르면 `unknown` 이다(README 규칙 1의 기본값 규약을 따른다).

자리 식별자는 코드가 붙인다 — `e1:<값 순번>:w<n>` · `e1:<값 순번>:r<n>`. 모델이 만들지 않는다.

## 4. e2 — 주체

**질문:** e1 이 낸 자리마다, 그 자리에서 **어느 개체를 대신해** 값이 바뀌거나 읽히는가.

자리 목록은 식별자와 인용을 붙여 그대로 준다. 이름은 **확정 개체 목록에서만** 고른다.
맞는 개체가 없으면 `unresolved` 와 이유다 — 지어낼 자리를 주지 않는다.

```json
{"site_actors": [{"site_id": "e1:v0:w0", "entity": "수거", "attribute": null,
                  "why": "...",
                  "evidence": [{"file_path": "...", "start_line": 410, "end_line": 410,
                                "quote": "for (CollectionEvent ce : ...)"}]}]}
```

**주체 근거는 자리 인용과 별개의 자리를 요구한다.** `fill[ce.building][t]` 한 줄로는 `ce` 가
무엇인지 알 수 없고, 그것을 말해 주는 것은 감싸는 선언·반복문 머리다. 근거 없이 이름만 적은
주체는 `unresolved` 로 간다.

`attribute` 는 그 자리에서 갱신·소비되는 속성이다. 못 대면 `null` 이다. 코드가 지어내지 않는다.

## 5. 결합 파생 — `flow.py`

모델은 이 단계에 참여하지 않는다. 순수 함수이며 모델 호출 없이 시험된다.

**규칙.** 값 하나마다 `쓰는 자리 × 읽는 자리` 를 전부 짝짓는다.

- 주체가 **서로 다른** 쌍 → 결합. 같은 `(출발 개체·속성, 도착 개체·속성, 값)` 으로 여러 쌍이
  나오면 **결합 하나로 합치고** 기여한 자리 인용을 전부 단다. 쓰는 행이 둘이라고 결합이 둘이
  되지 않는다.
- 주체가 **같은** 쌍 → 결합이 아니다. `internal_update` 판정 기록으로 가며 `origin_raw` 를
  단다. README 규칙 3(조용한 삭제 없음)이다.
- 주체가 `unresolved` 인 자리가 낀 쌍 → `held: unknown_reference`. 자리 인용은 살아 있으므로
  사람이 주체만 붙이면 살아난다.

`payload.kind` 는 공유 값에서 파생되었으므로 `shared_state` 로 확정된다. `mechanism` 은
값 표현식과 기여한 행 번호로 코드가 조립한다.

`fill` 에서 나오는 것:

```
쓰기 {배출@454, 수거@424} × 읽기 {수거@414, 넘침판정@470}
  배출 → 수거        shared_state: fill[건물][종류]
  배출 → 넘침판정    shared_state: fill[건물][종류]
  수거 → 넘침판정    shared_state: fill[건물][종류]
  수거 → 수거        ← 같은 주체. internal_update
```

414행 `dueTotal += fill[...]` 의 수거 판단은 **수거 자신이** 한다. 읽는 쪽을 무조건
별도 판정 개체로 세우지 않는다 — 그러면 같은 주체 쌍이 영영 생기지 않고, 자기 갱신이
결합으로 위장한다.

ref-v8 의 `수거지점.적재량 → 적재초과 판정.판정` · `→ 임대인 점검 판정.판정` 이 이 모양이다.
방향이 처음으로 코드에서 나온다.

## 6. 트리 모양 계약

ref-v8 은 세 층을 정해진 순서로 반복한다.

```
수거장 적재 시스템  ─aspect「적재 구성」→   수거지점 집합 · 폐기물 유형 집합
수거지점 집합       ─multi 「수거지점 다중」→ 수거지점
거주민             ─spec  「직업 축」→      생산직 · 학생 · 전업주부 · 야간 교대근무자 · 1인 직장인
```

**`fill[건물][종류]` 의 두 축은 ref-v8 에도 둘 다 있다.** 다만 부모-자식이 아니라
`수거장 적재 시스템` 의 ASPECT **형제**이고, 각자 `집합 → 개체` 로 따로 내려간다. 그러므로
규칙은 "배열 차원을 버려라"가 아니라 **"배열 차원은 형제다. 부모-자식으로 묶으면 기각"** 이다.

합법 간선. 어휘는 기존 `ENTITY_KIND`(`stateful`·`boundary`·`set`·`type`·`unknown`)를 그대로 쓴다.
표는 **정답지의 간선을 전부 훑어** 뽑았다 — 좁게 잡으면 정답지 자신이 위반이 된다.

| 부모 역할 | 종류 | 자식 | 금지 |
|---|---|---|---|
| `boundary` · `stateful` | ASPECT | `boundary` · `set` · `stateful` | 자식에 `type` |
| `set` | MULTI | **개체 하나** (`stateful`) | 둘 이상, 이종 자식 |
| `boundary` · `stateful` | SPEC | `type` 들 | 부모가 `set` |

ASPECT 자식을 집합으로만 좁힐 수 없다 — 정답지에 `경로 교통 시스템 ─aspect→ 수거 경로`
가 있다. 개체도 ASPECT 부모가 된다 — `민원 판정 ─aspect→ 적재초과 판정 · …`. boundary 도
SPEC 부모가 된다 — `시나리오 실험 ─spec→ 단일 실행 · …`. 남는 불변은 셋이다: **MULTI 의
부모는 집합이고 자식은 하나**, **SPEC 의 자식은 유형**, **ASPECT 의 자식에 유형은 없다**.
집합은 MULTI 로만 가르고, 유형은 부모가 되지 않는다.

이것이 `운행 → 트럭` 을 구조적으로 막는다. 운행은 `set` 이 아니고 트럭은 운행의 복제
인스턴스가 아니므로 MULTI 를 만들 자리가 없다. ref-v8 모양이면 `운행 집합 ─multi→ 운행` 이고
트럭은 형제 계통이다.

**분해에 축 이름을 요구한다.** ref-v8 의 분해는 전부 이름을 갖는다 — `시스템 구성`·`직업 축`·
`수거지점 다중` — 그리고 트리 그림의 중간 상자가 그 이름이다. 현재 계약에 분해 이름 필드가
없어 그 모양이 나올 수 없다. `decompositions` 에 `label` 을 넣고 `d.md` 가 축 이름을 묻는다.

## 7. 집행 — 조립기 보류

계약 위반(`contract.py` 실패)으로 승격하지 않는다. 거짓 양성이 승인 경로 전체를 막기 때문이다.
조립기가 `held` 로 옮기고 사람이 검토에서 되살린다. 예외는 자기결합 하나다(9절).

| 조건 | 판정 |
|---|---|
| 역할이 6절 표에 어긋난다 | `held: shape_violation` |
| MULTI 자식이 둘 이상이다 | `held: shape_violation` |
| 두 자식의 `member_evidence` 가 **같은 선언 행**을 가리킨다 (ASPECT·MULTI 만) | `held: shape_violation` — 같은 선언의 서로 다른 차원 |
| `member_evidence` 가 없다 (**자식이 기존 개체여도**) | `held: unknown_reference` |

같은 선언 행 규칙을 **SPEC 에는 걸지 않는다.** 축의 값들은 열거 상수 선언 한 줄에 함께
적히는 것이 정상이다 — 정답지의 `직업 축`(5종)이 그렇다. 부분(ASPECT·MULTI)에서 한 줄이 두
자식을 똑같이 가리키면 그 줄은 어느 쪽이 어느 쪽인지 보이지 못하므로 역할 근거가 아니다.

마지막 항목이 `assemble.py:431` 의 조건 변경이다. 자식이 새 개체인지와 무관하게 요구한다.
트리 모드에서는 `composition.py` 가 이미 같은 것을 요구하므로, 실제로 새로 막히는 것은
트리 모드가 아닌 경로다. 자기 참조·빈 자식 검사는 역할 근거보다 **앞**에서 본다 — 더
근본적인 어긋남이므로 그쪽 이름으로 보류되어야 진단이 정확하다.

## 8. 루트 — 검토 리비전

`T2-flow` 의 단계에서 `r`·`r2` 를 뺀다. 추출은 숲으로 끝난다. `structure.py` 가 이미 진입 차수
0 개체를 세므로, 보고서는 "루트 후보 N개, 루트 없음"을 사실대로 적는다. 없는 것을 묻지 않는다.

루트는 `review.py` 의 새 판정 종류 `root_designation` 으로 들어온다. 사람이 적는 것:

- 루트 이름과 역할(`boundary`), 사유
- 후보들을 묶는 ASPECT 분해와 그 `label` (ref-v8 의 `시스템 구성`)

새 리비전이 만들어지고 재검증을 거친다. 이때 만들어진 개체·분해에는 `origin: "human"` 이
박힌다. 보고서와 채점은 이 표시로 **모델이 뽑은 것과 사람이 넣은 것**을 가른다. "파이프라인이
루트를 찾았다"는 주장이 생길 자리를 없앤다.

## 9. 계약 변경

- **`SELF_COUPLING` 추가** — `source.entity_id == target.entity_id` 인 결합은 불합격.
  파생 경로가 자기쌍을 막더라도 다른 경로로 들어온 것이 통과하는 구멍을 닫는다.
- **`decompositions[].label`** — 축 이름. 없으면 `held`(계약 실패가 아니다).
- **`couplings[].derived_from`** — 기여한 e1 자리 식별자 목록. 역추적 가능성을 위한 것이다.
- `schema_version` 을 올린다. 기존 산출물은 옛 버전으로 읽힌다.

## 10. 단계 배선

```
T2-flow = a b2 g c d e1 e2 f b3
```

`r`·`r2` 없음. `CONTEXT_FROM`:

- `e1` ← `b2`(`entity_state` 항목의 값 표현식과 `state_evidence`·`consumption_evidence` 씨앗), `a`
- `e2` ← `e1`(자리 목록), `b2`·`g`·`d`(확정 개체 이름)
- `f` ← `b2`, `d`, 파생된 결합 (`e` 대신 `flow.py` 산출물)
- `b3` ← `b2`, 파생된 결합

`e1`·`e2` 를 `NAME_LIST_STAGES` 에 넣는다 — `e2` 는 확정 개체 이름 목록을 받아야 한다.
`e1` 은 이름을 쓰지 않으므로 넣지 않는다.

## 11. 시험

기존 인수 시험 47건은 그대로 둔다. 추가하는 것:

| 시험 | 확인 |
|---|---|
| 씨앗 | b2 의 `state_evidence`·`consumption_evidence` 가 자리 목록에 `from: "b2"` 로 들어가고, e1 이 중복해 낸 자리가 하나로 합쳐진다 |
| 정정 | e1 의 `corrections` 가 가리킨 씨앗 자리가 목록에서 빠지고 사유가 판정 기록에 남는다 |
| 파생 | 고정 e1·e2 입력(`fill` 예)에서 결합 3건 + `internal_update` 1건. 모델 호출 없음 |
| 병합 | 같은 `(출발, 도착, 값)` 쌍 둘이 결합 하나로 합쳐지고 자리 인용 둘이 다 붙는다 |
| 미해결 | `unresolved` 주체가 낀 쌍이 `held` 로 가고 자리 인용이 보존된다 |
| 자기결합 | `source == target` 인 산출물이 `SELF_COUPLING` 으로 불합격 |
| 모양 | `운행 ─MULTI→ 트럭`, MULTI 자식 둘, 같은 선언 행을 가리키는 두 자식 — 각각 `held` |
| 역할 근거 | 자식이 **기존 개체**인 분해에서 `member_evidence` 가 없으면 `held` |
| 루트 | `T2-flow` 산출물이 루트 없이도 검토까지 가고, `root_designation` 후 재검증을 통과한다 |
| 출처 | 사람이 넣은 개체·분해가 보고서에서 `origin: "human"` 으로 갈라진다 |

**정답지 대조** — ref-v8 의 결합 목록을 상대로 `flow.py` 파생 결과를 재는 척도를
`score_ses.py` 에 넣는다. 현재는 옛 계약 기준이라 결합을 재지 못한다(README "아직 하지 않은 것").

## 12. 범위 밖

- **`엔진 실행` 가지.** 손그림 트리에는 `엔진 실행 → DEVS 엔진` 이 있으나 ref-v8 은 이를
  뺐다 — `_meta` 에 "engine(실행 수단)"으로 제외 사유가 적혀 있고, `r.md` 규칙 3("실행 엔진은
  구조를 돌리는 것이지 구조의 일부가 아니다")과 같은 판단이다. **ref-v8 을 따른다.**
- 자동 수리 루프. 첫 비교에서 제외한다.
- AST 색인. 정규식 색인으로 시작한다.
- 실행 매개변수 연결 후보 생성.

## 13. 이 설계가 주장하지 않는 것

이 설계는 모델이 SES 를 더 잘 뽑게 만들지 않는다. **코드에 적혀 있지 않은 것을 묻지 않게**
만들 뿐이다. 이 코드에 적혀 있는 것은 색인 축과 값 흐름이고, 지금까지 파이프라인은 색인 축만
읽었다. 값 흐름을 읽게 하는 것이 전부다.

부분-전체 관계는 여전히 코드에 없다. 6절의 모양 계약은 틀린 분해를 **막을** 뿐 옳은 분해를
만들어 내지 못한다. 루트가 사람 몫으로 남는 것과 같은 이유다.
