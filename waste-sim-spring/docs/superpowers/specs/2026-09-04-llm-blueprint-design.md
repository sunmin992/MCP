# LLM 설계도 구성 · 시나리오 생성 설계

## 1. 목적

사용자가 자유 문장으로 요청하면, LLM이 그 문장에서 시뮬레이션 설계도를 채우고, **부족한 값은
지어내지 않고 되묻고**, 만들 수 없는 요청은 **무엇이 필요한지와 함께 거부한다.**

지금은 요청이 들어오면 고정 문항 33개를 순서대로 다 묻는다. 이 설계는 그 흐름을 없애지 않고
LLM 경로를 하나 더 만든다.

### 관통하는 원칙

> **LLM은 읽고, 시스템은 판정한다.**

LLM이 잘하는 것은 자연어에서 값을 뽑는 것이고, 믿을 수 없는 것은 "이 요청이 가능한가",
"이 값이 유효한가" 같은 판정이다. 그래서 LLM 출력은 **사용자가 손으로 친 답변과 완전히
동일하게** 취급한다 — 기존 검증기를 통과하지 못하면 설정에 들어가지 못한다.

이 프로젝트가 반복해서 겪은 실패는 근거 없는 값이 사실처럼 흘러든 것이다(지어낸 좌표로 낸
"구간별 3.8배 편차"가 장량동의 성질처럼 인용됐다). LLM은 그 실패를 자동화할 수 있는 위치에
있으므로, 신뢰 경계를 명시적으로 둔다.

## 2. 범위

### 이 설계에 포함되는 것

- 자유 문장에서 설계도 필드를 채우는 LLM 추출
- 추출값이 요청에 실제로 근거하는지 검사(인용 강제)
- 필드별 근거 선언과 그에 따른 자동 채움 / 되묻기 분기
- 만들 수 없는 요청의 거부와 "무엇이 필요한지" 안내
- 근거 없는 값을 단일 값이 아니라 범위로 보고하는 다중 실행

### 포함되지 않는 것 (의도적 제외)

| 제외 항목 | 이유 |
|---|---|
| 다른 지역 지원 (지역 온보딩) | 별도 프로젝트. 거부 메시지가 그 재료 목록을 낸다 |
| 3축 이상 격자 실험 | 조합이 터진다. 2축까지 |
| LLM이 거부를 판정하는 것 | 판정은 결정적으로 유지 — 테스트로 고정해야 한다 |
| LLM이 결론 문장을 쓰는 것 | 범위와 반응 여부는 계산해서 내고, 해석은 사람이 한다 |
| 기존 13개 실험의 축 재작성 | 그대로 둔다 |
| 기존 33문항 흐름 대체 | 남긴다. LLM 실패 시 폴백 경로다 |

## 3. 현재 상태 (2026-09-04 코드 대조)

### 고정 문항 세트 v3

- `src/main/resources/subtask/jangnyang-simulator-v3.json`
- SHA-256 `03e17000541fc68799e297e283dfddfa31469226c7bb040d9b5a27316670ea47`
- 33문항 / 6단계, 단계별 **3 → 5 → 7 → 8 → 7 → 3**
- `stage` 분포: `COLLECT` 31 · `CONFIRM` 2
- 해당없음 허용 9개: `dischargeWindow`, `collectionTimes`, `routeAvailableCapacityKg`,
  `dispatchIntervalMinutes`, `trafficProfileId`, `routeTravelMinutes`,
  `serviceMinutesPerSite`, `intraZoneTravelMinutes`, `routeSequence`
- 반드시 답해야 하는 22개(COLLECT · 해당없음 불허)

### 이미 있어서 재사용하는 것

| 구성요소 | 상태 | 이 설계에서의 역할 |
|---|---|---|
| `JangnyangScenarioSpec` | 있음 | **이것이 설계도다.** 세트 해시·답변 원본·적용 기본값·가정·최종 설정을 담는다 |
| `SubtaskAnswerSource.LLM_NORMALIZED` | **선언만 있고 쓰는 곳 없음** | LLM이 넣은 값의 출처 표시 — 이 설계가 그 자리를 채운다 |
| `retryQuestion` (문항별) | 있음 | 되묻기 문구 |
| `AppliedDefault` | 있음 (3필드: `engine`, `routeTravelMinutes`, `trafficProfileId`) | 근거 있는 값 자동 채움 + 근거 기록 |
| `JangnyangSubtaskValidator` | 있음 | LLM 값도 이 검증기를 통과해야 한다 |
| `ScenarioService` 13개 실험 | 있음 (축이 코드에 고정, `yLabel` 기본 "월 평균 민원") | 다중 실행의 기존 사례 |
| `DataQualityFlag` · `isNotForOperationalUse()` | 2026-09-02 추가 | 가정 비교 실험 표시 |
| `ZoneAssignmentRule` | 2026-09-02 추가 | 근거 없는 비교 축의 첫 사례 |

### 근거가 코드에 거의 없다

`wasteMeanKg`·`capacity`·`threshold`는 "논문 원본 재현"이라는 **공통 주석에 묶여 있을 뿐
개별 출처(절·표)가 없다.** `days`·`seeds`·`wasteSigma`·`leaveSigma`는 아무 근거 표시도 없다.

그리고 **그 출처를 되짚을 방법이 없다.** 저장소에 논문도 참고문헌도 없고 남은 것은 주석
문장 하나뿐이다. 그래서 이 값들은 "확인하지 않은 값"이 아니라 **이 시뮬레이터가 정해 둔
값**이다 — 언젠가 확인될 것처럼 표시하면 있지도 않은 숙제를 가리키게 되므로, `MODEL_DEFAULT`
종류로 그 성질을 그대로 적는다.

## 4. 설계

### 4.1 전체 흐름과 신뢰 경계

```
사용자 요청 (자유 문장)
  │
  ├─① RequestInterpreter (LLM)
  │     문장에서 값을 뽑는다. 출력: {필드, 값, 근거가 된 원문 조각}
  │     언급 없는 필드는 비워 둔다 — 채우지 않는다
  │
  ├─② FeasibilityGate (결정적, LLM 아님)
  │     뽑힌 값으로 판정한다. 거부면 이유 + 부족한 것 목록을 반환하고 끝낸다
  │
  ├─③ 기존 세션에 LLM_NORMALIZED로 제출
  │     기존 검증기가 전부 검사한다. 실패한 값은 버리고 되묻기 대상으로 내린다
  │
  ├─④ GapResolver
  │     남은 필드를 **근거로** 가른다 (§4.2)
  │
  ├─⑤ 되묻기 (기존 retryQuestion) → USER_DIRECT
  │
  └─⑥ 기존 ScenarioBuilder → JangnyangScenarioSpec → 미리보기 → 실행
```

②가 LLM이 아닌 것이 요점이다. LLM은 "부산"이라는 단어를 뽑을 뿐이고, "부산은 지원하지
않는다"는 코드가 정한다. 그래야 거부 동작을 테스트로 고정할 수 있다.

#### 판정용 추출 필드

거부 판정에 필요한 것은 33개 답변 필드에 없다. 그래서 추출기는 **설계도 필드와 별개로**
셋을 더 뽑는다. 이들은 설계도에 값으로 들어가지 않고 게이트만 본다.

| 필드 | 쓰임 | 없으면 |
|---|---|---|
| `targetRegion` | `OUT_OF_REGION` 판정 | 장량동으로 본다 — 이 시스템의 유일한 대상이므로 |
| `targetDomain` | `NOT_A_SIMULATION` 판정 | 생활쓰레기 수거로 본다 |
| `requestedConclusion` | `AXIS_NOT_IN_MODEL` · `DATA_UNAVAILABLE` 판정 | 판정하지 않고 통과 |

`targetRegion`이 비었을 때 거부하지 않는 이유는, "장량동 시뮬레이터 만들어 줘"에서 지역을
생략한 요청("시뮬레이터 만들어 줘")이 정상이기 때문이다. **다른 지역이 명시됐을 때만**
거부한다 — 침묵을 거부 근거로 쓰지 않는다.

**변경 없이 그대로 두는 것:** 카탈로그, 검증기, 세션 저장소, 완결성 검사, 시나리오 조립기,
미리보기, 엔진, 결과, 기존 33문항 흐름.

검증 로직이 두 벌이 되지 않게 한다. 2026-09-03에 잡은 결함 두 건이 정확히 "같은 로직이 두
곳에 있어서" 생겼다(검증기가 엔진과 다른 경로를 검사했고, 요약이 provenance를 버렸다).

### 4.2 필드 근거 선언

서브태스크 JSON에 필드마다 붙인다. 세트 해시가 이미 덮으므로 변조 추적이 따라온다.
세트 변경이므로 **v4로 올린다**(D-45).

```json
{
  "answerField": "wasteMeanKg",
  "basis": { "kind": "MODEL_DEFAULT", "value": 0.9,
             "source": "이 시뮬레이터의 기본값 — 밖에서 대조할 출처가 없다" }
}
{
  "answerField": "collectionSchedule",
  "basis": { "kind": "REGULATION", "value": [0,1,3,4],
             "source": "생활쓰레기 배출정보 표준데이터 경북 포항시 (배출 일·월·수·목 → 수거 +1일 해석)" }
}
{
  "answerField": "trafficProfileId",
  "basis": { "kind": "MEASURED", "value": "jangryang-weekday",
             "source": "TMAP 24시간 288회 측정 2026-09-01" }
}
{
  "answerField": "days",
  "basis": { "kind": "MODEL_DEFAULT", "value": 30,
             "source": "이 시뮬레이터의 기본값 — 밖에서 대조할 출처가 없다" }
}
{
  "answerField": "serviceMinutesPerSite",
  "basis": { "kind": "NONE", "why": "현장 기록 0건. 순회 시간의 대부분이 이 값에서 나온다" }
}
{
  "answerField": "simulationGoal",
  "basis": { "kind": "EXPERIMENT_INTENT" }
}
```

다섯 종류이고 동작은 셋이다.

| kind | GapResolver 동작 |
|---|---|
| `REGULATION` · `MEASURED` | 기본값 + `AppliedDefault`에 출처 기록 |
| `MODEL_DEFAULT` | 기본값을 쓰되 결과에 `MODEL_DEFAULT_USED` 표시 |
| `NONE` · `EXPERIMENT_INTENT` | **반드시 되묻는다** |

가르는 기준은 하나다 — **읽는 사람이 찾아가서 대조할 곳이 있는가.** 포항시 표준데이터와
TMAP 측정 기록은 있고, 모델 기본값은 없다.

#### `MODEL_DEFAULT`가 이 설계의 정직한 부분

§3에서 확인한 대로 지금 21개가 여기 들어간다. 그러면 결과에 "시뮬레이터 기본값으로
채웠다"가 붙는다. 보기 싫은 표시지만 사실이고, **줄어들 표시가 아니다** — 그 값들은 원래
밖에서 대조할 곳이 없다. 표시의 목적은 숙제를 알리는 것이 아니라, 대조할 수 있는 값과 그냥
정해 둔 값을 결과에서 구별하는 것이다.

#### `NONE`은 현재 정확히 셋

`serviceMinutesPerSite`, `intraZoneTravelMinutes`, `zoneAssignmentRule`.
2026-09-02에 하루 종일 경고 표시를 붙인 그 값들이다.

### 4.3 거부 게이트

거부는 "안 됩니다"에서 끝나지 않고 **무엇이 있으면 되는지**를 담는다.

네 가지 사유:

| reason | 예 | 부족한 것 목록 |
|---|---|---|
| `OUT_OF_REGION` | "부산 시뮬레이터" | 아래 표 |
| `AXIS_NOT_IN_MODEL` | "종량제 봉투 가격을 올리면" | 모델에 가격 변수 없음 + 근사 가능한 축(배출량 변화) |
| `DATA_UNAVAILABLE` | "지점 단위 최적 경로" | 수거 지점 좌표 0곳 + **구역 단위로는 가능**(`ZONE_PROXY_HYBRID`) |
| `NOT_A_SIMULATION` | "장량동 배출량 알려줘" | 조회성 요청 — 다른 경로 안내 |

`OUT_OF_REGION`의 응답 형태:

```json
{ "feasible": false, "reason": "OUT_OF_REGION",
  "message": "이 시뮬레이터는 포항시 북구 장량동만 다룹니다.",
  "whatWouldBeNeeded": [
    { "item": "교통 구역 정의", "obtainable": false,
      "why": "장량동 A~D는 교통량 CSV 링크 매핑과 랜드마크로 정했다. 대상 지역에 그 자료가 없으면 사람이 구역을 정해야 한다." },
    { "item": "주민 배출 모델", "obtainable": false,
      "why": "0.9kg/인·일과 직업별 외출·귀가 시각은 원룸촌 논문 모델이다. 주거 형태가 다르면 맞지 않는다." },
    { "item": "도로 자유주행시간", "obtainable": true, "how": "OSRM — 구역이 정해지면 자동 수집" },
    { "item": "시간대 혼잡",       "obtainable": true, "how": "TMAP — 프로파일 1개당 288회 호출" },
    { "item": "수거 일정·미수거일", "obtainable": true, "how": "배출정보 표준데이터(시군구별, 채움 편차 있음)" },
    { "item": "인구·세대수",       "obtainable": true, "how": "주민등록 통계" }
  ] }
```

`obtainable: true` 넷이 곧 지역 온보딩 작업의 재료 목록이다.

`DATA_UNAVAILABLE`이 중요하다. 요청한 **결론**만 거부하고 가능한 범위는 열어 둔다 — 통째로
막으면 사용자가 우회로가 있다는 것을 모른다.

#### API 계층은 이미 지역 중립적이다

`TmapRouteService`에 지역 참조 0건, `OsrmRouteService`도 사실상 없다. 그런데 그 위층은
아니다: 장량동이 12개 파일에 하드코딩돼 있고 `CollectionSiteRegistry`가 좌표 bbox
(129.34~129.42 / 36.04~36.11)로 막는다. 지역 확장을 막는 것은 API가 아니라 **구역 정의와
모델 파라미터**다.

또한 엔진은 실행 중 외부 API를 부르지 않는다(NFR-02 재현성). API는 **데이터 준비 시점**에만
쓸 수 있고, "요청이 오면 즉시 호출해 시뮬레이터를 만든다"는 실행 경로에서 성립하지 않는다.

### 4.4 LLM 추출과 실패 처리

#### ① 값을 지어낸다 — 인용 강제로 막는다

LLM은 값마다 근거가 된 **원문 조각**을 함께 내고, 시스템은 그 조각이 실제 요청 문자열에
있는지 결정적으로 검사한다.

```
요청: "장량동 26개 동으로 한 달 돌려줘"

{"field":"numBuildings","value":26,"span":"26개 동"}  → 요청에 있음   → 채택
{"field":"days","value":30,"span":"한 달"}            → 있음         → 채택 (정규화는 정당)
{"field":"seeds","value":10,"span":"10회 반복"}       → 요청에 없음   → 버림 → 되묻기
```

`request.contains(span)` 한 줄이다. "한 달 → 30일" 같은 정당한 정규화는 통과하고 순수한
창작은 걸린다.

#### ② 형식이 깨진다

스키마 검증 실패 시 **추출 전체를 버린다.** 부분 파싱 금지 — 반쯤 읽은 결과를 쓰면 무엇이
빠졌는지 알 수 없다.

#### ③ 서비스가 죽는다

폴백은 기존 33문항 흐름이다. **조용히 기본값으로 채우지 않는다.** 사용자에게 "해석기를 쓸
수 없어 문항으로 진행합니다"를 알린다.

#### ④ 범위 밖 값

기존 검증기가 잡는다. 그 필드만 되묻기로 내려가고 전체가 실패하지 않는다.

#### 재현성은 설계도에 있다

LLM 추출은 비결정적이다. 하지만 NFR-02가 요구하는 것은 **엔진**의 재현성이다.

> 재현 단위는 요청 문장이 아니라 **설계도**다.

설계도가 확정된 뒤에는 같은 시드가 같은 결과를 낸다. 재실행은 설계도에서 하고 문장에서
하지 않는다 — 기존 `answers` 필드가 이미 그 역할을 한다. 같은 문장을 두 번 넣으면 설계도가
다를 수 있고, 그것은 정상이며 설계도를 비교하면 무엇이 달랐는지 보인다.

### 4.5 다중 실행 실험

#### 근거 없는 필드가 곧 비교 축이다

`basis: NONE`인 필드는 값을 모르니 하나를 고를 수 없다. 그래서 되묻기가 형태를 바꾼다.

```
❌ "정차시간 몇 분입니까?"        → 사용자도 모른다. 현장에서 재본 적이 없다
✅ "0·5·10분으로 각각 돌려 범위로 보여드릴까요?"
```

단일 값을 정하지 못해도 "이 축이 무엇을 좌우하는가"는 답할 수 있다.

#### 근거 선언에 스윕을 붙인다

```json
{
  "answerField": "serviceMinutesPerSite",
  "basis": { "kind": "NONE", "why": "현장 기록 0건" },
  "sweep": {
    "defaultValues": [0, 5, 10],
    "respondingMetrics": ["avgCompletionMinutes"],
    "inertMetrics": ["totalComplaints", "truckUtilizationPercent", "uncollectedDemandKg"],
    "note": "§8 측정 참조"
  }
}
```

`inertMetrics`가 중요하다. 축마다 반응하는 지표가 다르고, 기존 실험의 기본 지표는 "월 평균
민원"이다. 새 축을 그 틀에 얹으면 평평한 선만 그린다.

**선언이 없는 축은 어떻게 하는가.** 아직 측정하지 않은 축에는 `sweep` 선언이 없다. 그때는
지표를 고르지 않고 **전부 보고하고, 각 지표가 반응했는지를 계산해서 표시한다**(최댓값과
최솟값의 차이가 0이면 "반응하지 않음"). 선언을 요구하면 측정 전에는 축을 쓸 수 없게 되고,
그러면 "측정하지 않은 축을 탐색한다"는 이 기능의 용도 자체가 막힌다. 선언은 이미 아는
사실을 미리 알려 주는 것일 뿐 전제 조건이 아니다.

#### 새 구성요소: `ParameterSweep`

```
ParameterSweep {
  axes:    [{ field, values[] }]   // 1개 또는 2개
  metrics: [String]                // 근거 선언에서 유도, LLM이 추가 가능
  base:    JangnyangScenarioSpec   // 축 외의 모든 값은 설계도에서 고정
}
```

- **2축까지만.** 2026-09-02에 실제로 필요했던 것이 2축이었다(배정 규칙 × 구역 내 이동시간).
  3축부터는 조합이 터진다.
- **실행 수 상한 300.** `조합 수 × seeds`가 300을 넘으면 실행하지 않고 되묻는다
  ("시드를 줄이거나 값을 줄이시겠습니까?"). 2축 3값이면 9조합 × 시드 10 = 90회로 통과하고,
  2축 5값 × 시드 30 = 750회는 막힌다. 300은 근거가 있는 수가 아니라 **한 요청이 몇 분 안에
  끝나야 한다는 운영 판단**이므로, 설정값으로 두고 이 사실을 기록한다.

#### 결과는 범위로 보고한다

반응하지 않은 지표를 **지우지 않고 표시한다.** "민원이 안 움직인다"가 실제 발견이고 그
사실이 결론의 일부다.

각 실행의 `dataQualityFlags`를 합쳐 결과에 싣는다 — 조합 중 하나라도 가정을 썼으면 전체가
가정 비교 실험이다.

#### LLM의 역할은 여기서도 좁다

LLM이 뽑는 것은 "무엇의 영향을 보고 싶은가" 하나다.

```
"정차시간이 얼마나 영향 있는지 보고 싶어"
  → { axis: "serviceMinutesPerSite", span: "정차시간이 얼마나 영향" }
  → 값 목록은 선언된 defaultValues 또는 되묻기
  → 지표는 선언에서 유도
```

축을 지어내지 못하게 인용 검사가 그대로 걸린다. 값 목록도 LLM이 창작하지 않고 선언 또는
사용자에게서 온다. 상한 초과·모호한 축은 되묻는다.

## 4.6 구현 단계

구성요소가 다섯이라 한 계획으로는 크다. 두 단계로 나눈다 — 1단계만으로도 쓸 수 있다.

| 단계 | 범위 | 끝나면 되는 것 |
|---|---|---|
| **1단계** | §4.1~4.4 — 추출·인용 검사·거부 게이트·근거 선언·되묻기 | 한 문장으로 단일 실행 시나리오가 만들어진다. 부족하면 되묻고, 안 되면 이유와 함께 거부한다 |
| **2단계** | §4.5 — `ParameterSweep` | 근거 없는 축을 범위로 보고한다 |

1단계의 근거 선언(`basis`)이 2단계의 축 판단(`NONE`이면 축 후보)의 입력이므로 순서를
바꿀 수 없다.

## 5. 새로 만드는 것

| # | 구성요소 | 역할 | 의존 |
|---|---|---|---|
| 1 | `RequestInterpreter` (인터페이스 + LLM 구현) | 문장 → 후보 답변 + 인용 조각. 판정하지 않음 | `OpenAiService` |
| 2 | `FeasibilityGate` | 거부 판정 + 부족한 것 목록. 결정적 | 추출 결과만 |
| 3 | `FieldBasis` + `GapResolver` | 근거 선언을 읽고 자동 채움 / 되묻기를 가름 | 서브태스크 JSON v4 |
| 4 | `ParameterSweep` | 축을 여러 값으로 돌려 범위를 낸다 | `SimulationService` |
| 5 | `DataQualityFlag.MODEL_DEFAULT_USED` | 출처 미확인 기본값 표시 | 기존 enum 확장 |

## 6. 검증 규칙 (신설)

| id | 내용 | 막는 것 |
|---|---|---|
| V-L1 | 인용 조각이 요청 문자열에 없는 추출값은 채택하지 않는다 | LLM이 지어낸 값 |
| V-L2 | 추출 스키마 검증 실패 시 전체를 버린다 | 부분 파싱으로 빠진 필드를 모르는 것 |
| V-L3 | `basis.kind`가 `NONE`·`EXPERIMENT_INTENT`인 필드를 기본값으로 채우지 않는다 | 근거 없는 값의 조용한 주입 |
| V-L4 | LLM 실패 시 기본값으로 채우지 않고 문항 흐름으로 전환하며 사용자에게 알린다 | 조용한 폴백 |
| V-L5 | 스윕 축은 1~2개, `조합 수 × seeds`가 상한 이하 | 조합 폭발 |
| V-L6 | 거부 응답은 `reason`과 비어 있지 않은 `whatWouldBeNeeded`를 함께 담는다 | "안 됩니다"로 끝나는 거부 |

## 7. 테스트 전략

**LLM을 테스트에서 부르지 않는다.** `RequestInterpreter`를 인터페이스로 두고 고정 응답
스텁으로 검증한다. 실제 호출은 별도 통합 확인으로 분리한다 — TMAP·OSRM에 쓴 방식과 같다.

| 대상 | 검증 |
|---|---|
| 거부 게이트 | 4개 사유 × 대표 요청. 결정적이라 완전히 덮인다 |
| 인용 검사 | 지어낸 값 주입 → 버려지고 되묻기로 내려가는가 |
| GapResolver | 6개 `basis.kind` × 동작 3개 |
| 폴백 | LLM 예외 → 문항 흐름 진입, **조용한 기본값 0건** |
| 설계도 재현 | 같은 설계도 → 같은 결과 |
| 스윕 | 축 1·2개 통과, 3개 거부, 상한 초과 거부 |
| 표시 전파 | 조합 중 하나가 가정을 쓰면 전체가 가정 비교 실험 |

**변이 테스트로 잠글 것:** 인용 검사 제거 / `UNVERIFIED` 표시 제거 / `NONE`을 기본값으로
채우기 / 거부 게이트 무력화 / LLM 실패 시 조용한 기본값 / 검증기 우회 / 거부 응답에서
`whatWouldBeNeeded` 제거 / 스윕 상한 제거.

## 8. 측정 근거 (2026-09-02, seed 42, days 28)

`sweep.note`와 `inertMetrics`의 출처다. 두 규모를 섞지 않는다.

### 26동 `JANGRYANG_CAPACITY` · `ZONE_PROXY_HYBRID` · `ROUND_ROBIN`

| 정차/지점 | 순회분 | 트럭 가동률 | 미수거kg | 민원 |
|---|---:|---:|---:|---:|
| 0분 | 50 | 92.5% | 0.0 | 0 |
| 5분 | 180 | 92.9% | 0.0 | 0 |
| 10분 | 310 | 93.2% | 0.0 | 0 |

### 4동 (논문 기준선 규모) · `ZONE_PROXY_HYBRID`

| 정차/지점 | 순회분 | 트럭 가동률 | 미수거kg | 민원 |
|---|---:|---:|---:|---:|
| 0분 | 9 | 1.8% | 0.0 | 27 |
| 5분 | 29 | 1.8% | 0.0 | 27 |
| 10분 | 49 | 1.8% | 0.0 | 28 |

**정차시간은 순회 시간만 좌우한다.** 26동에서 순회가 6.2배(50→310분) 벌어지는데 가동률은
0.7pp만 움직이고 미수거·민원은 전혀 움직이지 않는다. 4동에서도 순회 5.4배에 민원은 1건
차이다.

이것이 `inertMetrics`를 선언해야 하는 이유다. 기존 실험의 기본 지표(월 평균 민원)로 이 축을
보면 아무것도 보이지 않는다.
