# 서브태스크 판정 기록 — 시뮬레이터가 요청의 단계를 알고, 단계마다 판정과 근거를 남긴다

2026-11-02 · 대상 모듈 `simulator` · 대상 시뮬레이터 장량동(8090)

## 1. 왜

- **판정 과정을 보여 주거나 측정할 수 없다.** 교수님은 서브태스크가 언제 생기고 언제 완료되는지를 알고리즘 수준으로 설명하라고 하셨다. 지금은 그 과정이 어디에도 남지 않는다.
- **시뮬레이터가 같은 요청의 몇 단계째인지 모른다.** `plan_subtasks` 는 상태 없는 도구이고, 남는 것은 `mcp.calls` 의 한 줄 요약뿐이다.
- **FILLED 가 "충분함"을 뜻하지 않는다.** 지금 FILLED 는 `answers.get(answerKey) != null` 만 본다. 허용값 밖의 값이나 근거 없는 값도 FILLED 다. 형식 검사(`validate_answers`)는 선택이고, 근거 검사(`EvidenceGuard`)는 `build_scenario` 에서만 돈다.
- **논문의 시스템 성능 평가에 쓸 기록이 필요하다.** 요청이 몇 단계에 완료됐는지, 최소 몇 단계가 필요했는지, 근거 없이 채워진 값은 얼마나 되는지를 셀 수 있어야 한다.

## 2. 목표

1. **요청 식별:** 시뮬레이터가 사용자 요청 하나에 `planId` 를 붙이고, 같은 요청의 호출을 단계로 이어 센다.
2. **단계 기록:** 단계마다 템플릿별 상태와 이유, 이전 단계 대비 변화, FILLED 로 인정한 근거를 기록한다.
3. **FILLED 의 뜻을 "충분함"으로 바꾼다.** 형식 검사를 통과해야 FILLED 다. 근거 검사는 발화가 함께 왔을 때 적용한다.
4. **기록 위치:** 기록은 응답 · 로그 · 조회 도구 · **파일(JSONL)** 에 남긴다. 파일은 논문 평가용이다.
5. **최소 필요 단계:** 생성 조건의 의존 깊이로 요청마다 최소 필요 단계를 계산해 함께 남긴다.

## 3. 비목표

- **단계 상한:** 두지 않는다. 사용자 결정이다 — 서버의 SES · 템플릿 수와 사용자 응답에 따라 필요한 단계가 다른 것이 정상이고, 필요한 서브태스크가 다 채워지면 멈춘다.
- **집계 스크립트:** 파일을 읽어 평균 단계 수 등을 내는 스크립트는 이번 범위가 아니다. 파일 형식이 그것을 가능하게만 한다.
- **의미 충분성 판정:** "아침 일찍"이 6시인지 되물어야 하는지 같은 판단은 여전히 LLM 몫이다.
- **북구 · 포항 서버:** 다른 저장소다.

## 4. 실패로 보는 것

- **같은 답변으로 다시 부른 호출이 단계를 올리는 것.**
- **planId 없이 부르는 기존 흐름이 깨지는 것.** planId 없는 호출은 계속 동작해야 한다.
- **형식 검사에서 떨어진 값이 FILLED 로 남는 것.**
- **파일 기록이 실패해 도구 호출이 실패하는 것.** 기록은 부가 기능이라 실패해도 응답은 나가고, 실패는 로그에 남긴다.

## 5. 정한 것

| 항목 | 결정 | 누가 |
|---|---|---|
| 서버가 단계를 안다 | planId 로 같은 요청을 잇는다 | 사용자 |
| 1단계의 정의 | 직전 단계보다 답변(값 또는 출처)이 늘었거나 바뀐 호출. 같은 답변의 재호출은 같은 단계의 재확인 | 사용자 확인 |
| 단계 상한 | 없음. `complete()` 에 닿으면 완료 | 사용자 |
| 기록 위치 | 서버가 파일로 따로 남김(논문 평가용). 응답 · 로그 · 조회 도구에도 | 사용자 |
| FILLED 기준 | B — 형식 검사 통과가 필요하고, 근거 검사는 발화가 있을 때 적용 | 사용자 |
| planId 발급 | 시뮬레이터가 첫 `plan_subtasks` 에서 만든다. 형식은 `plan-` + UUID 앞 12자 | 내 판단 |
| 브로커 연결 | `plan_subtasks` 가 선택 인자 `matchId` 를 받아 기록에 싣는다. 검증은 하지 않는다 | 내 판단 — 매칭 바퀴와 서브태스크 단계를 한 요청으로 이어 볼 수 있다 |
| 메모리 보관 | 최근 1000건 LRU (브로커 `MatchRounds` 와 같은 방식) | 내 판단 |
| 파일 형식 | `logs/plan-history/plan-history-YYYY-MM-DD.jsonl`, 한 줄 = 한 사건 | 내 판단 |

## 6. 어떻게

### 6-1. 단계 잇기

- **새 요청:** `plan_subtasks` 에 `planId` 가 없으면 새 planId 를 만들고 1단계로 기록한다. 응답에 `planId` 를 싣고, 설명문에 "이후 호출에 이 planId 를 그대로 넣으십시오"를 적는다.
- **이어지는 호출:** `planId` 가 있으면 그 요청의 마지막 단계와 비교한다.
  - 정규화 뒤의 답변 맵(실험 변수 값 목록 포함)과 출처 맵이 같으면 **같은 단계**다. 단계 번호를 올리지 않고 `recheck` 사건으로 기록한다.
  - 다르면 **다음 단계**다.
- **모르는 planId:** 거절한다(`ToolFailure`). 메시지는 "planId 를 모릅니다 — planId 없이 다시 부르면 새 요청으로 시작합니다"이고, 브로커의 모르는 matchId 처리와 같다.
- **planId 를 받는 다른 도구:** `validate_answers` · `build_scenario` 도 선택 인자 `planId` 를 받는다.
  - 이 도구들은 단계를 올리지 않는다.
  - 결과를 그 요청의 현재 단계에 사건으로 붙인다(`validate`, `build`).
  - 확인(`ScenarioConfirmController`)과 실행(`run_scenario_by_token`)은 scenarioId 로 planId 를 찾아 `confirm` · `run` 사건을 붙인다. 이를 위해 `ScenarioStore` 가 scenarioId → planId 를 보관한다.

### 6-2. FILLED 기준 (B)

`SubtaskPlanner.plan` 의 ACTIVE 분기에서 값이 있을 때 다음을 차례로 본다.

1. **형식 검사:** `AnswerNormalizer` 로 템플릿 계약(값 종류 · 허용값 · 범위 · 목록 중복)을 확인한다.
   - 실패하면 상태는 **UNFILLED** 이고, 인스턴스에 `reason: {code, message}` 를 싣는다. code 는 `OUT_OF_RANGE` 같은 정규화 코드다.
   - 값은 비운다. 잘못된 값으로 FILLED 를 흉내 내지 않는다(6-6 의 3).
2. **근거 검사:** 호출에 `userUtterances` 와 `evidence` 가 함께 왔을 때만 한다(6-6 의 1). 규칙은 지금 `EvidenceGuard.check` 를 그대로 쓴다.
   - 막히면 **UNFILLED** 이고, `reason.code = "NO_EVIDENCE"` 로 메시지를 그대로 싣는다.
   - 판단하지 못함(unverified)이면 FILLED 이되 `evidence: "UNVERIFIED"` 를 단다.
3. **통과:** 둘 다 통과하면 FILLED 이고, 인스턴스에 `evidence: "VERIFIED" | "UNVERIFIED" | "NOT_CHECKED"` 와 출처를 단다.

**적용 범위:**
- `ScenarioBuilder` 도 같은 planner 를 쓰므로 `build_scenario` 에서도 같은 기준이 적용된다. 형식 오류는 지금까지 평탄화 · 검증기 오류로 나왔지만, 이제 "물어야 할 결정 X — 사유"로 나온다.
- `EvidenceGuard` 를 planner 가 쓸 수 있도록 같은 패키지 밖에서 부를 수 있게 연다. 근거 검사 규칙 자체는 바꾸지 않는다.

**complete():** 정의는 그대로다(UNFILLED · DEFERRED 없음). FILLED 가 "충분함"이 되었으므로 complete 도 "필요한 서브태스크가 모두 충분히 채워짐"을 뜻하게 된다.

### 6-3. 단계 기록의 내용

사건은 **한 줄 = 한 JSON 객체**이고, 공통 칸은 다음과 같다.

| 칸 | 값 |
|---|---|
| `ts` | ISO-8601 |
| `planId`, `matchId` | matchId 는 없으면 null |
| `serverId` | 능력 카드의 serverId |
| `sesId`, `sesVersion` | |
| `event` | `round` / `recheck` / `validate` / `build` / `confirm` / `run` |
| `round` | 현재 단계 번호 |

**`round` 사건의 추가 칸:**

| 칸 | 값 |
|---|---|
| `instances` | 템플릿마다 `{templateId, answerKey, status, reason, origin, evidence, waitingOn(DEFERRED 일 때), condition(NOT_GENERATED 일 때 생성 조건 식)}` |
| `changes` | 이전 단계 대비 상태가 바뀐 것 `[{answerKey, from, to}]`. 1단계는 from = null |
| `counts` | 상태별 개수 |
| `complete` | 불리언 |
| `completedAtRound` | complete 가 처음 참이 된 단계면 그 번호, 아니면 null |
| `minRounds` | 6-4 의 최소 필요 단계 |

**다른 사건의 추가 칸:**

| 사건 | 칸 |
|---|---|
| `recheck` | `counts`, `complete` |
| `validate` | 정규화 결과 `{normalized, rejected}` |
| `build` | `scenarioId`, `valid`, 막힘 목록 개수(`blocks` · `backVerificationBlocks` · `branchBlocks`), `droppedDefaults`, `guardUnverified` |
| `confirm` | `scenarioId`, 승인 / 거절 |
| `run` | `scenarioId`, 성공 여부 |

**응답:** `plan_subtasks` 응답에 `planId`, `round`, `changes`, `completedAtRound`, `minRounds` 를 더한다. 인스턴스에는 `reason` · `evidence` 가 붙는다.

**로그:** `mcp.calls` 에 단계마다 한 줄을 남긴다. 예: `[6 서브태스크] planId=… 3단계 · 새로 채움 2 · 새로 생김 1 · 남음 4 · 완료 아님`

**조회 도구:** `get_plan_history(planId)` 가 메모리의 사건 목록을 순서대로 낸다. 메모리에서 밀려난 planId 면 "기록이 메모리에 없습니다 — logs/plan-history 파일을 보십시오"라고 답한다.

### 6-4. 최소 필요 단계

마지막 단계의 답변으로 계산한다. 사용자가 묻는 것마다 한 번에 다 답했다고 가정했을 때의 단계 수다.

- **깊이 정의:** ACTIVE 결정 d 의 깊이 `level(d)` 는 다음과 같다.
  - 생성 조건이 읽는 답변키 중 **다른 ACTIVE 결정**이 없으면 0 이다.
  - 있으면 `1 + max(level(그 결정들))` 이다.
  - 자기 자신을 읽는 것은 제외한다. 예: `given(collectionTimesMinutes)`.
- **minRounds:** `1 + max(level(d))` 이다. ACTIVE 결정이 없으면 1 이다.
- **장냥 예:** 구역 근사 + 6동 + 덩어리 배정이면 구역 내 이동시간의 level 이 2 이므로 minRounds 는 3 이다. 의존 경로는 건물 수 · 이동시간 방식 → 구역 배정 규칙 → 구역 내 이동시간이다.
- 비교 변수가 있으면 비교 값마다 계산해 가장 큰 값을 쓴다.

### 6-5. 파일

- **위치:** 설정값 `plan.history.dir` 이고, 기본은 `logs/plan-history` 다. `logs/` 는 이미 .gitignore 에 있다. 테스트는 임시 디렉터리를 쓴다.
- **쓰기:** 사건마다 한 줄을 덧붙인다(append). UTF-8 이고 줄바꿈은 LF 다. 동시 호출을 막는 것은 파일 쓰기 하나를 동기화하는 정도로 충분하다.
- **실패:** 쓰기 실패는 `log.warn` 으로만 남기고 도구 응답은 그대로 낸다.

### 6-6. 경계에서 정한 것 (빌더 점검 후, 모두 내 판단)

1. **근거 검사 위치:**
   - **`plan_subtasks`:** 선택 인자 `userUtterances` · `evidence`(build_scenario 와 같은 모양)를 받는다. `SubtaskPlanner` 에는 선택 인자로 "근거 묶음(발화 목록 + 답변키 → 구절)"을 넘기고, 없으면 근거 검사를 하지 않는다(`NOT_CHECKED`).
   - **`ScenarioBuilder`:** 근거 묶음 없이 planner 를 부른다. 그래서 build 에서는 **형식 기준만** 새로 적용된다.
   - **`build_scenario`:** 지금의 근거 검사 즉시 거절(`ToolFailure` "근거 검사(GUARD)")을 그대로 유지한다. 검사가 두 번 도는 일은 없다. plan 단계는 UNFILLED 로 알리고, build 단계는 지금처럼 거절한다.
2. **실험 변수의 형식 검사:**
   - `planAcross` 에서 변수 값마다 정규화한다.
   - 하나라도 실패하면 합친 변수 인스턴스는 FILLED 로 덮어쓰지 않고 **UNFILLED** 로 둔다. `reason` 에는 실패한 값과 코드를 싣고, `onlyFor` 에 그 값들을 싣는다.
   - 모두 통과하면 지금처럼 FILLED(값 목록)다.
3. **인스턴스에 싣는 값:**
   - 형식 검사를 통과한 **정규화된 값**을 싣는다.
   - 생성 조건 평가도 정규화된 값으로 한다. 예: "4" → 4.
   - 형식 검사에서 떨어진 값은 조건 평가 입력에서 빠진다. 따라서 그 값에 기대는 결정은 DEFERRED 가 된다. 잘못된 값으로 가지를 정하지 않기 위해서다.
4. **"바뀜"의 범위:**
   - 비교는 **호출에 들어온 원래 답변 맵 + 출처 맵 + 실험 변수(키 · 값 목록)** 로 한다.
   - 값이 하나라도 추가 · 삭제 · 변경되면 다음 단계다. 형식 오류 값이 다른 형식 오류 값으로 바뀌어도 다음 단계다.
   - `evidence` · `userUtterances` 만 달라진 호출은 `recheck` 다. 근거만 보탠 것이지 사용자 답이 새로 온 것이 아니기 때문이다.
5. **minRounds:**
   - 단계마다 그 단계의 답변으로 다시 계산해 싣는다. 초반에는 DEFERRED 가 많아 작게 나오다가 커질 수 있다.
   - **평가에 쓰는 값은 완료 단계(`completedAtRound`)의 minRounds** 다. 문서와 사건에 "완료 시점 값이 정본"이라고 적는다.
   - level 의 간선은 "조건이 읽는 답변키가 템플릿 결정이고 그 결정이 ACTIVE(FILLED 또는 UNFILLED)"인 경우만 센다. SesCatalog/TemplateCatalog 가 조건이 템플릿 밖 키를 읽지 못하게 이미 막는다.
6. **메모리에서 밀려났거나 모르는 planId:**
   - 거절한다(6-1 과 같다). 메시지는 "planId 를 모릅니다(서버 재시작이나 오래되어 메모리에서 밀려났을 수 있습니다) — planId 없이 다시 부르면 새 요청으로 시작합니다"이다.
   - 파일의 옛 기록에 이어 붙이지 않는다. 새 planId 의 첫 사건에 `previousPlanId` 칸을 두어, 호출자가 옛 id 를 주면 기록만 남긴다.
   - planId 는 발급 시점의 sesId · sesVersion 을 갖는다. 서버의 sesVersion 과 다르면 거절한다. 실제로는 재시작해야 버전이 바뀌므로 메모리에서도 사라진다.
7. **scenarioId → planId:**
   - `ScenarioStore` 의 시나리오 항목에 planId 를 함께 둔다. 수명은 시나리오와 같고, 메모리에만 있다.
   - 재시작 뒤의 confirm · run 은 planId 를 모르므로, 사건을 `planId: null` 과 `scenarioId` 로 파일에 남긴다. 집계 때 scenarioId 로 build 사건과 이을 수 있다.

## 7. 확인 방법

- **단계 세기:**
  - planId 없이 부르면 → planId 와 1단계
  - 같은 답변으로 다시 부르면 → 같은 단계, `recheck` 사건
  - 값을 하나 더해 부르면 → 2단계, `changes` 에 그 결정
- **모르는 planId:** 거절된다.
- **FILLED 기준:**
  - `numBuildings=99`(범위 밖) → UNFILLED, `reason.code=OUT_OF_RANGE`, complete=false
  - 같은 값이 범위 안이면 → FILLED
  - USER 출처에 근거 구절이 없는데 발화가 함께 오면 → UNFILLED `NO_EVIDENCE`
  - 발화가 없으면 → FILLED `NOT_CHECKED`
- **build_scenario 의 형식 오류:** "물어야 할 결정 … — 사유"로 나온다.
- **minRounds:**
  - 장냥 기본(조건부 결정이 모두 비활성) → 1
  - 차량 3대 + 건물 4동 → 2 (배차 간격이 truckCount · numBuildings 를 읽음)
  - 구역 근사 + 6동 + 덩어리 → 3
- **파일:** 한 요청을 plan → plan → build → confirm → run 으로 돌리면 파일에 같은 planId 로 사건 5줄이 순서대로 쌓인다.
- **파일 쓰기 실패:** 디렉터리가 쓰기 불가여도 `plan_subtasks` 응답은 정상이다.
- **기존 테스트:** planId 없이 부르는 기존 테스트는 그대로 통과한다. 형식 오류를 평탄화 단계에서 기대하던 테스트는 새 메시지에 맞춘다.

- 로그 한 줄의 정확한 문구
