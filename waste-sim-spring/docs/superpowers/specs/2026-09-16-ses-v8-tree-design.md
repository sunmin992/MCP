# 참조 SES 재편 설계 — ref-v7 → ref-v8

2026-09-16 · 코드 `develop @ 12937be` · 대상 `docs/research/s1-ses-extraction/reference-ses.json`

장량동 모델의 참조 SES를 **시스템 구성 골격**으로 재편한다. 목표 골격은 손으로 그린 트리
그림에서 왔고, 잎 값과 근거는 ref-v7에서 그대로 온다. 이 문서는 무엇을 바꾸고 무엇을
바꾸지 않는지를 확정한다.

## 1. 왜 바꾸는가

ref-v7의 최상위는 `대상 시스템 · 실험 · 관측` 세 형제다. 이것은 SES 문법으로는 맞지만,
시뮬레이터를 **구성하는 절차**(설정 → 모델 → 실험 → 결과)를 보여 주지 않는다. 특히
`구성결정-SES-대응표.md`가 확인한 29개의 구성 결정이 트리에서는 여기저기 속성으로만
흩어져 있어, "무엇을 정해야 이 시뮬레이터가 서는가"를 트리에서 읽을 수 없다.

ref-v8은 그 절차를 트리의 1급 가지로 올린다.

엔티티 51개 → **62개**. 새 엔티티 11개(설정 6 · 시스템 5)이고, 기존 51개는 하나도 사라지지
않는다. 개명 3건과 재배치가 있을 뿐이다.

## 3. 넣지 않는 것 — 엔진·이벤트

그림에는 `엔진 실행 ─ DEVS 엔진`과 `이벤트 실행 시스템 ─ 이벤트 집합`이 있다. **넣지 않는다.**

ref-v7의 `_meta.note`가 그 판단을 이미 적어 두었다 — v1은 "실행 엔진·이벤트 시스템을 구조
트리의 형제로 둔 명백한 오류를 포함한다". `구성결정-SES-대응표.md` 3행도 `engine`을
"**실행 수단**이다. 프롬프트 규칙 3이 제외하라고 한 범주"로 제외했다. ref-v8은 이 판단을
유지한다. 따라서

- `시스템 구성`의 자식은 그림의 5개가 아니라 **4개**다.
- `DEVS 모델 구성`의 자식은 그림의 6개가 아니라 **5개**다.
- `DischargeEvt` · `CollectEvt` · `InspectEvt`는 엔티티가 아니라 **결합의 기제**로 남는다.
  이미 `couplings` 6건의 `mechanism`에 그렇게 적혀 있다.

이 선택은 `reference-ses.json`의 `_meta.corrections`에 한 줄로 기록한다.

## 6. 설정 가지 — 중복 없이 잇는 법

### 6-1. 제약

SES는 한 엔티티가 두 부모를 갖는 것을 금한다(`sesx/contract.py`의 `multi_parent`). 그래서
설정 가지는 **모델 엔티티를 다시 소유하지 않는다**. 그림이 `거주민/배출 설정` 아래 그린
`배출 시각 모델 → 직업별 외출시각 / 포항시 배출시간대`는 spec 축의 복제인데, 그 축은
`거주민` 아래에 한 번만 둔다. 설정 쪽에서는 **선택자 속성** 하나(`배출시각모델`)로만 적는다.

같은 규칙이 `차종`(spec 차종 축) · `이동시간방식`(spec 이동시간 방식 축) · `실험유형`(spec
실험 유형 축)에 적용된다.

### 6-2. `sets` — 새 스키마 확장

설정의 각 결정이 모델 트리의 **어느 자리를 정하는가**를 명시한다. `active_when` ·
`attr_spec`과 같은 층의 선택적 확장이다.

```json
"차량·수거 설정": {
  "attrs": ["수거시각", "수거요일", "차종", "차량수", "적재용량",
            "초기적재량", "배차간격", "지점당수거시간"],
  "decompositions": [],
  "sets": {
    "차량수": { "target": "수거차량 집합.개수",
                "evidence": "문항 20 truckCount -> setNumTrucks" },
    "차종":   { "target": "수거차량.차종 축",
                "evidence": "문항 19 truckType -> setTruckType, spec 선택" }
  }
}
```

`target`은 `엔티티.속성` 또는 `엔티티.축이름` 중 하나다. 후자는 그 결정이 spec 축에서
하나를 고른다는 뜻이다.

`_meta.schema_extensions`에 `sets` 항목을 추가하고, `active_when` · `attr_spec`과 같이
**추출 프롬프트에 넣지 않으며 `score_ses.py`도 채점하지 않는다**고 함께 적는다.

않는다.** 설정 가지는 이미 검증된 대응표를 트리로 승격한 것이다.

적는다. 이 한 건만 `엔티티.속성` 형식을 따르지 않는다.

### 6-4. 설정 속성은 모델 속성을 대체하지 않는다

`거주민 집합.개수`는 v8에서도 그대로 있다. 설정 가지의 `거주민수`는 그것을 **정하는 결정**
이고, 모델 가지의 `개수`는 그 **성질**이다. 둘은 다른 것이고, `sets`가 둘을 잇는다.

이 중복은 의도한 것이다. 이것 없이 설정을 트리에 올리면 모델 엔티티가 속성 없는 껍데기가
된다.

## 7. 결합 · 임계점 · 근거

- `couplings` 6건 — **내용 불변**. `대상 시스템`을 가리키는 이름이 있으면 개명만 반영한다.
  `active_when` 2건도 그대로다.
- `critical_points` 5건 — **내용 불변**. CP의 `where`(`민원 판정` · `폐기물 유형.임계값` 등)는
  모두 v8에 그대로 있다.
- `evidence` 87건 — 개명 3건에 걸린 키를 새 이름으로 옮긴다. 값은 그대로다.
- 새 엔티티 11개의 근거를 새로 붙인다:

| 새 엔티티 | 근거의 출처 |
|---|---|
| 시뮬레이션 설정 | `model/SimulationConfig.java` — 결정값의 소비 형태 |
| 설정 5종 | `subtask/JangnyangScenarioBuilder.java` `toConfig()`의 해당 구간 |
| 거주민 배출 시스템 | `SimulationEngine` `DischargeEvt`(227) 생성·처리 경로 |
| 수거장 적재 시스템 | `fill[building][type]` 적재 상태와 `WasteType` |
| 차량 수거 시스템 | `CollectEvt`(213) 처리와 `TruckType` |
| 경로 교통 시스템 | `RoutePlanner` · `TravelTimeCalculator` · `TrafficProfile` |
| 민원 감시 시스템 | `InspectEvt`(236) 및 민원 누적(`:460` · `:473` · `:483`) |

다섯 시스템 노드의 근거는 **묶음의 근거**다. 새 개체를 주장하는 것이 아니라, 이미 근거가
있는 개체들이 코드에서 한 덩어리로 돈다는 사실을 가리킨다. 이 점을 `_meta`에 적는다.

## 8. 대가 — 과거 실행과의 비교가 끊긴다

**이것이 이 재편의 가장 큰 비용이다.**

ref-v7의 `schema_extensions._주의`는 `active_when` · `attr_spec`을 추출 프롬프트에서 뺀
이유를 "기존 실행 12건(C·Cs·Csr·Cd)과의 비교를 보존하기 위한 선택"이라고 적었다. ref-v8은
엔티티를 51 → 62로 늘리고 최상위 골격을 바꾸므로, **추출기가 낼 수 없는 구조가 11개 늘어난다.**
과거 12건을 ref-v8로 채점하면 재현율이 구조적으로 떨어지고, 그 하락은 추출 품질의 변화가
아니라 정답지 변경의 결과다.

### 완화 — 정답지 두 개를 병존시킨다

1. 현재 `reference-ses.json`을 `reference-ses-v7.json`으로 **그대로 복사해 동결한다.**
   내용을 한 글자도 바꾸지 않는다.
2. `reference-ses.json`을 ref-v8로 교체한다.
3. `score_ses.py`의 `--ref` 인자를 쓴다. **이미 있다**(`score_ses.py:288`,
   기본값 `reference-ses.json`). 채점기는 고치지 않는다.
4. `README.md`에 규칙을 적는다 — **과거 12건은 v7로 잰다. 새 실행은 v8로 잰다. 두 수를
   같은 표에 놓지 않는다.**

## 9. `aliases.json`에 생기는 변화

- 추가: `대상 시스템 → 생활쓰레기 수거 모델`, `실험 → 시나리오 실험`, `관측 → 시뮬레이션 결과`
- **`_skipped.SimulationConfig`를 실제 별칭으로 옮긴다.** v7에서는 "참조에 대응 노드가 없다"는
  이유로 건너뛴 것인데, v8에는 `시뮬레이션 설정`이라는 대응 노드가 생긴다. 건너뛴 사유가
  사라졌으므로 `SimulationConfig → 시뮬레이션 설정`으로 등재하고, `_skipped`에서 그 항목을
  지운 사실을 `참조-검증-기록.md`에 적는다.
- `_skipped`의 나머지(`OccupationType` · `SimulationResult의 속성 14개` 등)는 그대로 둔다.

## 10. 건드리는 파일

| 파일 | 하는 일 |
|---|---|
| `reference-ses.json` | ref-v8로 재편 |
| `reference-ses-v7.json` | 신규 — 현재 파일 그대로 동결 |
| `aliases.json` | 9절대로 |
| `구성결정-SES-대응표.md` | `SES 자리` 열을 v8 경로로 갱신 |
| `참조-검증-기록.md` | v7 → v8 재편 근거, 새 엔티티 11개의 근거, 미검증 항목 |
| `README.md` | 정답지 두 개 병존 규칙 |
| `ses-tree.html` · `ses-mapping.html` · 두 `.png` | `python render_ses.py --png`로 재생성 |

`render_ses.py`는 루트에서 트리를 걷기 때문에 코드를 고치지 않는다. 주석 한 줄(`:174`)이
`대상 시스템`을 언급하는데, 그 문장은 `engine`을 제외하는 사유이고 v8에서도 참이다.

`sesx/` · `extract.py` · `exp/` · `run_s1.py` · `run_t.py` · `runs/` 는 **건드리지 않는다.**
`sesx`는 id 기반의 별도 계약(v1)을 쓰며 `reference-ses.json`을 읽지 않는다.

## 11. 검증

1. `python score_ses.py --selftest` — 자체 검증 6건 통과. 이 검증은 `민원 판정` · `거주민` ·
   `폐기물 유형` · `수거지점`을 이름으로 쓰는데 넷 다 v8에 있다.
2. `python score_ses.py --ref reference-ses.json --runs reference-ses.json` — v8을 v8로
   채점해 완전일치(정밀도·재현율 1.0)를 확인한다.
3. `python score_ses.py --ref reference-ses-v7.json --runs 'runs/*.json'` — 과거 12건의 점수가
   재편 **이전과 같은지** 확인한다. 다르면 동결에 실패한 것이다.
4. 구조 불변식을 직접 확인한다 — 부모가 둘인 엔티티 0건, 고아 0건, 순환 0건, 엔티티 62개,
   `sets.target`이 가리키는 자리가 모두 실재.
5. `python render_ses.py --png` — 그림이 새 골격으로 나오는지 눈으로 확인한다.
6. `_meta.verified_against`를 `develop @ 12937be`로 갱신한다.

## 12. 이 설계가 하지 않는 것

- `sesx` 파이프라인이 이 골격을 내도록 프롬프트를 고치는 일. 별도 작업이다.
- `score_ses.py`가 `sets` · `active_when` · `attr_spec`을 채점하게 만드는 일.
- 다섯 시스템 노드가 DEVS 결합 모델로서 포트를 갖게 하는 일. v8은 분해 구조만 바꾼다.
- 그림에 있는 엔진·이벤트를 되살리는 일 (3절).
