# 브로커 — 애매한 요청을 몇 바퀴 고쳐야 맞는 시뮬레이터에 닿는지 재고 판정한다

2026-11-02. 대상: `broker` 모듈(`find_simulators`, `CandidateMatcher`, `BrokerSessions`)과 평가 자료.

## 1. 목적과 이유

여러 시뮬레이터 중 사용자 요청을 수행할 서버를 고를 때, 요청이 애매하면 브로커는 지금 `ADJUST_REQUEST` 한 번을
내고 끝난다. 다시 조회하는 일은 LLM 에 맡겨져 있어 **몇 번 고쳐야 맞는 서버에 닿는지** 아무도 세지 않고,
`NONE` 은 "켜진 서버가 없음" 일 때만 나온다.

지도교수 피드백(SES 매칭의 판단 기준과 절차 부재, "몇 단계를 거쳐 매핑할 수 있느냐")에 답하려면 이 과정이
**측정 가능한 절차**여야 한다. 이 설계는 다음을 브로커의 규칙으로 정한다.

- 1단계 = 사용자에게 한 번 되묻고 답을 받는 대화 한 바퀴.
- 5바퀴 안에 맞는 서버에 닿으면 그 바퀴 수가 측정값이다. 6번째 고친 조회는 `NONE` 이다.
- 첫 조회(1바퀴)의 판정은 오류가 없어야 한다. 특히 **못 하는 서버를 맞다고 하는 오류**를 가장 먼저 막는다.

바퀴 수가 "요청이 얼마나 애매했는가" 를 재려면 브로커가 틀려서 생긴 바퀴가 섞이면 안 된다. 그래서 1바퀴
판정의 정확도가 이 설계의 전제다.

## 2. 목표 · 비목표 · 실패 조건

**목표**

- 대화 한 바퀴마다 브로커가 몇 번째 바퀴인지 알고 응답에 적는다.
- 맞는 서버가 없으면 **후보마다** 고칠 곳 전부와 고칠 방법을 한 번에 낸다.
- 사용자가 목표 서버를 고르며 요청을 고치면, 그 다음부터는 그 서버 하나와만 대조한다.
- 6번째 고친 조회는 `NONE` 으로 판정한다.
- 1바퀴 판정 정확도를 정답이 붙은 요청 모음으로 따로 잰다.

**비목표**

- 브로커가 자연어를 해석하는 일. 해석은 지금처럼 LLM 이 하고 브로커는 카드가 선언한 말과 대조만 한다.
- 브로커가 후보를 대신 고르는 일. 순서는 보기 편하게 두는 것이지 추천이 아니다.
- 임베딩 · 의미 검색 도입, 시뮬레이터 서버 추가.

**실패 조건 (동작은 해도 실패로 본다)**

- 못 하는 서버가 `MATCH` 로 나온다. 1바퀴 정답 모음에서 이 오류는 0 이어야 한다.
- 조건을 빼거나 목적이 바뀌어 닿은 경우가 "성공" 으로 셈해진다.
- 맞지 않는 항목 수만으로 `NONE` 이 된다(한 바퀴에 하나씩 묻는 방식이 이렇게 된다 — 그래서 한 번에 다 묻는다).

## 3. 정해진 것 (사용자 결정)

| 항목 | 결정 |
|---|---|
| 1단계 | 브로커가 고칠 곳을 돌려주고 사용자가 답해 요청을 고친 뒤 다시 조회하는 대화 한 바퀴 |
| 한도 | 고친 조회 5번까지. 6번째 고친 조회(첫 조회 포함 7번째 조회)는 `NONE`. 측정값은 0–5 |
| 한 바퀴에 묻는 양 | 맞지 않는 항목 **전부**를 한 번에. 사용자가 한 번에 고친다 |
| 후보가 여럿일 때 | 후보마다 수정안을 모두 보여 주고 사용자가 목표 서버를 고른다 |
| 목표 서버 | 사용자가 요청을 고칠 때 목표 서버도 함께 정한다. 다음 바퀴부터 그 서버 하나와만 대조한다 |
| 오류 우선순위 | 둘 다 줄이되, 못 하는 서버를 맞다고 하는 오류를 먼저 막는다 |

## 4. 1바퀴 판정 — 항목 분류

후보마다 요청의 항목(구절) 하나하나를 넷 중 하나로 나눈다. 지금은 "근거" 와 "불일치" 둘뿐이다.

| 분류 | 조건 | 뜻 |
|---|---|---|
| 일치 | 카드 어휘에 **확실히** 걸린다 | 이 서버가 할 수 있다 |
| 불일치 | 카드의 `unsupported` 에 걸린다, 또는 카드가 그 칸의 목록을 적었는데 거기에 없다 | 이 서버는 못 한다 |
| 애매 | 확실히 걸리지 않는다 — 서로 다른 뜻의 어휘에 함께 걸리거나(예: "평일 교통" 이 교통 조건과 수거 요일에 동시에), 판단할 근거가 모자란다 | 되물어야 한다 |
| 미제시 | 사용자가 말하지 않았다(`null`) | 대조하지 않는다 (지금과 같다) |

규칙:

- `unsupported` 를 먼저 보는 지금 순서를 유지한다. 구절이 `unsupported` 와 지원 어휘에 함께 걸리면 **불일치**다 —
  `unsupported` 는 카드가 "못 한다" 고 선언한 것이라 확실하다. 애매는 `unsupported` 에 걸리지 않고 **지원 어휘
  둘 이상에 서로 다른 뜻으로** 걸릴 때다(예: 장량동 카드에서 "평일 교통" 이 `traffic-profile`("교통") 과
  `weekday-schedule`("평일") 에 함께 걸림). 걸린 어휘 하나가 다른 걸린 어휘를 품으면 긴 쪽만 걸린 것으로 본다 —
  "평일 교통량" 은 `traffic-profile` 의 "평일 교통량" 이 `weekday-schedule` 의 "평일" 을 품으므로 교통 조건 하나다. (내 판단)
- 도메인 구절이 서로 다른 도메인의 별칭에 함께 걸리는 경우(지금은 불일치)는 **애매**로 옮긴다. 사용자가 도메인을
  하나로 정하면 풀리는 것이지 서버가 못 하는 것이 아니다. (내 판단)
- **확실하지 않으면 일치로 보지 않는다.** 애매는 `MATCH` · `CHOOSE` 를 막는다. 놓침이 조금 늘더라도 잘못
  걸림을 막는 쪽을 택한다(3절 우선순위).
- **카드가 그 칸의 목록을 아예 적지 않았으면 애매다**(사용자 결정). 지금은 목적(`objectiveMatchKeys` 없음) ·
  비교 축이 이 경우 판단을 건너뛰어 `MATCH` 를 막지 않고, 거주민은 불일치로 낸다 — 셋 다 애매로 바꾼다.
  적혀 있지 않은 능력을 할 수 있다고 보지 않기 위해서다. 이 때문에 지금 `MATCH` 인 요청 일부가 `ADJUST_REQUEST`
  로 바뀌고, 기준선과 비교할 때 이 변경의 몫을 따로 보인다. 늘어난 되묻기는 카드에 목록을 채워 줄인다(8절).
- 애매와 불일치를 응답에서 구분한다. 그래야 놓침(할 수 있는데 못 한다고 한 것)을 측정할 수 있다.
- "확실히 걸린다" 를 무엇으로 판정할지(어휘 길이, 구절 전체 대 일부, 한 구절이 여러 칸에 걸릴 때)는 빌더가
  정한다. 단 정해진 기준은 7절 정답 모음에서 잘못 걸림 0 을 지켜야 한다.

## 5. 바퀴 흐름과 판정

```
조회 (바퀴 r, 목표 서버 t 는 선택)
  r ≥ 7 → 대조하지 않고 NONE (사유: 고친 조회 5번 안에 닿지 못함)
  t 없음 → 모든 후보와 대조
  t 있음 → t 하나와만 대조
  그대로 맞는 후보(일치만, 불일치 · 애매 없음, 호출 가능):
     1개  → MATCH   (측정값: r)
     2개+ → CHOOSE  (t 가 있으면 생기지 않는다)
  없음:
     호출 가능한 서버 없음 → NONE (사유: 서버 없음 · 꺼짐 — 지금과 같다)
     그 밖           → ADJUST_REQUEST
```

- 첫 조회는 r = 1 이다. 첫 조회에서 `MATCH` · `CHOOSE` 면 고친 바퀴 수는 0 이다.
  측정값 "고친 바퀴 수" = 닿았을 때의 r − 1. 한도 5는 이 고친 바퀴 수에 건다 — 고친 조회가 다섯 번까지이고
  여섯 번째 고친 조회(r = 7)가 `NONE` 이다.
- `ADJUST_REQUEST` 응답:
  - 후보마다 맞지 않는 항목 전부. 항목마다 현재 값 · 분류(불일치/애매) · 고칠 방법 · 사유 · `changesPurpose`.
  - 후보 수 제한(`MAX_SUGGESTIONS = 3`)을 없앤다.
  - 순서: 목적을 바꾸지 않는 후보 먼저, 그 안에서 고칠 항목이 적은 후보 먼저, 같으면 서버 id.
  - 다른 도메인 후보는 같은 도메인 후보가 하나도 없을 때만 싣는다.
  - 응답에 지금 바퀴 r 과 남은 바퀴 수를 적는다.
  - `nextStep`: 사용자에게 후보별 수정안을 보이고 **목표 서버와 고친 요청을 함께** 받아 다시 조회하라고 안내한다.
- 목표 서버를 정한 뒤 사용자가 목표를 바꿔도 바퀴 수는 이어서 센다. 세는 단위는 서버가 아니라 대화다.
- 목표 서버가 다른 도메인이면 도메인 항목은 계속 불일치로 내되 `changesPurpose` 가 참이다. 사용자가 그 조정을
  받아 도메인을 바꿔 닿으면 목적 변경으로 기록한다. (내 판단)
- 목표 서버가 꺼졌거나 지어낸 후보면 `ADJUST_REQUEST` 로 그 사실을 알리고 다른 후보를 다시 보인다(목표를 풀고
  전체와 대조). 이 조회도 한 바퀴로 센다. (내 판단)
- `targetServerId` 만 오고 `matchId` 가 없으면 입력 오류로 돌려준다. 바퀴로 세지 않는다. (내 판단)

## 6. 바퀴를 잇는 방법

지금 `BrokerSessions` 는 (MCP 세션, 조회 인자) 쌍으로 "이미 넘겨준 서버" 만 기억한다. 조건이 바뀐 조회는
별개 요청으로 보므로 고친 요청을 이어 셀 수 없다.

결정(내 판단): 브로커가 첫 조회에서 **매칭 id** 를 발급해 응답에 싣고, LLM 은 고친 조회에 그 id 와 목표 서버
(`targetServerId`)를 함께 넘긴다. 브로커는 매칭 id 별로 바퀴 수 · 목표 서버 · 바퀴별 요청과 판정을 기억한다.

- 매칭 id 없이 오는 조회는 새 요청(r = 1)이다. 사용자가 전혀 다른 시뮬레이션을 물으면 LLM 은 id 를 넘기지 않는다.
- 다른 MCP 세션의 매칭 id 는 받지 않는다.
- 저장은 지금처럼 메모리에 두고 오래된 것부터 버린다. 브로커가 다시 뜨면 id 를 모른다 — 이때는 "모르는 매칭 id"
  로 알려 주고 새 요청으로 시작하게 한다(조용히 r = 1 로 세면 측정값이 틀린다).
- `find_simulators` 입력에 `matchId` · `targetServerId` 를 더하고, 도구 설명에 언제 넘기는지 적는다.

## 7. 측정

**기록할 값 (매칭 id 마다, 판정 로그 `[4 매칭]` 에도 남긴다)**

| 값 | 뜻 |
|---|---|
| 고친 바퀴 수 (0–5) 또는 NONE | 요청이 얼마나 애매했는가 |
| 목적 변경 여부 | 닿기까지 `changesPurpose` 가 참인 조정이나 조건 제거가 있었는가. 있으면 "닿았지만 원래 질문이 아님" 으로 따로 센다 |
| 조건 제거 | 바퀴 r 에서 r+1 로 갈 때 **칸 단위로** 본다: 한 칸(환경 조건 · 거주민 · 비교 축)의 구절 수가 줄었거나 값이 있던 칸이 `null` 이 되면 제거다. 구절 수가 같고 글만 바뀐 것은 고쳐 쓴 것이다. 문자열 뜻은 해석하지 않는다. (내 판단) |
| 첫 조회의 애매 · 불일치 항목 수 | 브로커의 첫 진단 |
| 바퀴별 요청 · 판정 | 어느 바퀴에서 무엇이 풀렸는가 |

**1바퀴 정확도 — 정답 모음**

- 논문 6.2절(RQ1)의 첫 요청 54개를 모은다. 출처는 `docs/reports/baseline-experiment-v2-2026-10-21` 등 실행
  기록이다 **[빌더 확인: 54회가 어느 보고서의 어느 실행인지 확인]**.
- 요청마다 정답을 붙인다: 그대로 맞는 서버(들), 항목별 정답 분류(일치/불일치/애매). 정답은 연구자가 붙이고
  붙인 근거를 남긴다.
- 두 층으로 나눠 잰다.
  - 대조 층: 정답으로 채운 요청 프로필을 브로커에 직접 넣는다(LLM 없음). 단위 시험처럼 반복 실행한다.
  - 해석 층: LLM 이 뽑은 요청 프로필이 정답 프로필과 얼마나 같은가.
- 지표: **잘못 걸림**(못 하는 서버를 일치/MATCH 로 판정) — 주 지표, 목표 0. **놓침**(할 수 있는 서버를 불일치로
  판정) — 보조 지표. 애매로 분류된 것은 놓침이 아니라 되묻기로 센다.
- 바꾸기 전 규칙으로 먼저 재서 기준선을 남긴다.
- 라벨은 빌더가 카드와 실행 기록을 근거로 초안을 붙이고, 연구자가 검토해 확정한다. 구현은 라벨 확정을 기다리지
  않고 진행하되, "잘못 걸림 0" 완료 판정은 확정된 라벨로 한다. (내 판단)

## 8. 하지 않는 것 · 남겨 두는 것

- 판정 규칙의 단위 시험(`BrokerVerdictTest` 등)은 새 분류와 바퀴 규칙에 맞게 고치고 늘린다. 시험 구성은 빌더가 정한다.
- 카드의 `matchKeys` 를 늘려 놓침을 줄이는 일은 이 설계 뒤에, 정답 모음의 놓침 사례를 보고 한다.
- 시뮬레이터 서버 쪽(`plan_subtasks` 이후)은 바꾸지 않는다.

## 9. 빌더에게 맡기는 것

- "확실히 걸린다" 의 구체 기준(4절). 조건은 잘못 걸림 0.
- 매칭 id 형식, 저장 크기, 응답 JSON 의 필드 이름.
- 정답 모음의 파일 형식과 위치, 측정 스크립트.
- 시험 구성.
