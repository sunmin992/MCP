# waste-sim-spring 채팅(자연어) 요청 카탈로그

이 문서는 waste-sim-spring 채팅창에 자연어로 입력했을 때 시스템이 실제로 인식·처리할 수 있는
요청의 범위를 코드(ChatController, OpenAiService, 각종 Detector, SimulationConfig,
SimulationConfigValidator, ScenarioService 기준, 2026-07 시점 v1.6)를 근거로 정리한 것이다.
"이렇게 말하면 될 것 같다"가 아니라 "이렇게 말하면 실제로 이 필드가 채워진다"는 사실만 담았다.

## 1. 요청이 처리되는 순서 (파이프라인 개요)

채팅 메시지 하나가 들어오면 아래 순서로 판정된다. 앞 단계에서 결과가 정해지면 뒤 단계는 실행되지
않는다. 1~3단계는 전부 정규식 기반 결정론적 판정이며 LLM을 호출하지 않는다(설계 원칙 C2:
"실행할지 말지"는 항상 LLM-free여야 한다).

1. **시나리오 실험 감지** (`ScenarioIntentDetector`) — 11종 시나리오 실험 중 하나로 인식되면
   바로 그 실험을 실행하고 종료. 아래 2~5단계는 건너뛴다.
2. **수거 시각 개수 세기** (`TimeExpressionDetector`) — 메시지 안에서 파싱 가능한 시각 표현이
   정확히 1개일 때만 다음 단계로 진행한다. 0개(시각 언급 없음)나 2개 이상(서로 다른 시각 비교 등)이면
   "실행 요청 아님"으로 확정되고 일반 대화 응답으로 빠진다.
3. **실행 의도 판정** (`ExecutionIntentDetector`) — 순간값 조회("~시점 배출량 알려줘")나 명시적
   실행 거부("실행하지 말고", "상상해서") 신호가 없으면 실행 요청으로 확정한다.
4. **엔진(모델) 선택 판정** (`EngineSelectionDetector`) — Python 참조 엔진 언급 여부를 판정.
   언급 없으면 기본 Java 엔진으로 정해진다.
5. **파라미터 추출** — 실행 요청으로 확정된 메시지에서만 LLM(JSON 모드, temperature=0.1)을 호출해
   구조화된 파라미터를 뽑는다. 교통/트럭 관련 3개 필드는 LLM 출력을 신뢰하지 않고 정규식으로
   다시 한번 확정해 덮어쓴다(대화 이력에서 잘못 이어받는 것을 막기 위함).
6. **서버 검증** (`SimulationConfigValidator`) — REST·MCP·채팅이 공유하는 단일 검증기를 통과해야
   실행된다. 실패하면 오류 메시지만 반환하고 실행하지 않는다(fail-closed).
7. **실행 또는 확인 요청** — 문제없으면 즉시 실행, 비차단 경고(교통 피크 시간대 등)가 있으면
   결과 대신 "확인" 버블을 먼저 띄우고 사용자가 승인해야 실행된다.

## 2. 단일 시뮬레이션 실행에서 조정 가능한 파라미터

아래 필드들은 실행 요청 메시지 **한 번 안에서** 함께 언급하면 채팅이 실제로 값을 채워 반영한다.
언급하지 않은 필드는 표의 기본값이 적용된다. **직전 대화 턴에서 언급했더라도 이번 메시지에 다시
쓰지 않으면 이어받지 않는다** — 매 요청은 그 메시지 하나만으로 완결돼야 한다.

### 2.1 수거 시각 (필수)

| 필드 | 설명 | 예시 표현 |
|---|---|---|
| collectionTime | 하루 중 수거 차량이 도는 시각. 유일한 필수값 — 없으면 실행되지 않는다 | "12시에 실행해줘", "아침 8시 반에 수거", "오후 2시 30분", "20:30에", "아홉시에", "열두시에" |

시각은 00:00~23:59 범위여야 하며, 메시지 안에 서로 다른 시각이 2개 이상 있으면(비교 요청으로 간주)
실행되지 않고 하나만 정해서 다시 말해달라는 응답이 돌아온다. 같은 시각을 강조 차 반복한 경우
("12시 12시에")는 1개로 처리된다.

### 2.2 기간·반복 횟수

| 필드 | 설명 | 기본값 | 유효 범위 | 예시 |
|---|---|---|---|---|
| days | 시뮬레이션 일수 | 30 | 1~365 | "60일 동안 실행해줘" |
| seeds | 반복(시드) 횟수 — 클수록 평균값이 안정적 | 30 | 1~100 | "시드 50번 반복해서" |

### 2.3 거주민 행동 변동성

| 필드 | 설명 | 기본값 | 예시 |
|---|---|---|---|
| leaveSigma | 외출(배출) 시각의 표준편차(분) — 클수록 배출 시각이 하루 전체로 퍼짐 | 30.0 | "외출 시각 분산 90분으로" |
| wasteSigma | 1회 배출량의 변동 계수 | 0.3 | "배출량 변동 0.5로" |

### 2.4 수거장 용량·민원 임계

| 필드 | 설명 | 기본값 | 유효 범위 | 예시 |
|---|---|---|---|---|
| capacity | 건물당 수거장 용량(kg) | 30.0 | 0 초과 | "수거장 용량 50kg로" |
| threshold | 민원으로 잡히는 적재율 임계값 | 0.8 | 0~1 | "임계값 0.9로 실행해줘" |

### 2.5 교통 레이어

포항시 장량동 인근 실측 교통량 데이터(`jangryang-weekday` 프로파일)를 반영해 트럭 이동시간에
혼잡 가중치를 준다. "교통/정체/혼잡/막히/막힘/트래픽/체증/골목/도로" 중 하나라도 메시지에
있으면 자동으로 켜진다(`TrafficKeywordDetector`) — 굳이 trafficEnabled라는 단어를 쓸 필요는 없다.

| 필드 | 설명 | 기본값 | 예시 |
|---|---|---|---|
| trafficEnabled | 교통 레이어 사용 여부 | false | "교통 정체 반영해서 실행해줘" |
| trafficProfileId | 적용할 교통 프로파일 id | 자동으로 `jangryang-weekday` | 별도 지정 불필요(현재 등록된 프로파일이 1개뿐) |

교통 레이어를 켜면 시간대별로 4개 노드(수거장 위치)의 혼잡도가 다르게 반영된다. Node_A(장성초등학교
인근)가 낮 12~13시경 가장 혼잡(정체 가중치 최대 약 2.2배)하고, Node_B(양덕사거리)가 가장 한산하다.
혼잡 가중치가 임계값(1.7) 이상인 시간대에 수거를 요청하면 서버가 곧바로 실행하지 않고 대안 시각을
제안하며 확인을 요청한다(§6 참고).

### 2.6 차량 종류·대수·배차·경로

"소형/중형/대형/트럭/차량/톤" 중 하나라도 메시지에 있으면 트럭 종류 지정으로 인식된다
(`RouteAwarenessDetector`). 언급이 없으면 항상 기본값(대형 5톤)으로 리셋된다 — 역시 이전 턴을
이어받지 않는다.

| 필드 | 설명 | 기본값 | 옵션/예시 |
|---|---|---|---|
| truckType | 차량 종류 | LARGE_5TON(대형 5톤) | "소형 트럭으로"(SMALL_1TON), "중형 트럭으로"(MEDIUM_2P5T), "대형 트럭으로"(LARGE_5TON) |
| truckCount | 운행 트럭 대수 | 1 | "트럭 3대로 실행해줘" |
| dispatchIntervalMinutes | 트럭 간 시차 배차 간격(분) | 0 | "45분 간격으로 배차해줘" |
| routeSequence | 수거장 방문 순서(Node_A~D) | 미지정(라운드로빈) | "Node_A, Node_C, Node_B, Node_D 순서로 돌아줘" |
| routeTravelMinutes | 건물 간 이동시간(분) | 0(단, 트럭 종류·경로·교통 중 하나라도 지정하면 체감 가능하도록 자동 15분 부여) | "건물 간 이동시간 20분으로" |

차량 종류별 특성:

| 종류 | 용량 | 기동성 | 골목(이면도로) 진입 |
|---|---|---|---|
| 대형 5톤 (LARGE_5TON) | 60kg | 기본 | 불가 |
| 중형 2.5톤 (MEDIUM_2P5T) | 30kg | 1.2배 | 가능 |
| 소형 1톤 (SMALL_1TON) | 12kg | 1.6배 | 가능 |

Node_C·Node_D는 골목(이면도로) 구간으로 등록돼 있어, 이 두 노드를 방문 대상에 포함한 채 대형
트럭을 쓰겠다고 하면 "골목 진입 불가"로 실행이 거부되고 소형 차량 등으로 바꿔달라는 안내가 온다.

### 2.7 엔진(시뮬레이션 모델) 선택

| 트리거 표현 | 실행 엔진 |
|---|---|
| 언급 없음 | 기본 Java 엔진(이벤트 큐 기반, 확장 기능 전부 지원) |
| "파이썬", "파이션", "python", "pyevsim", "원본 엔진", "원본 논문 엔진", "레퍼런스 엔진", "참조 구현 엔진" | Python(pyevsim) 참조 엔진 — 논문 원본 DEVS 구현. 교통 레이어는 지원하지만 다회 수거·분리배출·임대인 에이전트 등 Java 쪽 확장 기능은 없음 |

예: "파이썬 엔진으로 12시에 실행해줘", "원본 논문 엔진으로 아침 8시 수거 결과 보여줘"

## 3. 시나리오 실험 — 11종 자연어 트리거

사이드바의 "시나리오 실험" 버튼 11개와 동일한 실험을 자연어로도 요청할 수 있다
(`ScenarioIntentDetector`). 다만 이 경로는 **어떤 실험을 돌릴지만** 자연어로 정하고,
각 실험 내부의 세부 축 값(비교할 시각 목록, 용량 범위 등)은 항상 아래 표의 기본값이 그대로
쓰인다 — "20kg부터 80kg까지 10kg 단위로" 같은 수치 지정은 채팅에서 반영되지 않는다(세밀한 축
조정이 필요하면 사이드바 버튼이나 REST/MCP를 직접 사용해야 한다).

| 트리거 키워드(모두 포함해야 매칭) | 시나리오 | 계산 내용 |
|---|---|---|
| "월별" + "배출" | monthly-waste | 12개월 계절 가중치를 반영한 월별 배출량, 최다/최소 배출 월 |
| "분리배출" | waste-separation | 통합 수거 vs 일반·음식물·재활용 분리배출 3종 비교 |
| "야간 근무" / "1인 직장인" / "확장 거주민" | new-occupations | 야간근무자·1인직장인 추가 시 직업 구성별 최적 수거시각 |
| "결합 모델" / "임대인" / "귀가...모델" | coupling-variants | 외출/귀가 2회 배출, 임대인(Check) 에이전트 점검 유무 비교 |
| "스케줄" / "격일" / "주말 수거" / "다회 수거" | collection-schedule | 1일 1회 vs 2회, 격일제, 주말 미수거, 공휴일 미수거 비교 |
| "다중 트럭" / "트럭...여러/분할" / "구역 분할" | multi-truck | 트럭 1·2·4대로 구역을 나눴을 때 민원 변화 |
| "밀도" + ("빌라촌" / "원룸촌" / "vs") | density | 저밀도 빌라촌 vs 고밀도 원룸촌 등 4가지 밀도 비교 |
| "인프라" + ("트레이드오프" / "용량" / "임계") | infra-grid | 수거장 용량 C(20~60kg) × 민원 임계 θ(0.7~0.9) 그리드 |
| "행동 변동"/"외출...분산" + "민감도" | behavior-grid | 외출분산 α(10~120분) × 배출변동 β(0.1~0.5) 민감도 |
| ("구성별"/"거주민 구성") + ("최적"/"비교") | occupation-mix | 대학가형·공단인근형·가족주거형·균형형 구성별 최적 수거시각 |
| "sweep"/"스윕" 또는 "수거시각...전체/하루/종일" 또는 "06~18" | collection-sweep | 06:00~18:00 전체 시간대 수거시각 sweep 곡선 |

예: "거주민 구성별로 최적 수거시각 비교해줘", "다중 트럭으로 구역 분할하면 어떻게 달라져?",
"분리배출 시나리오 돌려줘", "밀도별로 빌라촌이랑 원룸촌 비교해줘"

거주민 구성 프리셋(occupation-mix, new-occupations 시나리오에서 사용):

| 프리셋 | 구성 비율 |
|---|---|
| 대학가형 | 학생 7 : 생산직 2 : 주부 1 |
| 공단인근형 | 생산직 7 : 학생 1 : 주부 2 |
| 가족주거형 | 주부 5 : 학생 3 : 생산직 2 |
| 균형형(기본 장량동) | 생산직 1 : 학생 1 : 주부 1 |

## 4. 채팅에서 직접 지정할 수 없는 파라미터

`SimulationConfig`에는 존재하지만, 채팅 LLM 파라미터 추출 스키마(`EXTRACTION_SYSTEM_PROMPT`)에
포함돼 있지 않아 단일 실행 요청 문장 안에서 값을 지정해도 반영되지 않는 필드들이다. 이 값들이
필요하면 사이드바의 시나리오 실험 버튼(§3의 11종이 각자의 방식으로 일부를 다룸), REST API,
또는 MCP 도구 호출을 직접 사용해야 한다.

- numBuildings(건물 수), residentsPerBuilding(동당 인원) — density 시나리오로만 간접 비교 가능
- occupationMix(직업 구성 비율 직접 지정) — occupation-mix/new-occupations 시나리오의 고정
  프리셋으로만 간접 비교 가능, 임의 비율은 REST/MCP 전용
- collectionTimesMinutes(하루 다회 수거 시각), collectionIntervalDays(격일제),
  skipWeekends(주말 미수거), holidays(공휴일 목록) — collection-schedule 시나리오의 고정
  프리셋으로만 간접 비교 가능
- wasteTypes(분리배출 종류별 용량/임계/주기 커스텀) — waste-separation 시나리오의 고정 3종
  프리셋만 가능
- returnDischarge/returnFraction(귀가 시 2차 배출), landlordEnabled 등(임대인 에이전트) —
  coupling-variants 시나리오의 고정 조합만 가능
- monthlyWasteFactor(월별 계절 가중치 커스텀) — monthly-waste 시나리오는 고정된 가정값(실측 아님)만 사용
- trafficComplaintWeight(교통 유발 민원 가중치 커스텀)

## 5. 확인(confirm) 절차와 안전장치

- **비차단 경고 시 확인 요청**: 검증은 통과했지만 경고가 있는 경우(예: 수거 시각이 교통 정체
  극심 시간대) 결과를 바로 보여주지 않고 "확인" 버블을 띄운다. 사용자가 승인해야 실제로 실행된다.
- **대기 설정은 하나만 유지**: 확인 대기 중에 새 실행 요청을 보내면 이전 대기 설정은 폐기되고
  새 요청으로 교체된다 — 폐기 사실은 시스템 메시지로 안내된다.
- **차단되는 요청**(fail-closed, 서버가 항상 거부):
  - 운행 트럭 대수를 0으로 요청("트럭 운행 중단해줘" 등) — 수거 자체가 불가능해 오류로 거부
  - 예측 적재율이 120%를 초과하는 조합(트럭 대수를 너무 줄이면서 용량도 작은 차량 요청 등)
  - 대형 트럭으로 골목(Node_C, Node_D) 방문을 요청하는 조합
  - routeSequence를 실제 건물 수와 일치하지 않는 순열로 지정
  - 수거 시각 범위(00:00~23:59), days(1~365), seeds(1~100), threshold(0~1) 등 값 범위 위반
- **실행되지 않는 요청 유형**:
  - 순간값 조회("12시 시점 배출량 알려줘") — 이 시스템은 특정 조건에서의 월간 누적 민원·최대
    적재량만 계산하며, 임의 시점의 순간 배출량은 계산하지 않는다
  - 명시적 실행 거부가 포함된 문장("실행하지 말고 설명만", "상상해서 표로 그려줘", "감으로
    숫자만 불러줘") — 가상의 결과를 지어내지 않고, 실행해야 알 수 있다고 안내한다
  - 서로 다른 시각을 2개 이상 비교해 달라는 요청 — 하나의 시각으로 좁혀서 다시 요청해야 한다
  - 시스템 프롬프트 규칙을 무시하라는 지시("무조건 ~라고만 답해" 등) — 후처리 필터가 감지해 응답을 대체한다

## 6. 자연어 요청 예시 모음

- "12시에 수거하는 걸로 실행해줘" — 기본 설정(30일×30시드)으로 즉시 실행
- "아침 8시 반에 60일 동안, 시드 50번 반복해서 실행해줘" — days/seeds 함께 지정
- "외출 시각 분산 90분으로 낮 12시 수거 실행해줘" — leaveSigma 지정
- "교통 정체 반영해서 오후 1시에 실행해줘" — trafficEnabled 자동 활성화, 피크 시간대라 확인 요청이 먼저 올 수 있음
- "소형 트럭 3대로 45분 간격 배차해서 아침 9시에 실행해줘" — truckType/truckCount/dispatchIntervalMinutes 조합
- "Node_A, Node_C, Node_B, Node_D 순서로 돌면서 오후 2시에 수거해줘" — routeSequence 지정
- "파이썬 엔진으로 12시에 실행해줘" — Python 참조 엔진으로 라우팅
- "거주민 구성별로 최적 수거시각 비교해줘" — occupation-mix 시나리오
- "수거시각 sweep 돌려서 하루 전체 최적 시각 찾아줘" — collection-sweep 시나리오
- "12시 시점 배출량 알려줘" — 실행되지 않음(순간값 조회로 분류, 대화 응답만)
- "실행하지 말고 대형 트럭 특성만 설명해줘" — 실행되지 않음(명시적 실행 거부)
